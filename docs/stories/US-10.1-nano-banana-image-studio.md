# US-10.1 — Nano Banana Image Studio

## Story

As a **content manager for the network of 3D-equipment stores (internal editorial team)**,
I want **to upload product photos, describe in a chat with Gemini (Nano Banana) the image I
need, and refine the result through follow-up edits in the same session**,
so that **I get a publish-ready visual without a designer and without re-explaining the
context — cutting product-visual turnaround from hours to minutes, with one tool instead of a
photo → designer → revisions loop**.

**Key scenario:** upload a printer photo → "white background, soft shadow below, 1:1" →
"make the shadow softer" → "add a subtle gradient" → download v3.

## Context

Requested by the editorial team (originating note dated 2026-10-31, author Andrii). Today the
app produces text content only; its "Image Tools" mode (alt text / image processing) is under
product review and does not generate images. This Story adds a new mode with its own route
`/image-studio`, backed by the Gemini Developer API (AI Studio key, not Vertex AI) called only
from the Express BFF.

Model recommendation carried from the source note: **Nano Banana 2** (Gemini 3.1 Flash Image)
is the default for iteration; **Nano Banana Pro** (Gemini 3 Pro Image) is an opt-in "high
quality" mode and is **required in MVP**. Model IDs live in configuration, not in code.

Model limits that drive the criteria (as stated in the source note): up to 7 MB per base64
image; input context 131 072 tokens (Flash Image) / 65 536 tokens (Pro Image); up to 14
reference images; output 1K / 2K / 4K; total inline request size 20 MB (larger goes through the
Files API). The model is stateless — "memory" is the full history resent on every turn.

Repository facts checked while writing this Story (they differ from the source note and shaped
AC-30 and AC-44): the global `express.json` limit in `server/index.js` is already `50mb` (not
the 100 KB default), and there is no admin UI — cost data is recorded via `server/usage/` and
read through `GET /api/usage`.

## Acceptance criteria

Each is observable and falsifiable. The original source-note label is kept in brackets for
traceability.

### Upload

- **AC-1 [U1]:** The user can add images via a button, via drag & drop, and via clipboard paste (Ctrl+V).
- **AC-2 [U2]:** PNG, JPEG and WEBP files are accepted. The file type is verified on the BFF by magic bytes, not by file extension (a file with a `.png` extension and non-PNG content is rejected).
- **AC-3 [U3]:** At most 5 images can be attached to one message; attaching a 6th is rejected with an explanatory message.
- **AC-4 [U4]:** An image with a long side > 2048 px or a size > 5 MB is downscaled on the client to a long side of 2048 px before it is sent.
- **AC-5 [U5]:** EXIF metadata, including GPS, is stripped from every image before it is sent to the model.
- **AC-6 [U6]:** Thumbnails of attached images are shown before sending, and each thumbnail can be removed.
- **AC-7 [U7]:** A rejected file shows the reason (format / size / count); the other attached files remain attached.

### Chat and generation

- **AC-8 [C1]:** A message may be text-only (text-to-image) or text plus images (edit / composition).
- **AC-9 [C2]:** Before sending, the user selects an aspect ratio (1:1, 4:3, 3:4, 4:5, 16:9, 9:16) and a resolution (1K, 2K; 4K only in Pro mode). Defaults are 1:1 and 1K.
- **AC-10 [C3]:** The model response is rendered in the chat as text and images in the order the API returned them.
- **AC-11 [C4]:** While a generation runs, a status indicator and a Cancel button are shown, the input field is locked and the rest of the UI stays responsive. Cancel aborts the upstream call to Gemini on the BFF (AbortController).
- **AC-12 [C5]:** A request that exceeds 120 s times out and shows an error with a Retry button.
- **AC-13 [C6]:** Each generated image gets a version number (v1, v2, …) and a label with the model and resolution.
- **AC-14 [C7]:** The BFF response is validated against a Zod schema before it enters application state; an invalid response is surfaced as an error, never as an empty image.

### Prompt presets

- **AC-15 [P1]:** Before the first message the user can pick a preset; picking one fills the prompt template, aspect ratio, resolution and model, and the prompt text stays editable before sending.
- **AC-16 [P2/P3]:** Presets are data in a separate registry named `PROMPT_PRESETS` (modelled on `STORE_REGISTRY`), not code in a component. Each preset has `id`, a UA name and an EN name, a prompt template with a `{product}` placeholder, and defaults (aspect ratio, resolution, model). Adding a preset is a configuration change only.
- **AC-17 [P4]:** The MVP registry contains exactly these presets:
  - White background — 1:1, 2K, Flash; clean #FFFFFF, soft shadow, product centred.
  - Lifestyle — 4:3, 2K, Pro; product in a real environment (workshop, office, classroom).
  - Banner — 16:9, 2K, Pro; free area reserved for text, the model does not draw text.
  - Social — 4:5, 1K, Flash.
  - Detail close-up — 1:1, 2K, Pro.
- **AC-18 [P5]:** After v1 exists, quick-edit chips "Прибрати фон", "Світліше", "Тінь м'якша", "Інший ракурс" are shown; each sends a predefined follow-up instruction.
- **AC-19 [P6]:** The log records which preset was used and whether the resulting image was downloaded.

### Session memory and iterative edits

- **AC-20 [M1]:** Given a session that already holds v2, when the user sends a text-only correction, the model edits v2 and returns v3, with the rest of the composition preserved.
- **AC-21 [M2]:** Every request carries all prior turns — texts, user-uploaded images and model responses — including every service field the API returned (e.g. `thoughtSignature`), unmodified.
- **AC-22 [M3]:** Every earlier version has an "Edit this version" action that attaches that version as an input image of the next message.
- **AC-23 [M4]:** A strip above the input field shows thumbnails of all session versions; clicking one opens a full view.
- **AC-24 [M5]:** The BFF counts the history tokens (`countTokens`). Above 80% of the model's input limit the oldest intermediate turns are removed, while the original uploads and the latest version are always kept; the user is shown a message about it.
- **AC-25 [M6]:** A session survives a page reload (IndexedDB on the client) and is kept for 7 days.
- **AC-26 [M7]:** A "New session" button clears the current history after confirmation; the previous session remains available in a session list.
- **AC-27 [M8]:** Switching between Flash and Pro mid-session starts a new branch seeded with the latest version as its input image; history is not mixed between models.
- **AC-28 [M9]:** The BFF sends user-uploaded images to the Gemini Files API once; the history stores the `file_uri`, not base64. If a Files API file has expired, the BFF re-uploads it from the session copy, transparently to the user.
- **AC-29 [M10]:** Before each call the BFF computes the request size; above 18 MB the oldest intermediate model versions are removed from the history (originals and the latest version never), and the user is shown a message. Complements AC-24.
- **AC-30 [M11]:** A body limit of 30 MB applies to `/api/image-studio/*` routes only; the global `express.json` limit is unchanged.

### Download

- **AC-31 [D1]:** Every version downloads in one click at the native resolution returned by the API, without re-compression.
- **AC-32 [D2]:** The download format is selectable — PNG (default), WEBP, or JPEG (quality 90) — converted on the client.
- **AC-33 [D3]:** The file name is `{product-name}_v{N}_{ratio}.{ext}`, e.g. `bambu-lab-h2d_v3_1x1.webp`; the product name is entered by the user, otherwise `image` is used.
- **AC-34 [D4]:** A "Copy to clipboard" action exists for PNG.
- **AC-35 [D5]:** "Download all versions" returns a ZIP of the whole session.
- **AC-36 [D6]:** The interface states that Gemini images carry an invisible SynthID watermark that cannot be removed.

### Errors

- **AC-37 [E1]:** On HTTP 429 and 5xx the BFF retries up to 3 times with exponential backoff (1 → 2 → 4 s), then returns an error shown with a Retry button. The model is never silently substituted.
- **AC-38 [E2]:** A safety block (`finishReason` such as `IMAGE_SAFETY` / `PROHIBITED_CONTENT`) shows a plain explanation and a suggestion to rephrase; the turn does not corrupt the history.
- **AC-39 [E3]:** If the model returns only text and no image, the text is shown, no version is created, and a Retry action is offered.
- **AC-40 [E4]:** A failed turn never enters the history that is sent to the model.

### Security, cost, accessibility

- **AC-41 [S1]:** The Gemini API key exists only in the BFF environment; it does not appear in the client bundle, and this is checked automatically.
- **AC-42 [S2]:** Image generation is limited to 30 generations per hour per client IP address (no user accounts exist in the product); the 31st generation within the hour is rejected with a visible message.
- **AC-43 [K1]:** Every request logs `usageMetadata` — input and output tokens, model, resolution.
- **AC-44 [K2]:** The session shows a running estimated cost in dollars as a cumulative total. Image-studio usage rows are recorded in the existing usage store and are retrievable through `GET /api/usage`.
- **AC-45 [A1]:** The drag & drop zone has a keyboard-operable equivalent: a real `<button>` plus `<input type="file">`.
- **AC-46 [A2]:** Generation status is announced through `role="status"` exactly twice — "Генерую…" at the start and "Версію v3 готово" (with the actual version number) at the end — with no intermediate updates.
- **AC-47 [A3]:** Each generated image has `alt` text that is a short summary of its prompt.
- **AC-48 [A4]:** After a generation finishes, focus remains in the input field.

## Out of scope

- Mask / brush inpainting UI.
- Batch generation for the catalog.
- Direct upload to OpenCart.
- Shared sessions between users.
- A dedicated admin UI for cost reports (cost data is available through the existing `GET /api/usage`).
- Budget cap / spend ceiling (deferred in the source note; does not block MVP).
- The source note's Definition-of-Done manual checks — the E2E scenario on 10 real catalog products, keyboard and NVDA screen-reader verification, and the first-week spend report — are human acceptance activities, not testable acceptance criteria of this Story (see Q6).

## Open questions

- **Q1:** What are the exact Gemini model ID strings for Nano Banana 2 (Flash) and Nano Banana Pro?
  - Checked: the source note — IDs differ across sources (`gemini-3.1-flash-image` vs `gemini-3.1-flash-image-preview`) and says to verify in AI Studio at implementation. `server/providers/gemini.js` does not reference an image model.
  - Impact if unresolved: the spec cannot name the default config values; implementation would guess an ID that may 404.

- **Q2:** How does the BFF derive the client IP for AC-42 behind Railway's proxy?
  - Checked: `server/` has no `trust proxy` setting and no `X-Forwarded-For` handling; the BFF is deployed on Railway per the source note.
  - Impact if unresolved: without trusting the proxy header every client shares the proxy's IP (one global 30/hour bucket); trusting it blindly lets clients spoof their IP.

- **Q3:** How is image generation reconciled with AGENTS.md architecture Rule 1 (all LLM work through `LlmProvider`; vendor SDK calls only inside `server/providers/`), and does it depend on `LLM_PROVIDER`?
  - Checked: AGENTS.md §3 Rule 1 and Rule 4 (`GEMINI_API_KEY` is documented as optional); README "Configuration" (`LLM_PROVIDER=anthropic` is the primary setup). The current `LlmProvider` interface is text/JSON-shaped.
  - Impact if unresolved: the planner must choose between extending the interface, a separate image-provider module, or an arch-guard exception without direction; and whether the mode works while `LLM_PROVIDER=anthropic`.

- **Q4:** Which price table is used for AC-44 (estimated $), and does the existing usage store accommodate image models and resolutions?
  - Checked: `server/usage/pricing.js` and `server/usage/store.js` exist (`computeCost`, `insertUsage`); the source note gives no prices.
  - Impact if unresolved: the cost shown in the UI cannot be verified; a schema migration of the usage table may be required.

- **Q5:** How do the retry, timeout and cancel rules combine — does the 120 s timeout (AC-12) cover the 3 backoff retries (AC-37), and what does Cancel (AC-11) do during a backoff wait?
  - Checked: AC-11, AC-12, AC-37 each state their rule independently.
  - Impact if unresolved: worst-case latency is undefined (120 s vs ~7 s of backoff plus 4 upstream calls) and test authors would have to invent the precedence.

- **Q6:** Are the source note's Definition-of-Done items (≥ 80% Vitest coverage, E2E on 10 real products, NVDA check, first-week spend report) delivery gates for this Story?
  - Checked: AGENTS.md §6 defines the mechanical gate and coverage rules; the E2E, NVDA and spend-report items have no automated form.
  - Impact if unresolved: the reconciliation stage cannot tell whether missing manual evidence blocks the Story.

- **Q7:** Interaction of history trimming with history fidelity — may whole turns be dropped (AC-24, AC-29) without invalidating the `thoughtSignature` chain required by AC-21, and how are the Files API URI (AC-28) and the client-held session copy (AC-25) kept consistent when a file expires?
  - Checked: the source note; the BFF has no session store, so the only persistent copy is the client's IndexedDB.
  - Impact if unresolved: a trimmed or re-uploaded history may be rejected by the API or silently degrade edits; the spec must otherwise assume how the client supplies bytes for a re-upload.

- **Q8:** AC-4 downscales to 2048 px, but an image ≤ 2048 px and > 5 MB cannot become smaller by resizing — what is the expected behavior (re-encode at lower quality, reject)?
  - Checked: AC-4 and AC-7 as written in the source note.
  - Impact if unresolved: a falsifiable test for the > 5 MB branch cannot be written.

- **Q9:** What does "checked automatically" mean for AC-41 (the source note says "in CI")?
  - Checked: `.github/workflows/` has no workflows; the existing automated check is `arch-guard.sh` (Rule 4, no keys in frontend), run locally.
  - Impact if unresolved: the spec would either invent a new CI pipeline or silently weaken the criterion to the local arch-guard.
