# US-10.3 - Image Studio security hardening, real-browser tests and opt-in live smoke tests

> **Split note.** This Story was split from the original US-10.2 v1 draft (`image-studio-security-resilience`), which covered four
> parts in one Story. The human answered the split question (old Q14) with **SPLIT**: US-10.2 is now the narrow Node-runtime-pin
> Story (old section C), and this Story carries the rest - section A (security), section B (real-browser tests) and section D (opt-in
> live smoke). Acceptance criteria and Open questions were renumbered from 1; their substance is unchanged. Mapping from the v1
> draft: old AC-1..AC-17 are AC-1..AC-17 here; old AC-21..AC-28 are AC-18..AC-25; old Q1..Q10 are Q1..Q10; old Q13 is Q11. The old
> section C (AC-18..AC-20) and old Q11, Q12 and Q14 are not here (see US-10.2).

## Story

As the **maintainer and operator of the deployed Content Swiss Knife** (the owner of the shared `GEMINI_API_KEY`, who also
carries the anonymous `/api/image-studio/*` surface that the studio put on the internet),
I want **the abuse and availability gaps, the untested persistence and conversion code and the never-verified live Gemini calls
left behind by US-10.1 to be closed or explicitly decided**,
so that **one anonymous request can no longer burn the shared Gemini quota or hold the server for minutes, the studio's
browser-only code is proven by something stronger than a fake, and every Gemini-facing constant the studio rests on has been
checked against the real service at least once**.

## Context

US-10.1 (Image Studio, PR #145, merge commit `bd31254`, archived) passed every gate and still carried recorded, deferred
findings. The sources of truth, all in the repository, are `docs/knowledge/US-10.1-delivery-summary.md`,
`docs/reviews/security/US-10.1-security-review.md` (v3), `docs/verification/US-10.1-verification-report.md` (v3),
`docs/reconciliation/US-10.1-reconciliation-report.md` (v3), `docs/pr/US-10.1-pr-summary.md` and
`docs/knowledge/project-state.md`. They state that the first PR approval was rejected because every Gemini-facing test was a mock
(two real defects, the Files API upload 404 and the `undici` dispatcher skew, were found only against the live service), and that
the following were deferred, not decided by any gate:

- **Security (anonymous-reachable, non-blocking at the time, N-1, N-2, N-4 recommended before merge):** N-1 history turns and parts are
  uncapped and `countTokens` runs once per retained turn before the rate limiter charges (a 1.06 MB request produced 20 001 upstream
  calls); N-2 `fileData.fileUri` / `mimeType` / `inlineData.mimeType` reach Gemini unvalidated; N-4 `/upload` has no limiter and no
  decoded-size cap, and a timed-out upload is retried while the earlier transfer keeps running (up to 4 overlapping transfers for
  about 407 s; an estimate of about 140 MiB retained per request at the 30 MiB body limit, not measured), with no client deadline for
  attach-time uploads (F-8); N-3 malformed JSON returns the Express HTML error page with a stack trace; N-5 the limiter is keyed by
  raw `req.ip` and rests on the unverified `trust proxy = 1` assumption A-2. FR-66's "zero upstream calls" wording is inconsistent
  with FR-27's order (security review, spec-versus-code note).
- **Test debt (RC-3, no waiver):** AC-25..AC-27 persistence were tested only against an in-memory fake IndexedDB, and AC-31..AC-35 real
  conversion only against a fake codec; `indexeddb-session-store.ts`, `browser-image-codec.ts` and `browser-ports.ts` have no spec.
- **Live verification gap (RC-8, security review "live smoke" paragraph):** no live `generateContent`, no studio-path `countTokens`
  with images, no live `FILE_MISSING`, and no Railway run was ever done; the model ids, prices and the `Content-Length` behaviour rest on
  `docs/evidence/US-10.1-pre-implementation-checks.md`, which is unregistered and has no raw output. AGENTS.md section 6 item 9 and
  section 5 now require an opt-in env-gated spec (the `LIVE_DOC_TEST` pattern) for this class.

The runtime debt that US-10.1 also recorded (D-1: the unpinned Node and the `undici` override, and the Node 24.15.0 Windows worker
fault) is **not** here; it is the narrow Story US-10.2.

**Relationship to US-10.2 (a note, not a blocker).** US-10.3 depends on US-10.2 only for the pinned Node: the live smoke specs and the
real-browser specs should run on the pinned runtime. US-10.3 does not wait for US-10.2 to be specified or approved, and no
acceptance criterion below requires a particular Node version.

## Acceptance criteria

Each is observable and falsifiable. Where a numeric value or a mechanism is undecided it is named by its Open Decision
(Q-n); the specification must resolve that decision before the criterion's test can be written, and the value then appears in
the criterion unchanged. No value below is invented.

### A. Anonymous-reachable security findings

- **AC-1 (N-1, bound):** A `POST /api/image-studio/generate` whose `history` has more turns than the maximum decided in Q1 is
  rejected with HTTP 400 `{ "error": "INVALID_REQUEST" }` before any call to the Gemini provider; a stubbed provider records zero
  `countTokens` and zero `generateImage` calls. A request at exactly the maximum is accepted.
- **AC-2 (N-1, parts):** A request in which any single turn has more `parts` than the maximum decided in Q2 is rejected with
  HTTP 400 `INVALID_REQUEST` before any upstream call (zero provider calls).
- **AC-3 (N-1, amplification):** For a request that is accepted, the number of upstream `countTokens` calls it triggers never exceeds
  the bound that follows from Q1/Q2 (turn maximum plus one for the new turn), asserted with a stub provider that counts calls; the
  20 001-call reproduction (a 1.06 MB body of 20 000 one-character turns) now yields zero upstream calls.
- **AC-4 (N-1, limiter order):** The behaviour decided in Q3 (charge the limiter before `countTokens`, or keep FR-27's order with a
  cap) is covered by a test against the real `createApp` on loopback: when it is "charge first", the 31st request from one IP within the
  window answers 429 `RATE_LIMITED` with `Retry-After` and zero upstream `countTokens` and zero `generateImage` calls; when it is
  "keep the order", the test pins the exact number of upstream calls the 429 request is allowed to make. In both cases FR-66's
  wording and the test agree.
- **AC-5 (N-2, file URI):** For a user-origin part, a `fileData.fileUri` that is not under the Files API prefix decided in Q5
  (for example `https://evil.example/x.mp4`) is rejected with HTTP 400 `INVALID_REQUEST` and zero upstream calls; a `fileUri` under the
  prefix is forwarded byte-identical.
- **AC-6 (N-2, MIME):** For a user-origin part, `inlineData.mimeType` and `fileData.mimeType` other than `image/png`, `image/jpeg` or
  `image/webp` (for example `application/pdf`, `video/mp4`) are rejected with HTTP 400 `INVALID_REQUEST` and zero upstream calls; the
  three allowed types are accepted.
- **AC-7 (N-2, passthrough kept):** A model-origin part carrying `thoughtSignature` (and any other passthrough field FR-35 requires)
  is still forwarded unmodified; the allow-list applies to user-origin parts only. A regression that strips `thoughtSignature` fails
  this test.
- **AC-8 (N-4, decoded size):** `POST /api/image-studio/upload` whose base64 decodes to more than the cap decided in Q6 is rejected
  with the status and code decided in Q6 (`INVALID_REQUEST` 400 or 413) and `uploadFile` is never called; a payload at the cap is
  accepted. The 15 MiB PNG-signature reproduction (20.97 MB body, 15 728 648 decoded bytes forwarded) is rejected.
- **AC-9 (N-4, throttle):** The upload throttle decided in Q7 (a per-IP budget, a concurrency cap, or both) is enforced against the
  real `createApp`: a caller exceeding it receives the decided rejection (429 with `Retry-After`, or the decided concurrency code)
  with CORS headers and no further `uploadFile` call; a caller within budget is unaffected.
- **AC-10 (N-4 / F-8, no upload retry on timeout):** When the provider's upload attempt times out, the BFF does not start another
  `uploadFile` attempt while the earlier one may still be running (decision Q8): with a stub that never settles, exactly one
  upload attempt is made and the request ends with the decided error; an HTTP-status upstream failure keeps the FR-60 retry behaviour
  unless Q8 decides otherwise. A late success after a lost race is still deleted best effort (existing behaviour must not regress).
- **AC-11 (F-8, client deadline):** An attach-time upload from the composer is aborted by the client after the deadline decided in
  Q9 and the attachment ends in the existing failed state with a retry affordance, not an indefinite `uploading` state; the abort
  signal reaches `LlmService.uploadImageFile`. Asserted with a fake clock and a request that never resolves.
- **AC-12 (N-3, only if Q4 decides in scope):** Malformed JSON posted to `/api/image-studio/generate` and to
  `/api/image-studio/upload` returns HTTP 400 `application/json` with `{ "error": "INVALID_REQUEST" }`; the response body contains no
  `SyntaxError` text, no stack frame and no absolute filesystem path, regardless of `NODE_ENV`.
- **AC-13 (N-5, only if Q4 decides in scope):** Two requests that differ only in an IPv6 address within the same /64 consume the same
  limiter bucket (decision Q4/N-5 a), and the `trust proxy` hop-count assumption A-2 is either verified and recorded as evidence or
  documented as an explicit accepted assumption with its failure effect; a direct (no-proxy) request with a client-chosen
  `X-Forwarded-For` cannot select a fresh bucket (decision Q4/N-5 b).

### B. Real-browser tests for IndexedDB and Canvas

- **AC-14 (RC-3, persistence):** Under a real browser engine (runner per Q10), the real IndexedDB session store
  (`indexeddb-session-store.ts`) round-trips a session: create, add turns and sent bytes, reload the store, read back identical data;
  a transaction aborted midway (simulated quota or abort) leaves no partial session across the `sessions`, `turns` and `sentBytes`
  stores; sessions older than 7 days are removed on load and a 21st session evicts the oldest (AC-25..AC-27 behaviour of US-10.1 that was fake-only).
- **AC-15 (RC-3, conversion):** Under a real browser engine, the real canvas codec (`browser-image-codec.ts`) converts a known fixture
  image to PNG, JPEG and WebP, and each output decodes back to the fixture's dimensions with the correct magic bytes; a transparent
  PNG converted to JPEG has the fill colour the specification requires (AC-31..AC-35 of US-10.1, conversion halves that were fake-only).
- **AC-16 (RC-3, ingest):** Under a real browser engine, ingesting an image that carries EXIF/GPS metadata through the real codec yields
  bytes with no EXIF segment (the AC-5 outcome of US-10.1 that was plumbing-only under W-2) when Q10's runner and fixtures can show it; if they
  cannot, the report states which part stays unproven.
- **AC-17 (not part of the default gate unless decided):** The real-browser specs have a documented single command and are listed in
  AGENTS.md section 5/6 in the way Q10 decides (part of `npm test`, a separate script, or opt-in); the existing gate commands
  (`npm run lint`, `npm test`, `npm run test:coverage`, `npm run build`, `bash arch-guard.sh`) still pass unchanged, and
  `vitest.config.ts` coverage `include` and thresholds are not narrowed or lowered.

### C. Opt-in live smoke tests

(Lettered C here; it is section D of the original v1 draft. The v1 section C, the Node runtime, is US-10.2.)

- **AC-18 (gating):** Every live smoke spec is skipped unless the environment variable decided in Q11 is set to `1` and the real key
  is present; with it unset, `npm test` and `npm run test:coverage` run and skip them (they are never part of the gate), exactly as
  `test/doc-generation-live.spec.ts` skips unless `LIVE_DOC_TEST=1`. A test asserts or the report shows the skip with the variable unset.
- **AC-19 (generateContent, both models):** With the variable set, a real image generation on `gemini-3.1-flash-image` and on
  `gemini-3.1-pro-image-preview` through the real route returns HTTP 200 `kind: images` with at least one decodable image, writes
  exactly one usage row labelled `image-studio|<preset>|<resolution>`, and the recorded cost equals the per-image price in the catalogue
  ($0.03 flash, $0.06 pro per `docs/evidence/US-10.1-pre-implementation-checks.md`); a mismatch with the real usage metadata is a
  failure that names both numbers.
- **AC-20 (edit turn, thoughtSignature):** A second turn that sends the first turn's model-origin parts back, including a real
  `thoughtSignature`, is accepted by the real API and returns HTTP 200 (the multi-turn edit path).
- **AC-21 (countTokens):** The studio-path `countTokens` is exercised live with (a) an `inlineData` image part, (b) a `fileData`
  part with a real `fileUri` from a live upload, and (c) an over-limit session that makes the size/token trim remove at least one
  turn pair and report `trimmedTurnIds`; the real response shape matches what `trim.js` consumes.
- **AC-22 (FILE_MISSING):** After a live upload object is deleted (or a never-existing Files API URI of the allowed prefix is used), the
  real generate call returns HTTP 410 with the `FILE_MISSING` shape the client expects (FR-17), proving the upstream status/message that
  `server/image-studio` recognises is what Gemini really sends.
- **AC-23 (cleanup and cost control):** Every Files API object a live smoke spec creates is deleted in `afterAll`/`finally`, including
  when an assertion fails; the spec never logs the API key or a full request payload; the number of paid calls per run is bounded by the
  budget decided in Q11 and printed at the end of the run.
- **AC-24 (constants verified):** The live run records the real response for the model ids `gemini-3.1-flash-image` and
  `gemini-3.1-pro-image-preview` and for the per-image prices, in a registered evidence artifact (type `evidence`, with the
  artifact-schema front matter, method, tool and runtime versions, date, runner and raw output), replacing reliance on the
  unregistered `docs/evidence/US-10.1-pre-implementation-checks.md` for these values. A constant that the live run contradicts is
  reported, not silently corrected.
- **AC-25 (production proxy, only if Q11 decides in scope):** A recorded check through the Railway production proxy shows that a
  browser-style `POST` reaches Express with a plain-integer `Content-Length` (no chunking), and that a request without one answers 411
  `CONTENT_LENGTH_REQUIRED`; the real output is stored in the evidence artifact of AC-24.

## Open questions

Everything below is genuinely undecidable from the sources. None is guessed in the criteria above. `so-clarifier` formalises
these into the Open Decisions log (AGENTS.md section 11); every one of them blocks the specification stage for the criteria that name it.
Q10 and Q11 are human-only blocking decisions.

- **Q1 (N-1): the maximum number of `history` turns.**
  - Checked: security review N-1 suggests "a few hundred turns" without a number; the studio keeps at most 20 sessions and the US-10.1
    specification has no history cap; the 30 MiB body allows roughly 500 000 minimal turns.
  - Impact if unresolved: AC-1 and AC-3 have no threshold; the specification writer would have to invent one.
- **Q2 (N-1): the maximum number of `parts` per turn** (and whether a total-parts cap across the whole request is also wanted).
  - Checked: the same sources; the composer allows at most five attachments per message (US-10.1), which bounds a legitimate user turn,
    but model turns can carry several parts.
  - Impact if unresolved: AC-2 has no threshold.
- **Q3 (N-1): charge the limiter before `countTokens`, cap only, or both.** FR-27 fixes the current order (parse, trim with
  `countTokens`, then `limiter.tryConsume`), and FR-66 says a 429 means "zero upstream calls", which the code does not do (the 31st
  request still makes k+1 `countTokens` calls). Charging first changes FR-27/FR-66 and means a request later rejected as INVALID
  still consumes budget (or the limiter is only checked, not charged, before the count).
  - Checked: security review N-1 and the spec-versus-code note; reconciliation RC-5 (Specification gap, needs a human decision).
  - Impact if unresolved: AC-4 cannot say which of the two behaviours the test pins.
- **Q4 (N-3 and N-5): are they in scope?** N-3 (route-scoped error middleware mapping parser errors to `INVALID_REQUEST`) is rated
  non-blocking and not an FR-61 breach; whether production runs with `NODE_ENV=production` is unverified. N-5 has two halves: (a) key
  IPv6 clients by /64, (b) verify or document the `trust proxy = 1` hop count (assumption A-2, depends on Railway behaviour).
  - Checked: security review N-3, N-5 and its A-2 note; nothing in `server/`, `package.json` or any deploy file sets `NODE_ENV`.
  - Impact if unresolved: AC-12 and AC-13 are conditional and are dropped if the human says out of scope; the recommendation of the
    sources is to include N-3 (cheap) and the human decides on N-5.
- **Q5 (N-2): the exact `fileUri` allow-list.** The review recommends the prefix `https://generativelanguage.googleapis.com/v1beta/files/<id>`
  (the Files API of the Gemini endpoint), but it also states that the vendor's current URI schemes were not verified; and whether a
  `fileUri` must be bound to the session or caller (nothing binds it today) is a separate, larger decision.
  - Checked: security review N-2; `server/providers/gemini.js` returns the real `fileUri` for uploads (live run: `fileUri` from a real
    upload), but the exact form was not recorded in a registered evidence artifact.
  - Impact if unresolved: AC-5 may reject legitimate URIs or admit non-Files URIs; the live smoke (AC-21) is the natural source of the
    real URI form.
- **Q6 (N-4): the decoded-size cap value and the rejection code.** The review suggests "about 5 MiB plus margin" (the client already
  enforces 5 MB, FR-12, `5 242 880` bytes) and `INVALID_REQUEST` 400 or 413.
  - Checked: security review N-4 and D-3; FR-9, FR-12 and OD-40 accept that a direct API call bypasses the 5 MB bound today.
  - Impact if unresolved: AC-8 has no threshold or status.
- **Q7 (N-4): the upload throttle mechanism.** A separate per-IP limiter, a shared per-IP budget with `/generate`, a concurrency cap, or
  a combination; and the budget value.
  - Checked: FR-16 and FR-66 say uploads are not counted by the limiter; the review lists "a separate limiter or a shared per-IP budget
    for uploads" and "a concurrency cap".
  - Impact if unresolved: AC-9 has no mechanism and no number; choosing it changes FR-16/FR-66.
- **Q8 (N-4 / F-8): stop retrying upload timeouts?** Options named by the sources: do not retry a `TimeoutError` for uploads, or wait for
  the previous attempt to settle before the next. FR-60 currently applies the retry loop to uploads.
  - Checked: verification F-8, security review D-3, reconciliation RC-7; the SDK upload promise cannot be cancelled.
  - Impact if unresolved: AC-10 cannot say whether a timeout makes one attempt or up to four.
- **Q9 (F-8): the client-side deadline for an attach-time upload** (the generation deadline is 120 s; the BFF upload attempt timeout is
  100 s) and whether the user gets a Cancel control for an attach-time upload.
  - Checked: verification F-8 (client `uploadImageFile` accepts a signal but nothing sets a timeout); FR-21 shows Cancel only while a
    generation runs.
  - Impact if unresolved: AC-11 has no deadline value.
- **Q10 (BLOCKING, AGENTS.md section 7 item 8 dependency decision - for the human only): the real-browser test runner and whether it
  joins the gate.** The human suggested Playwright or Cypress. Adding either is a new devDependency (plus a browser download and
  possibly a CI edit); alternatives the sources mention are a human waiver (W-3), V-10-style manual evidence, or the existing
  `ng test` runner if it can run a real browser. This Story does not decide it.
  - Checked: reconciliation RC-3 lists "W-3 waiver, V-10 evidence, or a test dependency"; AGENTS.md section 5 runner split (logic runner on
    `happy-dom`, component runner via `ng test`); `package.json` has no browser-automation dependency today; the existing
    `docs/evidence/US-10.1-pre-implementation-checks.md` V-10 is "baseline", without raw output.
  - Impact if unresolved: AC-14..AC-17 cannot be planned; this blocks the specification for section B and must be answered by the human
    before any dependency is added. Also unanswered: whether the specs are part of `npm test` and of `test:coverage`.
- **Q11 (BLOCKING for section C, spend decision - for the human only): the live smoke budget and operation.** (This is Q13 of the
  original v1 draft.) Needs: the maximum number of paid calls per run and an approved total; the name of the opt-in variable (the
  repository's precedent is `LIVE_DOC_TEST`; this Story must not assume a name); whether the specs call the running local server or the
  Gemini provider directly; who runs them and with which key (the real shared `GEMINI_API_KEY` is required and the author may not have
  it); whether `.env.example` gains the variable; and whether the production-proxy `Content-Length`/411 check through Railway (AC-25) is
  in scope.
  - Checked: AGENTS.md section 5 (`LIVE_DOC_TEST=1`, skipped by default, never part of the gate) and section 6 item 9; PR summary
    "What this PR does not prove"; prices from the evidence note ($0.03 and $0.06 per image) put one flash plus one pro generation at
    $0.09 before the edit turn, but the real spend is unknown.
  - Impact if unresolved: AC-18..AC-25 cannot be planned or run; this blocks any paid call and must not be decided by an agent.
