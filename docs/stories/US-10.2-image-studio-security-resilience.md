# US-10.2 - Pin the Node runtime and the undici override together

> **Split note.** Version 1 of this Story (a draft, never started) covered four parts: security (A), real-browser tests (B), the Node
> runtime (C) and opt-in live smoke tests (D). The human answered its split question (old Q14) with **SPLIT**. This version 2 keeps
> only the Node runtime part (old section C, old AC-18..AC-20 and old Q11 and Q12), narrowed by the human's concrete instruction below.
> Sections A, B and D moved, with their acceptance criteria and Open questions renumbered, to
> `docs/stories/US-10.3-image-studio-security-tests-live-smoke.md`. The slug `image-studio-security-resilience` is kept only so the
> file name and the catalog path stay stable; it no longer describes the Story, the title does.

## Story

As the **maintainer and operator of the deployed Content Swiss Knife** (who builds, tests and deploys it on one Node runtime and
cannot tell today which one that is),
I want **the Node version pinned in `.nvmrc` and `package.json` `engines`, and the scoped `undici` override pinned to the `undici`
version that exact Node bundles, with the pair proven against the real Gemini Files API**,
so that **a different Node can no longer silently reopen the `undici` version skew that broke the Image Studio upload in US-10.1,
the guard test fails the moment the two drift apart, and the pin has been shown to work on the real route and not only in a source
check**.

## Human instruction (verbatim intent)

"Update Node.js to 24.22.2 (or a newer stable release), pin it in `.nvmrc` and `package.json` `engines`, and accordingly update the
`undici` pin in `package.json` to the version bundled in the new Node, with a mandatory live check." The human also chose to run
this through the pipeline (Story, Specification, tests first, implementation, gate), not as an ad-hoc edit.

## Decisions already made (recorded as decided, not open)

- Node is upgraded to **24.22.2 or a newer stable release** (the exact choice is Open question Q1; the default is 24.22.2).
- The Node version is pinned in **both** `.nvmrc` and `package.json` `engines.node`.
- The `overrides.cheerio.undici` pin is updated to **the `undici` version bundled in the new Node**.
- The **live check is mandatory** (not opt-in, not skippable, not replaced by a mock).
- The global Node on the human's machine is changed **by the human, not by the agent**.
- Split: this Story is narrow; security, real-browser tests and live smoke are US-10.3.

## Context

US-10.1 (Image Studio, PR #145, merge commit `bd31254`, archived) shipped `package.json` `overrides.cheerio.undici = 7.24.4`, chosen
to equal the `undici` bundled in Node v24.15.0 (the version installed where it was built). Without it, `cheerio` (loaded by
`server/retrieval/*`) pulled the hoisted `undici` 7.28.0 and installed a process-wide dispatcher that the Node-bundled `fetch`
could not use, so the real Gemini Files API upload failed with `UND_ERR_INVALID_ARG` (502 `UPSTREAM_RETRIES_EXHAUSTED`); the
US-10.1 planner's sweep found `7.24.4` and `7.25.0` working and `7.26.0` and newer failing under Node 24.15.0's bundle
(`docs/plans/US-10.1-task-breakdown.md`). The defect is a **version skew between the npm copy and the Node-bundled copy**, so the
pin is only correct for one runtime. The repository has no `engines` entry and no `.nvmrc`; the production Node (Railway) is unknown.
AGENTS.md section 7 item 10 (added by PR #146) now requires such a pin and the runtime pin to land in the same change.

Facts recorded by the sources, none re-verified here:

- Node v24.15.0 bundles `undici` 7.24.4 (measured: `node -p process.versions.undici` on this machine prints `7.24.4` under `v24.15.0`).
- The human states that Node 24.22.2 bundles `undici` 7.30.1. No registered artifact records that; it must be measured (AC-4), not assumed.
  Under the old bundle, `7.30.1` was one of the failing npm versions, so **that result is expected to flip under the new Node and
  MUST be re-verified live**.
- `npm audit` (security review D-1) flags `undici` `<=6.29.0 || 7.0.0 - 7.30.0` high at all three installed locations; the fix is
  7.30.1 or later. The review's stated "clean exit" is a Node whose bundled `undici` is 7.30.1 or later, then removing the override
  (Open question Q4).
- Node v24.15.0 on Windows kills the vitest fork worker (exit `0xC0000409`, "Worker exited unexpectedly") on many short-lived
  `agent: false` loopback connections; the fault is absent on Node 22 and 24.22.2 (builder evidence in `pipeline_status` v9/v10,
  not reproduced by the gate). It is mitigated by one shared keep-alive agent in two specs (`4723778`), documented in AGENTS.md
  section 5 "Loopback HTTP tests". That mitigation stays (Open question Q6 asks whether more is needed).
- `test/undici-pin.spec.ts` currently encodes the pin as a verified **window `[7.24.4, 7.26.0)`**, which cannot accept 7.30.1.
- README.md has one Node mention, "**Node.js** (LTS recommended) and npm" (Prerequisites); AGENTS.md names `v24.15.0` in section 5 and
  uses `7.24.4`/`24.15.0` as the example in section 7 item 10.

Sources of truth: `docs/knowledge/US-10.1-delivery-summary.md`, `docs/reviews/security/US-10.1-security-review.md` (v3, D-1),
`docs/reconciliation/US-10.1-reconciliation-report.md` (v3), `docs/verification/US-10.1-verification-report.md` (v3, F-6),
`docs/pr/US-10.1-pr-summary.md` (item 4, D-1), `docs/knowledge/project-state.md`, `test/undici-pin.spec.ts`, `package.json`, `AGENTS.md`.

## Acceptance criteria

Each is observable and falsifiable. Where a value is undecided it is named by its Open question (Q-n); the specification must
resolve that decision before the criterion's test can be written, and the value then appears in the criterion unchanged. "The pinned
Node" means the version decided in Q1 (default 24.22.2); "the bundled `undici`" means the output of `node -p process.versions.undici`
under exactly that Node.

### A. The runtime pin

- **AC-1 (`.nvmrc`):** A file `.nvmrc` exists at the repository root and its content, trimmed and with an optional leading `v`
  removed, is the exact `MAJOR.MINOR.PATCH` version decided in Q1 (24.22.2 by default). It is a stable 24.x release, not a range,
  alias or prerelease.
- **AC-2 (`engines`):** `package.json` has `engines.node` naming the same version as `.nvmrc`, in the form decided in Q2 (an exact
  version or a range that contains that version). With Q2 decided as a range, the range admits no Node whose bundled `undici`
  differs from the pin.
- **AC-3 (agreement is enforced):** A test fails when `.nvmrc` is missing, when `engines.node` is missing, when `.nvmrc` is not an
  exact version, when `.nvmrc` is outside `engines.node`, or when `.nvmrc` names a different version than `engines.node`
  (non-vacuity shown on synthetic inputs for each failing case, in the style of `test/undici-pin.spec.ts`).

### B. The undici pin follows the bundled version

- **AC-4 (pin equals bundled):** `package.json` `overrides.cheerio.undici` is an exact `MAJOR.MINOR.PATCH` string equal to
  `node -p process.versions.undici` under the pinned Node (7.30.1 expected for 24.22.2; measured and recorded, not assumed). Verified
  by a test that, when it runs on the pinned Node, asserts `process.versions.undici` equals the pin and, when the pin differs, fails
  with a message naming the pinned Node, the pin and the bundled version. The behaviour on a Node other than the pinned one is
  decided in Q5.
- **AC-5 (the guard encodes the relationship, not the old window):** `test/undici-pin.spec.ts` no longer asserts the window
  `[7.24.4, 7.26.0)`; an override of `7.30.1` (or whatever AC-4 measures) passes the guard, a pin that differs from the bundled
  version fails it, and `7.24.4`/`7.26.0`-style hard-coded window constants are gone. The version is not hard-coded in the test: it is
  read from `.nvmrc`/`engines` and from the runtime.
- **AC-6 (the other guard checks survive):** The updated guard still asserts, each with its existing non-vacuity proof: the pin is an
  exact `MAJOR.MINOR.PATCH` string; `package-lock.json` has `node_modules/cheerio/node_modules/undici` at exactly the pin with
  `resolved` and `integrity`; the installed copy resolved from cheerio's directory is that nested copy at the pin and a missing
  install fails rather than skips; `undici` appears in no dependency field and the only override path naming it is `cheerio > undici`;
  no file under `server/` imports the bare specifier `undici`.
- **AC-7 (tests first, red then green):** The updated `test/undici-pin.spec.ts` is written by TEST_WRITING
  before any change to `package.json`, `.nvmrc` or `package-lock.json`; run against the unchanged tree (no `.nvmrc`, no `engines`,
  pin `7.24.4`) it fails, naming the missing runtime pin; after the change it passes. Both real outputs are recorded.

### C. Consistency of the installed tree

- **AC-8 (lockfile and node_modules regenerated consistently):** After the change, on the pinned Node, `npm install` leaves
  `package-lock.json` unchanged on a second run, `npm ls undici` exits 0, and the lockfile's nested
  `node_modules/cheerio/node_modules/undici` entry and the installed copy are the pin (or, if Q4 drops the override, the nested entry
  is absent and the guard asserts that).
- **AC-9 (no other dependency change):** `dependencies`, `devDependencies` and `optionalDependencies` in `package.json` are
  byte-identical to the base commit; `overrides` differs only in `cheerio.undici` (its value, or its removal per Q4); `package.json`
  gains only `engines`; in `package-lock.json` no package other than `cheerio`'s nested `undici` changes version, and the root entry
  gains only the matching `engines`. Shown by a recorded diff of those keys.

### D. Mandatory live verification

- **AC-10 (real upload on the pinned Node):** With `node -v` recorded as the pinned version, a real `node server/index.js` (not
  `createApp` in a test, not a stub) answers `POST /api/image-studio/upload` with a small valid image with **HTTP 200 and a `fileUri`**
  (AGENTS.md section 6 item 9). The Files API object the call created is deleted and the deletion is confirmed (a follow-up request for
  it no longer succeeds, or the delete call's real status is recorded). The shared key is never printed, logged or written into the
  evidence; the real response status and shape (with the `fileUri` identifier, not the key) are recorded in the evidence artifact.
  If this call fails, the change is not done and the failure is reported, not worked around.
- **AC-11 (is the override still needed?):** On the same pinned Node, the same live upload is run **without** the `overrides.cheerio.undici`
  entry (a scratch tree or a temporary, uncommitted edit that is reverted; the committed `package.json` is not left without it unless
  Q4 says so). The real status of that run (HTTP 200, or the `UND_ERR_INVALID_ARG` / 502 `UPSTREAM_RETRIES_EXHAUSTED` failure) is recorded
  next to AC-10's, together with the hoisted `undici` version that run used. The outcome is the input to Q4; the criterion is the
  recorded measurement, not a prediction.
- **AC-12 (the evidence is registered):** The raw output of AC-4, AC-10 and AC-11 (commands, `node -v`, `process.versions.undici`,
  `npm ls undici`, statuses, date, runner) is stored in a registered `evidence` artifact with the artifact-schema front matter, resolved
  from `docs/workflow/artifact-paths.yaml`, and contains no secret.

### E. The gate on the new runtime

- **AC-13 (full gate green on the pinned Node):** On the pinned Node, with `node -v` recorded, every one of these exits 0 with real
  output recorded: `npm run lint`, `npm test` (both runners: `npm run test:logic` and `npm run test:components`),
  `npm run test:coverage` (thresholds and the coverage `include` unchanged), `npm run build`, `bash arch-guard.sh` (no `--rebaseline`).
  `npm run validate:harness` is run if any file under `docs/workflow/` or any `so-*` skill is touched.
- **AC-14 (Windows worker fault):** On the pinned Node on Windows, `npm run test:logic` is run N consecutive times (N decided in Q6)
  with zero "Worker exited unexpectedly" / `0xC0000409` exits, with the output recorded. The shared keep-alive agent in the two specs
  that carry it today (`4723778`) is not removed by this Story. Any additional mitigation is exactly what Q6 decides, nothing more.

### F. Documentation

- **AC-15 (docs do not contradict the pin):** After the change, `README.md` Prerequisites names the pinned Node version or points at
  `.nvmrc` in the form decided in Q8, and a search of README.md and `docs/` (excluding archived Stories and reports that record history)
  finds no live instruction naming a different Node version. AGENTS.md is not edited by the agent; the places in it that mention
  `v24.15.0` or `7.24.4` are listed in the report for the human (Q8).

## Open questions

Everything below is genuinely undecidable from the sources. None is guessed in the criteria above. `so-clarifier` formalises these
into the Open Decisions log (AGENTS.md section 11). The "Decisions already made" above are not repeated here.

- **Q1: the exact Node version to pin - 24.22.2 (default) or a newer stable 24.x.**
  - Checked: the human's instruction says "24.22.2 (or a newer stable release)"; only 24.22.2 is named by any source, and the
    builder evidence that the worker fault is absent applies to 24.22.2 and Node 22 only. A newer 24.x would bundle a different
    `undici`, which is not known here.
  - Impact if unresolved: AC-1, AC-2, AC-4 and AC-10 have no version; the specification writer would have to invent which 24.x to
    pin. **Default for the specification stage: 24.22.2.** If a newer release is chosen, the bundled `undici` and the worker-fault
    status must be re-measured for it.
- **Q2: the form of `engines.node` - an exact version (`24.22.2`) or a range (for example `>=24.22.2 <25`)?**
  - Checked: AGENTS.md section 7 item 10 requires `engines.node` "naming that Node version" without fixing the form; the bundled
    `undici` differs between 24.x releases, so a range can admit a Node whose bundle no longer equals the pin.
  - Impact if unresolved: AC-2 and AC-3 cannot say whether a range is allowed, and whether npm's `engine-strict` is relied on
    (the repository's `.npmrc` sets only `node-options` for diagnostic reports; it has no `engine-strict`, so `engines` alone only
    warns on a mismatch).
- **Q3: how the builder and the verifier obtain the pinned Node: the human installs it, or the pipeline uses an isolated Node download?**
  - Checked: the global Node on this machine is v24.15.0 and is changed by the human, not the agent; no Node manager configuration
    was found in the repository. The human's wording allows either: "the pipeline uses an isolated Node download for verification, or
    the human's installed Node".
  - Impact if unresolved: AC-8, AC-10, AC-11, AC-13 and AC-14 all require the pinned Node, and the builder cannot start the live
    check or the gate until it exists. An isolated download also must not touch the global install, `PATH` of other sessions, or the
    repository's `node_modules` of the other Node line without re-running `npm install` on the pinned one.
- **Q4: keep an override equal to the bundled version, or drop it if the skew no longer exists?**
  - Checked: the skew is between the npm copy `cheerio` gets and the Node-bundled copy; with an override equal to the bundle the skew
    is zero by construction, while without it `cheerio` takes the hoisted `undici` (7.28.0 today, required exactly by
    `@angular/build`), which differs from a 7.30.1 bundle. Whether that difference still breaks the upload on the new Node is
    unknown; AC-11 measures it. The security review names dropping the override as the clean exit once the bundle is 7.30.1 or later.
  - Impact if unresolved: AC-6, AC-8, AC-9 and the guard's whole shape depend on whether the nested entry exists; if dropped,
    AGENTS.md section 7 item 10 no longer has a pin to protect, and the guard must assert the absence and the live result instead.
    The decision belongs to the human after AC-11's measurement.
- **Q5: what the guard does when it runs on a Node other than the pinned one** (fail with a message, warn, or compare only against a
  recorded relationship between `.nvmrc` and the pin).
  - Checked: `test/undici-pin.spec.ts` is a pure source-and-lockfile guard today with no runtime dependency; AGENTS.md section 7
    item 7 forbids `skip` over a real defect, and the human's machine and the pinned Node differ until the human upgrades.
  - Impact if unresolved: AC-4 and AC-5 cannot say whether a developer on the wrong Node sees a red test (stricter, matches
    `engines`) or a green one (looser).
- **Q6: the Windows worker fault - is the keep-alive agent enough, and what is N?** The human decided the keep-alive agent stays; whether
  anything more is needed (for example a general shared helper plus a guard test that no spec opens `agent: false` loopback
  connections, or removing the AGENTS.md section 5 caveat once the pinned Node is shown clean) is not decided.
  - Checked: AGENTS.md section 5 "Loopback HTTP tests"; PR summary item 4 (0 of 4 gate runs crashed after the mitigation, a weak
    sample); the fault is absent on 24.22.2 per builder evidence only.
  - Impact if unresolved: AC-14 has no N and no statement of whether additional work is in scope.
- **Q7: who runs the live check and with which key?** The real shared `GEMINI_API_KEY` is required (AC-10, AC-11); the repository
  `.env` exists locally but the sources do not say that the pipeline may use it for a Files API upload, nor whether a dedicated test
  key exists.
  - Checked: AGENTS.md section 6 item 9 (one real call from the running server path, record the real response, delete what the call
    created; "if it cannot be run, say so and do not claim the call verified"); US-10.1 ran the same call in its fix cycle.
  - Impact if unresolved: AC-10 and AC-11 cannot be run; per section 6 item 9 the report must then say the call was not verified.
- **Q8: README.md wording and the AGENTS.md references.** README Prerequisites currently says "Node.js (LTS recommended)"; AGENTS.md
  section 5 and section 7 item 10 name `v24.15.0` and `7.24.4`. Whether README should name the version or only point at `.nvmrc`, and
  whether the human wants the AGENTS.md examples updated (an AGENTS.md edit needs the human's approval, section 7 item 8).
  - Checked: README.md line 144; AGENTS.md sections 5 and 7; no other doc names a Node version for the project (search to be repeated
    at the specification stage).
  - Impact if unresolved: AC-15 cannot say what the README line must contain.
- **Q9: does the production deployment follow the pin?** There is no Dockerfile, nixpacks or Railway configuration in the repository,
  and the production Node is unknown.
  - Checked: security review D-1; PR summary item D-1/O-12 (the Node-upgrade risk was accepted out of scope in US-10.1).
  - Impact if unresolved: the pin is proven only for the build/test/run environment; whether Railway honours `.nvmrc` or `engines`
    is unverified by any source. This Story cannot verify it without a Railway run (not in scope); the human decides whether to
    record it as an accepted assumption or request a follow-up.
