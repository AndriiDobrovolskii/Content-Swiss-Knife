## 0. How this plan treats the Open Decisions (read first)

**No Open Decision has an owner ruling** (the log has no "Owner answers" section). This plan therefore invents none. Every OD that shapes the design is placed in exactly one of four buckets, and the bucket is named where the decision is made:

- **PD - planner decision.** The Specification's Out-of-scope section assigns "which layer fans out ... and the mechanism that shares the price values" to `so-planner`, "within the owner's rulings on OD-4 and OD-14". The plan decides, gives the reason and a rejected alternative, costs out the other branch, and says "overruled if the owner rules otherwise under OD-n".
- **AB - anchored to base text.** The Story or an AC points one way; the plan designs to it and cites it.
- **RD - recorded default, pending owner ruling.** The Specification's own **Proposed (OD-n)** text, taken as written. It is a reviewable assumption, not a ruling, and the plan says what changes if the owner rules otherwise.
- **SE - seam.** The Specification lists options and declines to choose, or leaves the value to the owner. The plan puts the choice behind one named function or constant, shows the options in a table and **does not choose**. Nothing downstream may assume a value until the owner rules.

## 1. Approach

The BFF fans out. One generate request carries an optional `imageCount` (1, 2 or 4; omitted when 1, so a one-image request is byte-identical to today). After the existing validation, key check, size/token trim and a price-pair check, the limiter grants `min(U, N)` units in one atomic step, and the handler makes that many upstream calls in parallel under one abort signal, each inside the existing retry loop. A pure reducer folds the per-slot outcomes, in slot order, into one `images` response whose `parts` are the successes' parts concatenated (so the client stores them as one model turn and `applyResponse` numbers them consecutively with no change), one total `costUsd`, and, only when N > 1, an optional `batch` report (requested, granted, succeeded, per-failure cause). One usage row is written per successful upstream call (that is, per image in the normal case of one image per call) at `price(model, resolution, <the images that call returned>)`, exactly as the unchanged single-image handler prices a response, from a single price table that both the server cost and the client estimate read from the shared contract JSON. Upscale 4K and Variation need **no new wire shape**: each is an ordinary generate request with an empty history and a new turn that carries the source version inline, built by the existing request builder, with Upscale pinned to 4K and Variation using the Images selector as its K. The Style ref role is a Turn-level tag in the stored session (never on a Part, so it can never be forwarded to Gemini); the Style-ref sentence is a text part, from a new non-frozen prompt file. Everything new on the client is a pure function in `src/utils/image-studio/` plus a port-backed signal service, so the large store, the runner and the components change by small, named seams.

## 2. Domain model

`src/domain/` is not touched; no `ProductDescriptionDoc` or `ConsumablesDoc` field changes and no corpus fixture moves (impact hazards 2, 3, 5).

The Image Studio stored-session shape (`src/utils/image-studio/ports.ts`, `schemas.ts`) gains **optional** fields only:

- `Turn.styleRefPartIndex?: number` on a stored **user** turn: the index in `parts` of the one Style ref image of that send. Absent means every image of the turn is Product. At most one Style ref per generation (FR-11) is therefore structural, not a rule to remember.
- Nothing is added to `Version`. An Upscale or Variation version reuses the existing `editOfVersion` (US-10.5) to name its source and the existing `resolution` and `model`; AC-1's "resolution label is 4K" is `Version.resolution`. Whether the card's "edit of" wording suits a derived version is OD-11 copy.

Compatibility: a session saved before this Story has no `styleRefPartIndex`; `readTurnExtras` (`schemas.ts`) validates it as a non-negative integer that points at an image part and otherwise ignores it, so a stored value that is not valid is treated as Product and the session is not discarded (FR-14 failure path). `toTurnRecord` spreads the whole turn and `fromTurnRecord` passes through `parseStoredTurn` (`.passthrough()`), so the field persists with no change to the IndexedDB adapter, and the standing scan (no hand-written row mapping) stays satisfied. The tag is also **shown**: after a reload or a reopened session the input thumbnails of a card carry the role (FR-14, "the image is still shown with its Product or Style ref role"). `feed.ts` builds each `FeedThumb` from the model turn's `inputRefs`; it gains an optional `role: 'style-ref'`, set when the referenced user turn's `styleRefPartIndex` (read through `readTurnExtras`) equals the thumb's `partIndex`, and `studio-turn-card` renders a "Style ref" label on such a thumbnail (a Product thumbnail shows no label, as today; a session without the tag renders exactly as before). The label text is a new studio text id (FR-25) and its placement is OD-11. Fixtures: stored-session fixtures **without** the tag (must load as Product) and **with** it are added to `test/image-studio/helpers/sessions.ts` (FR-14).

`ComposerDraft` (never persisted) gains `imageCount: 1 | 2 | 4` and `Attachment` gains `role: 'product' | 'style-ref'`. Neither reaches storage.

## 3. The chain: contract -> request schema -> handler -> response schema -> apply -> feed

Image Studio has its own chain (impact hazard 3). The plan's rule is that **every new wire field changes the server Zod schema and the client schema in the same task, and a spec drives one through the other**, because both default `z.object`s silently strip unknown keys (impact S1, S2).

### 3.1 Shared contract (`src/prompt-core/image-studio-contract.json` and `.ts`)

Additions (the one place both runtimes read; the BFF imports the JSON by import attribute, the client through the typed accessors):

- `imageCounts: [1, 2, 4]` (closed list for the selector and for the request schema).
- `imageFailureCauses: ["safety", "empty", "retries_exhausted", "file_missing"]` (closed list for the `batch` report, FR-9 (a)). **Every slot outcome that is not an image success maps into this list, and `reduceSlots` is the only place that maps** (B-2): a `safety` slot is `safety`; a `failed` slot (classifier class 4, the `EMPTY_RESPONSE` case) is `empty`; **a `text` slot (the model answered with words and no image) is `empty` too**; a thrown error matching `isFileMissing` is `file_missing`; any other thrown error is `retries_exhausted`. No value outside the list can reach the wire, so the client's closed `z.enum` cannot reject a 200 that carries paid images. The text a text-only slot returned is not shown when other slots produced images (the batch report states "no image" for that slot, as an empty response does). The list is **not** extended with a `text` member: FR-9 (a) enumerates exactly four cause classes and the Specification's text is the owner's wording. When **no** slot produced an image the rule of section 5.2 applies instead (the lowest-numbered slot's outcome is returned as a one-image request would return it, so an all-text batch still answers `kind: text`) and no `batch` and no cause is produced.
- `imagePrices`: `{ "<model id>": { "<resolution>": <usd per image> } }`. **The values come from the OD-2 evidence and are not written here.**

`errorCodes`, `responseKinds`, `aspectRatios`, `resolutions` are unchanged, so `image-studio-contract.spec.ts`'s pinned error-code table is untouched. No new error code is introduced (FR-1, FR-8 b, FR-22 reuse existing ones).

### 3.2 Request and response

Request (`server/image-studio/request-schema.js`): `imageCount` is optional and, when present, one of `contract.imageCounts`. `assertConsistent` is unchanged. A request with `imageCount` omitted behaves exactly as today.

Response (`kind: 'images'`), client `ImagesResponse` in `schemas.ts` and the server body grow **together**:

```
batch?: { requested: number, granted: number, succeeded: number, failures: Array<{ cause: <imageFailureCauses> }> }
```

`batch` is present only when `requested > 1`, so every existing response assertion is unchanged. The three counters have one defined unit each (B-1, see 5.0): `requested` is the N the operator asked for (images, one expected per upstream call), `granted` is the number of upstream calls the limiter allowed (units consumed, `min(U, N)`), `succeeded` is the number of **images that exist**, i.e. the sum over successful slots of that slot's `imageCount` (non-thought image parts). `failures` has one entry per **failed call**; `failures.length` is therefore `granted` minus the number of successful calls, and the images never attempted (`requested - granted`) have no failure entry (they are the rate-limit warning). In the normal case (one image per call) the three read as images throughout. `costUsd` is the total for the images that exist, `price(model, resolution, succeeded)`. `safety` and `text` kinds are unchanged. The wire shape is listed in full above; no other field is added.

The agreement between the links is held by three specs that cross the runtimes (section 9.2): a round-trip spec that feeds the real handler's JSON to the real client `parseGenerateResponse` and asserts `batch` survives (S2); a spec that feeds the real client request builder's output to the real server `parseGenerateRequest` and asserts `imageCount` survives (S1); and a spec over every catalogue (model, resolution) pair asserting the server cost and the client estimate agree (FR-21).

### 3.3 Conditional branch: one call, N candidates (OD-1b)

The Story says "otherwise one call". This plan implements the N-parallel-calls branch **unconditionally**, because it is the Story's stated fallback, needs no provider change and holds whichever way OD-1b comes out. The single-call branch is a **conditional extension**, built only if the OD-1 evidence shows multi-candidate is supported **and** the owner wants it: `server/providers/gemini.js` gains a candidate-count parameter (a surface change, OD-17, and an AGENTS.md section 6 item 9 live smoke), `classifyResponse` (which reads only `candidates[0]` today) learns to read all candidates, and the usage-row token attribution for one call producing N images needs a rule. The observable result (FR-5) is the same either way, which is why the wire contract above does not depend on it.

### 3.4 AGENTS.md section 4 criteria

Not applicable and not touched: no Description HTML is generated, no renderer or `output-validator` is reached (Specification "Generated-HTML requirements"). The `meta-description-currency` rule stays disarmed; nothing here arms it.

## 5. Server design

### 5.0 Units: call, image, row (B-1)

The unchanged handler and its pinned spec define the billing unit: the classifier's `imageCount` is the number of valid **non-thought** image parts in the first candidate, and the handler prices `price(model, imageCount)` (`handlers.js`; `generate-handler.spec.ts` lines 220 to 231: two image parts give `price(FLASH, 2)` and `costUsd` about 0.06; a thought image plus a final image gives `price(FLASH, 1)`). One slot of the fan-out **is** one such unchanged call, so the same rule applies to it and a slot's success unit is **its `imageCount`**, not 1.

| Term | Unit | Defined as |
|---|---|---|
| `requested` | images asked | N from the request (1, 2 or 4); one image is expected per upstream call |
| `granted` | upstream calls (limiter units) | `min(U, N)`; every granted call consumes one unit whatever its outcome (RD, OD-5 a) |
| slot | one upstream call | its result is `images` (with its own `imageCount` >= 1), or a failure cause |
| `succeeded` | images | sum of `imageCount` over the image slots; thought parts are excluded exactly as in the classifier |
| usage row | one successful call | `costUsd = price(model, resolution, slot.imageCount)`; with one image per call this is one row per image (FR-9 (d)) |
| response `costUsd` | images | `price(model, resolution, succeeded)`, i.e. `unit * succeeded`, the same expression over the same unit as the sum of the rows (Rule A: no rounding anywhere) |

What this keeps consistent: FR-9 and AC-5 ("billed only for the images that exist") hold because every image in the merged `parts` is billed once; AC-14 and FR-21 hold because the estimate is `unit * N`, the recorded cost is `unit * succeeded`, and `succeeded == N` when nothing failed and every call returned one image; the limiter unit (FR-8, NFR-6) is the call, unchanged from today where one request is one unit regardless of how many images it returned. A call that returns two images consumes one unit and bills two, as the single-image handler does today (FR-70); the case is not expected from the vendor with one requested image and is covered because the existing spec pins it. `succeeded` can then exceed `granted` or `requested`; the text builder prints the numbers as reported and never clamps an image that was paid for out of the turn.

### 5.1 Fan-out (PD, OD-4)

**Decision (planner decision; overruled if the owner rules otherwise under OD-4): server fan-out.**

Weighed against the constraints the Specification and the impact analysis name:

| Constraint | Server fan-out | Client fan-out |
|---|---|---|
| FR-8 and NFR-6 atomic partial grant | One atomic step grants `min(U, N)` | Each request takes one unit; the same total, arrival-order dependent |
| FR-8 (c) "Generated k of N" from server numbers (Proposed) | Holds: the server reports `batch` | Client counts 200s and 429s: client arithmetic |
| FR-9 (c) Cancel keeps images already returned (Proposed) | **Does not hold.** `abortOnEarlyClose` aborts when the response closes, so a request that fans out cannot return partial results after Cancel (impact S13) | Holds: each request is aborted or finished on its own |
| FR-9 (d) one row per image | Holds: one row per successful slot | Falls out: one request, one row |
| OD-1b vendor answer | Contract unchanged either way | Contract unchanged either way |
| OD-17 `gemini.js` | Not touched | Not touched |
| Body and trim traffic | History sent once; `trimRequest` runs `k+1` `countTokens` once | History and `k+1` counts multiplied by N (up to 4 x the 18 MB size-trim bound) |
| FILE_MISSING recovery (US-10.1 FR-17) | One recovery repeats one request | N concurrent 410s need a coordinated single re-upload in the runner |
| Server files that change | `handlers.js`, `rate-limiter.js`, `request-schema.js`, contract, new `fan-out.js` | `handlers.js` (price arity only); limiter, schema, classifier untouched |
| Existing specs forced to change | Few (section 9.3): the single-image path is unchanged | Fewest |

Two Proposed items conflict whichever layer is chosen (FR-8 (c) against FR-9 (c)); neither is base text. Server fan-out wins on FR-8/NFR-6 atomicity, on body size, on trim traffic and on FILE_MISSING recovery, and loses on FR-9 (c). **FR-9 (c) is not honoured by this plan** and the owner must rule OD-4 and OD-6 together. The consequence under the chosen layer: Cancel discards the whole action, which is the existing US-10.1 discarded-paid-response rule extended to N calls (a response that arrives after Cancel produces no row and no version), so the recorded cost still covers only images the operator can see.

**Delta if the owner rules client fan-out (OD-4):** the handler stays one-image-per-request (only the price arity changes); `rate-limiter.js`, `request-schema.js`, the `batch` field and `fan-out.js` are not built; the generation runner gains N concurrent `generateImage` calls under one deadline and one cancel, a single coordinated FILE_MISSING recovery, and merges the N responses into one `images` response itself before `applyResponse`; the "Generated k of N" text becomes client-derived; `generation-runner.spec.ts` assertions that pin `generateCalls` length 1 per action change for N > 1.

### 5.2 Handler order and slots

`createGenerateHandler` keeps the FR-27 order and adds three steps (RD, OD-5, OD-15):

1. body validation (400); key check (501).
2. **price-pair check before any upstream call (RD, OD-15 timing):** `price(model, resolution, 1)`; an unpriced pair answers with one closed code held in a single constant (SE, OD-15 code: `INVALID_REQUEST` 400 or the existing `PRICE_NOT_CONFIGURED` 500; not chosen here). Under the owner keeping the post-call check, this step is removed and the existing post-call placement stays.
3. size trim then token trim, **once** per request.
4. limiter: `imageCount` omitted or 1 takes the unchanged `limiter.tryConsume(ip)` path; `imageCount` greater than 1 takes the new `limiter.tryConsumeUpTo(ip, N)`, which returns `{ granted, retryAfterSeconds }`, grants `min(U, N)` in one synchronous check-and-increment (no `await`, as today), and refuses with `granted: 0` and `retryAfterSeconds` when none remain. `granted: 0` answers the existing `RATE_LIMIT_EXCEEDED` (429) with `Retry-After` (RD, OD-5 b). The unit is per image and a slot that reached the upstream call counts whatever its outcome (RD, OD-5 a, the existing US-10.1 FR-66 / OD-13 rule per image; the lock-out-earlier effect is recorded in risks). Keeping `tryConsume` untouched keeps `rate-limiter.spec.ts` and `app-limiter.composition.spec.ts` green.
5. **slots** in new `server/image-studio/fan-out.js`: `granted` upstream calls start together; each is `runWithRetry(logged(...generateImage...))` with the shared `signal`, `sleep` and `log`, so the retry policy, redaction and per-attempt logging are the existing ones.
6. each slot is classified with the existing `classifyResponse` (unchanged) into the classifier's `images | safety | text | failed`, or a thrown error. A slot is **successful** when it is `images`, and then it carries its own `imageCount` (non-thought image parts, section 5.0) and its `parts`. Every other outcome maps to one `imageFailureCauses` member, with no gap (B-2): `safety` -> `safety`; `failed` -> `empty`; **`text` -> `empty`** (a text-only slot inside a batch that has at least one image is an empty slot for the report); a thrown error matching `isFileMissing` -> `file_missing`; any other thrown failure -> `retries_exhausted` (an upstream rate-limit answer on one call is that cause for that image only, FR-9 (a)). The mapping lives in one function in `fan-out.js` and is pinned by a table spec covering all five outcomes.
7. `if (signal.aborted) return;` once, after all slots settle and before any row, exactly as the existing single-call ordering (no row after a Cancel).
8. one usage row per **successful slot** through the unchanged `buildUsageRow`, `costUsd = price(model, resolution, slot.imageCount)` (the same call shape the unchanged handler makes for `result.imageCount`, now with the resolution), tokens from that slot's `usageMetadata`; a row-write failure is logged and never changes the 200 (FR-69). The response `costUsd` is `price(model, resolution, succeeded)` where `succeeded` is the sum of the slots' `imageCount` (section 5.0), the same expression over the same unit price (Rule A). A missing price for the pair is checked once before any call (step 2); it cannot arise here.
9. response.

`reduceSlots(slotResults)` in `fan-out.js` is pure: it orders by slot index (not completion), builds `parts` as the successful slots' parts in slot order (so a slot's thought parts stay with it, as in a one-image response), `succeeded` (sum of `imageCount`), `costUsd`, `usage` (summed tokens) and `batch` (`requested` = N, `granted`, `succeeded`, one `failures` entry per failed slot with its mapped cause). It never counts a slot as one image: a slot is worth the `imageCount` it carries. When no slot succeeded it returns the outcome of the **lowest-numbered slot** exactly as a one-image request would (safety, text, `EMPTY_RESPONSE`, or the rethrown error), so an all-text batch answers the `text` kind and no cause mapping is involved, and when every slot is `file_missing` it throws `FILE_MISSING` so the client's existing recovery runs. This keeps every zero-image path on a code the client already maps.

`usage-row.js`, `classify-response.js`, `errors.js`, `routes.js` (the default `price: computeImageCost` wiring), `server/index.js` and `server/usage/store.js` are **not changed**. `gemini.js` is **not changed** (section 3.3, section 8).

## 6. Price table and the single source (PD OD-14a, AB OD-14c, SE decimals)

- **Source (PD, overruled if the owner rules otherwise under OD-14a):** `imagePrices` in `image-studio-contract.json` (section 3.1). `server/usage/pricing.js` builds `IMAGE_PRICES` from it by the same import attribute `request-schema.js` already uses; the client reads the same JSON through a typed accessor in `image-studio-contract.ts`. Rejected: an endpoint (FR-20 says the estimate "needs no request", and it would add a loading state to a pure number); the model catalogue `model-catalog.json` (its readers include `model-settings.component.ts`, `model-settings.service.ts`, `model-support.js` and three specs, impact B11, for no benefit); a second hand-kept client copy (the failure class `image-model-consistency.spec.ts` was written against).
- **Shape and no flat fallback (guards S4):** `getImagePrice(modelId, resolution)` and `computeImageCost(modelId, resolution, count)` take the resolution **as a required argument**; an unknown model, an unknown resolution for a known model, or a missing resolution throws `PriceNotConfiguredError` (which carries both). There is no model-only entry and no default, and the old one-argument form is removed, so a stale caller passing `(model, count)` fails loudly instead of billing a 4K image at a 1K price.
- **Rule A (AB, OD-14c):** neither the estimate nor `costUsd` is rounded; the estimate is `unit * N` and the recorded cost is the same expression over the same unit (`unit * succeeded`, section 5.0; each row is `unit * slot.imageCount`). The test compares per image and against the shared expression, and does not assert an exact floating-point sum of rows (Specification FR-21 limitation). Display rounds, never storage.
- **Decimals of the estimate text (SE):** one function `formatMoney(amount, decimals)` is the only place text is formed from a cost. The existing `formatCost` (`$` + `toFixed(2)`) is the base for the AC-12 spend figures (RD, OD-13 e). The estimate decimals are the owner's: options are (i) two decimals everywhere, (ii) enough decimals to show the price exactly, up to a stated maximum. The plan does not choose; the estimate spec needs the ruling.
- **Consistency spec extended (FR-21):** `image-model-consistency.spec.ts` keeps its model-key assertions and gains the resolution dimension: every catalogue (model, resolution) pair has a price, no extra pair has one, and for each model the 4K price is greater than the 1K and the 2K price (AC-14a). Whether 1K equals 2K is not asserted.

- `apply-response.ts`: **no behavioural change.** The merged model turn is numbered image by image, `modelTurn.cost` is the total, `meta.costUsd` adds the total. Its spec gains N-image cases.

### 7.4 Style ref and the role invariant (RD OD-10, FR-10..FR-14)

- Tag location (RD): Turn level, `styleRefPartIndex` (section 2). ### 7.5 User presets (RD OD-12, FR-15..FR-17)

- **Port, not `localStorage` in a util (guards S9):** `UserPresetStoragePort { load(): { ok:true, presets } | { ok:false } ; save(presets): { ok:boolean } }` in `ports.ts`, a token in `image-studio.tokens.ts`, a browser adapter in `browser-ports.ts` that wraps every `localStorage` access in `try/catch`. Tests use an in-memory fake. Data that does not parse is ignored and **not** deleted by loading; a save that cannot be stored is reported as not saved.

## 8. Derived actions on the wire (RD OD-7, OD-8)

No new wire shape and no `server/providers/` change are planned for either.

A request over the cap would answer `PROTECTED_HISTORY_EXCEEDS_LIMIT` or `REQUEST_BODY_TOO_LARGE`, which the client already maps; the live evidence records real 4K byte sizes.

## 11. Server persistence, secrets, rules

- **`usage_log` (NFR-8):** no column is added and no migration is needed. Rows keep `mode` null and `taskLabel` `image-studio|<presetId|none>|<resolution>`, so rows written before and after this Story are counted by one rule. A new column would be silently ignored by `CREATE TABLE IF NOT EXISTS` on a populated database; this plan adds none.
- **Rule 1** (provider independence): no SDK call outside `server/providers/`; `gemini.js` is not edited. **Rule 2** (retrieval separate): nothing is added; review must confirm the diff adds no search or page fetch because no automated check exists. **Rule 3**: prompt text is in `src/prompt-core/`. **Rule 4**: prices are not secrets; no key reaches the bundle. **`STORE_REGISTRY`**: untouched; "UA and EN" is `uiLanguage`.
- `.env.example`: no setting is added.

## 12. Spend and estimate on the client (AB OD-3 b, RD OD-13)

- **Selection (AB):** the Story says spend comes from the **existing** `GET /api/usage`, so the header makes one `UsageService.fetch({ from: <UTC month start> })` call and selects Image Studio rows on the client (`taskLabel` prefix `image-studio|`, `mode` null), then derives today and month from that one result. No server filter is built. Delta if the owner rules a server prefix filter or aggregate: the route lives in `server/index.js`, which no spec imports (impact hazard 7), so it would first need extraction into a testable module, a new test seam and a new spec.
- **Volume:** the month figure needs every usage row of the month, text-generation rows included, with no limit or aggregation on the endpoint (Specification FR-18 planner note). The plan accepts that for now and records it as a risk; the trigger to build the server-side alternative is the row count, which no requirement bounds.
- **Refresh (RD, OD-13):** on studio open and after an action that ended with at least one image, via the store's `imageActionsCompleted` signal observed by the container. **Who triggers which fetch (N-4):** the `image-studio` container owns both triggers. It calls `spend.refresh()` once when the studio opens (a single call in its initialisation, FR-18 (c)) and again from an `effect` on `imageActionsCompleted`; `studio-header` only renders `SpendService.state` and fetches nothing itself, and `SpendService` does not fetch in its constructor, so a header rendered in a spec without the container issues no request. While loading and after a failed fetch the header shows a neutral placeholder and no figure, never `$0.00`; a failed fetch hides nothing else. The per-session running total (FR-71) is kept and is not replaced.
- **Estimate (AB):** `estimateCost` is computed from the contract and the draft's model, resolution and `imageCount`, shown next to Generate for Generate only (RD, OD-14 a), updating as those change, with no request.

## 15. Rejected alternatives

| Alternative | Why it lost |
|---|---|
| Client fan-out (N requests) | Multiplies the history upload and the `countTokens` traffic by N, needs a coordinated FILE_MISSING recovery in the runner, and makes "Generated k of N" client arithmetic. It does win FR-9 (c) and a smaller server diff; that is the delta recorded in 5.1. |
| Server-side `GET /api/usage` prefix filter or aggregate | The Story says "existing" endpoint; `server/index.js` is untested; adds a server surface the Story did not list. |
| A price endpoint for the estimate | FR-20 says no request; adds a loading state to a pure number. |
| Prices in `model-catalog.json` | Reaches the text-model settings UI and three more specs for no gain (impact B11). |
| A role tag on a `Part` | Forwarded to Gemini as an unknown field (impact S3). |
| A new `derived` discriminator on the request | Upscale and Variation are expressible as a normal generate request with an empty history; a discriminator would add a wire field and a schema change with no information the server needs. |
| One model turn per response | Consecutive model turns break the alternating, even-length history and fail the next request (impact S11). |
| Making the limiter's `tryConsume` take a count | Changes every existing limiter and handler assertion; a new method keeps them green. |
| A flat model-only price fallback for unknown resolutions | Bills a 4K image at a 1K price with a 200 (impact S4). |
| Putting the Style-ref sentence in `prompt-presets.ts` | Widens the edit surface of the registry-presets file (section 4). |
| Count a slot as exactly one image (bill `price(..., 1)`), truncating extra image parts | Contradicts the unchanged handler and its pinned FR-70 spec (two image parts bill 2), or drops images the vendor already charged for (section 5.0). |
| Add `text` to `imageFailureCauses` for a text-only slot | Grows a closed list FR-9 (a) enumerates as four classes; `empty` is the existing class for "the call produced no image" (section 3.1). |
| Rule B (server rounding) | A server change the Story does not authorise; changes stored values and the FR-18 sums. |
