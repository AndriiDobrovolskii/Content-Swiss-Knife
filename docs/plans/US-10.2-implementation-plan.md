## Approach

This is a tooling, configuration and test change. **No file under `src/`, `server/`, `tools/`, `angular.json`, `arch-guard.sh`,
`vitest.config.ts` or `tsconfig*.json` changes, and no prompt, renderer, schema, store, locale or FROZEN file is touched.** The domain model,
the prompt -> schema -> renderer -> validator chain, the `PromptPayload` / `systemBlocks` separation, the Angular surface, the server surface
and `server/usage/store.js` are all unchanged, so the corresponding design areas of the planner contract have no decision to make (stated once
here; each is "unaffected" in the check below).

The solution has five parts. (1) The guard `test/undici-pin.spec.ts` is rewritten around a **pure decision** that takes plain values and returns a
tagged verdict (`[C1]`..`[C5]`); the real-runtime cases and the synthetic non-vacuity cases call the *same* functions, every file read is lazy
and non-throwing, and the old version-window assertion is replaced by "the Pin equals the bundled undici of the Running Node". (2) One atomic
change set: measure the bundled undici under the Pinned Node, write `engines.node` and `overrides.cheerio.undici`, create `.nvmrc`, and let npm
regenerate `package-lock.json` and `node_modules` in the same sitting, with no guard run and no commit in between. (3) A live verification that is
*recorded evidence, not a test*: a real `node server/index.js` upload on the Pinned Node, deletion of exactly the object it created, a scratch-copy
measurement without the override. (4) **A hold / resume / failure protocol (DD-21, DD-22)** that lets the one IMPLEMENTATION stage contain those human-dependent
checks without a human gate: the builder returns `BLOCKED` at each human step, the human acts, `/so:next` resumes at the first task not yet recorded in
`pipeline_status`; and **one evidence file that only the human writes and commits** (DD-16). (5) The gate, a ten-run `test:logic` series on the final tree,
and a README line edited before the series. AGENTS.md (lines 332 and 405-407) and `docs/knowledge/project-state.md` are left to a human follow-up.

## Design decisions

### DD-1. The guard is a pure decision plus thin real adapters (FR-5, FR-8, OD-11)

`test/undici-pin.spec.ts` gains a set of **pure functions** in the file itself. Each receives plain values and returns
`{ ok: true } | { ok: false; cause: 'C1'..'C5'; field: string; message: string }`. They read neither `process.version`, `process.versions` nor any
file. The inputs object has five members: the raw `.nvmrc` text (or `null` when the file is missing), `engines.node` (as parsed, `undefined`
when missing), the running Node string, the bundled undici string, and the Pin (as parsed, `undefined` when missing).

Functions (one per FR-4 / FR-6 / FR-7 condition): `nvmrcPresent`, `nvmrcExact`, `enginesPresent`, `enginesExact`, `nvmrcEqualsEngines`,
`runningNodeIsPinned`, `bundledUndiciEqualsPin`.

**Design invariant (the reason for the whole seam):** the *real* case and the *synthetic* cases for a condition call the **same function**. The real
case is `verdict = fn(realInputs())`, the synthetic cases are `fn(syntheticInputs)`. If they were different code the non-vacuity proof would prove
nothing about the real case (Impact silent-failure risk 2). The real adapters are exactly: read `.nvmrc` / `package.json` through the reader of
DD-2, read `process.version` and `process.versions.undici` at call time inside the `it`, hand the values to the function, and assert `ok`
with the verdict's message as the vitest failure message (so the printed failure *is* the attributable message).

Why in the spec file and not a fixture module: see Rejected alternatives A1. NFR-7 leaves `test/` as the only place such code can live; the
single-file form also keeps "the guard file was not weakened between the red and green runs" (FR-15) a one-file hash comparison.

### DD-2. Every read is lazy and non-throwing (impact hazard 3, FR-14 failure path)

Removing the throw for `.nvmrc` alone is not enough: today `const pkg = readJson(...)` and `const lock = readJson(...)` also run at module
scope and throw when a file is missing, and `describe()` bodies compute `lock.packages?.[...]` at collection time. All of that moves inside
`it()` bodies behind one reader:

- `readTree(io)` takes an injected `io = { exists(rel): boolean; read(rel): string }` and returns, per file (`.nvmrc`, `package.json`,
  `package-lock.json`), a result `{ state: 'ok', ... } | { state: 'missing' } | { state: 'unreadable', reason }`. A missing file, a JSON parse error
  and an I/O error each become a result, never an exception at import time or inside the reader.
- The real `io` is bound to `root`, which is still `process.env['UNDICI_PIN_ROOT']` resolved, else `process.cwd()` (the seam stays, it stays
  unset in the gate; it only chooses *which tree* the file cases read, the runtime cases still read the real `process`).
- Synthetic readers (fake `io` objects) prove the reader itself: missing `.nvmrc` -> `missing` (no throw); invalid JSON -> `unreadable` naming the
  file; a tree that lacks every file -> three `missing`. This keeps NFR-1 (the guard reads, it does not write) and needs no temporary directory.

A case whose file result is `missing` or `unreadable` fails **that case** with a message naming the file. A missing `package.json` or lockfile fails
its survivor cases the same way. Nothing can fail the file as a whole at import: every red on the unchanged tree is one named case (FR-14).

### DD-3. Causes are machine-readable; the mapping is fixed (FR-4, FR-14, Definitions)

Each failing message starts with its single tag, for example `[C1] .nvmrc is missing under <root> ...`, and contains no other tag. The FR-14 table
is then filled from the printed output, not by interpretation. The mapping, decided here so TEST_WRITING and the builder do not guess:

| Condition (function) | Failing input | Cause | Field named |
|---|---|---|---|
| `nvmrcPresent` | file missing | C1 | `.nvmrc` ("is missing") |
| `nvmrcExact` | missing -> C1 "is missing"; empty/whitespace -> C1 "is empty"; not exact -> C1, content quoted | C1 | `.nvmrc` |
| `enginesPresent` | `engines` missing -> "package.json `engines` is missing"; `engines.node` missing -> "`engines.node` is missing" | C2 | `engines` / `engines.node` |
| `enginesExact` | missing, not a string, not exact | C2 | `engines.node` |
| `nvmrcEqualsEngines` | first missing/non-exact precondition in order `.nvmrc`, then `engines.node`; else the two differ | C1, C2, or C5 | the file/field at fault |
| `runningNodeIsPinned` | `.nvmrc` missing/empty/not exact -> C1 (never a mismatch); else running != `.nvmrc` | C1 or C3 | `.nvmrc`, or the three values (pinned, running, files that name the pin) |
| `bundledUndiciEqualsPin` | Pin missing/non-exact (names `overrides.cheerio.undici`), bundled missing, or differ | C4 | `overrides.cheerio.undici` / `process.versions.undici` |

"Missing" and "empty" are different messages that carry the same tag (C1). FR-7's *verdict* depends only on the Pin and the bundled undici; the
pinned Node (from `.nvmrc`, or the text "`.nvmrc` unavailable") appears in the message only.

### DD-4. Normalisation rules differ between the two files (FR-1, FR-2, NFR-9)

- `.nvmrc`: `trim()` (which already removes `\r`, `\n`, spaces, and the BOM U+FEFF), then remove **at most one** leading `v`, then the result must match
  `^\d+\.\d+\.\d+$`. So `24.22.2`, `24.22.2\n`, `24.22.2\r\n`, `v24.22.2\n`, ` 24.22.2 ` and `﻿24.22.2` are accepted; `vv24.22.2`, `24`, `24.22`,
  `lts/*`, `node`, `^24.22.2`, `24.22.2-rc.1`, `24.22.2.1`, `24.22.2\n25.0.0`, the empty string and whitespace-only are rejected.
- `engines.node`: **no** normalisation. It must be a string matching the same exact form with no `v` and no whitespace; `v24.22.2`, `>=24.22.2 <25`,
  `24.22`, a number and `null` are rejected.
- The running Node (`process.version`, e.g. `v24.22.2`) has one leading `v` removed before comparison inside `runningNodeIsPinned`.
- Offending content in a message is shown with non-printable characters escaped (e.g. `"﻿24"`), so an invisible character is visible in the failure.

Why trim-tolerant for `.nvmrc` only: git on Windows turns the file CRLF and editors add a trailing newline; `engines.node` is JSON and is written by npm.
The strictness of the Pinned Node itself (no `24`, no alias) is the point of FR-1.

| FR-4 | (d) `engines.node` exact | real | red `[C2]` |
| FR-4 | (e) `.nvmrc` equals `engines.node` | real | red `[C1]` (first missing precondition) |

| FR-9 | existing non-vacuity proofs of cases 1, 5, 6 | synthetic | green |
| DD-2 | reader with fake `io` (missing / unreadable / all missing) | synthetic | green |

Synthetic groups (each failing input paired with a passing one, each failing verdict asserted for `ok === false`, the **expected single cause tag**,

- S1 normalisation (DD-4 list, including CRLF, leading `v`, BOM, `vv`).
- S2 `.nvmrc`: missing, empty, `24`, `lts/*`, `node`, `24.22`, `^24.22.2`, `24.22.2-rc.1` -> `[C1]`; `24.22.2` passes.
- S3 `engines.node`: missing (`engines` absent and `engines.node` absent are two messages), `>=24.22.2 <25`, `v24.22.2`, a number -> `[C2]`; `24.22.2` passes.

Because the synthetic cases carry the proof "any wrong Node fails", FR-6 stays a *real* case that fails (never skips, `todo`, warns or downgrades; NFR-2) and
is proven non-vacuous on **any** Node through S5.

### DD-6. The old window is deleted, and the deletion is traced (FR-8, AC-5, AGENTS.md 7.7)

`WINDOW_MIN`, `WINDOW_BELOW`, `windowProblem`, the old case 2 and its non-vacuity case are removed. This has the shape of "deleting a failing test" (7.7)
because on the new Pin the old case 2 would fail (`7.30.1` is "at or above 7.26.0"); it is legitimate only because the **requirement changed the rule**
(FR-8, AC-5: the rule is "the Pin equals the bundled undici of the Running Node", not a fixed range). Trace, following the precedent of
`src/prompts/task-c.description-bytes.spec.ts` (its `US-9.1 AMENDMENT` header):

1. The spec file's header comment is rewritten and carries a block headed **`US-10.2 AMENDMENT (AGENTS.md 7.7: a requirement changed the rule of this guard)`**
   stating: what stops being pinned (the fixed range from the Node-bundled copy up to the first release that failed on Node 24.15.0, and the hard-coded bounds); what is
   newly proven (the Pin equals the bundled undici of the Running Node, for any value, plus the runtime-pin cases); what cannot be shown any more (the guard no longer
   encodes *which* npm versions were empirically good or bad on 24.15.0; that sweep stays in `docs/plans/US-10.1-task-breakdown.md`); the requirement ids FR-8 / AC-5; and that the
   replacement cases are FR-7 plus S6.
2. To keep the FR-8 search clean, the amendment block names the old things in prose ("the version-window constants and window check") and **does not contain the identifiers**.
3. TEST_WRITING's `test_generation_report` and `ac_test_matrix` (AC-5 row) list the removed assertion and its replacement in a "removed / replaced assertions" table.
4. The FR-8 recorded source search uses the patterns `WINDOW_MIN|WINDOW_BELOW|windowProblem` (whole file: zero hits required) and `7\.26\.0|verified window|first release that failed`
   (hits allowed only inside the amendment block or as a synthetic input of a non-vacuity case, each hit listed and classified). The synthetic literals of the case-1 exactness proof
   (`7.24.4`, `7.25.0`, `10.0.1`, ...) are allowed because FR-8 permits version literals as synthetic inputs.
5. Nothing is `skip`ped, `todo`ed or `only`ed anywhere; the guard file is not changed between the FR-14 red run and the FR-15 green run, checked by a sha256 of the file recorded in both tables.

### DD-7. Survivors keep their assertions and become lazy (FR-9)

Cases 1, 3, 4, 5, 6 and their non-vacuity proofs keep their assertions and failure messages unchanged except for two edits: the Pin comes from the lazy reader (DD-2), and the
header no longer claims a window. Case 3 (lockfile nested entry at exactly the Pin with `resolved` and `integrity`) and case 4 (installed copy resolved from cheerio's directory,
absent `node_modules` / `cheerio` / `undici` fails, never skips) keep reading `package-lock.json` and `node_modules` under `root`. The hoisted `node_modules/undici` and
`node_modules/node-gyp/node_modules/undici` stay deliberately unasserted. `UNDICI_PIN_ROOT` stays and stays unset in the gate; every recorded gate / series command records
`echo "${UNDICI_PIN_ROOT-unset}"` once so an exported variable cannot silently point the cases at a scratch tree.

### DD-8. The Pin is a measured value, never a constant (FR-10, FR-8)

The Pin is whatever `node -p process.versions.undici` prints under the Pinned Node at IMPLEMENTATION (expected `7.30.1`). The measurement is one recorded command line, run before any
write, that prints `node -v`, the undici version and `npm -v` together: `node -v; node -p process.versions.undici; npm -v`. If it prints something other than `7.30.1`, the measured value is
written and the difference goes into the evidence (FR-20). Nothing in the guard, the tests or the README names `7.30.1`; the guard learns the expected value from the running Node.

### DD-9. One atomic change set and its order (FR-15, NFR-5, impact hazard 4)

The pin, `.nvmrc`, `engines`, the lockfile and the installed tree land as one unit. The guard cases 3 and 4 compare the Pin with the lockfile and `node_modules`; they are red between the
`package.json` write and the end of `npm install`. The design property is that **no guard run, no gate and no commit happens in that window**. Steps, all on the Pinned Node, in this order:

1. Precondition (DD-12): `node -v` is `v24.22.2`, else `BLOCKED` (DD-21).
2. **Record the base (N-1).** The base commit is `6b377a5`, but `HEAD` is **not** required to equal it (a docs commit may legitimately precede IMPLEMENTATION). The checks are:
   `git merge-base --is-ancestor 6b377a5 HEAD` exits 0; `git diff --quiet 6b377a5 -- package.json package-lock.json` exits 0; `.nvmrc` is not tracked at `HEAD`
   (`git ls-files --error-unmatch .nvmrc` fails) and does not exist; `git status --porcelain -- package.json package-lock.json .nvmrc` is empty. Record `git rev-parse HEAD`, sha256 of `package-lock.json`
   and `npm -v`. Any check failing returns `BLOCKED` with the printed values (the base is not the base the plan was written against; a human decides). The key diff of DD-10 is taken against `6b377a5`.
3. Measure the Pin (DD-8).
4. Write `package.json`: `engines` = `{ "node": "24.22.2" }` and `overrides.cheerio.undici` = the measured value. Method: `npm pkg set engines.node=24.22.2` and
   `npm pkg set overrides.cheerio.undici=<measured>` (npm preserves the file's indent and newline style); fall back to a precise text edit if `npm pkg set` reformats anything. Either way the
   result is judged by the parsed key diff of DD-10, not by assumption.
5. Create `.nvmrc` containing `24.22.2` and a newline (a plain write; line-ending normalisation is the guard's job, DD-4).
6. `npm install` (no flags, no package argument, never `npm ci`, `npm update`, `npm dedupe` or `npm audit fix` in the real tree), then record sha256 of `package-lock.json`.
7. Second `npm install`; record sha256 again; the two hashes must be equal (FR-12).
8. `npm ls undici`; record the exit code (0 required) and output. If the nested entry is not the Pin, the R1 fallback of DD-10 applies and **steps 6-8 are repeated in full after it**
   (N-3): the fallback's `npm install`, a further `npm install`, both lockfile hashes equal, `npm ls undici` exit 0. The idempotence claim of FR-12 is thus always about the last two installs.
9. Only now: run the guard (FR-15 green table), then the parsed key diff (DD-10).
10. `npm run lint` exits 0; the FR-8 source search is re-run (DD-6 item 4).
11. **One commit (N-2), staged by explicit path:** `git add -- package.json package-lock.json .nvmrc test/undici-pin.spec.ts` (never `git add -A`, `git add .` or `git commit -a`: the working tree
    also holds untracked `docs/**` and `.tmp.driveupload/`), then `git diff --cached --name-only` must list **exactly those four paths** before `git commit`.

**Failure path (N-3).** If step 6 or 7 fails outright (for example the registry is unreachable): restore the two `package.json` edits to the base values, confirm the lockfile hash equals step 2's,
remove the `.nvmrc` this task created, and return `BLOCKED` with the verbatim output. `node_modules` is not tracked and cannot be reverted by a git command; a partially run install may have left it in an
intermediate state. The task therefore also records, verbatim, `npm ls undici` (exit code and output) and the version found in `node_modules/cheerio/node_modules/undici/package.json` (or "absent"), and
states in `blocking_issues` that `node_modules` was left as the failed install left it and that a plain `npm install` on the restored base is the human's choice to run. No half-applied tracked set is left.

### DD-10. npm regenerates the lock for a scoped override; the other `undici` copies stay (FR-12, FR-13, OD-14)

- **Expected behaviour.** `cheerio@1.2.0` requires `undici ^7.19.0`; `@angular/build` requires exactly `7.28.0` (hoisted copy); `node-gyp` requires `^6.25.0` and keeps its nested `6.27.0`. A nested
  `7.30.1` cannot dedupe into `7.28.0`, so `npm install` replaces only `node_modules/cheerio/node_modules/undici`. The hoisted `7.28.0` and `node-gyp`'s `6.27.0` are untouched, and
  the guard deliberately does not assert them.
- **Risk and fallback (decided now, no hand edit).** npm might not re-resolve the nested entry when only the override *value* changed. It shows in guard cases 3 and 4 and in
  `npm ls undici`. Fallback: delete the untracked directory `node_modules/cheerio/node_modules/undici` and run `npm install` once more, then repeat DD-9 steps 6-8 (N-3). If the nested entry is still not the Pin, return
  `BLOCKED` with the output; never patch `package-lock.json`.
- **Key diff for FR-13 is on parsed JSON, not text.** A small throwaway script, piped on standard input (`node --input-type=module -`, nothing written into the repository), loads
  `git show 6b377a5:package.json` and `git show 6b377a5:package-lock.json` and the working-tree files, and prints every path whose value differs. Allowed paths: `package.json` -> added `engines`
  (only key `node`), changed `overrides.cheerio.undici`; `package-lock.json` -> the keys of `packages["node_modules/cheerio/node_modules/undici"]` (`version`, `resolved`, `integrity`, and

### DD-21. The hold / resume / failure protocol for the human-dependent work inside IMPLEMENTATION (B-1; FR-16, FR-17, FR-18, FR-19, FR-20, FR-22, AGENTS.md 6.9)

**The problem.** Three pieces of work need a human (the real-route upload, the without-override run, the evidence file) and one is long (the series). `IMPLEMENTATION` is a `composite_skill` with a single
`so-builder` entry for the `server` track; `stage-map.yaml` gives it **no human gate** and four loop-back keys (`partial`, `blocked_by_plan`, `blocked_by_architecture`, `changes_required_tests`); `PASS` advances to
QUALITY_GATE; `BLOCKED` holds the stage and has **no** loop-back key; `partial` re-dispatches and increments `stage_attempts[IMPLEMENTATION]` (capped at 3; only `PASS` resets it). The builder cannot idle on a human.

**What the precedent shows (read, not assumed).** In US-10.1 the builder worked through **many tasks in one dispatch** (the history records "T18-T40 DONE (24 commits ...), ledger in pipeline_status v2" and "T41-T45 DONE" as the
content of single `IMPLEMENTATION` events), kept a **task ledger table in `pipeline_status`** (`Task | Track | State | Commit`), bumped the `pipeline_status` version per dispatch, returned `BLOCKED` when it could not go on
(events at 14:30 and 18:30), and the `BLOCKED` hold was resolved by **a human decision that the orchestrator recorded as a loop-back with the human as actor** (the 18:50 event). So "one dispatch per task" in `so-builder`
means "each task's outcome is recorded when it completes", not "each task is a separate orchestrator round-trip"; this protocol builds on that and uses `partial` only as a last resort (below).

**Decision: keep the human-dependent checks inside IMPLEMENTATION, held by `BLOCKED`.** Moving them out to a human step "after IMPLEMENTATION" is rejected (A14): `stage-map.yaml` has no stage or gate between IMPLEMENTATION and
QUALITY_GATE and the orchestrator may not add one; an IMPLEMENTATION `PASS` with the live check unrecorded would run the gate and the expensive series on a pair whose only hypothesis (U-5) is untested; and AGENTS.md 6.9 puts the
live record in the story's **pipeline status**, which only the builder writes and which closes with IMPLEMENTATION.

#### Rules of the protocol

1. **Ledger and resume rule.** `pipeline_status` carries a task ledger (`Task | State | Outcome pointer`) with states `DONE`, `AWAITING_HUMAN`, `FAILED`, `NOT_STARTED`. **Every dispatch starts** by printing `node -v` (DD-12), reading the
   ledger and the hand-off location (DD-22), revalidating `DONE` records that carry a fingerprint (rule 7), and then **resumes at the first task in the breakdown's order that is not `DONE`**. A task is never re-done once `DONE`
   and valid.
2. **Human-free tasks run to completion inside the dispatch.** The builder carries on from one completed human-free task to the next in the same dispatch (one commit or one record each, as the breakdown says); it does
   **not** return `partial` between them. `partial` is reserved for a dispatch cut short by the environment (for example the dispatch's own context limit) after at least one task completed and a human-free task remains;
   it increments `stage_attempts[IMPLEMENTATION]` (cap 3), so the protocol is designed to need **none** (see the dispatch plan) and treats a cap hold as a safe, human-decided stop.
3. **Hold = `BLOCKED` with no loop-back key.** At a task that needs the human and whose input is absent, the builder (a) writes the task's state `AWAITING_HUMAN` and a **human command sheet** into its own `pipeline_status`
   (section "Human actions", with the exact commands, the pass conditions and the exact files to leave behind), and (b) returns `verdict: BLOCKED`, `loop_back_stage: null`, with `blocking_issues` that name, as separate items:
   the **action** ("T2: run the real upload and delete as written in `pipeline_status` section 'Human action T2'"), **who** (human, or "reply `T2.runner=builder` to have the builder run it"), the **sheet location** (`pipeline_status`
   path and section), the **drop location** (the absolute path of the hand-off directory and the file name(s), DD-22), what "done" looks like, and **the resume command (`/so:next`)**. The builder then ends. It does not wait,
   sleep, poll, read `.env`, or start any server while it waits.
4. **Resume = `/so:next`, which is a re-dispatch.** The orchestrator's continue flow holds a `BLOCKED` stage (`status: BLOCKED`) and ends the run; the next `/so:next` reaches step 5 ("check for existing stage output ... no open
   `CHANGES_REQUIRED` or `BLOCKED` record - do not regenerate"), which by its own wording is **not** satisfied while a `BLOCKED` record is open, so it falls through to step 6 and dispatches `so-builder` again; the builder's rule 1 then
   resumes at the first task not yet recorded. This is the same re-dispatch that resolved the US-10.1 holds. (`continue-flow.md` does not say in so many words that `/so:next` leaves `status: BLOCKED`; the plan relies on this
   reading and the US-10.1 precedent and states it as an item for the human at HUMAN_PLAN_APPROVAL.)
5. **Idempotent hold.** A resume that finds the drop location empty (or the required lines missing) writes **nothing** to `pipeline_status` and returns the same `BLOCKED` with the same `blocking_issues`, naming what is
   missing. No ledger change, no attempt counter change (`BLOCKED` neither increments nor resets it).
6. **Accepting the human's output.** When the drop file is present, the builder: (a) runs the secret search on it (DD-16) and stops with `BLOCKED` on a hit without copying it; (b) checks it for completeness against the sheet
   (the first line `node -v` = `v24.22.2`; date; runner; the items the sheet lists); (c) **copies it verbatim into `pipeline_status`** (section "Live check records", labelled "supplied by the human, copied verbatim, secret-search
   result: ...") - this is the AGENTS.md 6.9 record; (d) decides the outcome by the Specification's rules; (e) marks the task `DONE` / `FAILED` with the outcome pointer. When `runner=builder`, the builder runs the sheet itself in
   the dispatch (no drop file), records the raw output in the same section and labels it "run by so-builder at the human's instruction: <the control-file line, quoted>".
7. **Validity of recorded results (re-entry after a loop-back).** The T7 record stores the relevant-change-set fingerprint (DD-17); the T2 record stores a **pair fingerprint** (the same construction over `package.json`,
   `package-lock.json`, `.nvmrc` and `server/`). On any re-entry (a QUALITY_GATE `changes_required`, a rejection, a reconciliation loop-back) the builder recomputes both: a differing T7 fingerprint -> the series is
   `NOT_STARTED` again (restart of ten); a differing pair fingerprint -> T2 is `NOT_STARTED` again (a new hold). Unchanged -> `DONE` stands and nothing is re-run.
8. **`PASS` only when all seven tasks are `DONE` and valid** - T2, T3, the series and the evidence verification included. The orchestrator is thereby unable to advance to QUALITY_GATE while one of them is unrecorded.
9. **Anything not in the table below returns `BLOCKED`**, never `PASS` and never an invented key. Cap safety: `BLOCKED` does not touch `stage_attempts`; the only counted return is `partial`, used by none of the endings below.

#### Dispatch order (what this plan requires of the breakdown) and why

Order: **change set (T1) -> README (T4) -> scope and pre-series checks (T5) -> live upload (T2, human) -> without-override run (T3, human) -> ten-run series (T7) -> evidence (T6, human writes and commits, builder verifies)**.
Reasons: (i) the live results are only worth recording on the **final** pair, so everything that could still change the relevant change set (README, scope findings, `test:components`, coverage) is finished before the human is
asked for anything; version 1's "T2 immediately after T1" gave an earlier failure signal for U-5 but made T4/T5 "meanwhile" work that a per-dispatch builder cannot do, and a failed U-5 costs only a README commit on an unpushed
branch (A16); (ii) the series runs only after T2 and T3, so no live server runs during it and the worker-fault evidence is not confounded; (iii) the evidence step is last so the `PASS` return coincides with the final human act.

Nothing: it has already returned. It prepared, before returning, the command sheet and the evidence block in `pipeline_status` (its own file), and it prepared nothing in the repository: no skeleton at the evidence path (a

### DD-22. The hand-off location, its files and its rules (B-1; supports DD-15, DD-16, DD-21)

- **Where.** A fixed absolute directory **outside the repository and outside the session scratchpad**: the operating-system temporary directory, subdirectory `US-10.2-live` (Git Bash `"$TEMP/US-10.2-live"`, Windows
  `%TEMP%\US-10.2-live\`). The builder prints the resolved absolute path in the `blocking_issues` of every hold and in `pipeline_status`. Why not the scratchpad: it is per session, and `/so:next` after the human acts
  may run in another session; why not the repository: a log or output in the repository risks a commit and a secret. It is **never** under `.tmp.driveupload/`. The human creates it if absent.
- **Files** (the sheet names each one):
  - `T2-output.txt`, `T2-rerun.txt`; `T3-output.txt`, `T3-rerun.txt` — the raw output of the live checks (the sheet makes each command `2>&1 | tee -a <file>` and starts the file with a header line: date, runner,
    `node -v`, `node -p process.versions.undici`, `npm -v`, `npm ls undici`).
  - `T7-run-1.log` .. `T7-run-10.log`, `T7-exit-codes.txt`, `T7-start.txt`, `T7-end.txt` — only for series Form 3 (DD-17).
  - `control.txt` — optional, human-written, `key=value` lines, the only control channel the builder reads: `T2.runner=builder|human`, `T3.runner=builder|human`, `T2.new-attempt=<reason>`,
    `T3.rerun=skip`, `T3.after-failed-T2=yes`. Absent or missing a key = the default (`human`; the others off). The builder copies the lines it acts on, quoted, into `pipeline_status` (the audit trail).
- **Rules.** The builder reads, never edits, a human-written file; it runs the secret search on a file before copying it (DD-16); it does not copy `control.txt` content other than the keys above. The builder **deletes the
  hand-off files only in the dispatch that returns `PASS`**, after the evidence verification, so that a repeated dispatch can always re-read them. The hand-off files are not artifacts, not committed and not cited.
- **Not a gate.** The human's decision about a failure (rows 9, 11, 17) is communicated to the orchestrator in the conversation, as in US-10.1, and recorded by the orchestrator; `control.txt` only carries the three
  data choices that the builder itself must see.

## Rejected alternatives

- **A1. Put the pure decision in `test/fixtures/undici-pin-decision.ts`** (precedent: `task-c-description-guard.ts`). Rejected: a new file is outside the impact survey (it would be a `changes_required_impact`), it splits the red-to-green
  hash check across two files, and the same-file form already guarantees real and synthetic cases share code.
- **A2. Use `semver`** for parsing and range checks. Rejected: NFR-4 forbids a dependency; exact `MAJOR.MINOR.PATCH` strings and `===` suffice because OD-2 made `engines.node` exact.
- **A3. Skip or warn the runtime case on a wrong Node.** Rejected: OD-5 and NFR-2 require a failure.
- **A4. Hard-code `24.22.2` / `7.30.1` in the guard.** Rejected: FR-8 and DD-8; the guard learns the values from `.nvmrc`, `package.json` and the runtime, so a deliberate Node bump changes three files and never the test.
- **A5. `npm ci`, or `npm install --package-lock-only`.** Rejected: FR-12 specifies `npm install`; `npm ci` deletes `node_modules` and does not regenerate the lock; `--package-lock-only` leaves `node_modules` stale and turns cases 3/4 red.
- **A6. Hand-edit `package-lock.json`.** Rejected: forbidden (FR-12, out of scope).
- **A7. Throw at import for a missing file.** Rejected: destroys attribution (hazard 3).
- **A8. Fake a missing `.nvmrc` by writing temporary directories in the spec.** Rejected: the guard reads, it does not write (NFR-1); an injected `io` gives the same proof with no filesystem write.
- **A9. Scratch measurement in place** (temporarily remove the override in the real repository). Rejected: risks the real `package.json`, lockfile and `node_modules` (OD-10).
- **A10. Scratch correction by deleting the scratch lock and reinstalling, as the default.** Not chosen as the default: a full re-resolve can change unrelated packages and confound the measurement; `npm dedupe` removes only the
  duplicate (DD-14). It stays the recorded alternative and is the literal wording of FR-18; the choice is put to the human (N-6).
- **A11. An opt-in live vitest spec for the upload.** Rejected: that is US-10.3; this Story needs one recorded real call on the running server.
- **A12. `engines.node` as a range and `engine-strict`.** Rejected by the human (OD-2).
- **A13. Agent-written evidence from remembered results, or "transcription" by the builder.** Rejected: NFR-6, the registry ownership rule and `artifact-lifecycle.md` section 3; the human is the only writer (DD-16).
- **A14. Move the human-dependent live checks out of the builder's loop into a human step recorded after IMPLEMENTATION and before QUALITY_GATE.** Rejected (DD-21): no such stage or gate exists in `stage-map.yaml` (the
  orchestrator cannot add one), so `IMPLEMENTATION` would return `PASS` with T2 unrecorded and the gate and the ten-run series would run on an unverified pair; nothing would stop `/so:next` from advancing; AGENTS.md 6.9 puts
  the live record in the pipeline status, which closes with IMPLEMENTATION.
- **A15. Wait with `partial`** (return `CHANGES_REQUIRED` / `partial` while the human acts). Rejected: `partial` re-dispatches automatically and increments the 3-attempt counter, so it spins or exhausts the cap with no human
  action in between; `BLOCKED` is the only verdict that holds without a counter.
- **A16. Keep version 1's order (T2 immediately after T1, T4/T5 "meanwhile").** Rejected: a dispatch cannot work "meanwhile"; and the live results must be recorded on the final pair, so the change set, README and scope checks
  come first. The price is that a failed U-5 leaves the T1 and T4 commits on an unpushed feature branch for the human to deal with.
- **A17. The builder writes the evidence file under a human-granted exception.** Not adopted and not assumed: it needs the registry or the lifecycle rule to say so, neither of which this Story may edit. Offered to the human as a
  request only (DD-16).
- **A18. The session scratchpad as the hand-off location.** Rejected: per-session; the resume may run in another session (DD-22).
- **A19. Human output pasted into the chat for the builder to copy.** Rejected: a dispatch reads files, not conversation (`so-orchestrator`: "reads its inputs from files, never from conversation history"); a message cannot be re-read by
  a repeated dispatch.
