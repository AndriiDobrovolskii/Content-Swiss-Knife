## Approach

Image Studio is an additive vertical slice with a hard seam at the HTTP boundary and three seams on each side of it.

**Server.** A new package `server/image-studio/` of small, dependency-injected ESM modules (body-limit middleware, per-IP limiter, a
fixed-schedule retry loop, request schema, magic-byte detector, 18 MB measure, deterministic trim, response classifier, `FILE_MISSING`
recognizer, usage-row and price helpers, and two handler factories). `server/app.js` (new) exports `createApp(deps)`, which composes the
middleware in the order FR-27 and FR-51 require and mounts the image routes; `server/index.js` keeps only `listen`, the process
handlers and SIGTERM and registers the existing routes on the returned app. `GeminiProvider` gains three **single-shot** methods
(generate image, upload file, count tokens) with no retry and no fallback; retry, the limiter, trimming and classification live in the
image-studio modules, so Cancel, the clock and the rate-limit atomicity are all controlled in one place. Pricing gets an exact-key
per-image path that cannot reach `FALLBACK_PRICE`.

**Shared catalogue.** The two image models are appended to `model-catalog.json`. Each runtime derives a **text-only** catalogue at its
boundary (client `model-catalog.ts`, server `model-support.js`) from a union-typed raw list, so every existing text path (`findModel`,
`defaultModel`, `resolveSlot`, `clampLevel`, the tier fallback, `deepModels`/`fastModels`, `restore`) is image-blind by construction,
and a new `findImageModel`/`IMAGE_MODELS` surface is the only way to reach an image entry.

**Client.** Pure, injectable, coverage-scoped logic under `src/utils/image-studio/` (ingest pipeline, upload rules, output-format and
delivery rules, alt text, file name, request building, response application, session lifecycle, generation runner, error dispatch,
texts). Thin adapters under `src/services/image-studio/` (a `providedIn: 'root'` signal store, the IndexedDB adapter, the canvas
codec, browser ports). `LlmService` and `LlmProvider` gain two non-retrying methods. A new standalone `ImageStudioComponent` (plus three
children) is mounted as a full-area branch of `AppComponent` exactly as the Dashboard and HTML editor are. Generation state lives in the
root store, not in the component, so switching mode during a paid call neither aborts nor orphans it.

**Testability.** Neither runner has IndexedDB or a canvas. Two ports (`SessionStorePort`, `ImageCodec`) carry every behaviour the
Specification wants to test, with in-memory fakes that can throw `QuotaExceededError`; the real adapters are thin and their residual
(real transaction atomicity, real canvas output) is stated, not hidden (see Risks, R1/R2).

No FROZEN file is touched and no sibling file is needed. No store, locale, STORE_REGISTRY value, prompt chain, renderer, validator,
corpus fixture, domain schema or `usage_log` column is touched.

## Design decisions

### 1. Domain model and persisted data (`src/domain/`)

`ProductDescriptionDoc` and `ConsumablesDoc` do **not** change, so the fixtures in `test/fixtures/corpus/` parse exactly as before and
none is regenerated. `src/domain/` is not touched: its 95/95/90/95 floors belong to the description artifacts, and the studio's schemas
are API-boundary and local-storage schemas, so they live in `src/utils/image-studio/schemas.ts` (Zod, already a dependency) (DD-27).

New schemas (all in `src/utils/image-studio/schemas.ts`, Zod):

- `GenerateResponseSchema`: a discriminated union on the closed field `kind` (`images` | `text` | `safety`, SD-1). `images`: ordered
  `parts` (at least one valid image part, passthrough for service fields), `costUsd` (finite, non-negative), `usage` (input/output token
  counts), `trimmedTurnIds` (array of non-empty strings, length bounded by the number of ids the request carried, always present).
  `text`: `text`, `trimmedTurnIds`. `safety`: `reason`, `trimmedTurnIds`. A malformed or guard-violating `trimmedTurnIds` fails the whole
  response (D-6). A 200 matching no variant is an invalid response, never an empty image (FR-24).
- `UploadResponseSchema`: `{ fileUri, mimeType }`.
- `StoredSessionSchema` / `StoredTurnSchema`: the persisted shapes below, with `schemaVersion: 1`. A stored record that fails its
  schema is ignored (not listed, not counted, not deleted) rather than crashing the studio, and a record with an unknown
  `schemaVersion` is treated the same way, so a future version can read what an older one wrote. There is **no migration** because
  there is no earlier version (this is the first persisted shape).

**Compatibility.** Nothing on disk exists yet for this feature (IndexedDB is new), the SQLite `usage_log` schema is untouched (NFR-10),
and no existing artifact gains or loses a field.

**IndexedDB layout (DD-16).** Database `cwk-image-studio`, version 1, three object stores:

| Store | Key | Value | Why separate |
|---|---|---|---|
| `sessions` | `id` | session meta: `id`, `createdAt`, `lastActivity`, `model`, `costUsd`, `nextVersionNumber`, `turnOrder: string[]`, `versions` (per version: number, turn id, part index, label data, input format, `downloaded`), `schemaVersion` | Small; lets the session list and the 20-cap/7-day logic run without loading images |
| `turns` | `[sessionId, id]`, index on `sessionId` | one turn exactly as it must be resent: role and parts including `thoughtSignature`, thought parts, `fileData`, inline versions | A commit appends/deletes individual turns instead of rewriting a multi-megabyte session record on every response |
| `sentBytes` | `[sessionId, fileUri]`, index on `sessionId` | the sent bytes (SD-24) and their MIME type | Quota-prone write (FR-16) kept apart; deleted with its session |

The single-transaction operations (FR-44 commit, FR-86 evict-and-create, session delete) span these stores inside one IndexedDB
transaction. Session-level data that the Specification lists as "survives a reload" (turns, versions, sent bytes, downloaded flags,
running cost) is exactly the union of the three stores.

### 2. The contract chain and how the links stay in agreement

The §4 HTML chain (prompt → schema → renderer → validator) is not in play. The studio has its own chain, and each link is tied to the next
by a single source of truth, not by convention:

```
image-studio-contract.json  ──►  server request schema  ──►  handlers / classifier  ──►  response builder
 (error codes + statuses,         (zod, passthrough parts)      (closed sets from SD-23)     (kind, costUsd,
  aspect ratios, resolutions,                                                                 trimmedTurnIds)
  response kinds)                                                                                   │
        └────────────────────────────────►  client GenerateResponseSchema  ◄─────────────────────────┘
                                             client error-dispatch (status + code)  ──►  studio texts (en/uk)
```

**DD-1. A shared contract file.** `src/prompt-core/image-studio-contract.json` holds only closed values both runtimes need: the error
code to status map (SD-2), the aspect-ratio list (FR-19), the resolution list, and the response `kind` values. It is read by Node
through the same JSON import attribute `model-support.js` already uses for the catalogue, and by the client through
`src/prompt-core/image-studio-contract.ts` (typed accessors, in the coverage include list, tested). Rationale: a prompt asked for a field
the schema lacks is a runtime failure; here, a code the client does not dispatch on is the same failure, and a second copy of the code
list would drift. The alternative (two lists plus a parity test, as the catalogue spec does for a different purpose) is rejected
because a parity test detects drift after the fact while a single file prevents it. Limits that only the BFF uses (30 MB, 18 MB, 80%,
retry schedule, rate limit, concurrency, `IMAGE_TOKEN_ESTIMATE`) stay server-side in `server/image-studio/constants.js`; the 120 s
deadline stays client-side.

**Request/response shapes (the "payload contract").**

- Generate request: `{ model, aspectRatio, resolution, presetId?, history: Turn[], newTurn: { id, parts } }`. `Turn` is
  `{ id, role: 'user' | 'model', parts }`; `Part` is `{ text } | { inlineData } | { fileData }` plus passthrough service fields
  (`thought`, `thoughtSignature`). The BFF validates structure (alternating roles starting with `user`, even-length history, unique
  non-empty ids, closed ratio/resolution lists, a resolution allowed for the model, `presetId` matching `^[a-z0-9][a-z0-9-]{0,63}$`, a
  new turn with non-whitespace text or at least one image part) and passes parts to Gemini **unmodified** (FR-35). No system
  instruction is ever set (FR-80). `PromptPayload`/`systemBlocks` are not used by this Story, so NFR-4 holds trivially (no caching
  consequence; `src/prompt-core/payload.ts` is not touched).
- Generate response (200): `images` carries the ordered parts exactly as returned (thought parts included, for storage per D-18), the
  model-turn id is **not** invented by the BFF (FR-43): the client assigns it locally.
- Upload: `POST /api/image-studio/upload` `{ data: base64 }`, response `{ fileUri, mimeType }`; the MIME type returned is the one the
  BFF **detected** from the bytes, never the client's claim.

**Which §4 criteria must keep holding.** All of them (spec-count parity, `figure`/`figcaption`, first-image-eager/rest-lazy, no
duplicate lead-in, video survival, `meta_title`, `meta_description`, no Product schema, number/unit spacing) are enforced where they
are today (`src/utils/output-validator.ts`, the render conformance and reconciliation specs). This plan edits no `src/render/`,
`src/prompts/`, `src/domain/` or validator file, so those specs stay the guard and are unchanged. NFR-6's compatibility is checked
by running them as part of `npm test`.

### 5. Shared catalogue and every text-model path

**DD-2. Union at the boundary, text-only view for existing consumers.**

- `model-catalog.json`: append `gemini-3.1-flash-image` (label "Nano Banana 2, Flash") and `gemini-3.1-pro-image-preview` (label "Nano
  Banana Pro, Pro") **after** all existing Gemini entries (neither is `models[0]`). Each carries `modalities: ["image"]`, `tier`
  (advisory: `fast` for Flash, `premium` for Pro), `inputTokenLimit` (131072 / 65536, verified under V-3 and V-7), and no `levels`,
  `defaultLevel` or `maxOutputTokens` (SD-8). IDs are human-supplied and unverified (V-3); they are spelled in exactly these places:
  the catalogue (source), `IMAGE_PRICES` keys, `prompt-presets.ts` defaults, tests and fixtures; a consistency test (below) makes a
  V-3 correction fail loudly until all agree (FR-2 failure path).
- `model-catalog.ts`: `ImageModelSpec`, `CatalogEntry`, `isImageModelSpec(entry)`. `MODEL_CATALOG` (what every existing consumer
  imports) is the text-only derivation, so `ProviderSpec.models` stays `ModelSpec[]` and no existing consumer compiles differently.
  New: `IMAGE_MODELS`, `findImageModel(id)`. `findProvider`, `findModel`, `defaultModel`, `clampLevel` run on the text-only view, so a
  crafted text request naming an image ID is "not found" and takes the existing fallback (FR-3 failure path) and `clampLevel` can never
  see an entry without `levels`.
- The derivation is an **exported pure function** `textModelsOf(entries)` in `model-catalog.ts` (and the same in `model-support.js`), applied
  once to the raw JSON list to produce `MODEL_CATALOG`. It exists so the catalogue tests can feed it a synthetic list (a text entry with
  `levels`, an image entry without, a reordered list) and assert the text-only result, `findModel`, `defaultModel` and `clampLevel` on it,
  **without mocking the JSON module** (PLAN_REVIEW N-10, P-16). The real-catalogue assertions in `model-catalog.spec.ts` stay.
- `model-support.js`: the same derivation, plus `isImageModel`, `findImageModel`, `IMAGE_MODELS`. `resolveSlot`'s tier fallback
  (`find(m => m.tier === preferTier)`) and `defaultModel` (`models[0]`) therefore ignore image entries even if a later edit reorders
  the JSON.
- Image routes use `resolveImageModel(id)` (new, server): accepts only an entry whose `modalities` include `image`; anything else
  throws a 400 `INVALID_REQUEST` (FR-3 failure path). It does not go through `resolveRequest`/`LLM_PROVIDER`.
- Not edited: `model-settings.service.ts`, `model-settings.component.*`, `llm-request.js`, `anthropic.js`, `openai.js`, `factory.js`.
  New tests assert they never list/accept/persist an image ID (`setDeepModel(imageId)` is a no-op, a stored image ID in `restore()`
  falls back, the Deep and Fast option lists equal the text-only lists).

**DD-3. Supported resolutions live on the catalogue entry.** Each image entry carries `resolutions` (Flash `["1K","2K"]`, Pro
`["1K","2K","4K"]`), an additive field beyond SD-8's list. Reason: FR-19 ("4K only in Pro mode") and the BFF's `INVALID_REQUEST` check
need a per-model rule, FR-2 forbids model facts in code, and `tier` is documented as advisory so behaviour must not hang on it. Flagged

### 6. Server surface (`server/`)

**DD-4. `createApp(deps)`** (see the impact table). Middleware order is the contract and is asserted by tests that read response
headers: a 31 MB declared body to `/api/image-studio/...` is rejected **with CORS headers** (413 `REQUEST_BODY_TOO_LARGE`); the same
body to a probe route registered after `createApp` is accepted by the 50 MB parser; a POST without `Content-Length` to the image prefix
gets 411 `CONTENT_LENGTH_REQUIRED`; GET/HEAD/OPTIONS are never rejected; the limiter runs after the body limit. `trust proxy` is 1 and
nothing else in `server/` reads `req.ip` today (NFR-6). `createApp` receives: allowed origins, the Gemini adapter getter, key-presence
function, clock, sleep, `insertUsage`, price functions, a logger, and an optional `registerRoutes(app)` hook (used by tests; production
registers the existing routes in `index.js` after the call).

**DD-5. Handler factories.** `createGenerateHandler(deps)` and `createUploadHandler(deps)` in `server/image-studio/handlers.js`; every
effect is an injected dependency: `getGemini()` (default `resolveProvider('gemini')`, independent of `LLM_PROVIDER` and the factory's
provider choice, FR-6), `hasGeminiKey()`, `now()`, `sleep(ms, signal)`, `limiter`, `insertUsage`, `price`, `log`. Order for generate
(FR-27), the first failing check answers and later steps do not run or count: body validation (400) → key check (501) → size trim and
protected-remainder byte test (413 `PROTECTED_HISTORY_EXCEEDS_LIMIT`) → token trim (count calls under the retry loop) and
protected-remainder token test (same 413) → atomic limiter step (429 `RATE_LIMIT_EXCEEDED`) → Gemini generate under the retry loop →
classification → price → usage row → response. Order for upload: body validation (400) → magic bytes (415 `UNSUPPORTED_IMAGE_TYPE`)
→ key check (501) → Files API under the retry loop. The upload order is this plan's choice (P-5); the Specification fixes only
the generate order.

**DD-6. Provider methods are single-shot.** `GeminiProvider` gains `generateImage({ model, contents, aspectRatio, resolution, signal })`,
`uploadFile({ bytes, mimeType, signal })` and `countTokens({ model, contents, signal })`. They call
`ai.models.generateContent` (with `responseModalities: ['TEXT','IMAGE']`, `imageConfig: { aspectRatio, imageSize }`, no
`systemInstruction`), `ai.files.upload` and `ai.models.countTokens`, pass `abortSignal`, set a per-call
`httpOptions.timeout` (the constructor's 20-minute client floor is for Doc generation and must not govern an image call), and let the SDK
`ApiError` (with `status`) propagate. They never call `withRetry` and never fall back to another model ("the model is never silently
substituted", FR-60). The constructor still has **no** `retryOptions` (the existing warning in `gemini.js` applies). Exact request
fields depend on V-3, V-6 and V-9 results.

**DD-7. The retry loop is separate from `withRetry`.** `server/image-studio/retry-loop.js` runs an operation up to four times, waiting
exactly 1000, 2000, 4000 ms between attempts with no jitter, retrying upstream 429 and any 5xx including a bare 500, never retrying a
4xx other than 429, using an injected `sleep(ms, signal)` that rejects on abort (so Cancel in the middle of a backoff makes no further
upstream call). The same loop wraps the first upload, the re-upload and every `countTokens` call (FR-60, OD-29). Rationale for not
parameterising `withRetry`: it counts attempts, uses a 3000 ms base with jitter, has a separate policy budget of 6 for 429/503, never
retries a bare 500, and has callers in `gemini.js`, `anthropic.js` and `openai.js` with pinned behaviour in `test/retry.spec.ts` and
`test/gemini-provider.spec.ts`; adding five knobs to it risks every text call (Rule 5, behavioural compatibility). The new loop is
itself provider-independent (it takes an operation and a classifier), so architecture Rule 5 is respected. An error with no numeric
`status` (a transport failure or a per-call timeout) is treated as a transient 5xx-class failure: retried on the same schedule and, when
exhausted, answered 502 `UPSTREAM_RETRIES_EXHAUSTED`. The Specification does not name this case (P-3 below).

**DD-8. The limiter.** `server/image-studio/rate-limiter.js`: `createRateLimiter({ limit: 30, windowMs: 3_600_000, now })` with
`tryConsume(ip)` returning `{ allowed, retryAfterSeconds }`. It is one synchronous check-and-increment (no `await` between check and
increment), so concurrent requests cannot take a key past 30 (FR-66); a key's window starts at its first counted request (D-1); entries
are swept on access so the tracked-key count never exceeds the IPs active in the last hour; `retryAfterSeconds` is the whole seconds
left, rounded up (SD-16). It is called exactly once per generate request, immediately before the Gemini call and **outside** the retry
loop (so one request with BFF retries is one unit, and `withRetry`'s `429` string match cannot refund or double count). A read-only
`peek` pre-check before the token trim is permitted by FR-27 but not planned; the atomic step decides.

**DD-9. Trim, measure and token budget.** Pure modules: `measure.js` computes the 18 MB measure (inline image = base64 text length;
`fileData` part = its own serialized length only; text = UTF-8 length). `trim.js` takes the validated history and new turn, derives the
protected set (the first user turn and the model turn holding the latest version; a model turn with several images is protected whole),
and removes whole pairs `(M_i, U_{i+1})` oldest first (SD-9, FR-42), first by the 18 MB measure and then by the token sum. The token
sum comes from an injected `countTokens` called once per retained turn after the size trim plus once for the new turn (k + 1), at most 4
in flight (SD-10, a small `mapWithLimit`), each call under the retry loop; one failing call ends the action with no generate call, no
row and no count (FR-40). The result is a pure function of the body and the counts (no clock, no randomness), so equal input gives
equal `trimmedTurnIds`. `IMAGE_TOKEN_ESTIMATE` (258, "human-supplied example, unverified") sits in `constants.js` as a structured
config value with its recorded source and applies only if V-7 selects it. **Placement is a plan choice (P-13):** SD-8 lists the estimate
together with the catalogue-entry shape and calls it a "configuration value"; the plan puts it in `server/image-studio/constants.js`, not on
the catalogue entry, because only the BFF trim uses it (the client never reads it) and a field on the shared JSON would widen the contract
both runtimes parse. If the human prefers it on the catalogue entry, only `constants.js`, `model-catalog.json` and the V-7-conditional trim
step change. The trim strategy has **one seam**, `removalUnits(history)`,
implemented as pair removal; if V-1 selects the human's fallback (collapse to the first user turn plus the latest version) that one
function is what changes, and the tests cover only the selected strategy (FR-42).

**DD-10. The classifier** (`classify-response.js`): a pure function from the SDK response to one of the four classes in the FR-26 table,
top to bottom, with the closed sets of SD-23 written as string constants (candidate safety set, prompt-level safety set, normal finish =
`STOP`). Thought parts (`part.thought === true`) are never "valid image parts" (FR-84). A class-2 result with no resolvable price is
converted by the handler into 500 `PRICE_NOT_CONFIGURED` before anything is written (FR-26 precedence, N-11). Tests iterate the installed
`FinishReason` and `BlockedReason` enums (imported from the SDK in the test) crossed with part shapes and candidate presence and assert
each combination lands in exactly one class; a value outside the enums maps to the abnormal class.

**DD-11. Error mapping; `sendError` is not reused on image routes.** Existing routes answer `describeError(error)` to the browser. The
image routes must not (FR-61: upstream text never reaches the browser). They throw/return `ImageStudioError(code, status)` for the
closed codes, answer upstream-derived failures as `{ status: <upstream>, error: 'Помилка API' }` (no reserved code) or
`UPSTREAM_RETRIES_EXHAUSTED` (original status), and log the upstream detail server-side through the existing `describeError` /
`formatCallError`, never with the API key or the prompt payload (NFR-3). A reserved upstream status (410, 411, 413, 501) is never read
as the BFF's own signal because every BFF signal is recognised by status **and** code. The `FILE_MISSING` recognizer
(`file-missing.js`) is the conjunction in FR-17 (the request carried a `fileData` part; the upstream error is of the class V-2
establishes; the error itself names a file resource) and is pinned to V-2 with a file-missing fixture and a model-not-found fixture.

**DD-12. Pricing and usage.** `pricing.js` gets `IMAGE_PRICES` (`gemini-3.1-flash-image: 0.03`, `gemini-3.1-pro-image-preview: 0.06`,
placeholders until V-5, with a source/date comment like the existing entries), `getImagePrice`, `computeImageCost(id, count)` and the
`computeCost` guard (see the impact table). A response with two images costs twice the unit price; thought images are excluded;
zero images costs 0 (FR-70). The usage row (`usage-row.js`) maps `usageMetadata` the way `GeminiProvider.#usage` does (output =
candidates + thoughts) and sets `taskLabel = 'image-studio|' + (presetId ?? 'none') + '|' + resolution` (SD-7), written through the
existing `insertUsage` with no schema change, once per successful request regardless of BFF retries or the FR-17 repeat; a failure to
write the row is logged and does not change the HTTP 200 already produced (FR-69). `server/usage/store.js` is not touched, so there is
**no migration question**: no column is added, `CREATE TABLE IF NOT EXISTS` is irrelevant, and existing databases are unaffected.

**DD-13. Abort propagation.** Each handler creates an `AbortController` and aborts it when the request or response closes before the
response is finished. Its signal is passed to the retry loop (so a backoff wait stops), to `generateImage`, `countTokens` and
`uploadFile` (FR-21, PD-5). A test with a stubbed provider asserts the signal reaches the stub and that no further upstream call
follows an abort in the middle of a backoff. No second BFF timer is added beyond the per-call upstream timeout of DD-6 (SD-30).

### 7. Client services and state (`src/services`, `src/utils`)

**DD-14. One `providedIn: 'root'` signal store owns session, generation and announcement state.** `ImageStudioStore`
(`src/services/image-studio/image-studio.store.ts`) holds the session list, the current session, per-session in-memory drafts (DD-17),
the in-flight generation (abort controller, deadline timer, session id), the blocked-state flag per FR-47/D-12, the running status
announcement and the pending error/notice. Reason: FR-21 keeps the mode switch enabled during a generation, and `AppComponent`
destroys and recreates the studio branch on a mode change; component-local state would unsubscribe a paid request and lose its
result. Signals only; no RxJS outside the HTTP boundary.

**DD-15. Ports (all injectable through tokens in `image-studio.tokens.ts`; NFR-14).** `Clock` (`now`), `Scheduler` (`setTimeout`,
`clearTimeout`), `IdSource` (turn and session ids, SD-20), `SessionStorePort`, `ImageCodec`, `AlertPort` (wraps `window.alert`),
`ConfirmPort` (wraps `window.confirm` for T-23), `ClipboardPort`, `SavePort` (wraps `file-saver`), `UiLanguage` (the `lang` input),
and `Announcer` (`announce(text)`, `clear()`; DD-23). All interfaces, `Announcer` included, are declared in
`src/utils/image-studio/ports.ts` (so `generation-runner.ts` depends on the interface only); the store provides the implementation bound
to its `statusMessage` signal, and tests provide a recording fake (P-15).
`ImageCodec` is two operations: `probe(bytes)` (decode, returns width and height as displayed, or a decode failure) and
`transcode({ bytes, targetMime, maxLongSide?, quality?, fillWhite? })` (returns bytes, the actual output MIME and the dimensions).
`SessionStorePort`:

```
loadAndExpire(now)                    -> meta[]    one transaction; deletes sessions with age > 604 800 000 ms (SD-33)
loadSession(id)                       -> { meta, turns[] } | null
createWithEviction(newSession, pick)  -> { created, evictedIds }   one transaction; `pick(metas)` chooses victims inside it (D-23..D-25, SD-41)
commit(sessionId, batch)              -> void      one transaction: put/delete turns, delete their sent bytes, put meta
putSentBytes / getSentBytes / remapFileUris(sessionId, ...)
deleteSession(id)
```

Both adapters are thin: the IndexedDB adapter maps each method onto one `IDBTransaction` and maps `QuotaExceededError` to the typed
`StorageQuotaError`; the canvas codec maps `probe` to `createImageBitmap` (orientation applied, so D-32 holds) and `transcode` to a
canvas draw plus `toBlob`, comparing `blob.type` with the requested MIME (a mismatch is the D-31 failure). They contain no decisions.
The in-memory fakes implement the same interface with real all-or-nothing batch semantics and a switch that makes any write throw
`StorageQuotaError`, and a fake codec that works on a tiny synthetic raster format so the FR-82 tests can check dimensions, signatures,
quality, the white fill parameter and "never resized" without a browser.

**DD-17. Uploads happen at attach time (SD-30 delegates this).** Each accepted file is ingested (DD-20) and uploaded immediately; the
attachment then holds its `fileUri` and shows `uploading`, `ready` or `failed` (a failed one offers the T-22 Retry when the cause was
an exhausted retry loop, T-7, and is removable). Send is disabled while any attachment is `uploading`. Consequences: the 120 s deadline
does not cover attach-time uploads (SD-30 allows it); Cancel of a generation never has an upload to abort except inside the FR-17
re-upload; the sent-bytes store happens at attach, so the FR-81 alert for a failing store fires at attach (D-28 already describes "a
store failure while attaching up to five files gives one alert"); removing a thumbnail leaves an orphan Files API object that Google
expires (the BFF makes no delete call, FR-49 spirit). The alternative (upload at Send) is rejected: it puts up to five uploads inside the
deadline, makes the T-7 retry semantics ambiguous for a half-sent message, and contradicts D-28's wording.

**DD-18. `LlmService` and `LlmProvider` gain `generateImage(request, signal?)` and `uploadImageFile(request, signal?)`.** They do not use
`post()`. A private `postOnce` issues a single `HttpClient.post` with no `retryTransport`, no merge of the model-settings snapshot,
and an `AbortSignal` bridged by unsubscribing (a small RxJS helper at the HTTP boundary, the one place RxJS is allowed). `generateImage`
never retries (FR-85); `uploadImageFile` keeps `retryTransport` (SD-31). The interface change is additive and `LlmService` is its only
implementer. Failures are returned as a normalised `{ status, errorField? }` so the pure `error-dispatch.ts` can decide without
`HttpErrorResponse`. **Test style (PLAN_REVIEW N-10):** the `LlmService` image methods are tested in the **logic runner** following the
`llm.service.spec.ts` precedent (a bare `Injector` with a stubbed `HttpClient`, no TestBed, so no `HttpTestingController`); the unsubscribe
bridge is exercised by a stub whose returned observable records unsubscription. `HttpTestingController` is used only in the **component**
runner (C9, C10), where TestBed is the norm.

**DD-19. `GenerationRunner`** (`src/utils/image-studio/generation-runner.ts`, plain TypeScript, ports injected) owns one user action:
build the request from the session snapshot **before** any append (SD-27), start the single 120 000 ms deadline at Send/Retry (SD-30),
call `generateImage`, validate with `GenerateResponseSchema`, and return a closed outcome (`images`, `text`, `safety`, `failed` with a
text id and a retry flag, `blocked`, `cancelled`, `discarded`). On 410 + `FILE_MISSING` it re-uploads every `fileUri` found in the
retained history and the new turn from the stored sent bytes without a second re-encode, remaps them, and repeats **once** (SD-4); a
second `FILE_MISSING`, or any URI without stored bytes (never stored under OD-37, or cleared by the browser), ends in T-10 with no
upload request (FR-17). The deadline covers the `countTokens` waits and backoff on the BFF because it is measured on the client and
aborts the request; Cancel aborts at every stage; late responses are ignored; a response is applied only to the session that sent it
(SD-22). The store applies an `images` outcome through `apply-response.ts` and the `SessionStorePort.commit` (atomic, FR-44) and
treats `text`/`safety` as non-history events that still apply the cut (D-6).

**DD-20. The ingest pipeline** (`image-ingest.ts`, `upload-rules.ts`, `magic-bytes.ts`): per file, in the exact order of FR-11/OD-39:
magic-byte format detection of the user's file (D-19) → `probe` (decode failure is T-1 whatever the size, N-7) → downscale when the
as-displayed long side is above 2048 → draw → encode in the **same** format at SD-42 quality (PNG lossless) → compare the encoder's
output type with the required format (D-31 → T-1) → 5 242 880 B check on the **sent** bytes (D-7 → T-2) → store sent bytes (best
effort, OD-37) → upload. The FR-11/FR-12 decision table is implemented as one pure function over `(longSide, size)` with the four rows
and boundary values 2048/2049 and 5 242 880/5 242 881/5 000 000; the count rule (5 uploads, attached version outside the five, FR-10)
is another. A generated version attached under FR-37 is never ingested. An animated WEBP or APNG becomes its first frame silently
(D-30, taken by the codec's single-frame decode). The client magic-byte detector (TS) and the BFF's (JS, `magic-bytes.js`) are two
implementations of a four-line rule; one shared set of byte fixtures is run against both in a parity test.

**DD-21. Delivery** (`output-format.ts`, `delivery.ts`, `file-name.ts`, `zip.ts`): `outputFormat` implements the FR-82 first-match
rule (first uploaded image of the message; else the attached version's input format; else the latest version's; else PNG) and the
version stores its input format (D-22). `deliver(version, targetMime)` returns the API bytes untouched when the API format equals the
target (no codec call), otherwise `transcode` at native dimensions, JPG quality 90 with `fillWhite`, WEBP quality 90, PNG lossless.
The clipboard path always targets PNG (FR-57). `buildZip` uses the existing `jszip`, one entry per retained version in its current
target format, disabled with zero versions (SD-28); `saveAs` and `ClipboardItem` are behind ports. The "downloaded" flag is set only
after the success signals of SD-17.

## Rejected alternatives

| Alternative | Why it lost |
|---|---|
| Parameterise `server/utils/retry.js` `withRetry` for the 1/2/4 s schedule | Different semantics (attempt counting, jitter, separate 429/503 budget, bare 500 not retried); five callers and pinned specs; a regression there changes every text call (Rule 5). A separate, provider-independent loop is smaller and testable with an injected sleep (DD-7) |
| Filter image entries at every text consumer | Many edits across client and server, easy to miss one (Silent-failure risk 2). Deriving a text-only view at each runtime's boundary makes the existing consumers correct by construction (DD-2) |
| Make `levels` optional on `ModelSpec` | Forbidden by FR-4 and AGENTS.md section 7.7, and it would hide the consumers that assume `levels` from the compiler |
| A router module only, leaving `server/index.js` as the composition | Cannot prove CORS-before-body-limit, the 50 MB parser order, or `trust proxy` (Silent-failure risk 1). `createApp` is the smallest extraction that can (DD-4) |
| `fake-indexeddb`, `node-canvas`, `jsdom` or `sharp` as test dependencies | New dependencies are a human decision (AGENTS.md section 1, NFR-7, W-2 alternative B); a fake would still not prove real-browser behaviour. Ports plus in-memory fakes need none (DD-15) |
| Component-local studio state | The mode switch stays enabled during a generation (FR-21); destroying the component would drop a paid request. A root store avoids that (DD-14) |
| Upload at Send | Five uploads inside the deadline, ambiguous retry for a half-sent message, contradicts D-28 (DD-17) |
| Put image-studio schemas in `src/domain/` | `src/domain/` models description artifacts and carries 95/95/90/95 floors; these are API and storage schemas |
| Two copies of the error-code list plus a parity test | Detects drift after it happens; a shared contract file prevents it (DD-1) |
| Store turns inside the session record | Every response would rewrite a multi-megabyte record; a `turns` store lets a commit touch only the changed turns (section 1) |
| Reuse `sendError` / `describeError` for image routes | It would send upstream text to the browser, violating FR-61 (DD-11) |
| Image models in a second catalogue file | FR-2 requires the shared `model-catalog.json` as the single source; a second file is a second source |
| Collapse-to-originals as the primary trim strategy | The human's stated *fallback*; V-1 decides, and pair removal keeps more history (FR-42) |
| Put the limiter inside the retry wrapper | `withRetry` retries any message containing `429`; the limiter would count each retry (FR-60, FR-66) |
| Downgrade the FR-1 clear-all test to source pins | Weaker than the Specification's wording (a test that invokes clear-all and reads the sessions); pins are kept as an extra guard only |
| (v2) Adopt the Dashboard/HTML-editor fall-through for the Actions Footer | The final `@else` renders the Image Tools "Process images" button, enabled whenever Image Tools holds files, so in studio mode it would act on another mode's state; that is the exact condition T45's STOP names. Zero edits would be cheaper but is not safe (DD-25) |
| (v2) Hide the whole Actions Footer in studio mode | Also removes Clear-all (SD-12 presupposes the case is reachable) and the feedback block, which are mode-independent; a wider edit than one branch |
| (v2) Hide only the Clear-all button in studio mode | The button is a defined no-op in studio mode, matches Dashboard/HTML editor, and keeps SD-12's test literal; hiding adds a second condition around markup shared by every mode for no safety gain |
| (v2) Add a studio block to the sidebar body (session list or composer controls) | The Specification asks for none; studio controls live in the main area (DD-22) and the sidebar body already renders nothing in studio mode; a block would duplicate state with the children and add texts (SD-29) |
| (v2) Fix the fall-through for Dashboard and the HTML editor in the same Story | Behaviour change to two other modes, outside the Specification (Rule 5); recorded as R17 |
| (v2) Put `IMAGE_TOKEN_ESTIMATE` on the catalogue entry | Only the BFF trim reads it; widens the shared JSON contract both runtimes parse; SD-8 calls it a configuration value, not a field (P-13) |
| (v2) Mock the catalogue JSON module in tests | Fragile under Vitest module caching; an exported pure `textModelsOf(entries)` gives synthetic-list tests with no mock (P-16) |
