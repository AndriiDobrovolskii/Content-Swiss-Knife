## How the order was chosen

The plan has one load-bearing change that makes everything else safe or unsafe: the shared `model-catalog.json` swap. Once it lands,
a stored or requested retired id no longer exists, and Carbon becomes `models[0]` and the first `premium` model. So the catalog swap
is deliberately NOT first. It lands only after the safety nets it depends on (the `CONTINUATION` guard, both retired-id remaps, then the price entries) are
already in place, and those nets all work while the retired entries still exist in the catalog (they remap onto `gemini-3.8-flash`, which is already there).
The server remap goes before the pricing removal because the only price caller prices the provider-resolved model: without the remap, a still-selectable retired id
would be priced at `FALLBACK_PRICE` (plan D10, review NB-4). The only thing that goes first is the riskiest assumption: the `@google/genai` major upgrade.

## TDD and commit convention (applies to every task)

`TEST_WRITING` runs before `IMPLEMENTATION` as a whole stage, so each task's tests already exist and fail when it starts. Following the
US-4.1 convention, the spec edits that a task turns green are committed in the same commit as the production change, so that every
commit ends with lint, tests and build green. A spec rewrite is never its own commit (an isolated spec edit is indistinguishable from
a weakened one, AGENTS.md section 7.7). Where one spec file is edited by several tasks (`model-settings.service.spec.ts`,
`model-settings.component.spec.ts`, `gemini-provider.spec.ts`, `llm-routes.spec.ts`), `TEST_WRITING` should keep each task's cases in
distinct `describe` blocks so the file can be committed in slices. Every rewrite of an existing spec must stay non-vacuous (plan D12,
impact R-2): a rewritten case compares against a CURRENT model id, never a comparison that is true by construction.

Anchoring rule (plan D9 item 6, impact R-14): `clampLevel` and `defaultModel` fall back to the first Gemini model for an unknown id, so any assertion about
`gemini-4-carbon` or `gemini-4-hydrogen` that does not first prove the id is in the catalog (or that `resolveSlot` returns it) is green before T6 for the wrong reason. Such a case
must carry the existence assertion first; that assertion is the one that is red before T6.

Runner key: `test:logic` is vitest (`npm run test:logic`); `test:components` is the Angular `unit-test` builder (`npm run test:components`,
files named `*.component.spec.ts`). `npm test` runs both.

## Risk-first rationale

`T1` is first because the `@google/genai` 1.x to 2.x major upgrade is the one assumption whose failure is silent behind mocked specs
(Image Studio upload, retry, `thinkingLevel` values) and the live smoke is waived (OD-5 a); the evidence file shows it is a 3-line lock delta,
and proving it on the real tree while changing course is still cheap is the cheapest moment to find out otherwise.

## P-9b: pinned to option A (no open question)

Ruling 2 pins P-9b: a retired-id slot with no stored or requested level resolves to `high`, the `defaultLevel` of `gemini-3.8-flash`, in both runtimes, in both slots / tiers.
The existing `slot.level ?? model.defaultLevel` expressions already produce it, so no task adds code for it. `T5` (browser) and `T4` (server) each carry one test that
asserts `high` for the absent-level case. A test asserting `low`, or only membership of `levels`, would be wrong. The cost consequence in a Fast slot is intended
(impact R-8, risk K-14).
