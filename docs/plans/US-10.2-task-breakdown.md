## Execution protocol (binding on `so-builder` for the whole IMPLEMENTATION stage; plan DD-21, DD-22)

**Why it exists.** `IMPLEMENTATION` has no human gate; its only held verdict is `BLOCKED` (no loop-back key); `partial` re-dispatches and counts toward a cap of 3; only `PASS` resets the counter and advances to
QUALITY_GATE. The builder cannot idle on a human. So a human-dependent task **returns** (`BLOCKED`) and the human's `/so:next` re-dispatches the builder, which resumes. "Waits" in this breakdown means "has already returned".

1. **Ledger and resume rule.** `pipeline_status` carries a ledger `Task | State | Outcome pointer`; states `DONE`, `AWAITING_HUMAN`, `FAILED`, `NOT_STARTED`. **Every dispatch starts** by (a) printing `node -v`
   (must be `v24.22.2`, else `BLOCKED`, map row 1, nothing written), (b) reading the ledger and the hand-off location, (c) revalidating `DONE` records that carry a fingerprint (rule 7), then **resumes at the first
   task in the order T1, T4, T5, T2, T3, T7, T6 that is not `DONE`**. A task is never redone once `DONE` and valid.
2. **Human-free tasks run to completion inside the dispatch.** The builder passes from T1 to T4 to T5 (and from an accepted T2 to the T3 sheet, from an accepted T3 to T7, from T7 to the T6 hold) in the same
   dispatch. It does **not** return `partial` between them. `partial` is reserved for a dispatch cut short by the environment after at least one task completed (map row 24).
3. **Hold = `BLOCKED`, `loop_back_stage: null`.** At a task needing the human whose input is absent, the builder (a) sets the task `AWAITING_HUMAN` and writes the **human command sheet** into its own `pipeline_status`
   (section "Human action Tn": exact commands, pass conditions, the exact files to leave behind), and (b) returns `verdict: BLOCKED` with `blocking_issues` naming, as **separate items**: the **action**, **who** (the
   human, or "reply `Tn.runner=builder`" where allowed), the **sheet location** (path and section of `pipeline_status`), the **drop location** (the absolute path `%TEMP%\US-10.2-live\` and the file names),
   what **"done" looks like**, and the **resume command `/so:next`**. Then it ends. It does not wait, sleep, poll, read `.env`, or start a server while holding.
4. **Resume = `/so:next` = a re-dispatch of `so-builder`** (H-3a). Rule 1 then applies.
5. **Idempotent hold.** A resume that finds the drop location empty, or required lines missing, writes **nothing** to `pipeline_status`, changes no ledger state and no counter, and returns the **same** `BLOCKED` with
   the same `blocking_issues`, naming what is missing. (`BLOCKED` neither increments nor resets `stage_attempts`.)
6. **Accepting the human's output.** With the drop file present: (a) secret search on it (below) - on a hit stop `BLOCKED` (map row 22) **without copying**; (b) completeness against the sheet (first line `node -v` =
   `v24.22.2`; date; runner; every item the sheet lists); (c) **copy it verbatim into `pipeline_status`** section "Live check records", labelled "supplied by the human, copied verbatim, secret-search result: ..." (the
   AGENTS.md section 6 item 9 record); (d) decide the outcome by the Specification's rules; (e) mark `DONE` / `FAILED` with the outcome pointer. When `Tn.runner=builder` the builder runs the sheet itself in the
   dispatch (no drop file), records the raw output in the same section labelled "run by so-builder at the human's instruction: <the control-file line, quoted>"; it does not read `.env` (the sheet's commands load the key in-process).
7. **Validity of recorded results (re-entry after any loop-back).** The T7 record stores the **relevant-change-set fingerprint** (below); the T2 record stores a **pair fingerprint** (the same construction over
   `package.json`, `package-lock.json`, `.nvmrc` and `server/`). On every dispatch the builder recomputes both: a differing T7 fingerprint -> T7 is `NOT_STARTED` (the ten restart); a differing pair fingerprint -> T2
   is `NOT_STARTED` (a new hold). Unchanged -> `DONE` stands.
8. **`PASS` only when all seven tasks are `DONE` and valid** - T2, T3, the series (T7) and the evidence verification (T6) included. The stage cannot return `PASS`, and so the orchestrator cannot advance to
   QUALITY_GATE, while any of them is `NOT_STARTED`, `AWAITING_HUMAN` or `FAILED`. `FAILED` T2 or T7 never lets the stage pass.
9. **Anything not in the table below returns `BLOCKED`**, never `PASS` and never an invented loop-back key.

**Relevant-change-set fingerprint** (used by rule 7 and T7; mentions no `HEAD`): `git status --porcelain -- src test server package.json package-lock.json .nvmrc vitest.config.ts 'tsconfig*.json'` printed
(empty when all is committed), plus one sha256 over the sorted lines `<path> <sha256 of the working-tree bytes>` for `git ls-files -co --exclude-standard -- <the same pathspec>`. A docs commit (the evidence commit,
a delivery-docs commit) changes `HEAD` but not the fingerprint, so it cannot cause a spurious restart.

**Secret search (NFR-3).** A throwaway script piped on standard input (`node --input-type=module -`, nothing written into the repository) loads the key with `dotenv` in-process, reads the bytes to be checked from
standard input and prints **only** booleans for "contains the key value" plus counts for `GEMINI_API_KEY=`, `x-goog-api-key` and `key=`; every count must be zero; the sha256 of the searched bytes is recorded. It prints
neither the key nor any environment. A hit removes the text from the builder's own file and reports the key as exposed (the rotation decision is the human's).

**Hand-off location (DD-22).** `%TEMP%\US-10.2-live\` (Git Bash `"$TEMP/US-10.2-live"`), outside the repository and the session scratchpad, never under `.tmp.driveupload/`; the human creates it if absent; the absolute
path is printed in every hold and in `pipeline_status`. Files: `T2-output.txt`, `T2-rerun.txt`, `T3-output.txt`, `T3-rerun.txt` (raw live output, each command `2>&1 | tee -a <file>`, first line a header: date,
runner, `node -v`, `node -p process.versions.undici`, `npm -v`, `npm ls undici`); `T7-run-1.log`..`T7-run-10.log`, `T7-exit-codes.txt`, `T7-start.txt`, `T7-end.txt` (series Form 3 only); `control.txt` (optional,
human-written `key=value`: `T2.runner=builder|human`, `T3.runner=builder|human`, `T2.new-attempt=<reason>`, `T3.rerun=skip`, `T3.after-failed-T2=yes`; absent = `human`, others off). The builder reads, never edits, a
human file; copies only the keys it acts on, quoted, into `pipeline_status`; **deletes the hand-off files only in the dispatch that returns `PASS`**. They are not artifacts and are never committed.

**Strictly sequential.** The only independence worth stating: T4 and T5 do not depend on T2/T3, but plan DD-21 puts them **before** T2 on purpose, so the live results are recorded on the final pair. T2 and T3 do not
run while T7 runs (no live server during the series, so the worker-fault evidence is not confounded). No task is parallelisable within the stage.

**Risk-first rationale.** T1 is first because every other task needs the pair it builds, and the Story's riskiest assumption (U-5: nested `7.30.1` next to bundled `7.30.1` works on the real Gemini Files API, T2) cannot
be tested without it. Plan DD-21 deliberately places T4 and T5 between T1 and T2: the live results are worth recording only on the pair the Story ships, so everything that could still change the relevant change
set (README, scope findings, `test:components`, coverage) is finished before the human is asked for anything. The price is that a failed U-5 leaves the T1 and T4 commits on an unpushed branch (H-4; plan A16).
T7 follows T2/T3 (no concurrent server) and precedes T6 so the `PASS` return coincides with the final human act.
