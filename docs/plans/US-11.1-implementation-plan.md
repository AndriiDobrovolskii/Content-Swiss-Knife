## 1. Approach

The Story is a catalog-and-provider change, not a content change. The model list, levels, tiers and output ceilings stay in
the one shared file `src/prompt-core/model-catalog.json` (NFR-6); two entries go, two come in, and Carbon becomes both
`models[0]` and the first `premium` model, which silently moves every "first model" and "first premium model" default from
Gemini 3.1 Pro to Carbon. Around that data: the `tier` type gains `balanced` and the settings badge gets a third, sky-coloured
case; the settings service gets a provider-gated restore migration for the two retired ids, a persist-once rule that reuses the
existing `migrated` flag, and a small model-specific level rule for the dropdown (approver ruling OD-4, reading 2); the server's
`resolveSlot` gets the matching remap with a `console.warn`; `GeminiProvider#readText` gets one `CONTINUATION` branch; pricing
gets one flat and one date-dependent entry and loses the retired ones; `@google/genai` moves to `^2.32.0`, a change the evidence
shows is a two-hunk lock-file delta (the root range and one package entry). No prompt, schema, renderer, validator, FROZEN file, store, locale list or corpus fixture is
touched, and no `maxOutputTokens` cap of any provider path is changed. The riskiest line, the SDK major upgrade, was verified in a
scratch directory before the v1 plan was finished; every SDK-internal note in `gemini.js` still holds and none of the checks
failed, so no Surface widening is requested.

## 3. Design decisions

### D1. Domain model (`src/domain/`)

Not applicable: no Zod schema, no `ProductDescriptionDoc` / `ConsumablesDoc` field changes. Corpus fixtures in
`test/fixtures/corpus/` still parse and do not move (impact: "Fixture and corpus impact"). The only persisted artefact whose
shape is in play is `localStorage['seo_gen_model_settings']` (`{ provider?, deep, fast }`, each slot `{ provider, model, level }`).
Its shape does not change; the restore migration (D6) is the compatibility mechanism for the two retired values, and the
`usage_log` table needs no change (`model TEXT`, free text; no migration question arises, see D14).

### D2. The prompt -> schema -> renderer -> validator chain, and AGENTS.md section 4

No link of the chain changes: no file under `src/prompts/`, `src/prompt-core/` other than `model-catalog.{json,ts}`,
`src/domain/`, `src/render/` or `src/utils/output-validator.ts` is edited. The model id reaches the server through the settings
snapshot, not through a prompt, so the chain cannot disagree with itself because of this Story.

Statement for the record (approver ruling N-8): the section 4 criteria (spec-count parity, `<figure>`/`<figcaption>`, the
first-image-eager rule and video-embed survival, and the schema.org `Product` ban) are NOT touched by this Story and are NOT
re-verified for Gemini 4 output (Out of scope: output quality). They remain enforced where they are today
(`src/utils/output-validator.ts`, FROZEN, and `src/render/`), unchanged. The remaining section 4 bullets (unit spacing, meta limits,
anglicisms, HTML-only output) are likewise untouched; the AGENTS.md sentence of D12 is generic ("the criteria above") and covers
all of them. Placement of this statement: see D12 and finding F-4.

### D3. FROZEN files (AGENTS.md section 9)

Position: **none touched, no section 9 request, no sibling file needed.** None of `src/prompts/task-{a,b,c}.ts`,
`src/prompt-core/master-system-prompt.ts`, `src/utils/output-validator.ts` is on the Surface, and none is needed.
`master-system-prompt.ts` sits in the same directory as the catalog files, so the catalog change must edit only
`src/prompt-core/model-catalog.json` and `src/prompt-core/model-catalog.ts` and never the FROZEN neighbour (review NB-9); the
catalog task's file list must say so. `src/render/doc-schema-issues.ts` (not frozen, not on the Surface) is deliberately NOT edited
either: the new `CONTINUATION` error is worded to match its existing matcher instead (D9).

### D4. Prompt payload contract (`src/prompt-core/payload.ts`)

Unchanged. `PromptPayload` keeps `systemBlocks` and `userContent` separate and `GeminiProvider#generate` keeps joining the
blocks into `config.systemInstruction`, never into `contents` (NFR-3). Caching consequence: none. Gemini 4 supports implicit
caching only (evidence V5; minimum 4,096 prompt tokens), so the provider sends no `cachedContent`, which is the current
behaviour (FR-21 is verify-only).

### D5. Catalog and types

`src/prompt-core/model-catalog.json` (the single source, read verbatim by browser and server):

- Gemini text models in this order: `gemini-4-carbon`, `gemini-3.1-pro-preview`, `gemini-4-hydrogen`, `gemini-3.8-flash`; then the two image entries, which stay LAST (the image-blind specs and `textModelsOf` rely on text-first ordering; both helpers filter by `modalities`, so order only matters to the specs).
- `gemini-4-carbon`: label `Gemini 4 Carbon`, `tier: "premium"` (N-1), `levels ["low","medium","high"]`, `defaultLevel "medium"`, `maxOutputTokens 65536`.
- `gemini-4-hydrogen`: label `Gemini 4 Hydrogen`, `tier: "balanced"`, `levels ["low","medium","high"]`, `defaultLevel "high"`, `maxOutputTokens 65536`. `xhigh` is not registered (owner choice; the vendor does support it, evidence V3).
- `gemini-3.7-flash` and `gemini-3.6-flash` are removed. `gemini-3.1-pro-preview`, `gemini-3.8-flash` and the two image entries are byte-for-byte unchanged (FR-4). The vendor's own default level for 3.8 Flash and 3.1 Pro differs from the catalog (evidence V3); FR-4 freezes them.
- Each level array equals the vendor-documented set (evidence V3), `minimal` is absent from all three Gemini text models that matter (FR-9), which makes the UI offer exactly three levels with no code change, because the slider is sized from `spec.levels`.

`src/prompt-core/model-catalog.ts`: `ModelSpec.tier` (line 26) and `ImageModelSpec.tier` (line 55) are both typed with the inline
literal union `'premium' | 'balanced' | 'fast'` (FR-5). A shared alias was rejected for this Story (rejected alternative A-5).
`clampLevel` and `defaultModel` need no logic edit: both already derive from the catalog, so `clampLevel('gemini', M, 'minimal')` is
`low` for the three models (the nearest-neighbour rule, ties upward: `minimal` is index 2, `low` is 3). The comment on
`clampLevel` at line 115 that cites "Flash 3.6 @ minimal" is rewritten with a current example (FR-30; it is stale prose that none of
the four literal strings of FR-30 matches, impact R-13, so D12 gives the scan a pattern that catches it).

**Consequence stated once (N-4).** `defaultModel('gemini')` (browser and server), `resolveSlot('gemini', undefined|unknown,
'premium')`, the service's `pick('gemini','premium')` and `clampLevel`'s unknown-id fallback now resolve to Carbon, not to
Gemini 3.1 Pro. `resolveSlot(..., 'fast')` and `pick(..., 'fast')` still resolve to `gemini-3.8-flash` because the only
`fast` Gemini text model is 3.8 Flash and Hydrogen is `balanced` (FR-12). `GeminiProvider`'s own `FALLBACK_DEEP` stays an explicit
`gemini-3.1-pro-preview`, so a Carbon primary has 3.1 Pro as its same-provider fallback (Out of scope). Carbon is also the model
whose price doubles on 2026-12-01 (D10); this is documented in the comments of `model-support.js` and `model-catalog.ts`.

**Consequence for the tests (impact R-14, review NB-2).** Because `clampLevel` falls back to the first Gemini model for an unknown
id, any assertion about Carbon or Hydrogen that does not first prove the id is in the catalog is already green before the catalog
changes. D9 item 6 and section 11 turn this into a rule.

### D6. Settings service (`src/services/model-settings.service.ts`)

Everything below stays plain TypeScript with signals; no RxJS is introduced.

1. **Retired-model table.** `RETIRED_MODELS` becomes a `ReadonlyMap<string, { model: string; provider?: ProviderId }>` with three
   entries: `claude-sonnet-4-6` -> `{ model: 'claude-sonnet-5-5' }` (no provider constraint: this keeps the FR-17 outcome exactly
   as before), and `gemini-3.7-flash` / `gemini-3.6-flash` -> `{ model: 'gemini-3.8-flash', provider: 'gemini' }`. A `Map`
   (not an object literal) is deliberate: stored data is untrusted, and `RETIRED_MODELS['constructor']` on a plain object returns
   a function and sets `migrated = true` today. `Map#get` has no prototype keys.
2. **Provider gating (P-9a, accepted).** `restore()`'s `migrate` is given the slot's EFFECTIVE provider, derived by the same
   expression `validateSlot` uses (slot provider, else the legacy top-level `provider`, else the slot default). That expression
   is extracted into one private helper used by both, so the gate and the validator cannot disagree. A table entry with a
   `provider` applies only when the effective provider equals it. A retired Gemini id next to a stored non-`gemini` provider is
   therefore left alone and falls to `validateSlot`'s tier pick, exactly the P-9a behaviour (impact R-7).
3. **Level of a migrated slot (FR-15, P-9b = A).** After the id swap the existing `validateSlot` computes
   `clampLevel(provider, 'gemini-3.8-flash', slot?.level ?? spec.defaultLevel)`. A stored `minimal` becomes `low`; stored `low`,
   `medium` and `high` are kept. **A migrated slot with no stored level resolves to `high`** (`gemini-3.8-flash` `defaultLevel`):
   the approver pinned this (ruling 2), and the existing expression already produces it, so there is no new code and no special case.
   A test pins the `high` outcome (section 11); a test that asserted `low` for such a slot would be wrong (impact R-8). It is
   close to unreachable (the browser always persists a level) and, in a Fast slot, runs the most expensive Flash level: intended.
4. **Persist once (FR-16).** The existing `if (migrated) this.persist()` already writes the corrected snapshot; a second restore
   finds `gemini-3.8-flash` and migrates nothing. `migrated` is set only when a table entry passes the gate, so no spurious
   re-persist. Level-only corrections stay in memory, as the existing comment says.
5. **Dropdown level rule (approver OD-4, reading 2).** `setDeepModel` and `setFastModel` call one private helper: for
   `gemini-4-carbon` and `gemini-4-hydrogen` the new level is `spec.defaultLevel` (`medium` / `high`); for every other model it is
   the existing `clampLevel(provider, spec.id, currentLevel)` carry-over. The set of the two ids is a named, commented constant in the
   service. Why a service constant and not a catalog property: a new `ModelSpec` field would add a schema field, a type change
   and a server mirror for one ruling the Specification itself calls inconsistent across models; a constant is trivial to delete if
   the owner later rules for reading 1 (A-4). NFR-1 is respected: the rule branches on a model id inside the settings service
   (which already imports the catalog and branches on `tier`), not on the active provider and not in the orchestrator.
   FR-13 holds because `defaultLevel` is always a member of `levels`. Provider switches keep using `pick` + `defaultLevel` (FR-11, FR-12)
   unchanged: `pick('gemini','premium')` is Carbon at `medium`; `pick('gemini','fast')` is 3.8 Flash; `pick` is already typed
   `ModelSpec['tier']`, so it accepts `balanced` after FR-5 with no edit.
6. **Defaults and reset (FR-18).** `DEFAULTS` is unchanged. Comments are rewritten: the `RETIRED_MODELS` doc, the `DEFAULTS` doc
   and the `restore` doc (header lines 9 to 12, 21 to 45) currently say Gemini 3.7 / 3.6 Flash are "still in the catalog" (false after
   this Story; FR-30).
7. What the component test and the service test drive: see section 11.

### D7. Settings component (`src/app/components/model-settings/model-settings.component.ts`)

- `tierBadge` and `tierBadgeClass` become exhaustive lookups over `ModelSpec['tier']` (a `Record`), so a future fourth tier is a
  compile error instead of a silent fall-through. Values: `premium` -> `$$$` and the existing amber classes; `balanced` -> `$$ ⚡`
  and a **new sky set with both theme variants**, written as complete literals so Tailwind's content scan finds them:
  `bg-sky-100 dark:bg-sky-900/30 text-sky-700 dark:text-sky-300`; `fast` -> `$ ⚡` and the existing emerald classes. An
  undefined spec keeps today's result (the `fast` text and class). Anthropic badges are untouched (FR-7).
- The template needs **no** change: it renders `settings.deepModels()` / `fastModels()` and the two badge methods, and the level
  slider is sized from `spec.levels` (`max = levels.length - 1`, first and last label), so Carbon, Hydrogen and 3.8 Flash show a
  three-step slider with no `minimal` (FR-9). The `minimal` entries in `LABELS` stay (harmless; unreachable now, N-9).
- No `OnPush` change, no new signal, no new component. The comment at line 82 ("Gemini 3.6 Flash") is rewritten (FR-30).

### D8. Server model resolution (`server/providers/model-support.js`)

- `resolveSlot(provider, slot, preferTier)` gains a retired-id remap **inside the provider layer** (NFR-1), applied only when
  `provider === 'gemini'` (P-9a): a requested model id found in a module-level `Map` of `gemini-3.7-flash` / `gemini-3.6-flash`
  -> `gemini-3.8-flash` is replaced before the existing lookup, one `console.warn` is emitted that names the retired id (N-5), and
  the existing path then returns `{ model: 'gemini-3.8-flash', level: clampLevel(...), maxOutputTokens: 65536 }`. The level is
  the requested level clamped into `levels` (`minimal` -> `low`); **with no requested level it is `high`**, because the existing
  `slot?.level ?? model.defaultLevel` expression yields `gemini-3.8-flash`'s `defaultLevel` (P-9b = A; no code beyond the remap, a
  test pins it). Because it reuses the existing path, both `deep` and `fast` tiers behave the same (FR-19) and an unknown,
  non-retired id still falls back by tier exactly as before: `premium` to the first premium model (now Carbon), `fast` to the first
  fast model (still 3.8 Flash). A `Map` is used again: `slot.model` is client input.
- The remap works whether or not the catalog still contains the retired entries (it substitutes the id before the lookup). That
  property is what lets it land before the catalog swap, and it is the property D10 and D14 rely on.
- `resolveSlot('anthropic', ...)` is untouched (P-9a); a retired Gemini id there is an unknown id and falls back by tier.
- **Why the retired->3.8 map exists twice (browser service and `model-support.js`).** FR-1 forbids a retired id "anywhere" in
  `model-catalog.json`, so the mapping cannot be catalog data (e.g. a `replacedBy` field on a retired entry, or a top-level
  `retired` table). The server module mirrors the browser's `clampLevel` today for the same reason (N-2); the retired map is a
  second, small, explicitly cross-referenced copy, and each side's test pins its own (A-1).
- The doc comment of `resolveSlot` states the N-4 consequence (the premium fallback is Carbon).

### D9. Gemini provider (`server/providers/gemini.js`)

Verify-only for the request shape, shown by reading and pinned by new tests: `generate()` already builds `config` with
`systemInstruction`, `maxOutputTokens` (from the resolved slot), `httpOptions.timeout`, `thinkingConfig.thinkingLevel =
clampLevel(...)` and (JSON modes) `responseMimeType`, and **no** `cachedContent`, `temperature`, `topP`, `topK` and no streaming call
(FR-20, FR-21, FR-22). `thinkingLevel` equals the slot level for in-range levels and is never `minimal` for these models.

Changes:

1. **`#readText` gains a `CONTINUATION` branch** next to `MAX_TOKENS` and the safety branch. It throws (never returns text) and
   the message names the model and the call. Because `generate`, `analyzeImage` and `extractFromPdf` all read through
   `#readText` (lines 119, 255, 279), one branch covers all three. The abnormal case is real and reproducible on `2.32.0` (evidence S2:
   continuation disabled, or a `CONTINUATION` without a token, returns partial text with `finishReason: "CONTINUATION"`). Consequence
   worth stating: the guard therefore also reaches Image Studio's vision caption and PDF extraction.
2. **Message wording is a design constraint, not decoration.** The Doc repair gate (`isUnrepairableGenerationError` in
   `src/render/doc-schema-issues.ts`, outside the Surface) stops re-spending the repair budget only when the error text matches
   `/truncated: (hit|unterminated string|\d+ unclosed container)|refused by safety classifier|blocked by (safety|content) filter/i`.
   The new message therefore starts the same way as the `MAX_TOKENS` one, `[gemini] <what> truncated: hit ...`, for example "hit a
   CONTINUATION checkpoint on <model> before the answer was complete; the partial text was discarded". It must also contain none of
   the strings `withRetry` treats as transient or rate-limited (`429`, `overloaded`, `RESOURCE_EXHAUSTED`, `rate_limit`, `timed out`,
   `socket hang up`, `network error`, `fetch failed`, `Retryable HTTP Error`), has no `status`, and so `withRetry` fails fast (one
   attempt) as it does for `MAX_TOKENS`. A test pins all three properties (section 11); otherwise Carbon would be re-run up to the
   full Doc repair budget on a deterministic failure.
3. **The `retryOptions` comment is refreshed** (inside the Surface because this file is edited). The advice "do not add `retryOptions`"
   stays correct; the mechanism text is stale for `2.32.0` (no `Retryable HTTP Error`, `status` preserved, the cited line moved,
   evidence S4, S5). The `uploadFile` doc comment (1.52.0 internals) is re-checked and kept: both internals still hold (evidence S6),
   with the version reference updated. `server/utils/retry.js` (verify-only) keeps its `Retryable HTTP Error` backstop as dead-but-harmless
   code; finding F-6.
4. `FALLBACK_DEEP` / `FALLBACK_FAST` stay as they are (Out of scope).
5. **`maxOutputTokens` per path (Specification v2, FR-22 and N-3; no code change).** Three paths, three values, all unchanged:
   `generate()` passes the resolved slot's cap (`gemini.js` line 112; 65536 for Carbon and Hydrogen); `analyzeImage` passes
   `Math.min(8000, slot cap)` (line 250; 8000 for both models); `extractFromPdf` passes the literal `8192` (line 272, independent of
   the slot). The non-streaming clause holds on all three. No cap is raised and no streaming call is introduced. This is now a stated
   requirement, so the plan covers each path with its own assertion (section 11); the test-writer must not assert 65536 on the
   latter two, and must not leave them unasserted for Carbon and Hydrogen (an existing test pins 8000 on 3.1 Pro only; none pins
   8192 anywhere).
6. **Anchoring rule for the Carbon / Hydrogen request-shape tests (impact R-14, review NB-2).** `generate`, `analyzeImage` and
   `extractFromPdf` take an already resolved slot, and `clampLevel` falls back to the first Gemini model for an unknown id, so a test
   that hands the provider a hand-written `{ model: 'gemini-4-carbon', level, maxOutputTokens: 65536 }` passes today. The plan
   therefore requires that each FR-20 to FR-22 case obtain its slot from `resolveSlot('gemini', { model, level }, tier)` and assert
   that the returned `model` is the expected Gemini 4 id and `maxOutputTokens` is the catalog's value, before the provider
   assertion; or equivalently assert catalog membership first. The existence assertion is what is red before the catalog task; the
   provider assertions then follow from it. Under the 3.1 Pro fallback every in-range level yields the same `thinkingLevel` and the
   same 65536 cap, so the id assertion is the only discriminating one and must not be dropped.

### D10. Pricing (`server/usage/pricing.js`)

- Remove the `'gemini-3.6-flash'` entry from `DEFAULT_PRICES`, the `gemini37FlashPrice` helper and its branch in `getPrices` (FR-29).
- Add `'gemini-4-hydrogen': { in: 1.50, out: 7.50, cw: 0, cr: 0.075 }` to `DEFAULT_PRICES` (flat, exact key; FR-26). A suffixed id
  would still hit it through the substring loop (`model.includes(key)`).
- Add a date-dependent helper for `gemini-4-carbon` with an exact-match branch placed BEFORE `DEFAULT_PRICES` and the substring
  loop, like `gemini38FlashPrice`: `now < new Date('2026-12-01T00:00:00Z')` returns `{ in: 2.00, out: 10.00, cw: 0, cr: 0.10 }`,
  otherwise `{ in: 4.00, out: 20.00, cw: 0, cr: 0.20 }`; the boundary instant returns the later price (FR-27). It builds a fresh
  object per call and reads `now` per call (default parameter), never at module load. Carbon has no `DEFAULT_PRICES` key, so it
  cannot reach `FALLBACK_PRICE` or another Gemini entry for its exact id. A dated or suffixed Carbon id would miss the exact
  branch (impact R-4); catalog ids are exact and `resolveSlot` only ever returns catalog ids, so this is accepted and documented in
  the comment.
- `gemini38FlashPrice` and `gemini-3.1-pro-preview` are unchanged (FR-28). The evidence V2 shows the vendor page agrees with them.
- Comments are updated, and **no comment in the file may keep naming a retired model** (impact R-13): the `gemini38FlashPrice` comment
  currently says "same promo window and rates as 3.7 Flash" and is rewritten to stand alone; the Gemini block and the promo-window
  notes are rewritten; the Carbon cutover note names `2026-12-01T00:00:00Z` as the specification's UTC choice (the vendor page gives the
  date without a timezone).
- `computeCost` takes no clock, so it uses the wall clock: the Carbon price switches at the server's real 2026-12-01T00:00:00Z.
  `getPrices(model, now)` is the injectable seam for the unit test; a cost-level boundary test needs fake timers (NFR-7).
- A retired id after removal resolves to `FALLBACK_PRICE`; no requirement (P-9c, accepted). **Sequencing fact (review NB-4):** the
  only caller prices the provider-resolved model, so a retired id is never priced only if the D8 remap is already in place. While
