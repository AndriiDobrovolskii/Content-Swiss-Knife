## How "done" is read under the TDD gate

`TEST_WRITING` runs as a whole stage before the first task, so each task's `Tests` names files that **already exist and fail** when the task starts. A task is done when it is **gate-green** (the Per-task gate below): the tests it names turn green without being weakened (AGENTS.md 7.7), every test that was green before it is still green, and the type and build checks hold under the red-list rule. Tests named by a **later** task are red by design until that task. The full gate (`npm test`, both runners, coverage, `npm run lint`, `npm run build`, `bash arch-guard.sh`) is `QUALITY_GATE`'s and is meaningful only after the last task.

Runner rule (plan section 8, hazard 6): `*.component.spec.ts` -> `npm run test:components` (`ng test`, `@angular/build:unit-test` + vitest + happy-dom, `include` is `**/*.component.spec.ts`); every other spec, including store and service specs (`Injector.create`) and `src/app/app.component.image-studio-wiring.spec.ts`, `app.component.shell-wiring.spec.ts`, `app.component.export-guard.spec.ts` (their names do not end in `.component.spec.ts`), -> `npm run test:logic` (vitest). Spec file names below follow the sibling-spec convention; `TEST_WRITING` confirms the exact names.

### Per-task gate (finding B-1; interpretation of AGENTS.md section 6, open point O-1)

**Label for the human.** This gate is an **interpretation** of AGENTS.md section 6 and of the `so-builder` definition-of-done item "`npm run lint` is clean" for a tests-first branch. It follows the repository precedent in `docs/plans/US-10.1-task-breakdown.md` ("Per-task gate", open point O-1) and `docs/plans/US-8.1-task-breakdown.md` ("Per-task gate convention"). It changes no threshold, skips no check, and proves nothing the full gate proves: `QUALITY_GATE` still runs `npm run lint`, `npm test` (both runners), `npm run test:coverage`, `npm run build` and `bash arch-guard.sh` unchanged after the last task. It also bends **AGENTS.md section 13** ("a commit is one complete, working change (build/lint/tests passing), not a fixup or a checkpoint"), and section 13 is the rule most directly bent: on up to the first 29 commits (T1..T29) `npm run lint` and `npm run build` exit non-zero, because the spec files and helpers written at `TEST_WRITING` are red until their owner task lands, so those commits are not individually green by the letter of section 13. They are green by the red-list rule below (every diagnostic is an allowed class in a red-list file, no product file has one, and from T30 both commands exit 0 outright). The US-10.1 breakdown named the same tension (its non-blocking finding N-4, "Section 13 / section 6 tension") and the human accepted it there. Approving this plan at `HUMAN_PLAN_APPROVAL` accepts the interpretation of **both section 6 and section 13**; the alternative is to re-plan with each spec written alongside its owner task, which `TEST_WRITING` running as a whole stage before the first task does not allow.

**Why "lint and build green after every task" cannot hold (read from the repository, not assumed).**
- `package.json`: `lint` = `tsc --noEmit`; `build` = `ng build`; `test:components` = `ng test`; `test:logic` = `vitest run`.
- `tsconfig.json`: `"include": ["index.ts", "src/**/*", "test/**/*"]`, so every spec and test helper is in the TypeScript program. There is no `tsconfig.spec.json` in the repository (checked).
- `angular.json`: `build` uses `"tsConfig": "tsconfig.json"` and the `test` target (`@angular/build:unit-test`, runner `vitest`, `buildTarget: app:build:development`, `include: ["**/*.component.spec.ts"]`) sets no `tsConfig` of its own, so it inherits `tsconfig.json` from the build target.
- Specification-first testing means the specs written at `TEST_WRITING` import modules and call members that later tasks create (`feed`, `session-name`, `archive-name`, the two services, seven components; `sendState`, `checkedPresetId`, `reusePrompt`). Until their owner task lands, `tsc` and `ng build` report missing-symbol diagnostics for them. A task before the last owner therefore cannot make `lint` or `build` exit 0, and the v2 acceptance clauses ("`npm run build` green" in T1, T18, T19, T37; item (3) of "How done is read") are replaced by this gate.

**A task is gate-green when, after its commit:**

1. **Own tests.** Every case in its `Tests` table passes in the runner named. For a file with several owner tasks (rule below), a task's cases are the top-level `describe` blocks whose titles end with the task id; logic runner: `npx vitest run <file> -t "\(T13\)"` (the parentheses are escaped because `-t` is a regular expression: an unescaped `(T13)` is a group and would also match any title that merely mentions `T13`, and a bare `T1` would select `T13`); component runner: the scoped mechanism below.
2. **Regression.** Every case that passed before the task still passes, in both runners. A spec that did not load or build before because a later task's module is absent was not passing and is not counted. Component-runner regression uses the scoped mechanism ("Scoped component runs" below), whose roots are **positive**: the spec files being run, and nothing else. The three **non-studio** component specs run scoped **from T1** (`src/app/components/content-template-select/content-template-select.component.spec.ts`, `src/app/components/model-settings/model-settings.component.spec.ts`, `src/app/components/dashboard/dashboard.component.spec.ts`; their import closure is 14 source files, none under `test/`, so they reach neither `fakes.ts` nor `studio-render.ts`; checked with `tsc --listFilesOnly` on the current tree), at every task T1..T20. `src/app/app.component.shell.component.spec.ts` and `src/app/app.component.clear-all.component.spec.ts` are component specs too, but they **import `studio-render.ts`** (red until T20), so they are not roots of any scoped run before T21 and join at the T21 catch-up (shared-file table: type owner T20). **T21 is the catch-up** (finding N-6): it runs every pre-existing studio component spec (`image-studio.component.spec.ts`, `studio-version-strip`, `studio-composer`, `studio-composer.attachments`, `studio-session-list`) and the two helper-importing app specs (`app.component.shell`, `app.component.clear-all`) as well as the three non-studio ones, and classifies each failing case against the ownership tables ("Ownership of the existing-spec adaptations" and the shared-file table below). A case that fails and is not owned by a later task was broken by T1..T20 (T5, T6, T14 and T16 change behaviour those specs cover); **it is not fixed inside T21** (rule "An unowned catch-up failure" in "Scoped component runs"). From T21 every component spec whose first runtime owner is committed is part of the regression run.
3. **Types (`npm run lint`).** `npx tsc --noEmit` reports **no diagnostic outside the red list**, and **inside** the red list only the allowed classes below. The red list is the set of spec files **and shared test helpers** written by `TEST_WRITING` whose **type owner** (rule below) is a task not yet committed. Observable check: `npx tsc --noEmit 2>&1 | grep "error TS" | grep -v -E "^(<red-list paths, alternated>)\("` prints nothing, and every line it excuses carries one of the allowed codes.
   - *Allowed in a red-list file:* TS2307 (cannot find module) and TS2305 / TS2724 (no exported member, with or without a suggestion) for modules and exports owned by a later task; TS2339 / TS2551 (property or member does not exist) and TS2353 (object literal has an unknown property) for members owned by a later task; TS2554 (argument count) only where a later task adds the parameter; TS2322 / TS2345 / TS2741 only where a later task creates the union member, field or type involved. A `type`-only import of a later-task type (for example `LocalOffset` in `fakes.ts` until T18) falls under TS2305.
   - *Compiler options (finding N-14).* `tsconfig.json` sets no `strict` / `noImplicitAny`, so an unresolved import in a red-list file produces only the missing-symbol classes above, with no implicit-any cascade. If `TEST_WRITING` ever tightens a compiler option that changes this (for example `noImplicitAny`), the allowed list gains **TS7006 / TS7031** (parameter / binding element implicitly `any`) for the parameters of callbacks passed to an unresolved symbol of a later task, in a red-list file only; `TEST_WRITING` records any such change in `test_strategy`. It is not otherwise a licence to relax the list.
   - *Never allowed:* any diagnostic in a product (non-spec, non-helper) file; any diagnostic in a file whose type owner is this task or an earlier one (the task has not built what its own tests need, or `TEST_WRITING` imported something no task creates: a finding for `TEST_WRITING`, not an edit); any other class (syntax errors, TS2304 on a name nobody owns, implicit-any on an owned symbol).
4. **Build (`npm run build`).** `ng build` type-checks the same program (read, below), so its diagnostics are judged by the same rule until the boundary: every `[ERROR]` it prints must be an allowed code located in a red-list file; **no** `NG####` template diagnostic and no error in any other file is allowed at any task (product templates must compile at every commit). The build is **required to exit 0 outright from T30 on**; its exit code is expected non-zero before that.
5. **Frozen baseline.** `bash arch-guard.sh` exits 0 (no FROZEN file moves; none is listed).
6. **Scope.** `git diff` for the commit lists only the files in the task's Files table. The scoped tsconfig below lives under the git-ignored `.angular/` and is never committed.

**From T30 on `npm run lint` and `npm run build` must exit 0 outright.** T30 is the boundary because the last red type owner is the feed component spec (T30, `StudioFeedComponent`); every other late spec is clean earlier (table below). The boundary is defined as **the first commit at which every type-owner task of T1..T30 (less the retired T31) is committed**: under the execution order as listed that is T30. T30 does not itself depend on T22, T23, T24 or T25, so a builder that reorders those independent tasks later than T30 (the dependency graph permits it) must not apply the outright-exit-0 requirement at T30; it applies from the first commit after the last of them. If `TEST_WRITING`'s `test_strategy` names a later type owner than T30 for any file, the boundary is that later task: the builder takes the **later** of the two. After the boundary, specs may still be red at **runtime** (cases owned by later tasks); that is the normal tests-first state and is not a lint or build failure. The unscoped `npm run test:components` can build from T30 on and is `QUALITY_GATE`'s check after the last task.

**Standing guards.** Specs that only read source text (`test/image-studio-architecture.spec.ts`, `test/image-studio-theme.spec.ts`) import no studio symbol, so they are never on the red list. Their scans are runtime-red only until the task that owns them (the adapter-uses-helpers scan: T1; the theme scan: T37); the other architecture scans (a-g) must pass from the first commit, and a task that turns one red has broken a design rule, which is a defect of the task, not a red-list failure.

### Spec files with several owner tasks (finding B-1 (b))

Several spec files are touched by two or three tasks. The rule, so that each task's `Tests to turn green` is a **closed set**:

- **R1. One type owner per file.** The type owner of a spec or helper file is the **last task that creates a symbol the file imports or accesses**. The file is on the red list until that task's commit, and clean from it. The other tasks that add cases to it are **runtime owners**.
- **R2. Logic-runner files may have several runtime owners in one file.** `vitest` transpiles without type-checking, so a task's cases run (and the task's `Tests` row is proved) while the file is still on the red list. Each runtime owner's cases sit in their own top-level `describe`, title ending with the task id, so that `-t "\(T13\)"` selects exactly that task's cases. This is a `TEST_WRITING` requirement.
- **R3. A component-runner file must be type-clean at its first runtime owner.** `ng test` type-checks the program (mechanism below), so a component spec cannot be run while it is itself on the red list. `TEST_WRITING` writes each component spec so that it imports and accesses only symbols that exist when its first runtime owner lands (every shared component file below satisfies this: the later owners' cases are DOM and behaviour cases against symbols that already exist). If a later owner's case does need a symbol that task creates, the file is **split along the task seam** into sibling `*.<seam>.component.spec.ts` files (precedent: `studio-composer.attachments.component.spec.ts`), each with one owner, and the split is recorded in `test_strategy`. Pre-existing component specs have their first runtime owner at T21 (the catch-up).
- **R4. Gated cases never change a type owner.** The OI-A and OI-B fixtures (T40, T41) are authored after the ruling and add fixtures and assertions only, no new symbol (T38/T39 under option c are re-planned in any case).

### Scoped component runs and the type-check mechanism (finding B-1 (c), second revision; supersedes v3 and v2 F-9)

**What was verified, and how.** Read from the installed `@angular/build` 21.2.19 source (`node_modules/@angular/build/src`), **read-only; no `ng test` and no `ng build` was run** for this breakdown:
- `builders/unit-test/options.js` (L52-65): the unit-test builder uses its own `tsConfig` option if set (the file must exist, relative to the workspace root), else `tsconfig.spec.json` in the project root if that exists, else the build target's `tsConfig`. No `tsconfig.spec.json` exists and `angular.json` sets none, so the build target's `tsconfig.json` is used. `builder.js` (L320-326) overrides the build options' `tsConfig` with the option when given.
- `runners/vitest/build-options.js`: `browser` is cleared; the application build's **entry points** are the matched specs plus two virtual files (`angular:test-bed-init`, `angular:vitest-mock-patch`). `--include` replaces the `include` of `angular.json`.
- `tools/angular/compilation/aot-compilation.js` (L62, L96, L136, L179) and `jit-compilation.js` (L80-89, L106): the TypeScript program is created from the `rootNames` that the tsconfig yields, and diagnostics are collected over **every** source file of that program (`typeScriptProgram.getSourceFiles()`), not only over files reachable from the entry points.
- `tools/esbuild/angular/compiler-plugin.js` (about L345-375, `createMissingFileDiagnostic`): a TypeScript file that the bundler loads but that is **not in the TypeScript program** is not type-checked; if it contains Angular metadata (`@Component` and so on) it is an error ("must be part of the TypeScript compilation ... via the 'files' or 'include' property"), otherwise a warning. So **every spec that is run must be a root of the scoped program**, which the recipe below guarantees.

**The reading, and why the recipe does not rest on it.** The unit-test builder type-checks the **whole TypeScript program** its tsconfig yields (source reading; not executed). v3 claimed its recipe was "correct whether or not" the builder does that. That claim was false: with `include` globs plus an `exclude` list, the program still contains every file that an included file imports, so a red-list helper imported by a kept file stays in the program and fails the build. The claim made here is narrower and true: the **red-list rule for `tsc` and `ng build`** (unscoped, plain `tsconfig.json`) is judged by allowed codes in red-list files and does not depend on how the builder scopes its checks; and the **scoped recipe makes the program equal to the import closure of its roots, and its roots are exactly the entry points**. Under the verified reading (diagnostics over the whole program) that program is clean when the pre-check below passes; under the alternative reading (diagnostics only for files reachable from the entry points) the reachable set is the same closure. The recipe therefore gives the same answer under either reading, because it leaves nothing outside the closure to be type-checked. What is **not** verified by execution is that `ng test` accepts a `files`-only tsconfig and builds from it; that is what the T1 smoke check proves, so the recipe is a **requirement to be smoke-tested at T1, not a verified configuration**.

**The recipe (requirements R-S1..R-S6).**
- **R-S1. Positive roots.** The builder writes the untracked file `.angular/tsconfig.scoped.json` (`.angular/` is git-ignored, "Angular build cache" in `.gitignore`; never committed):
  `{ "extends": "../tsconfig.json", "include": [], "files": [ "../src/globals.d.ts", "../<spec path>", ... ] }`
  `files` lists exactly the specs passed to `--include`, and nothing else (`src/globals.d.ts` is comment-only today and is listed only so a future global declaration is not lost). **`"include": []` is mandatory**: omitting it inherits the base `include` and brings every file back (table row 2). **`exclude` is not used.** Paths in an extending config resolve against the extending file, hence the `../`. The file lists roots, not red files, so it no longer has to be regenerated from the red list.
- **R-S2. Import-closure requirement.** The import closure of every root contains **no red-list file**: every helper a root imports (`fakes.ts`, `studio-render.ts`, the shared `sessionOf` fixture, any other `test/image-studio/helpers/*` file) has its type owner already committed (shared-file table; `test_strategy` records the owner of every helper, F-14 (d)). Logic-runner specs are never roots of a component-runner run, so `fakes.ts` (red until T18) and its 29 importers are outside the program (unless a component root itself imports `fakes.ts`, in which case R-S2 applies to that root). A new component spec joins as a root at its first runtime owner, and not before.
- **R-S3. Pre-check, before every `ng test`.** `npx tsc --noEmit -p .angular/tsconfig.scoped.json` **prints nothing and exits 0**. Any output means the program contains a red or broken file: the root that reaches it is not runnable yet (drop it from `files` and from `--include`), or, if the file is one this task owns, the task is not done. Do not run `ng test` over a non-empty pre-check. (`tsc` does not check Angular templates; the `ng test` build adds the `NG####` diagnostics.)
- **R-S4. Run.** `npx ng test --no-watch --include <spec path> [--include <spec path> ...] --ts-config .angular/tsconfig.scoped.json` (`tsConfig` is a documented option of the builder, relative to the workspace root). The `--include` set and the `files` set are the same specs.
- **R-S5. Roots by task.** T1..T20: exactly the three non-studio component specs (closure verified above, re-verified by R-S3 at each task). T21 onwards: the three non-studio specs throughout, and every component spec whose first runtime owner is committed (type-clean by R3), plus `app.component.shell` and `app.component.clear-all` from T21 (type owner T20, shared-file table). A spec that is not yet runnable is simply not a root.
- **R-S6. The spec being verified is a root.** By R3 it is type-clean at its first runtime owner, so its own diagnostics are never the reason for a non-empty pre-check.

**Smoke check at T1, with its stop conditions.** At T1 the builder writes the file with the three non-studio specs as roots, runs the pre-check (R-S3), then runs `ng test` (R-S4), and expects the pre-check to print nothing and the three specs to build and pass. **Stop** (the builder stops, records a blocking question to the human, and does not choose a substitute) if any of these holds:
1. the builder rejects `--ts-config` or does not resolve the extended config;
2. the pre-check is not empty for the three non-studio specs (the program reaches a file that is already broken or red: say which file and which root reaches it);
3. **`ng test` fails to build on a red-list file reached by import** (a diagnostic in a red-list file, or in any file that the pre-check showed clean, so that the builder's program is not the pre-check's program, for example because it needs a root the recipe does not list or ignores `files`/`include`);
4. `ng test` rejects a `files`-only tsconfig for any other reason (for example the "not found in TypeScript compilation" error for a spec that is a root).

**Fallback put to the human if the smoke check stops (covers T1..T29, not only T21..T29).** No scoped component-runner check exists: component specs are run for the first time **unscoped at T30**, the first commit at which `ng test` can build (Per-task gate, boundary). For T1..T29 the regression is the logic runner (`vitest run`, which does not type-check and so is unaffected by the red list), the `tsc` red-list rule, and the `ng build` allowed-code rule. Consequences, stated rather than hidden: the three non-studio component specs and every studio component spec are not run between T1 and T29; behaviour changes made by T5, T6, T14, T16 and the component tasks T21..T29 are first observed at T30, which is the catch-up in that case (T21's catch-up and the own-test runs of T21..T29 move to T30, and each is classified the same way); a defect found there is attributed to the earliest task that can have caused it but is found up to 29 tasks late. **An unowned catch-up failure (finding N-11).** At the catch-up run (T21, or T30 under the fallback), a case that fails and is not owned by a later task was broken by an earlier committed task. The fix would edit files outside T21's Files table (Per-task gate item 6), and AGENTS.md section 13 forbids a fixup commit.
