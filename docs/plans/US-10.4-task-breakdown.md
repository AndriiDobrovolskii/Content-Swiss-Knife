# Task breakdown: US-10.4 (Redesign the app shell: grouped, collapsible navigation and restyled layout in light and dark themes)

This breakdown orders the work the approved plan (`docs/plans/US-10.4-implementation-plan.md`, v1) already decided. It adds no architecture. `DD-n` are the plan's
decisions, `FR-n` / `AC-n` the Specification's (v2, `APPROVED`). Every task is on the **angular** track (all files are under `src/app`, `src/styles.css`, `index.html` or
`docs/evidence/`); no `server` or `prompt` task exists. No task edits a FROZEN file (AGENTS.md section 9): `task-a.ts`, `task-b.ts`, `task-c.ts`,
`master-system-prompt.ts` and `output-validator.ts` are not in any task's file list, so no task carries a section 9 stop.

**Revision note (v2).** v1 was sent back by `PLAN_REVIEW` (attempt 1) for two blocking findings, both about who performs a step. B1: the two existing-spec adaptations were in
`so-builder`'s file lists; they now belong to `TEST_WRITING` (see "Ownership of the existing-spec adaptations"). B2: T1, T2, T7, T8 and T10 were written as `so-builder`
dispatches; they are now external-executor steps (see "External-executor steps and where `IMPLEMENTATION` pauses"). Task content, order, dependencies and the plan items covered are otherwise unchanged,
apart from the cheap task-level corrections listed at the end of the revision (T4 constant `true`, lint wording, gate-verdict labelling).

## How "done" is read under the TDD gate

`TEST_WRITING` runs as a whole stage before the first task. It leaves three **new** spec files failing: `src/app/shell-nav.spec.ts` (`test:logic`),
`src/app/app.component.shell-wiring.spec.ts` (`test:logic`) and `src/app/app.component.shell.component.spec.ts` (`test:components`). It also **adapts two existing spec files**
(DD-10, OD-30, FR-18), which are partly red by design until the task that builds the thing they now describe (see the next section). A task is done when (1) the tests it
names turn green without being weakened (AGENTS.md 7.7), (2) every test that was green before it is still green, and (3) `npm run lint` and `npm run build` pass. Tests named by
a **later** task are expected to be red until that task; that is the TDD state, not a defect of the earlier task. The full gate (`npm test`, both runners, coverage,
`bash arch-guard.sh`) is `QUALITY_GATE`'s, after the last task.

Two notes for `TEST_WRITING` (findings, not decisions): (i) `ng test` compiles every spec together, so a spec that references an `AppComponent` member by name before its
task exists can break the whole component runner; the component spec should reach behaviour through the DOM (role and text), as the plan's DD-14 describes. (ii) The evidence
artifact's author and slug, and the measurement procedure, are OD-28's, settled at `TEST_WRITING`; the external-executor tasks below follow that procedure.

## External-executor steps and where `IMPLEMENTATION` pauses (review finding B2)

T1, T2, T7, T8 and T10 create or modify `docs/evidence/US-10.4-<slug>-evidence.md` and need a real Chromium at exactly 1024 px with seeded results. `so-builder` owns only `pipeline_status` and may not
write that file; `stage-map.yaml` has no human gate inside `IMPLEMENTATION`. They are therefore **external-executor steps** under the `evidence` artifact's `external_ok: true` rule (registry owner
`so-planner`; humans may write it). `so-builder` never creates, edits or "fills in" the evidence file, and never records a verdict in it.

**Who supplies the file.** A human, or an external executor with a real Chromium, supplies the filled evidence file. The procedure (viewport sizes, seeded results, probe, who may run it, slug) is
OD-28's, settled at `TEST_WRITING`; this breakdown fixes only the hand-off contract below. T1 needs no plan, tests or code, so the executor may have produced it before `IMPLEMENTATION`
starts; the breakdown requires only that the file exist, with the stated marker lines, at each pause point. (Whether it is produced earlier than T1's slot is the owner's OD-29 timing decision and is not decided here.)

**The hand-off contract (marker lines the executor writes, the builder only reads).** Each is a single line, at the start of a line in the evidence file:

| Marker line | Written by | Meaning |
|---|---|---|
| `GATE-1 (gate pass under the baseline rule): PASS` or `FAIL` | external executor at T2 | the DD-12 baseline rule applied to the phase-1 table |
| `GATE-2 (gate pass under the baseline rule): PASS` or `FAIL` | external executor at T8 | the same rule applied to the 26-cell table |
| `EVIDENCE-COMPLETE: yes` | external executor at T10 | every section FR-19 requires is present |
| `FR-16 met: NOT DETERMINED (U-1 pending product owner)` | external executor at T2, T8, T10 | see "Gate verdict wording" |

**Pause points.** `so-builder` is dispatched by the orchestrator for the whole `IMPLEMENTATION` stage. It works the tasks it owns in order and, before each task that depends on an external step,
reads the evidence file. If the required marker is absent it does not start that task and returns the Result Envelope `verdict: BLOCKED` (hold at `IMPLEMENTATION`, `blocking_issues` naming the pending external task); it
does not write a placeholder and does not guess.

| Pause | Where | The builder needs | External executor does | Builder resumes at |
|---|---|---|---|---|
| P1 | before T3 | a `GATE-1 ...: PASS` line | T1 then T2 | T3 |
| P2 | after T5 and T6 are committed, before the first builder-owned task that follows T8 (T9) | a `GATE-2 ...: PASS` line | T7 then T8, on the T3-T6 build | T9 |
| P3 | after T9 is committed, before `IMPLEMENTATION` may return `PASS` | `EVIDENCE-COMPLETE: yes` | T10 | return `PASS` and `QUALITY_GATE` follows |

**How it resumes.** The executor commits or places the filled evidence file in the working tree; a human (or the same `/so:next` run) then re-dispatches `IMPLEMENTATION`. `so-builder` reads `pipeline_status` and the evidence
file, finds the first task not done, and continues. A paused run keeps all committed work; nothing is rolled back.

**A FAIL becomes the `BLOCKED` report.** When the executor writes `GATE-1 ...: FAIL` (T2) or `GATE-2 ...: FAIL` (T8), the next dispatch of `so-builder` reads that line, starts no further task, and returns
`verdict: BLOCKED` with `blocking_issues` that name the failing cells and elements (taken from the evidence file) and the consequence in "Gate routing" below. `stage-map.yaml` gives `IMPLEMENTATION` the
loop-back keys `partial`, `blocked_by_plan` and `blocked_by_architecture` only; there is **no** key back to `SPECIFICATION`, and this is a product amendment (Specification FR-16 failure path), not a plan or architecture defect.
So the envelope carries no `loop_back_stage`, nobody invents one, and a **human routes it**: the product owner decides the Story amendment (candidates in plan DD-12), which re-enters the pipeline at `SPECIFICATION`.

**A failed light-value check at T10.** If the executor's contrast or light-theme check finds a token value that fails FR-15, the executor records the failing value and the requirement as not met in the evidence file and does **not**
edit `src/styles.css` (it is product code). The correction is a re-entry of T9 (same files, same tests) done by `so-builder` on the next dispatch, after which the executor re-measures the affected rows and writes `EVIDENCE-COMPLETE: yes`.

## Gate verdict wording (non-blocking item, U-1)

DD-12's pass rule is baseline-relative: a cell passes when column (a) "clipped" is empty, the rail and its four bottom controls are reachable, and column (b) "needs horizontal scroll" lists nothing absent from the
unshifted 640 px baseline. That is the lenient reading of FR-16, and the strict-versus-lenient question (U-1) is the product owner's and still open. So in the evidence file and in any `BLOCKED` report:

- A gate verdict is worded **"gate pass under the baseline rule"** (or "gate fail under the baseline rule"). It is a go/no-go for building, not a finding that FR-16 is met.
- "FR-16 met" is stated **separately** and reads `NOT DETERMINED (U-1 pending product owner)` until the owner has read U-1. Both columns (a) and (b), and the pre-existing (baseline) entries, are always reported so the owner can decide with data.
- No task, report or summary says "FR-16 met" on the strength of a gate pass.

## Execution order

Gate 1 is the cheap abort; gate 2 re-checks on the real structure. Both come **before** the bulk restyle (T9). Marks: `[B]` so-builder, `[X]` external executor.

```
T1  [X] M-0 phase 1: measure 1024 px on the current build (proxy, no code)
T2  [X] Record the phase-1 verdict; PASS releases T3.., FAIL stops the Story        <- GATE 1   (pause P1: builder needs GATE-1 PASS)
T3  [B] Pure shell module and types
T4  [B] Replace the header controls and in-panel switcher with the expanded rail, and the panel header strip
T5  [B] Icon-only rail: collapse control and guarded persistence                    (independent of T6 in logic; same files, so run after T4, before or after T6)
T6  [B] Gate the panel by mode, hoist the generatorForm template
T7  [X] M-0 phase 2: measure 1024 px on the walking skeleton (rail + gate + widths, no tokens), 13 modes x 2 rail states
T8  [X] Record the phase-2 verdict; PASS releases T9, FAIL stops the Story          <- GATE 2   (pause P2: builder needs GATE-2 PASS)
T9  [B] Apply the shell colour tokens and painting layers (bulk restyle)
T10 [X] Complete the evidence artifact: light values, contrast, colour, geometry, final fit table   (pause P3: builder needs EVIDENCE-COMPLETE)
```

Dependency graph: `T1 -> T2 -> T3 -> T4 -> {T5, T6} -> T7 -> T8 -> T9 -> T10`. T5 and T6 do not depend on each other (T5 touches the rail only, T6 the panel gate), so either order
is valid; they edit the same two files, so they are done one after the other, not concurrently. T7 needs both. No other pair is parallelisable.

|---|---|---|---|
| 1: proxy on the current build | T2 (external executor) | T3..T10 are released | T3..T10 are **blocked**. No workaround is built (panel width and mode interiors are out of scope; FR-4 forbids defaulting the rail collapsed). `so-builder` returns `BLOCKED` with the cell table pointers (see "A FAIL becomes the `BLOCKED` report").
