# Implementation plan: US-10.4 (Redesign the app shell: grouped, collapsible navigation and restyled layout in light and dark themes)

This plan decides **how** the approved Specification (v2, `APPROVED`) is built. It does not order tasks or assign tracks (that is `so-implementation-planner`), and it
writes no code, test or fixture. `DD-n` are this plan's design decisions; `FR-n`, `NFR-n`, `AC-n`, `OD-n` are the Specification's / Open Decisions log's; `F-n`, `U-n` and
"hazard n" are the Impact Analysis's. Nothing here needs a Specification or Story change, so the verdict is PASS. The one requirement that cannot be proven from the
repository, FR-16 (width at 1024 px, OD-29), is **planned as a gating measurement with a defined failure route** (DD-12); it was not measured in this stage and no
number below is a measurement.

## Approach

US-10.4 is an Angular-track change confined to the app shell. **Everything that carries a source-text pin stays inline in `src/app/app.component.html`**: the rail is
hand-written markup (twelve literal `setMode('<mode>')` buttons), the input panel stays a gated `<aside>` in the same file, and the Actions Footer, Clear All and the
feedback block stay inside that gated `<aside>`. This is forced by `app.component.image-studio-wiring.spec.ts`, which OD-31 says must pass with its assertions unchanged
and which reads `app.component.html` for `setMode('image-studio')` and for the `<!-- Actions Footer -->` chain (DD-1). Nothing relocates, so OD-32's re-pointing
permission is never invoked.

The new logic is a **pure, Angular-free module** `src/app/shell-nav.ts` (group descriptor and counts, group membership, the panel-by-mode table, the nav-item visibility
rule, and a guarded rail-state storage helper) that the logic runner tests directly (DD-2). `AppComponent` adds a small amount of signal state on top of it (rail
expanded, group open/closed) and a handful of thin methods the template calls. The panel is gated with `@if (hasPanel())` around the `<aside>`, with the opening line
written at two spaces and the `<aside>` left un-reindented so the indentation-sensitive `faq-layout` / `template-wiring` regexes stay green (DD-5). The
`<ng-template #generatorForm>` is hoisted to the root of the template so both the gated panel and `<main>` can still reach it (DD-4). Colours become six to eight CSS
custom properties (dark values from the Specification, a derived light set) exposed to Tailwind as a `shell` colour family, so each token is declared once and the light
theme cannot keep a dark colour by construction (DD-9). The History overlay is anchored to a header-height token shared with the panel header (DD-8). Contrast, colour,
geometry and 1024 px fit are verified manually and recorded under `docs/evidence/` (DD-12, DD-13).

## Design decisions

### DD-1. Where the markup lives: all inline, zero new Angular components (F-3, OD-31 vs OD-32)

- **Decision.** The rail, the panel (header strip, form chain, Actions Footer), the History overlay and `<ng-template #generatorForm>` all remain in
  `src/app/app.component.html`. No file is added under `src/app/components/`.
- **Why.** `image-studio-wiring` L102 asserts `html.toContain("setMode('image-studio')")` and L110-128 assert the `<!-- Actions Footer -->` chain (including the empty
  `image-studio` branch before the final `processImages()` `@else`) in `app.component.html`. OD-31 fixes that spec as unchanged. A `NavRailComponent` that emits a mode, or
  an `@for` over the group list, removes the `setMode('image-studio')` literal from the file, and OD-32's "re-point the pin" permission cannot rescue it because OD-31 freezes
  that spec. Extracting the panel is also out: the panel binds well over a hundred `AppComponent` members and its footer is pinned in place. Because nothing relocates, the
  OD-31 / OD-32 tension (U-4) resolves in favour of OD-31 with no human decision needed.
- **Consequence for NFR-4.** NFR-4 ("every new component has its sibling `*.spec.ts`") is satisfied vacuously: there is no new component. The behavioural tests are
  `AppComponent`-level `*.component.spec.ts` files in the `clear-all` / `renderStudio` precedent (DD-14).
- **Markup rules for the rail buttons** (each derived from an existing pin; the builder and test writer must keep them):
  1. `(click)="setMode('<mode>')"` is the **first** attribute after `<button` (`template-wiring` `modeButton()` regex).
  2. The button contains exactly one `{{ uiLabels().x }}` interpolation and for the FAQ button it is `faqGenerator` (`template-wiring` L262-267). No count, tooltip or other
     interpolation inside a mode button.
  3. `setMode('faq-generator')` and its label stay within 500 characters (`template-wiring` L203). Class logic therefore lives in short methods (`navItemClass(mode)`,
     `navIconClass(mode)`), not in long inline `[class]` ternaries.
  4. One element per mode (no hidden second copy for the icon-only rail; DD-3).
  5. Exactly one `setMode('dashboard')` (the bottom control), one `<!-- History Panel`, one `<!-- Actions Footer -->`, one `<aside`.
  6. No `@else if (appMode() === '<mode>')` line in the rail (the 4-space `@else if` regexes of `faq-layout` / `template-wiring` match the first occurrence).
  7. File order is rail, then panel, then `<main>`.
  8. The nine SEO & Text mode buttons are **flat siblings** inside one group container, with no per-item `<div>` and no `</div>` between items. Visibility is an `@if`
     around the `<button>`, not a wrapper element.
  9. Stable anchor comments for the adapted pin and for the tests: `<!-- Nav Rail -->`, `<!-- Nav Rail: bottom controls -->`, `<!-- Nav Rail end -->`.

### DD-2. Pure shell module `src/app/shell-nav.ts` (OD-25 decided: counts are DERIVED)

- **Decision (OD-25).** Group counts are **derived** from a typed descriptor, not written as static text. `NavGroupId` and the `NavGroup` shape are added to
  `src/app/types.ts` (`'seo-text' | 'images' | 'code'`); the data and functions are in the new `src/app/shell-nav.ts`, which imports no Angular symbol:
  - `NAV_GROUPS`: the three groups, each with its ordered mode list exactly as FR-1 states (SEO & Text: generator, ua-generator, optimizer, translator, seo-generator,
    copywriter, readability, slug-generator, faq-generator; Images: image-tools, image-studio; Code: html-editor). `dashboard` is in no group.
  - `navGroupCount(id)` (= list length) and `groupOf(mode)` (undefined for `dashboard`).
  - `MODE_HAS_PANEL: Record<AppMode, boolean>`: true for the nine text modes and `image-tools`, false for `image-studio`, `html-editor`, `dashboard`. Typing it as a total
    `Record` makes the compiler force a decision for any future `AppMode` (an unlisted mode cannot silently default to rendering a panel, which is how the current footer
    leak arose) and `hasPanel(mode)` reads it.
  - `isNavItemShown(mode, activeMode, railExpanded, groupOpen)` implementing FR-2: shown if the rail is icon-only (FR-2 d), or its group is open, or it is the active mode.
  - The rail-state storage helper (DD-6).
- **Why derived.** The header count must equal the number of items in the group (FR-1). With a static `· 9` in markup or in the translation strings, the number is a second
  copy that drifts silently when a mode moves. Derived, the count and the visibility rule share one source of group membership.
- **Honest limit.** The buttons are hand-written (DD-1), so the **markup order and membership are a second copy of `NAV_GROUPS`**. That copy is guarded by a component test
  that reads the rendered items of each group and compares order and count with `NAV_GROUPS` (DD-14 category 3), not by the type system.
- **Why a separate pure module.** It runs in the fast logic runner (`@angular/core` signals are not even needed here; `AppComponent` owns the signals), has a sibling
  `shell-nav.spec.ts` like `tab-descriptors.ts` / `tab-descriptors.spec.ts`, and keeps `app.component.ts` (1504 lines) from absorbing more logic.
- **Header text.** The three headers are hand-written with the ratified form `{{ uiLabels().navGroupX }} · {{ navGroupCount('x') }}` in both languages. The exact UA
  strings are pinned by TEST_WRITING (OD-25 residue).

### DD-3. Rail structure, accessible names, one element per item (FR-1, FR-2, FR-3, FR-4, FR-6, FR-10; F-2, hazards 6, 7)

- **Element choice (F-2).** The rail is a `<nav>`, **not** an `<aside>` and not `role="complementary"`. No other template under `src/app/components/**` contains `<aside>` or
  `<nav>` (checked by grep), so `container.querySelector('aside')` returns exactly the input panel in a panel mode and `null` in a panel-less mode. The `<nav>` carries no
  `aria-label`: it is the only navigation landmark, and a landmark name would be new product copy that the FR-6 copy table does not contain (reported as a non-blocking
  finding, not decided here).
- **Layout.** `<nav>` is `flex-shrink-0`, `h-full`, `flex flex-col`, width `w-64` (expanded) or `w-16` (icon-only) chosen from `railExpanded()`, no z-index (it never overlaps
  anything and must stay below the `z-50` html-editor fullscreen and model-settings modal). Vertical fit (U-3): the logo row and the bottom controls are fixed
  (`shrink-0`); the group region between them is `flex-1 min-h-0 overflow-y-auto`, so a short viewport scrolls the middle instead of clipping the bottom controls.
- **Icon-only rail, one element per item.** Each mode is a single `<button>` holding an `<i>` icon (`aria-hidden="true"`) and a `<span>` label. In the expanded rail the span
  is visible; in the icon-only rail the same span gets `sr-only`. The accessible name is the span's text in both states, so the name never changes, is unique, and no second
  hidden copy exists (hazard 6). A `title` tooltip is bound only while icon-only. Group headers and items hidden by a collapsed group are removed with `@if`, never with CSS
  (FR-2 b; the component runner has no Tailwind, so a CSS-only hide would be invisible to tests, hazard 7).
- **Group headers.** In the expanded rail each header is a `<button>` with `[attr.aria-expanded]` and the visible text `name · N` as its accessible name. In the icon-only rail
  the header is replaced (`@if`) by a decorative separator (`aria-hidden="true"`), and all twelve items render (FR-2 d). The per-group open state lives in memory (a signal
  `navGroupOpen`) and re-applies when the rail is expanded again; it is never persisted (OD-24).
- **`aria-current` (FR-3; hazard 12).** Every item, the Dashboard control and nothing else binds `[attr.aria-current]="navCurrent('<mode>')"`, where `navCurrent` returns
  `'page'` only when `appMode() === mode`, else `null`. It reads `appMode()` only; the rail keeps **no active-item state of its own** and every item goes through
  `setMode()`, so the `html-editor` unsaved-changes `confirm()` guard still decides and a cancelled confirm leaves `aria-current` on the html-editor item. The Language, Theme,
  AI Settings and collapse controls never bind it. Note for tests: `studio-session-list.component.html` L19 uses `aria-current="true"` (value `true`); FR-3 counts must select
  `[aria-current="page"]`, not any `[aria-current]`.
- **Bottom controls (FR-10).** In DOM order: Dashboard (`setMode('dashboard')`, `aria-current` per above), Language, Theme, AI Settings. All four are `<button>`s in both rail
  states; their labels are `sr-only` when icon-only except the Language code, whose visible text ("EN" / "UA") stays in both states.
- **Language name (FR-6, WCAG 2.5.3).** A computed `languageCode` (`'EN'` for `en`, `'UA'` for `uk`) is both the visible text and the first part of the name; the name is
  `` `${languageCode()}, ${uiLabels().switchLanguage}` `` bound to `aria-label`. Label-in-name therefore holds by construction.
- **Dashboard accent.** The current Dashboard button puts violet on the whole button (`text-violet-600 dark:text-violet-400`). With a text label that becomes violet text and
  breaks FR-15. The accent is applied to the `<i>` only (`navIconClass`); label text uses the text tokens.
- **New translation keys (NFR-5, both `en` and `uk` maps in `app.component.ts`):** `navGroupSeoText`, `navGroupImages`, `navGroupCode`, `navCollapse`, `navExpand`,
  `switchLanguage`, `toggleTheme`, `aiSettings`, with the EN/UA strings of the FR-6 table. Dashboard reuses `dashboardTooltip`; mode items reuse the existing mode labels.
  A key missing from either map is a compile error because `uiLabels()` is the union of the two map types (`npm run lint`).
- **Icons** (Font Awesome 6.4, already loaded): generator `fa-wand-magic-sparkles`, ua-generator `fa-language`, optimizer `fa-bolt`, translator `fa-globe`, seo-generator
  `fa-tags`, copywriter `fa-pen-nib`, readability `fa-glasses`, slug-generator `fa-link`, faq-generator `fa-circle-question`, image-tools `fa-images`, image-studio
  `fa-palette`, html-editor `fa-code`, dashboard `fa-chart-line`, moon/sun `fa-moon`/`fa-sun`, settings `fa-sliders`. Collapse control: a chevron pair.

### DD-4. Gating the panel and the hoisted `generatorForm` template (F-4, hazard 3)

- **Decision.** `@if (hasPanel()) { <aside ...> ... </aside> }`, where `hasPanel = computed(() => hasPanelFor(appMode()))` reads `MODE_HAS_PANEL`. The `<aside>` is **removed from the
  DOM** in `image-studio`, `html-editor` and `dashboard` (not hidden). Clear All, Process Images, the feedback block (button, rename pen, popup-blocked notice) and
  History live inside this `<aside>`, so FR-9, FR-12 and FR-17 follow from the gate with no extra per-control conditions. The unreachable `image-studio` branch of the footer
  chain and the `case 'image-studio':` of `clearAll()` are **kept** (OD-31; the wiring spec pins them), with a comment that panel gating makes them unreachable at runtime.
- **The template-reference problem.** `<ng-template #generatorForm>` is currently declared inside the `<aside>` and also consumed at `<main>` (`*ngTemplateOutlet`, ~L1299, the
  centred pre-result form of generator and ua-generator). A reference declared inside an `@if` block is not visible outside it, so leaving the declaration where it is would
  break the main-area form while the panel still rendered (so a panel-presence check would not notice). **The `<ng-template #generatorForm>` is moved (not copied) to the root
  level of the template**, as a direct child of the root container, before the gated panel. A root-view reference is visible to the gated `<aside>` (an embedded view) and to
  `<main>`. It is moved, not duplicated, because `faq-layout` pins `uiLabels().supplementalContent`, `noContentYet` and `fillFormStart` as used exactly once in the whole
  template, and `generatorFormBlock()` finds the block by its markers, independent of position and indentation.
- **Failure it must not introduce.** After the move, pre-result generator and ua-generator must still show the centred form in `<main>` and post-result they must show it in the
  panel; the component test asserts both (DD-14).

### DD-5. Indentation: do not re-indent the panel (hazard 4; `faq-layout` `formBlock`, `template-wiring` `faqForm`)

- **Decision.** The `@if (hasPanel()) {` line is written at 2 spaces and the `<aside>` is left at its current 2-space indent, so its ~1000 lines of children stay at exactly
  4 spaces; the closing `}` follows `</aside>` at 2 spaces. A short comment explains why. No formatter or pre-commit hook exists in the repository (no `.prettierrc`,
  `.editorconfig`, husky or lint-staged; checked) that would reindent it.
- **Why.** `formBlock(mode)` (faq-layout L83-89) and `faqForm()` (template-wiring L195, L297) locate each form by `\n {4}@else if (appMode() === '<mode>')` and end it at the next
  `\n {4}@else`. Re-indenting adds two spaces and returns `''` (loud, caught by the baseline guards) or, worse, lets a stray 4-space line match the wrong block (silent).
  Not re-indenting needs **zero** edits to those two specs and keeps the diff reviewable.
- **Fallback if the builder's tooling reindents anyway.** An FR-18 (a) regex update (`{4}` to `{6}`) in the three affected helpers, listed in the implementation report; the
  property they assert (each form block is located and bounded) is preserved. The plan prefers not to need it.

### DD-6. Rail persistence: a guarded helper, not an effect, not `JSON.parse` (FR-4, FR-5; hazard 9)

- **Key and value.** `seo_gen_shell_rail_expanded`; the strings `'true'` (expanded) and `'false'` (collapsed). Nothing else is accepted.
- **Helper (in `shell-nav.ts`, pure).** `readRailExpanded(getStorage)` returns the matching boolean for exactly `'true'` / `'false'`, and `true` (expanded) for an absent key, any
  other value, a throwing `getItem`, or a throwing `getStorage()` (accessing `window.localStorage` can itself throw). It never uses `JSON.parse`. `writeRailExpanded(getStorage, expanded)` calls `setItem(key, String(expanded))` inside `try`/`catch` and swallows the failure. The storage is passed in
  as a `() => Pick<Storage, 'getItem' | 'setItem'>` so the logic runner uses a controlled double (NFR-4) and the default is `() => localStorage`.
- **Wiring.** `railExpanded = signal(readRailExpanded(...))` is initialised once in `AppComponent` (read once at start-up). `toggleRail()` sets the signal and then calls
  `writeRailExpanded`; **there is no `effect`**. The signal only changes in `toggleRail()`, so "written on every change" holds without an initial write on load and without
  effect-flush timing in tests. If the write fails, the signal has already changed, so collapse/expand keep working for the session and no exception escapes the click handler.
- **Do not copy the neighbouring pattern.** `seo_gen_dark_mode` is read with an unguarded `JSON.parse` in the constructor (L662-665); copying it would silently fail FR-5 (ii).
  The existing unguarded `seo_gen_form_state` reads/writes are not touched.
- **Test-double note for TEST_WRITING.** The `AppComponent` constructor and effects read/write `seo_gen_form_state`, `seo_gen_dark_mode`, `seo_gen_ui_lang` unguarded. A
  component-level storage double that throws must throw **only for the rail key**, or the component fails to construct for a reason unrelated to FR-5.
  `renderStudio` calls `localStorage.clear()` before each render, so the rail key starts absent (default expanded).

### DD-7. Mode switching, language and theme controls keep their existing methods (FR-7, FR-8)

- **Decision.** No new mode-change path. Rail items and the Dashboard control call the existing `setMode()`; Language calls `toggleLanguage()`; Theme calls `toggleDarkMode()`
  (class on `documentElement` and the `seo_gen_dark_mode` write stay in the existing effect); AI Settings calls `toggleModelSettings()`. `<app-model-settings>` stays at the
  end of the template, outside both the panel and `<main>`, so the modal opens in the panel-less modes with no further change (FR-7). The moon/sun swap (`darkMode()`) moves to
  the rail unchanged; its accessible name is the constant `toggleTheme` string in both states.
- **What does not change.** Main-area views, `clearAll()`, the History flag (`showHistory` is not reset on leaving generator, FR-11), `TOOL_LABEL`, feedback URL computation.
  `History` keeps its existing `title="History"` (not part of the FR-6 table; NFR-2).

### DD-8. Panel header strip and the History overlay anchor (FR-9, FR-11; OD-22)

- **Decision.** The app title and cube logo move to the top row of the rail (logo + title expanded; logo only icon-only, the `<h1>` text `sr-only` there so the page keeps a
  heading). The panel's first child is a header strip of a **mode-independent fixed height**, `h-[var(--shell-header-h)]`, containing **nothing but** the History button in
  generator mode (FR-9 / OD-22: no mode label, no other text). The rail's logo row uses the same token so the two rows align.
- **Anchor by construction.** The History overlay stays a child of the `relative` `<aside>`, with `absolute inset-x-0 bottom-0 top-[var(--shell-header-h)]`. The strip height and
  the overlay top read the **same** CSS variable (`--shell-header-h`, `4rem`, declared in `styles.css`), so the overlay's top edge equals the strip's bottom edge with no
  overlap and no gap, and neither a literal `top-[125px]` nor a coincidental `top-[64px]` remains. A wrapper `<div class="relative ...">` around the form chain was rejected
  because it would nest the chain at 6 spaces (DD-5).
- **Generator-only (FR-11).** The button and the overlay condition stay `appMode() === 'generator'` (and `showHistory()` for the overlay). History items, comparison and
  `clearHistory` markup inside the overlay are unchanged.
- **Verification.** Pixel adjacency cannot be asserted in the component runner (no Tailwind); it is part of the manual evidence (DD-13). The component test asserts what is
  observable: the button exists only in generator, toggles the overlay, no overlay in another mode with the flag set, overlay returns on coming back.

### DD-9. Theme tokens: CSS custom properties exposed as a Tailwind `shell` colour family (FR-13, FR-14, FR-15; hazard 8)

- **Decision.** `src/styles.css` declares the tokens once: light values on `:root`, dark values on `html.dark` (the same selector the file already uses for `color-scheme`).
  `index.html`'s `tailwind.config` (`theme.extend.colors.shell`) maps each to `var(--shell-*)`, giving classes such as `bg-shell-bg`, `bg-shell-rail`, `border-shell-line`,
  `text-shell-text`, `text-shell-muted`, `hover:bg-shell-hover`, `bg-shell-active`, `border-shell-accent`, `ring-shell-accent`. Opacity modifiers (`/50`) are not used on these
  tokens (a `var()` colour does not support them). Because every shell surface uses a token rather than a `x dark:y` pair, "no shell surface keeps a dark colour in light mode"
  holds by construction; the evidence still verifies it by looking (FR-14).
- **Dark values (Specification, fixed):** page `#0b1120`, rail `#111a2e`, border `#26324a`, accent `#7c3aed`. Developer-chosen dark extras: text `#f1f5f9`, muted text
  `#cbd5e1`, hover `#1a2540`, active `#243052`.
- **Light values (FR-14: developer's choice, to be confirmed and recorded in the evidence artifact).** Candidate set: page `#f1f5f9`, rail `#ffffff`, border `#cbd5e1`, text
  `#0f172a`, muted `#475569`, hover `#f1f5f9`, active `#ede9fe`, accent `#7c3aed` (unchanged). Contrast computed in this stage with the WCAG relative-luminance formula (a
  calculation, not a rendered measurement): dark text/rail 15.83, dark muted/rail 11.68, dark text/hover 13.86, dark muted/hover 10.23, dark text/active 12.39, dark muted/page
  12.68; light text/rail 17.85, light muted/rail 7.58, light muted/hover 6.92, light text/active 15.04, light muted/active 6.38, light muted/page 6.92. All are at least 4.5:1,
  so the candidates are expected to pass FR-15; the evidence artifact records the **measured** ratios of the final values. The accent as an icon colour on the dark rail is 3.04:1;
  non-text contrast is out of scope (Specification Out of scope), and the accent is never a text colour (FR-15).
- **Painting layers (FR-13 / OD-27, hazard 8).** The opaque layers between `<body>` and `<main>` all carry the same token so `#0b1120` is what is seen: `<body>` in
  `index.html` (`bg-shell-bg`, replacing `bg-slate-50 dark:bg-slate-900`), the root container (L2), and `<main>`, whose translucent `bg-slate-50/50 dark:bg-slate-900/50` is
  replaced by an **opaque** `bg-shell-bg`. `<main>` stays `relative` and keeps `overflow-hidden`: `dashboard` and `html-editor` are `absolute inset-0` children of it.
- **Panel chrome (FR-13 (3)(4)).** The `<aside>` surface, header strip and outer border use `bg-shell-rail` / `border-shell-line` so rail and panel read as one look. Everything
  inside the panel (forms, inputs, buttons, the Actions Footer container, the History overlay) keeps its `slate-*` classes (NFR-3). That the footer container's `slate-800`
  strip sits on a `#111a2e` panel is an accepted interior consequence; the evidence records how it looks.
- **Accent use (FR-15).** `shell-accent` appears only as an active item's icon colour and left border (`border-l-2`, transparent when inactive to avoid layout shift) and as
  `focus-visible:ring-2 focus-visible:ring-shell-accent`. It never appears with a `text-` prefix on a label.
- **Non-token CSS in `styles.css`.** Only the token declarations and `--shell-header-h`; the existing rules are untouched. `index.html`'s scrollbar `<style>` is unchanged.

### DD-11. Domain model, chain, FROZEN files, payload, server, RxJS, OnPush (the areas that do not apply)

- **Domain model (`src/domain/`):** not touched. No schema, no `ProductDescriptionDoc` / `ConsumablesDoc` change, so the corpus fixtures in `test/fixtures/corpus/` cannot move and
  nothing on disk needs migrating.

### DD-12. FR-16 / OD-29: the 1024 px fit, a gating measurement with a failure route (F-1)

- **What is known from the repository (impact analysis, arithmetic, not a measurement).** At 1024 px: ten panel modes have a 384 px `<main>` with the 256 px rail and 576 px with
  the 64 px rail (640 px today); the three panel-less modes have 768 / 960 px. The cell in doubt is "ten panel modes, expanded rail". `<main>` is `overflow-hidden`, so anything
  wider than it that is not in a scrolling child would be clipped; `md:` / `lg:` grids are keyed to the viewport and ignore the narrower `<main>`.
- **This stage did not measure it.** No browser session was run; the number is not asserted. The measurement is planned as a **gate before the bulk restyle**, because it
  is the main risk to the Story and a late discovery is expensive.
- **Measurement step M-0 (before any restyling work).**
  1. *Proxy on the current build, no code written:* in a real Chromium at exactly 1024 x 768 (and 1024 x 720 for the rail's vertical fit, U-3), with a dev build, shift the root
     container right by 256 px and by 64 px (a left spacer on the existing root), so the panel is 384 px and `<main>` is 384 / 576 px with the same viewport-keyed breakpoints
     active as the real layout. Compare with the unshifted 640 px baseline.
  2. *Then on the walking skeleton* (the real rail, the panel gate, the width classes only; no tokens): repeat for all 13 modes, rail expanded and collapsed.
  3. *Seeding.* Result views need content: seed a generator/ua/seo/slug/faq result for a five-language store (the largest tab strip), optimizer, translator, copywriter,
     readability results, and Image Tools thumbnails, by setting the component's signals in a development build (`ng.getComponent`), or by an equivalent the executor records.
  4. *Probe per cell.* For every element inside `<main>`, the panel and the rail, record (a) **clipped**: its box extends past the right edge of an ancestor whose computed
     `overflow-x` is `hidden` or `clip` and no scrolling ancestor lies between; (b) **needs horizontal scroll**: its nearest scroll container has `scrollWidth > clientWidth`.
     Also record whether every rail control and bottom control is reachable (visible or by the rail's own vertical scroll).
- **Pass / fail.** FR-16 passes a cell when (a) is empty, the rail and its four bottom controls are reachable, and (b) lists nothing that is not also present in the unshifted
  640 px baseline. Items in (b) that **also** exist at 640 px today (expected: the result tab strip, `no-scrollbar` is undefined so it simply scrolls, and wide generated
  tables) are **recorded separately as pre-existing**, not as regressions of this Story.
- **U-1 (strict vs lenient reading) is not resolved here.** Whether a deliberate in-component horizontal scroll breaches the literal "no horizontal scrolling is required to reach
  anything" is a product-owner reading. The evidence reports both columns (a) and (b) so the owner can decide with data. Flagged as a non-blocking finding.
- **If it fails.** If any cell has a non-empty (a), or a (b) entry that does not exist at 640 px, FR-16 is **not met** and the executor stops and reports BLOCKED with the cell
  table; **no workaround is built inside this Story**: the panel width and every mode interior are out of scope (NFR-3, Out of scope), and FR-4 forbids defaulting the rail to
  collapsed. The route is the Specification's own: a Story amendment, decided by the product owner. Candidates to put in front of the owner (not plan decisions): a narrower
  panel below `xl`; an expanded-rail layout that overlays instead of pushing at narrow widths; a default-collapsed rail below a width threshold (contradicts FR-4 as written);
  accepting in-component horizontal scroll (U-1). Which candidate wins changes the Specification, so it is a `changes_required` to SPECIFICATION, not a re-plan.
- **If it passes** the numbers go into the evidence artifact (DD-13) and nothing else changes.
