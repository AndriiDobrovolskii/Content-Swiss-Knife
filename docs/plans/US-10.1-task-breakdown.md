## Reading guide

**Preconditions (not tasks).** `docs/evidence/US-10.1-pre-implementation-checks.md` (V-1 to V-9) is a human-authored precondition of
IMPLEMENTATION (NFR-12, plan "Pre-implementation checks"). Each task below names the checks it is bound to under Notes. A task whose
bound check is not yet recorded builds to the plan's stated assumption and the builder reports the dependency; it never invents a value.

**Probe 0 (optional; not a task, owned by no task, never a gate).** Plan v2 (DD-25 and R12) repeats the recommendation that the task owner
schedule an early look at the plan's one "might not hold" assumption: that `AppComponent` can be instantiated for the FR-1 clear-all test
with only minimal provider stubbing. A builder who wants that signal early may, on the base tree before T1, instantiate `AppComponent` once
in a throwaway component-runner spec with `provideHttpClient` + `provideHttpClientTesting`, read the outcome and delete the file. Nothing
is committed and no Files table includes it. It is reported to the human only if it is negative (plan R12, choice P-10); a negative result
never downgrades the clear-all test to source pins. Skipping it changes no task.

**Test paths are expected names.** Test files are written by `so-test-writer` before IMPLEMENTATION and are failing when a task starts. The
paths in each Tests table follow the repository convention (server and catalogue logic under `test/` or beside the source, client pure
logic under `src/utils/image-studio/`, components as `*.component.spec.ts`). Where the plan names a file it is used verbatim
(`test/gemini-image-provider.spec.ts`, `test/security.spec.ts`, `test/image-studio-architecture.spec.ts`,
`src/app/app.component.image-studio-wiring.spec.ts`, `src/app/app.component.clear-all.component.spec.ts`,
`src/app/components/dashboard/dashboard.component.spec.ts`, `src/prompt-core/model-catalog.spec.ts`); the others are the expected
`<module>.spec.ts` beside or mirroring the module. `test_strategy` and `ac_test_matrix` fix the final names and win on a spelling conflict;
what binds the task is the **Covers** column and the **runner**. Server specs carry `// @vitest-environment node`. Runner `test:logic` is
`vitest run` (excludes `*.component.spec.ts`); runner `test:components` is `ng test` (only `*.component.spec.ts`).

**One owner per spec file.** A spec file is owned by the single task that makes it fully green and type-clean (the last task whose symbol
it imports). Until its owner lands it is on the red list of the per-task gate. Where a plan category spans two tasks (for example the
`createApp` composition tests, C4, and the generation-runner tests, C6), this breakdown asks `so-test-writer` to split along the task seam and says so under that task; if a
file is not split, it is owned by the later task and the earlier task's acceptance check is carried by the cases that exist.

**Per-task gate.** Tests precede implementation, so red specs of later tasks are on the branch while an earlier task lands (precedent:
US-8.1 "Per-task gate"). A task is **gate-green** when, after its commit:

1. every test in its own Tests table passes (its runner);
2. every test that passed before the task still passes (both runners; a spec that did not load because a later task's module is absent
   was not passing and is not counted);
3. `npx tsc --noEmit` (the body of `npm run lint`) reports **zero diagnostics outside the red list** and, inside the red list, only
   missing-symbol diagnostics (TS2307, TS2305, TS2339, TS2353, and TS2322/TS2345 only where a later task creates the union member or
   parameter type). **The red list for a task is the set of spec files in the Tests tables of tasks that are not yet committed.**
   `npm run build` type-checks the same program (`angular.json` points at `tsconfig.json`, which includes every spec), so it cannot exit 0
   while a red-list spec has a missing-symbol diagnostic: until T46 it is judged by the same `tsc` rule, and from T46 `npm run lint` and
   `npm run build` must exit 0 outright (the only specs left on the red list are T47's, which compile clean);
4. `bash arch-guard.sh` exits 0 (no FROZEN file or checksum moves, so the baseline is unchanged);
5. `git diff` for the commit lists only the files in the task's Files table.

**Standing guard.** `test/image-studio-architecture.spec.ts` is formally on the red list until T47 (it is in T47's Tests table), but it passes on arrival, so gate item 2 binds it from T1. It (DD-28 a to g: Rules 1 and 2, NFR-1, NFR-2, NFR-4, NFR-14,
FR-7) asserts properties that must stay true from the first commit, so it is expected to pass on arrival and at every task. Its scans strip comments and match import statements, not prose. In particular, from the first file onward the
non-spec files under `src/utils/image-studio/` contain none of `window.`, `document.`, `indexedDB`, `localStorage`, `navigator.`,
`Date.now`, `new Date(`, `setTimeout(`, `setInterval(`, `Math.random`, `crypto.`, `alert(`, `confirm(` (every ambient effect goes through a
DD-15 port), and no file under `server/` other than `server/providers/gemini.js` imports `@google/genai`. A task that turns this spec red
has broken a design rule; that is a defect of the task, not an expected red-list failure. If the spec as written fails on a tree that has no studio
files yet, that is a finding for `so-test-writer`. T47 owns the file and lists it.

The full mechanical gate (`npm run lint`, `npm test` both runners, `npm run test:coverage`, `npm run build`, `bash arch-guard.sh`) is proved
only by QUALITY_GATE after T47. This convention is an interpretation of AGENTS.md section 6 for a tests-first branch; it changes no
threshold and skips no check. It is surfaced as open point O-1.

## Risk-first rationale

T1 is first because it is the one change every existing text path runs through: the shared catalogue feeds `findModel`, `defaultModel`,
`resolveSlot`, `clampLevel`, the tier fallback and `restore()` in both runtimes, and an image entry that reaches any of them throws or is
silently selected (plan DD-2, Impact Silent-failure risks 2 and 5, plan R3). T1 makes the server derivation image-blind **before** any image
entry exists, so the first behaviour-changing commit (T2, which adds the entries) cannot break a text path. T5 and T6 follow because
`createApp` is the only other edit to code that existing routes already depend on (plan R7); everything after them is additive. The plan's
one stated "might not hold" assumption, R12 (`AppComponent` may be too costly to instantiate for the FR-1 clear-all test), has an optional
Probe 0 up front (Reading guide), which is the only place it can be proved or broken while changing course is still cheap; if it is skipped
or negative, the escalation it triggers changes only the clear-all test in T46 and no earlier design. **v4:** T48 is last by id only because it was added after the rest was built; nothing in T1 to T47 depends on it. Its own risk (that the pin does not remove the conflict on the real route) is taken first inside T48: the builder proves a candidate on the real upload route before committing anything, and the planner already ruled out the cheaper alternatives the human rejected. The PLAN_REVIEW B-1 footer decision,
which v1 left undecided and unscheduled inside the last real task, is now made in plan v2 (DD-25), so T46 carries a narrowed STOP and no
undecided design item.

## Findings and open points for HUMAN_PLAN_APPROVAL

Nothing here resolves an Open Decision, edits the Specification or the plan, or grants a waiver.

- **O-1. Per-task gate convention.** The "red list" form of the gate (Reading guide) is an interpretation of AGENTS.md section 6 for a
  tests-first branch (US-8.1 precedent). It changes no threshold. A human who wants every commit to carry a full-green `npm test` must
  change the stage order, not this breakdown. (This is the plan's open item N-4; see below.)
- **O-2. Spec-file seams.** This breakdown asks `so-test-writer` to split three plan categories along task seams: the `createApp`
  composition tests (C4: T6 vs T18), the root-store tests (C7: T39 vs T40) and the generation-runner tests (C6: T33 vs T34, where T33's
  spec must contain no 410 and no `FILE_MISSING` case, so T34 never turns a T33 test red). If any of these is not honoured, the affected
  earlier task is judged by the existing suites and the later task owns the single file; this is a `so-test-writer`/`so-plan-reviewer`
  finding, not a reason to merge tasks. T1 no longer assumes a JSON module mock: its spec feeds synthetic lists to `textModelsOf` (P-16).
- **O-3. Tasks with no automated test.** T36, T37 and T38 are thin browser adapters that no runner can exercise (no IndexedDB, no canvas,
  plan R1/R2/W-2). Their acceptance is compile + build + a reading of the diff (T36 also the T47 scan for `alert(`/`confirm(`); the residual
  is stated in the plan and V-10 is the proposed human check. T35 is a single ignore entry that changes no behaviour. T47 edits no file.
  Every other task owns at least one failing test or, for the guard specs in T47, a stated reason it is green on arrival.
- **O-4. Evidence-file dependency.** The tasks bound to V-1 (T11), V-2 (T13, T34), V-3 (T2, T4, T14), V-4 (T5, T6), V-5 (T14), V-6 (T11),

  exists; nothing mechanical enforces that file (NFR-12). R15 applies. (This is the plan's open item N-3; see below.)
- **O-5. Largest tasks.** T11 (measure + trim), T39/T40 (store) and T45 (container) are the widest; each stays one track and one commit, and
  the store and composer were already split in two (T39/T40, T41/T42) for that reason. The v1 runner task was split into T33/T34 here
  (PLAN_REVIEW N-6). If `so-plan-reviewer` judges any task too large, the natural seam left is `measure.js` vs `trim.js`.
