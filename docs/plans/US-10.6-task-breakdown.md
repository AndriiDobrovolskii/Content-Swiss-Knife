## How "done" is read under the TDD gate

`TEST_WRITING` runs as a whole stage before the first task, so each task's tests already exist and fail when the task starts. A task is done when it is **gate-green** (below): the tests it names turn green without being weakened (AGENTS.md section 7.7), every test that was green before it is still green, and the type and build checks hold under the red-list rule. The full gate (`npm test` both runners, `npm run test:coverage`, `npm run lint`, `npm run build`, `bash arch-guard.sh`) is `QUALITY_GATE`'s.

Runner rule: `*.component.spec.ts` -> `npm run test:components` (`ng test`); every other spec, including `server/**` specs under `test/image-studio/`, store and service specs, -> `npm run test:logic` (`vitest run`). Spec names below follow the sibling-spec convention; `TEST_WRITING` confirms the exact names. A spec file with several owner tasks (for example `test/image-studio/wire-agreement.spec.ts`, `src/utils/image-studio/request-builder.spec.ts`, `src/services/image-studio/image-studio.store.generation.spec.ts`) gives each task its own top-level `describe` whose title ends with the task id; the task runs `npx vitest run <file> -t "\(T20\)"` (parentheses escaped).

**Characterization cases (review N-7).** A few listed cases cannot be observed failing first, because the code they pin already behaves that way: `turn-record.spec.ts` in T9 (the record spreads the whole turn already), the N-image cases of `apply-response.spec.ts` in T27 (`apply-response.ts` has no planned change), the `send-state.spec.ts` case in T26 if the task is dropped, and every row below marked "regression, unchanged". They are valid regression or characterization cases, not TDD-red evidence. `so-test-writer` labels each one (its `it` title ends with `[characterization]`) and reports it separately from the failing-first set; the task Tests tables mark them. A characterization case that is red when its task starts is a stop (`blocked_by_plan`), not something the task fixes.

**Existing assertions owned by a later task.** An assertion in the OD-16 table is owned by exactly one task (the "Task" column), and is red from `TEST_WRITING` until that task. Until then it is on the red list for gate check 2 below; it is selected by its OD-16 table row (it is a pre-existing top-level case, so the `-t "\(Tn\)"` describe-suffix convention does not find it). The new assertion text is `so-test-writer`'s and the owner approves it with the table; this breakdown does not write it. Concretely, `generate-handler.spec.ts` has two owners: T3 (price arity, counts unchanged) and T4 (the four pre-call rows); `image-studio-contract.spec.ts` has one (T2).

### Per-task gate (an interpretation of AGENTS.md sections 6 and 13; open point O-1 for the human)

This breakdown reuses, unchanged in substance, the convention the repository already adopted for tests-first branches (`docs/plans/US-10.1-task-breakdown.md`, "Per-task gate"; `docs/plans/US-10.5-task-breakdown.md`, "Per-task gate" and "Scoped component runs"). `tsconfig.json` includes `src/**/*` and `test/**/*`, and `ng build` and `tsc --noEmit` type-check every spec, so specs written at `TEST_WRITING` that import a later task's module are type errors until their owner task lands. "Lint and build green after every task" therefore cannot hold. A task is **gate-green** when, after its commit:

1. every case in its Tests table passes in the runner named;
2. every case that passed before still passes (logic runner whole; component runner via the positive-roots scoped tsconfig of the US-10.5 breakdown until the first component task, then whole);
3. `npx tsc --noEmit` has no diagnostic outside the **red list** (spec files and shared test helpers whose type owner is a task not yet committed) and, inside it, only missing-symbol classes (TS2307, TS2305, TS2724, TS2339, TS2551, TS2353, and TS2554 / TS2322 / TS2345 / TS2741 only where a later task adds the parameter or type);
4. `npm run build` reports no `NG####` template diagnostic and no error outside the red list;
5. `bash arch-guard.sh` exits 0;
6. `git diff` lists only the files in the task's Files table.

From the first commit at which every type-owner task is committed (expected T38) `npm run lint` and `npm run build` must exit 0 outright. This bends AGENTS.md section 13 on the commits before that point; approving this plan at `HUMAN_PLAN_APPROVAL` accepts that interpretation (the alternative is to re-plan with each spec written alongside its owner task, which a whole-stage `TEST_WRITING` does not allow).

## T7 - Add the slot runner and the pure result reducer

| | |
|---|---|
| **Track** | server |
| **Depends on** | T2 |
| **FROZEN (AGENTS.md §9)** | no |

### What changes

A new `server/image-studio/fan-out.js` holds (a) a slot runner that starts `granted` upstream calls together, each `runWithRetry(logged(generateImage))` with the shared `signal`, `sleep` and `log`, and classifies each result with the existing `classifyResponse` (unchanged) into `images | safety | text | failed` or a thrown error, and (b) a pure `reduceSlots` over the slot results (it also takes the requested N and the numeric unit price) that orders by slot index (not completion). **Units (plan 5.0).** A slot is one upstream call and is **successful when its outcome is `images`; its success unit is the `imageCount` that call carries** (the classifier's non-thought image parts, exactly the count the unchanged handler prices today), not 1. `parts` is the successful slots' parts concatenated in slot order, a slot's thought parts staying with it as in a one-image response. `succeeded` is the **sum of `imageCount` over the successful slots** (images; it can exceed `granted` or `requested` and is never clamped). `granted` is the number of slots (calls). `requested` is N (images). `costUsd` is the unit price times `succeeded`, the same expression as the handler's `price(model, resolution, succeeded)`.
