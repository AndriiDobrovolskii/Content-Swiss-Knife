## 4. Where the Story wording and the owner-ruled build differ (for the human gate; none is a loop-back by itself)

Each of these is backed by an owner ruling in Open Decisions v4, but the Story file was not revised, so the Story text and the build differ. This stage does not accept them as equivalent; it reports them so a human accepts them at the gate.

- **C-1 Cancel (Proposed FR-9 (c)).** Spec v4 FR-9 (c) says "Cancel keeps the images already returned and bills them". Owner ruling G-2 A (server fan-out) says Cancel discards the whole action, so FR-9 (c) does not hold. I checked the Story: **no Story AC says anything about Cancel** (AC-5 speaks only of failures), so there is no Story contradiction. Recommend a one-line note in the Specification when it is next revised.
- **C-2 AC-6 "Each attached image has a Product / Style ref selector".** SM-3 (i): the attached "Edit this" version shows NO selector and is Product. The Story's "each attached image" read literally includes the attached version. Tested as `SM-3 i: the attached "Edit this" version has no Product / Style ref button`.
- **C-3 AC-1 "creates a new version `v{N+1}`".** Built (OD-7, accepted under G-8): the next number after the session's highest, so `v{N+1}` only when `v{N}` is the latest; for a non-latest source the number is highest+1 and nothing is renumbered (tested: Upscale of v1 in a v1..v3 session creates v4). The Story literal would collide. The Story wording is the imprecise side here.
- **C-4 AC-4 "Each generated image counts as one generation".** Built (OD-5 (a), G-8): one limiter unit per upstream CALL that was granted, including a call that then fails (tested: 4 granted, 2 fail, 26 left, not 28), and a slot that returns two images is one unit billed as two images (plan 5.0). This can lock the operator out earlier than the number of images shown. The warning's `{n}` is `succeeded` (SM-9 i), not `granted`.
- **C-5 AC-10 "applies exactly like a registry preset".** A user preset's prompt is applied literally; a registry preset's `{product}` is substituted from the product-name field (OD-12 (b), accepted). Everything else (ratio, resolution, model only while there is no version, `presetId` on the wire, aria-pressed) is the same and tested.
- **C-6 SM-8 "still a counted request".** The ruling text says an unpriced (model, resolution) pair is "still a counted request, now checked before the paid call". The build checks the price BEFORE the limiter, so such a request consumes no limiter unit; the pinned test asserts exactly that (`tryConsumeUpTo` and `tryConsume` not called; the real limiter still grants 30). The Story's AC-14a ("rejected before any usage row is written") is satisfied either way. Whether "counted" was meant literally is an owner question (verifier F-2, T39 item 7); if it was, the check moves after the limiter and the four T4 handler rows and one fan-out row change.
- **C-7 AC-12 wording of the Image Studio row marker.** Story: "`taskLabel` starting with `image-studio|`, `mode` being null". - **C-8 AC-4 / AC-5 / AC-12 Story wording versus what was built, as asked.** AC-4: warning text, 2 images, only 2 billed, request not rejected as a whole, all as the Story states, plus the C-4 extension. AC-5: 2 successes shown, recorded cost for the 2, failure shown in `role="alert"`, as the Story states; the retry choice (after a partial result the composer gets its content back and `retry()` re-sends with a NEW turn id) is built but pinned by no committed test (T39 item 9).
