## Round 3: the corrected `uploadFile` tests against FR-16 / FR-21 / FR-60 (bodies read)

The AC-28 row is one corrected case (above); the other corrected cases are FR-only supporting rows in matrix v8 and carry no AC. I read all of them in
`test/gemini-image-provider.spec.ts` (lines 154-372) against `server/providers/gemini.js#uploadFile` and `server/image-studio/handlers.js#createUploadHandler`.

- **FR-16, single-shot upload, correct request shape: asserted.** Exactly one `files.upload` call (`uploadCalls` length 1) in the success case and in the FR-60 rethrow case;
  the SDK object is returned by reference; no `files.delete` and no leftover timer on an ordinary upload or an SDK failure. The mock's 404-on-truthy-`httpOptions` is a faithful
  copy of the behaviour the builder measured live against SDK 1.52.0 (pipeline_status T16 rework table: `{mimeType}` OK, `httpOptions: {timeout}` and `httpOptions: {}` 404), and
  a separate guard case pins the mock itself. A regression to the old `httpOptions` shape fails two tests (key present; mock 404).
- **FR-21, Cancel stops the in-flight upload at the provider: asserted, with a precise meaning.** Abort before the call: rejects with `AbortError`, zero `files.upload` calls, no
  timer. Abort during the call with an SDK promise that never settles: the provider promise is `rejected`/`AbortError` after `flush()` with NO clock advance, no HTTP `status`, no timer
  left. This does prove that Cancel now ends the provider's wait immediately (before the rework the SDK ignored `abortSignal` on the upload path, which the builder proved live: an
  already-aborted signal and a 1 ms timeout signal both uploaded). It does not prove that the HTTP transfer stops: the SDK call cannot be cancelled, so the provider races it and,
  when the upload completes later, deletes the object (`files.delete({ name })`, asserted for both the abort and the timeout case, plus "not deleted when the abort comes after a
  finished upload"). A late SDK rejection and a failing cleanup delete are swallowed (no `unhandledRejection`, real timers, asserted). The chain at the BFF is read as well:
  `abortOnEarlyClose` aborts the controller when the response closes early, the same signal is handed to `uploadFile`, and `runWithRetry` rethrows an abort instead of starting
  another wait (`upload-handler.spec` lines 190-215, both the backoff and the in-flight case). This meets FR-21's own wording ("Cancel aborts the upstream call ... a test with a stubbed Gemini asserts the abort signal reaches the stub") and its failure path ("if the abort is not honoured by the upstream, the client still returns to the editable state and ignores any late response"). It is a weaker guarantee than a cancelled transfer and the best the SDK allows; recorded as RC-7.
- **Where a client Cancel can reach an upload.** Only the FR-17 re-upload runs inside a generation user action, and it carries the runner's AbortSignal. An attach-time upload (the user attaches a file, before Send) has no Cancel button and no signal: `studio-composer.component.ts#runIngest` passes none, and FR-21 shows Cancel only "while a generation runs". Removing the attachment or switching session does not abort the in-flight request (verifier F-8, read here; with F-4 from round 2). That is consistent with FR-21 as written, not a violation.
- **FR-60, retry discipline: asserted at the right layer.** The provider is single-shot and rethrows the SDK error unchanged with its `status` (`toBe(failure)`, `withRetryMock` not called). The 1/2/4 s schedule, four attempts, no retry of a non-429 4xx and the abort-in-backoff case belong to the BFF loop and stay proven by `retry-loop.spec` and `upload-handler.spec` (both green this round). A status-less failure (the new `TimeoutError`) is retried by `runWithRetry` because it is not a 4xx; the loop's header states the policy (a timeout is "treated as a transient 5xx-class failure", plan choice P-3). FR-60 itself names only 429 and 5xx; retrying a status-less timeout is a plan decision, not a Specification line.
- **Test fidelity limit.** All of the above runs against a mocked `@google/genai` and fake timers. The mock matches the builder's one live probe; it is not a live test.

### F-8 against FR-14 / FR-15 / FR-16 / FR-21 / FR-22 / FR-60: a Specification silence, not an FR violation

- FR-14 and FR-15 concern thumbnails and keeping the other attachments on a rejection; neither mentions upload duration.
- FR-16 requires one image per request, the retry loop and taxonomy of FR-60 and FR-61, and, as its failure path, `Помилка API` (non-retryable) or T-7 with Retry (exhausted 429/5xx). It sets no timeout for an upload. After the rework a persistent status-less timeout ends, after about 4 x 100 s + 7 s, as a 502 `UPSTREAM_RETRIES_EXHAUSTED` (T-7 with Retry): the specified failure path, only late.
- FR-22's single 120 s deadline covers "the upload requests made after Send or Retry" and the FR-17 repeat. An attach-time upload is neither: it happens before Send. FR-21's "Cancel is valid at every moment ... an upload" is scoped to the user action of a generation. So neither FR obliges a client deadline or a Cancel for an attach-time upload.
- FR-60 applies the retry loop to the first upload and carves out no timeouts, so a retry after a `TimeoutError` is the specified loop plus plan choice P-3. The "once" of FR-16/AC-28 means one upload per image (no re-upload on every send), not "at most one SDK attempt". The double-upload risk is real (up to four overlapping transfers; best-effort delete of the extras, which the cleanup covers except for a failed delete, a never-settling SDK promise or a restart), but it arises from the combination of specified or planned choices and nothing in the Specification forbids it.
- Conclusion: **a missing client upload deadline is a Specification silence (and a robustness finding), not an FR violation and not a failed AC.** Whether to add a client deadline, stop retrying upload timeouts, or accept, is the human's call.

## The security review findings and F-4 against the FRs

The security review (v2) rated N-1..N-5 non-blocking and PASSED; that PASS is not human approval. I re-checked each against the Specification text; v2 re-reproduced N-1 (20 001 `countTokens` calls from one 1.06 MB request) and N-2, which does not change the judgement below:

- **N-3 (malformed JSON reaches Express' default HTML error page) vs FR-61:** not an FR violation as written, and not an AC failure. Reasoning:
  FR-61 says "every failure is answered in the `{ error: string }` envelope" and lists its outcomes, but its own last sentences state that an
  "Express-default non-JSON error (for example a 413 from `express.json`) is shown as the generic non-retryable error (FR-52)", and FR-52 names
  "Express's own non-JSON 413" explicitly; `error-dispatch.spec.ts` pins that fallback and the component FAILS table includes "502 without the
  error envelope". So the Specification itself anticipates framework-originated non-JSON answers on these routes and defines the client behaviour.
  `INVALID_REQUEST` (FR-61/FR-27) is defined as body-validation failure, and FR-27 places the body parser before validation; a parser SyntaxError is
  not a validation outcome. The real client always serialises its own JSON, so no AC path reaches it, and the client shows `Помилка API` (non-retryable)
  if it ever does. What remains is a hardening gap, not a requirement: a closed-code envelope for every non-200 is not guaranteed, and the stack-trace
  exposure depends on `NODE_ENV`, which nothing in the repo sets (unverified). Open gap for the human (suggest a route-scoped error middleware mapping
  parser errors to `INVALID_REQUEST`), non-blocking.
- **N-1 (unbounded history, `countTokens` before the limiter) vs FR-27/FR-66:** the implementation follows the specified order exactly (verified:
  `tryConsume` called once after the last count call and before `generate`; `countTokens` is expressly "not counted" in FR-66; FR-27 allows but does not
  require a read-only pre-check). The Specification sets no cap on history turns, so nothing is violated; it is a Specification gap that needs a
  decision (a turn cap and/or a pre-check). Also noted: FR-66's failure path says the 429 causes "zero upstream calls", while FR-27's order means the
  31st request still spends k+1 `countTokens` calls; the test asserts only zero `generateImage` calls. The v2 re-reproduction confirms the amplification is real and that the implementation matches FR-27's order and FR-66's "`countTokens` is not counted"; the Specification sets no history-turn cap, so this is an **open specification gap for the human**, not a genuine FR/AC failure and not an
  IMPLEMENTATION loop. Non-blocking.
- **N-2 (client-chosen `fileUri`/MIME/`inlineData` reach Gemini unvalidated):** not a violation. FR-9 requires the magic-byte check at endpoints that receive
  user-supplied image bytes (the upload endpoint carries them; `/generate` carries references and generated versions), FR-35 requires pass-through, and OD-40
  records that a direct API call bypasses the client rules. Hardening only; the v2 re-reproduction shows the unvalidated values do reach Gemini, which is what FR-35 pass-through specifies, so N-2 is an open hardening decision for the human, not an FR/AC failure. Non-blocking.
- **N-4 (upload not rate-limited, no BFF decoded-size cap) and N-5 (IPv6 rotation, `trust proxy` hop count):** FR-16/FR-66 say uploads are not counted;
  FR-9/OD-40 accept no BFF size check; FR-67 lists IPv6 rotation as an accepted limitation; A-2 is a named assumption. Not violations.
- **N-4 strengthened (security_review v3, D-3) and F-8, round 3:** the review now recommends N-4 before merge: `/upload` has no limiter and no decoded-size cap, and with the working upload a timed-out attempt cannot be cancelled while the retry loop starts the next, so one anonymous request can hold up to four overlapping copies of the same bytes for about 407 s (an estimate of about 140 MiB at the 30 MiB body limit, not measured). Against the FRs this is still **not a violation**: FR-16 and FR-66 say uploads are not counted; the Specification sets no decoded-size cap at the BFF (FR-9 / FR-12 / OD-40 explicitly accept that a direct API call bypasses the 5 MB bound), and FR-60 applies the retry loop to uploads. It is a Specification gap whose cheap closures (a BFF decoded-size cap, a per-IP upload budget, not retrying an upload `TimeoutError`) each need a human decision, because each adds or changes a requirement. N-1 and N-2: judgments unchanged (N-1 a Specification gap: no cap on history turns, FR-27 order followed; N-2 hardening only: FR-35 requires pass-through, FR-9 limits the magic-byte check to the upload endpoint). Non-blocking.

  changed, so the finished upload's `fileUri` is dropped and the old session keeps an `uploading` attachment; no test covers it). It does not violate FR-14
