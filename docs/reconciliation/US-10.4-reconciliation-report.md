## Findings

All non-blocking.

- **R1: `FR-16 met: YES` is defensible only under a stated reading, and the line is mislabelled.** The owner's ruling does not waive the Story: Story v4 line 42 itself defines the AC-6a test as "no content clipped so that it becomes unreachable", and the measurements show (a) = 0 everywhere and nothing new against the 640 px baseline. Under that definition AC-6a is met and the YES is justified. But (i) the approved Specification's FR-16 carries a stricter parenthetical that the measurements do not meet (in-component horizontal scrolls in 10 of 13 modes), the Specification and Story were not amended, and FR-16 states it "is not softened"; (ii) the first `FR-16 met: YES` (gate 1, line 104) was written before any rail existed, on the phase-1 proxy, and the same paragraph says the file records "the owner's reading of U-1 and the phase-1 outcome, not a completed FR-16 measurement", so the line contradicts its own surrounding text; (iii) the gate-2 line is qualified ("under the owner's ruling on U-1"), and the final `FR-16 fit summary` is correct and honest ("met under the product owner's ruling on U-1; under the strict reading it is met except for the pre-existing in-component scrolls"). Verdict on the wording: not a false claim, because every instance carries the U-1 qualifier, but the bare token `YES` overstates what was measured. The accurate label is "AC-6a met; FR-16 met under the owner's reading of U-1; the strict reading is met except for pre-existing in-component scrolls". Recommended for the human gate: confirm the owner's reading in writing in a place a reviewer can find (an Open Decision entry or a Specification amendment), and treat the PR text accordingly. This stage does not edit the evidence file or the Specification.
- **R2: tooltip fix recorded outside the approved artifacts.** See item 1 above. The PR description must carry the exception; the permission should be copied into the decisions log or an amendment, not live only in the evidence file.
- **R3: E's FR-16 marker check accepts any text.** `^FR-16 met: .+$` would pass `FR-16 met: NO`. It does not misreport this Story, but it means AC-9's automated check cannot protect the FR-16 verdict. Test-quality note, not a criterion failure; a stricter pin would be a TEST_WRITING decision.
- **R4: T9 `app.component.ts` edit** not in the T9 file table; plan-sanctioned (verification N1).
- **R5: pixel and layout criteria rest on manual evidence only.** AC-3 widths in px, AC-4b "to the right", AC-4d adjacency, AC-5, AC-6, AC-6a have no automated assertion on rendered output; W pins are source-level (the matrix says so). FR-19 asks each check for raw output or a pointer: the FR-13/14/15/11 sections have raw tables; the final `FR-16 fit summary` re-measurement on the T9 build (52 cells at 768 and 52 at 720) is given as prose with per-mode counts and no raw table. The earlier phase-2 raw tables are on `6ac207a`, whose layout classes T9 did not change (T9 rewrote class strings and colours). This is a small FR-19 shortfall for the final build's fit claim.
- **R6: measurement independence.** The "external executor" of T1, T2, T7, T8, T10 is the same model that built the change, run in the user's browser. The numbers are raw computed values and reproducible, but they are not an independent human check.
- **R7: hygiene before the PR (from verification N4).** The six spec files, the evidence file and the US-10.4 docs are uncommitted, so commits T3 to T9 lack their tests; `.tmp.driveupload/` is untracked and must not be committed.
