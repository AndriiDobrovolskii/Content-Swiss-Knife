## R-2 - resolved (FR-17, FR-18, FR-19, FR-20)

- **Log.** FR-17 step 1 captures stdout and stderr of the real `node server/index.js` (spare `PORT`, recorded pid) to one file in the scratchpad / OS temp directory outside the repository; step 6 stops the process by pid and deletes the log; step 3 keeps only match counts (matching lines only after the NFR-3 secret search). Clear.
- **Object identification and deletion.** Step 4 derives `files/<id>` from the `fileUri` suffix and forbids deleting or claiming anything by listing, prefix, age or count (the Files API listing is project-wide and the key is shared). I checked the route against `server/providers/gemini.js`: the route answers only `{ fileUri, mimeType }`, the only provider delete is `this.ai.files.delete({ name })` for a lost race, and `server/index.js` calls `dotenv` `config()` and honours `PORT`. Step 5 is a stdin script (`node --input-type=module -`, no file in the repository) run from the repository root that loads the key with `dotenv`, builds the client like `gemini.js`, calls `ai.files.delete({ name })` then `ai.files.get({ name })`, and prints only the delete outcome and the follow-up status. The key, client configuration and environment are never printed. Executable and safe (see NB-2 for the status wording).
- **Transient failures** (my v1 NB-6) are handled: `UND_ERR_INVALID_ARG` is a defect and never retried; a transient 429/timeout/network cause is "not verified" with exactly one re-run, both runs recorded; FR-22 correctly has no retry.

The Specification allows exactly one correction (regenerate the scratch lockfile and reinstall), recorded, otherwise "not measured". The real repository's `package.json`, `package-lock.json` and the nested copy are checked before and after.
- **Key handling for the scratch run** - judged under AGENTS.md section 7 item 2 in NB-1. Short answer: acceptable, not a hard-coded or committed secret, but it widens OD-7 and the human should see it explicitly.

## Non-blocking findings

- **NB-1 (note for the human: `--env-file` key handling in FR-18, folded into OD-7).** Judged against AGENTS.md section 7 item 2 ("hardcoded secrets ... in code, tests, fixtures, or a committed `.env`; never log an API key") and section 3 rule 4: it is acceptable. The key is not hard-coded, not copied into the scratch tree, not committed, not printed, and the path (not the value) is the only thing visible in a process listing; an already-set environment variable wins over the file; the scratch directory and log are deleted. It is also a real widening of OD-7, which asks only "who runs the live check, with which key". Two things the human should see explicitly: (a) `node --env-file=<repo .env>` loads the **whole** `.env` (every provider key, not only `GEMINI_API_KEY`) into a process that runs a **freshly installed scratch dependency tree** (possibly with a regenerated lockfile, native build and install lifecycle scripts) rather than the reviewed tree; (b) the least-privilege alternative the Specification already names, the human exporting only `GEMINI_API_KEY` in their own shell for that run, avoids both. Recommendation: it should be a separate Open Decision (a new entry, for example OD-18, "how the key reaches the scratch run: `--env-file` of the whole `.env` vs only `GEMINI_API_KEY` exported by the human"), recorded by `so-clarifier`, rather than living inside OD-7's default. It does not block this PASS, because the Specification labels it a PROPOSED DEFAULT, shows it in the OD-7 row of the Open questions table and in FR-18, and nothing is decided silently.
- **NB-2 (FR-17 step 5 pass wording).** "the follow-up `get` fails with the API's not-found answer" assumes a 404. The Gemini Files API may answer a deleted or foreign object with a different client-error status (I recall 403 "does not exist or you do not have permission", unverified here, no live call made). Suggest the pass condition read "the follow-up `get` fails with an API error for a missing object, status and message recorded verbatim" so the runner is not stuck on the exact code. Not blocking: the verbatim recording is already required.
- **NB-3 (FR-7 message vs single-cause attribution).** FR-7 says its message names the Pinned Node "or states that `.nvmrc` is unavailable". On the unchanged tree that sentence could be read as naming a second cause (C1) next to C4, against the definition "names exactly one cause". The test author should word it as context, not as a cause, or the TEST_WRITING table should classify it as C4 only.
- **NB-4 (FR-22 README exclusion vs the "reads or loads" definition).** `test/active-docs-models.spec.ts` (run by `test:logic`) asserts on `README.md` and `AGENTS.md`, so those are files `test:logic` reads, yet FR-22 says README writes do not restart the series. Practically harmless because FR-24's README edit happens during IMPLEMENTATION before the series and the gate (FR-21) re-runs everything, but the plan should schedule the README edit before the ten-run series starts, or the text should justify the exclusion.
- **NB-5 (Open Decisions log not in step with the Specification).** OD-17 in `docs/decisions/US-10.2-open-decisions.md` v2 still says the count restarts "after any change to the tree"; the Specification (as I asked in R-3) narrows this to the relevant change set. OD-7 in the log does not mention `--env-file`. A human reading the log alone sees the older defaults; the Specification's Open questions table is the accurate view. I did not change either document. The orchestrator or `so-clarifier` can sync the log; the human should be told at the gate.
- **NB-6 (AC-12 checkers are required by the Specification, not by the skills).** `so-reconciliation-reviewer` and `so-pr-preparer` do not mention the `evidence` type in their skill text. The check only binds if the plan carries a task with the existence-and-conformance acceptance check, and the AC ↔ test matrix has an explicit AC-12 row (a manual-inspection row), which FR-20 already asks for.
