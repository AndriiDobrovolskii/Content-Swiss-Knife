## 3. Requested assessments

### 3.1 Request validation: `imageCount` contract and bounds

- `imageCountSchema = z.number().refine(c => contract.imageCounts.includes(c))` (`request-schema.js:56`) accepts only the numbers 1, 2, 4. A string `"4"`, `NaN`, `Infinity`, a fraction, 0, 3, 8 or a negative value gives 400 `INVALID_REQUEST`. The set comes from the shared JSON, so client and server cannot drift. A second guard sits in `tryConsumeUpTo` (`Number.isInteger(n) && n >= 1`, else grants 0). The handler routes `requested === 1` to the unchanged `tryConsume` and anything else to `tryConsumeUpTo`, so there is no path on which an unvalidated N reaches `Array.from({length: granted})` (`fan-out.js`): `granted` is `min(remaining, n)` with n in {2,4}.
- Body bound: the 30 MB `Content-Length` gate and the 18 MB history trim are unchanged and run before the limiter. The request side is not widened (`imageCount` adds a few bytes). Two things do scale with N and are in NB-1: upstream request egress and response size.

### 3.2 Limiter: atomic partial grant, keying, bypass and exhaustion

- Atomicity: `tryConsumeUpTo` has no `await` between reading `remaining` and writing `entry.count` (`rate-limiter.js`), and Node runs it to completion, so concurrent requests cannot take a key past 30. A request for 4 with 2 left gets 2, the 2 are counted, the window start is untouched; a zero grant neither counts nor moves the window. Granted units are counted exactly like `tryConsume` units (same map, key, window).
- Bypass: none found. Units consumed per request equal the number of upstream calls fanned out (`granted`), so the 30/hour ceiling is a ceiling on paid calls per key, not on requests. Splitting into more requests, or mixing `imageCount` 1 and 4, consumes from the same counter. `imageCount: 1` is the old path.
- Retry accounting is unchanged in kind: one unit covers a slot and its up to 4 attempts (`DD-8`, outside the loop). So a key can generate at most 30 slots x 4 attempts of upstream calls per hour, the same ratio as before.
- Keying: `req.ip` with `trust proxy` = 1 (`app.js`). Safe behind the single Railway hop the file documents. If the proxy were exposed directly with no hop in front, a client could forge `X-Forwarded-For` and mint a fresh key per request; that is pre-existing, documented in `app.js`, and not affected by this change (see O-1).
- Exhausting it for others: the pool is per IP, so a client cannot drain another IP's quota. Users behind one shared IP (office NAT) do share 30 units, and a 4-image request burns 4, so a shared pool empties faster than under US-10.1. That is the accepted per-IP design, not a new cross-user vector.

### 3.3 Pre-call price check

`priceOrRefuse(price, log, model, resolution, 1)` runs after body validation and the key check and before `getGemini`, the token count, the limiter and every generate call (`handlers.js:177-181`). An unpriced (model, resolution) pair, including a free-text `model` (the schema allows any string) or Flash at 4K, answers the existing closed 500 `PRICE_NOT_CONFIGURED` with no unit consumed and no paid call. `getImagePrice` requires both keys by `Object.hasOwn` (no prototype-key bypass, no model-only fallback). The post-call lookups (`handlers.js:250-252`) use the same pair, so they cannot throw after money was spent. Good: this closes the old gap where an unpriced pair was only discovered after a paid call.

### 3.4 Presets in `localStorage`

- `createBrowserUserPresetStorage` wraps every access in `try/catch`; `JSON.parse` failure gives `{ok:false}` and leaves the text in place (`browser-ports.ts`). `parseStoredPresets` is all-or-nothing: not an array, a non-object, a missing/mistyped field, an `id` that fails `^[a-z0-9][a-z0-9-]{0,63}$` or does not start with `user-`, or a duplicate id rejects the whole list (`user-presets.ts:114-140`). A prototype-pollution shape (`__proto__`) is not read because fields are copied by name.
- id into `taskLabel`: the id is generated (`user-<base36 clock>[-n]`), never taken from the typed name, and validated on load, so it contains no `|`. The server independently enforces the same regex on `presetId` (`request-schema.js:24, 62`), so a forged request cannot put a delimiter into `image-studio|<id>|<res>` either. The spend reader matches on the `image-studio|` prefix only (`spend.ts`), and cannot be fooled by the middle segment.
- Names render only through interpolation / attribute binding (section 2.2). No `bypassSecurityTrust*`, no `innerHTML`.
- A stored preset is same-origin data; a party able to write it already has script execution, so this is hardening, not an injection vector. See NB-4 for the load-time caps that are not enforced.

### 3.5 `GET /api/usage` consumer

`SpendService.refresh()` calls the existing `UsageService.fetch({from})` and sums client-side. The server side is unchanged and parameterised (`queryUsage` uses named bound parameters). Rows are metadata only. The consumer treats the data as numbers/strings with no HTML sink (the header shows `formatMoney` output through interpolation). See O-3.

## 4. Findings

Severity: Blocking = secret escape, bypass reaching the sanitizer, fetched page in `systemBlocks`. None found.

### Non-blocking

**NB-1. N parallel 4K Pro calls amplify memory and egress per request; no response-size or in-flight bound.** `server/image-studio/handlers.js:225-231` (fan-out), `:266` (`res.status(200).json(responseBody)`), `server/image-studio/classify-response.js` (returns whole parts, thought parts kept).
- The verifier's figure holds: one 4K Pro part is about 18.3 MB of JSON (about 8.1 MB base64 image + about 10.2 MB `thoughtSignature`, `docs/evidence/US-10.6-vendor-facts-evidence.md` E2). With `imageCount` 4 the server holds four such responses (SDK buffer, parsed object, base64 strings) and `res.json` builds one string of roughly 70-73 MB, so a single request can transiently need a few hundred MB. The browser must also parse and persist that response.
- Egress also scales: each of the N calls sends the same trimmed `contents` (up to about 18 MB, hard 30 MB body cap), so a 4-image request can put up to about 4x that upstream.
- Why not blocking: the limiter caps paid calls per IP at 30 per hour, so the aggregate worst case per IP (30 parallel calls) is the same as before this change (30 parallel one-image requests). What is new is the shape: one request now carries up to 4x the memory and a 70 MB response, and nothing bounds in-flight work per process. There is no authentication, so any caller who can reach the proxy (CORS does not stop non-browser clients) can drive it; several IPs multiply it. Not measured here.
- Recommendation (hardening, no code edited): an in-flight cap per process for generate calls (a small semaphore); and/or limit `imageCount` to 2 for `gemini-3-pro-image` at 4K; and/or measure peak RSS on a 4K Pro `imageCount` 4 request during the T40 live smoke and record it. Decide in the plan.

**NB-2. A cancelled or disconnected batch is paid and counted but leaves no usage row.** `handlers.js:235` (`if (signal.aborted) return;`) and `abortOnEarlyClose`.
- Rule G-2 (cancel discards the action, no row) pre-dates this Story, but with N parallel calls, N upstream calls may already be started or finished when the client aborts. Their limiter units stay consumed (so the cap still holds) while no row is written, so the usage table and the new header spend under-report real vendor spend for that action. Also a client can use abort-after-dispatch to avoid the spend meter, though not the rate limit. Cost-observability gap, not a confidentiality or integrity one.
- Recommendation: decide whether rows for already-completed slots should be written on abort; if G-2 is kept, state in the spec that the spend figure is "recorded spend", not "billed spend".

**NB-3. Log volume scales with N slots.** `handlers.js:42-50`, `fan-out.js:59`. Each failing attempt of each slot writes one `logged()` line (up to 4 slots x 4 attempts = 16 lines per request, each at most 300 characters after `redact`). Content is safe (status + redacted, truncated error description; no prompt or bytes). Only a volume amplification. Hardening: none required; consider logging once per slot.

**NB-4. Stored presets are not capped on load.** `src/utils/image-studio/user-presets.ts:114-140`. The 60-character name cap and the 30-preset cap are enforced on `createUserPreset` only; `parseStoredPresets` accepts any-length `name`, `prompt` and any number of presets, and does not validate `aspectRatio` against the contract. Effects stay local: names render escaped; a bad `aspectRatio` is rejected by the server enum (400); `model` / `resolution` go through `checkUserPresetForApply` and the catalogue; `id` is regex-bound. Worst case is a bloated or odd preset row in the user's own browser, writable only by a script already running on the origin. Hardening: apply the same caps and the `aspectRatio` enum in `isWellFormed`, and treat an over-cap list as `{ok:false}`.

### Observations (pre-existing or untouched)

- **O-1.** `req.ip` keying relies on `trust proxy` = 1 matching exactly one hop. If the proxy is ever exposed directly, `X-Forwarded-For` can be forged to mint rate-limit keys, and the per-key cost cap stops being a cap (with up to 4 paid calls per unit-request). Pre-existing, documented in `server/app.js`; not changed.
- **O-2.** `server/index.js` `cors()` allow-list and the global 50 MB JSON parsers are unchanged; the image routes keep the 30 MB `Content-Length` gate.
- **O-3.** `GET /api/usage` is unauthenticated and returns every provider's rows (metadata only: tokens, cost, model, labels, product names). The new consumer fetches the whole month on open and after each image-ending action and filters client-side (OD-3 a); the payload grows with monthly row count and has no `limit`. Server code is untouched. Pre-existing exposure; the consumer adds a request but no new data.
- **O-4.** `model` in the generate request is `z.string()`; only the price check and the catalogue lookup bound it. Unknown models are now refused before any upstream call (improvement).
