### Is the hoisted 7.28.0 reachable from `server/` at runtime?

- `@angular/build` and `@angular/cli` are listed under `dependencies` in `package.json` (not `devDependencies`), which is why `npm audit --omit=dev` still counts them. They are build and CLI tooling for the Angular client (`ng build`, `ng serve`, the test build inside `test/security.spec.ts`).
- `grep -rn "@angular" server` returns nothing; no `server/` file imports `undici` directly (`grep` for `from 'undici'` / `require('undici')` over `server` and `src` returns nothing); the only `cheerio` import is `server/retrieval/fetcher.js` line 2, which resolves to the nested 7.30.1 through Node's resolution. Node's resolution gives `server/retrieval/fetcher.js` -> `cheerio` -> its nested `undici`, never the hoisted copy.
- Conclusion: 7.28.0 is a build-time / CLI-time dependency; the Express proxy at runtime never loads it. It would be loaded only by `ng`/`vite` tooling on a developer or CI machine. Caveat: because `@angular/build` sits in `dependencies`, a production `npm ci --omit=dev` still installs it (present on disk, not loaded). That placement is pre-existing and outside this Story.
- node-gyp's 6.27.0 is reachable only during native-module builds at install time (npm internals); not at server runtime.

Result: supply chain **clear**; the diff reduces the advisory exposure relative to the base.

## 2. Retrieval fetcher exposure (`server/retrieval/fetcher.js`)

`server/retrieval/fetcher.js` is the only `server/` user of cheerio (`cheerio.load(html)` at line 141 on a string; it never calls cheerio's network helper), and everything on the wire goes through the global `fetch` (line 22: `redirect: 'follow'`, `AbortSignal.timeout`; Jina fallback line 43 with an optional `Bearer` header from `JINA_API_KEY`). The file is **unchanged**. What changed is which copy of undici installs itself as the process-wide dispatcher when cheerio is imported: 7.24.4 before, 7.30.1 now. Exposure statement:

- Untrusted pages from Serper, redirect-following, no private-address check and no response-size cap before the 12 000-character cut: **unchanged** (pre-existing, US-10.1 O-7).
- The advisories reachable through that fetch path (unbounded decompression `GHSA-3xpg`, excessive content-encodings DoS `GHSA-xjj6`, TLS-renegotiation DoS `GHSA-qrxm`, cross-origin-redirect cache items) applied to 7.24.4 and are fixed in 7.30.1 (7.30.1 matches none of the 23 ranges): **exposure reduced** for that path.
- No new URL, header, redirect rule or prompt placement is introduced: fetched content still enters the prompt as before, and nothing here touches `systemBlocks`.

## 3. The `engines` / `.nvmrc` pin

- `engines.node` is the exact string `24.22.2` and `.nvmrc` contains `24.22.2`; `README.md` names it. `.npmrc` contains only `node-options=--report-on-fatalerror --report-directory=.diagnostics`; there is **no `engine-strict`**, so the pin is advisory: npm prints a warning on a different Node, and does not refuse. No Dockerfile, Railway, nixpacks, Procfile or CI workflow is tracked, so the production Node is not known from the repository (OD-9, open for HUMAN_PR_APPROVAL).
- Effect of a mismatch: the dispatcher/bundled-undici skew returns and the Files API upload answers 502 (`UPSTREAM_RETRIES_EXHAUSTED`). That is an **availability** failure of image upload; it exposes no secret and reaches no sanitizer or prompt path. The guard spec `test/undici-pin.spec.ts` fails (does not skip) on a Node that differs from `.nvmrc`, which protects developer and CI machines but not a production host.
- No behaviour change at runtime from the pin itself: it adds no code path.

**`node --env-file=<repo .env>` into a scratch tree (accepted risk, OD-7 / H decisions).** E3 started a scratch copy of the tracked files, ran `npm install` (no key in that command's environment, see pipeline status line 1053, block 1) and then started the scratch server with `node --env-file=<repo .env>` (block 2), which loads **all** provider keys (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `SERPER_API_KEY`, `GEMINI_API_KEY`, and `JINA_API_KEY` if set) into a process executing code from a freshly installed tree. Assessment of the residual risk:
- Install-time lifecycle scripts ran **without** the keys in the environment (the key was introduced only for the later server process), so a hostile install script could not read them.
- At runtime the scratch server executed whatever the scratch tree contained. That tree started from the committed lockfile (integrity-pinned), but E3 deliberately ran `npm dedupe` once (changed 23 packages in the scratch tree, including node-gyp's nested undici 6.27.0 -> 6.29.1), so its content was not byte-identical to the committed lockfile. The packages are registry-signed (the real tree verifies 712 of 712 signatures) and the run was one request, so the exposure window was small, but it is a real if low residual: code from a tree that differs from the reviewed lockfile held all provider keys for the length of the run. The human accepted it (OD-7 and the H decisions recorded in `history.jsonl`). **Observation, no action required for this Story**; a stricter pattern for a future live check is to pass only the one needed key (`GEMINI_API_KEY`) rather than the whole `.env`.

## Why PASS

The skill's blocking class is: a secret can escape the server; content that never passed the generation pipeline reaches the sanitizer bypass; a fetched page reaches `systemBlocks`. None occurs: the diff has no `src/` or `server/` change, adds no secret path, no sanitizer path and no prompt path. The lockfile entry matches the registry in integrity and tarball, adds no install script and no package, and moves only the cheerio-scoped undici to a release that none of the 23 current undici advisories matches, which reduces the exposure that US-10.1 D-1 had accepted. Two non-blocking items remain: the advisory-only Node pin (availability, production Node unknown) and the broad `--env-file` use in the T3 scratch run (accepted, nothing left behind).
