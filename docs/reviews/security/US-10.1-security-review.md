### D-2 `GeminiProvider.uploadFile` rework T16 (no secret path, no confused deputy; one amplification caveat)

Read line by line and exercised with a probe (`C:\Users\works\AppData\Local\Temp\claude\C--Work-Content-Swiss-Knife\707092bf-3cd0-4fa5-a828-4d4f75581067\scratchpad\probe-upload.mjs`, stub `ai`, no network, no key). Real output:

```
1 abort -> AbortError
1 deleted [ 'files/late-1' ]
2 abort -> AbortError
2 unhandled []
3 pre-abort -> AbortError sdk calls 0
4 result { name: 'files/late-3' } deletes added 0
5 status 500
6 sdk args keys [ 'file', 'config' ] [ 'mimeType' ]
final unhandled []
```

- **Abort and timeout races.** Pre-aborted: no SDK call. Abort during the call: `AbortError` at once, no `status`, so `runWithRetry` rethrows because `signal.aborted`. Timeout: `TimeoutError` after `UPSTREAM_TIMEOUT_MS` (100 s), no `status`, so treated as transient and retried (D-3; the timeout path itself was read, not run, because it needs 100 s). A real SDK error keeps its `status` and is rethrown unchanged (probe 5).
- **Timers and listeners.** `clearTimeout` and `removeEventListener` run in a `finally` around the race; the listener is also `{ once: true }`. A later abort after success does not delete the returned file (probe 4).
- **Unhandled rejections.** The SDK promise is observed by the race and by the explicit `upload.then(ok, () => undefined)`; the cleanup is wrapped in `Promise.resolve().then(...).catch(() => undefined)`. A late SDK failure after an abort produced no `unhandledRejection` (probe 2).
- **Orphan delete: can a client cause deletion or leakage by name?** No. `files.delete({ name })` receives `file.name` from the SDK result of this very upload; the client supplies bytes and a MIME (magic-byte validated as PNG/JPEG/WEBP before this call) and never a name. No other route calls `files.delete`, so a client cannot make the server delete another object. Leaks that remain: a failed delete (swallowed by design), an SDK promise that never settles, a result with no `name`, or a restart; those objects expire on their own under the Files API retention.
- **Secrets.** The new error messages (`The operation was aborted`, `The upload did not finish within 100000 ms`) carry no key, URL or payload. Dropping `httpOptions`/`abortSignal` from the SDK call adds no header or field that could carry the key; log redaction (`handlers.js#redact`) is unchanged.
- **Cancel is now best-effort at the application level.** The SDK upload path ignores `abortSignal`, so an aborted or timed-out upload keeps transferring to Google in the background; the server stops waiting, not transferring. This is the root of D-3.

### D-3 Amplification: retried timed-out upload (verifier F-8) combined with N-4 (worse than in v2; still non-blocking; now recommended before merge)

Facts (read): `/upload` has no limiter and no decoded-size cap (N-4, `createUploadHandler` unchanged); `runWithRetry` makes up to 4 attempts, 1/2/4 s apart; each attempt builds `new Blob([bytes])`, which copies the decoded buffer; a timed-out attempt cannot be cancelled and continues in the background. So one anonymous request, while Google is slow or failing without an HTTP status, can hold up to four overlapping transfers of the same bytes for about 4 x 100 s + 7 s = 407 s, and there is no client-side deadline on an attach-time upload (verification_report F-8). At the permitted maximum (30 MiB body, about 22 MiB decoded) that is roughly one 30 MiB body string, one 22 MiB Buffer and four 22 MiB Blob copies, on the order of 140 MiB retained per request for the whole window (an estimate from the code, not measured); a handful of concurrent requests could exhaust a small instance, and every attempt that later succeeds adds a Files API object that must be deleted. In v2 the SDK call failed fast with a 404 (found by the live test), so this failure mode was not practically reachable; with the call now working it is, and the lack of cancellation makes it 4x worse than a design that aborts an attempt. It still needs an upstream slow or failing condition to multiply, so it is an availability and cost finding, not a secret, sanitizer or `systemBlocks` issue: **non-blocking**. Because both halves are cheap to close, **I now recommend N-4 before merge**: (a) reject a decoded size above about 5 MiB plus margin at the BFF (`INVALID_REQUEST`/413), bounding the multiplied footprint to roughly 20 MiB per request; (b) a per-IP budget or concurrency cap for `/upload`. Optionally do not retry a `TimeoutError` for uploads (or wait for the previous attempt to settle); that is the human's call per F-8.

## The five surfaces

### 1. Secret containment: CLEAR

- The only `GEMINI_API_KEY` read is `process.env.GEMINI_API_KEY` in `server/image-studio/routes.js` (`hasGeminiKey: () => Boolean(...)`, boolean only) and in `handlers.js#redact` (used to strip the key from log text). The key itself is held by the SDK inside `providers/gemini.js` (pre-existing construction); nothing in the new code serialises it.
- Response bodies: the closed vocabulary `{ error: <code> }` or `FIXED_API_ERROR`, plus success bodies built from `classifyResponse` output (`parts`, `text`, `reason` from a closed enum set) and `costUsd`/token counts. No config object, header, URL or request payload is echoed.
- Log lines: `[ImageStudio] <route> ... status=<int> detail=<redact(describeError(error))>` truncated to 300 characters, redacting the key and any `key=` query value. The other log line carries the model id only. No request body, prompt or image is logged. `call-log.js` is not touched. See O-4 for the verifier's prompt-echo question.
- Client: zero `GEMINI_API_KEY`/`AIza` in non-spec `src/`; the studio's texts name no environment variable (pinned by `test/security.spec.ts`, which also scans the built bundle, FR-65). `.env.example` is unchanged and needs no update: no new setting is introduced (the image model ids live in the catalogue, not in an env variable).
- No key in any added test, fixture or doc (key-shape grep over added lines found only the synthetic `AIzaSy...` strings inside the scanner's own non-vacuity test).

### 2. DomSanitizer bypass: CLEAR

- No new `bypassSecurityTrust*`; none in any studio file; `safe-html.pipe.ts`, `html-cleaner.ts`, `output-validator.ts` are not in the diff. The studio does not use the `safeHtml` pipe.
- What reaches the DOM in this change: (a) model text and the user's own text, rendered with `{{ }}` interpolation in `<p class="whitespace-pre-wrap">` (`image-studio.component.html`), so Angular escapes it; (b) images through `[src]`/`[attr.src]` set to `data:<mime>;base64,<data>` URLs. Angular's URL sanitizer rewrites a non-allow-listed data MIME (for example `image/svg+xml`) to `unsafe:`, and an `<img>` never executes script in any case. The studio opens no image in a navigable context (no `window.open`, no `<a href>` to a blob/data URL); the only exits are `file-saver` (Blob download) and `ClipboardItem('image/png')`; (c) `[alt]` from `buildAlt(prompt)` (a plain string, bound as an attribute value, so no HTML injection; code-point cut, no markup handling needed) and `attachment.fileName` (an `[alt]` binding, escaped).
- No object URLs are created by the studio (data URLs only), so there is no object-URL lifecycle to leak; the pre-existing `createObjectURL`/`revokeObjectURL` in `app.component.ts` (image-tools) is untouched.
- Part MIME is taken from the model response with only `startsWith('image/')` checked (server `classify-response.js`, client `schemas.ts`, `apply-response.ts`), and the strip casts it `as ImageMime`. This is bounded: a download or ZIP entry goes through `buildFileName`, which throws for anything but png/jpeg/webp, and a non-matching source is first transcoded through the canvas. Recorded as O-6, not a finding.

### 3. Untrusted HTML in the editor: CLEAR

`src/app/components/html-editor/` and `extensions/attr-helpers.ts` are untouched.

### 4. Prompt injection from retrieved pages: CLEAR (no retrieval)

- The studio imports no retrieval module (grep of `server/image-studio`, `src/services/image-studio`, `src/utils/image-studio`, `src/app/components/image-studio` for `retrieval|fetchUrl|serper`: only a comment line in `routes.js`; scan b of `image-studio-architecture.spec.ts` pins it). No fetched page reaches any Gemini call. `systemBlocks`/`PromptPayload` are not referenced and no `systemInstruction` is set (`gemini.js#generateImage` has none; FR-80).
- The residual surface specific to this Story is that user-supplied text and images (and, through re-use, earlier model output) form the model's input and the model's text comes back to the UI. An image carrying embedded instructions can steer the model; worst case is a wrong picture or reply text, rendered as escaped text. No action, no secret and no HTML path depends on it. Observation O-5.

### 5. The proxy: CORS, error surface, telemetry

- **CORS/ordering.** `createApp` mounts `cors()` before the image body limit, so the 411/413 carry CORS headers; CORS policy is the existing exact-match allow-list (`cors-policy.js`, unchanged, fail-closed). Note the pre-existing rule that a request with no `Origin` is allowed: the image routes are anonymous and not protected by CORS against non-browser callers. That raises the weight of N-1, N-2, N-4. Deployment, binding and origin handling are not changed by this Story.
- **Body limit.** `imageBodyLimit` rejects a non-GET/HEAD/OPTIONS request without a plain-integer `Content-Length` (411) and one over 30 MiB (413) before the 50 MB parser; the probe confirmed 411 for a chunked request. It checks the declared length only, but Node's HTTP parser bounds the real read to the declared length (and refuses conflicting framing), so a small declared length cannot carry a large body. A hostile client can still keep up to 30 MiB per request in flight with no concurrency cap (N-4).
- **Telemetry.** `usage-row.js` builds `provider='gemini'`, `model` (validated against the catalogue by `assertConsistent`/`findImageModel` before use), `taskLabel='image-studio|<presetId>|<resolution>'` (`presetId` constrained to `^[a-z0-9][a-z0-9-]{0,63}$`, `resolution` from a closed enum), token counts and cost. No prompt, no image, no fileUri, no text. `insertUsage` binds named parameters (`insertStmt.run({...})`), so no injection. No `usage_log` column is added. CLEAR.
- **Errors to the browser.** All handler paths answer a closed code or `FIXED_API_ERROR`; upstream text never reaches a response. One gap in the framework layer: N-3.

| N-5 | Non-blocking | Introduced | Limiter key is raw `req.ip`: IPv6 rotation, and an assumption (A-2) that nothing verifies |

### N-1: unbounded history and pre-limiter token counting (upstream amplification)

`request-schema.js` bounds neither the number of `history` turns nor parts per turn; only alternation and unique ids are checked. `handlers.js` runs `trimRequest` (one `countTokens` call per retained turn plus one for the new turn, each under the 4-attempt retry loop with 1/2/4 s backoff) **before** `limiter.tryConsume` (FR-27 fixes this order; FR-66 states `countTokens` is not counted). The size trim only reacts to bytes (18 MB), so tiny turns survive it. Probe: a 1.06 MB body with 20 000 one-character turns caused **20 001 upstream `countTokens` calls from one request**; at the 30 MiB cap that is on the order of 500 000. A rate-limited client is therefore never throttled on this work, and each call counts against the same Gemini key's quota that the rest of the product uses. A caller that keeps the connection open keeps the work running (it is aborted only when the response closes).
Reachability and impact (stated plainly): this is reachable **anonymously** (no credential, and CORS does not constrain a caller that sends no `Origin`, O-1), the work is done **before** the limiter is consulted, so the 30-per-hour limit never throttles it, and every `countTokens` call is made with the **shared** `GEMINI_API_KEY` that the rest of the product also uses, so it burns that key's request quota and can starve legitimate use (whether `countTokens` is billed was not verified; the quota and availability effect is the concern). A single request is enough; no volume of requests is needed.
Why non-blocking under the skill's severity table: no secret escapes, no unsanitised content reaches the sanitizer bypass, no fetched page reaches `systemBlocks`; it is an availability and quota-abuse path. Why this is not a pure IMPLEMENTATION fix: the order is specified (FR-27) and the spec sets no history cap, so closing it needs a spec decision (a maximum turn count enforced as `INVALID_REQUEST` before any upstream call, and/or charging the limiter before the count). Recommend recording that decision before merge and implementing a cap such as a few hundred turns (and/or a cheap synchronous limiter pre-check before the counts). The reconciliation report reaches the same conclusion (a Specification gap needing a human decision, not an IMPLEMENTATION-only fix).

### N-2: client-chosen `fileUri` / MIME / inline data reaches Gemini unvalidated

`partSchema` accepts any non-empty `fileData.fileUri` and `mimeType` and any non-empty `inlineData.mimeType`/`data` and passes them unmodified (FR-35, needed for `thoughtSignature` round-tripping). Consequences:
1. The BFF magic-byte gate (PNG/JPEG/WEBP, FR-9) exists only on `/upload`. A caller can skip it by sending `inlineData` (any MIME, any bytes, up to the 30 MiB body) straight to `/generate`.
2. `fileUri` is not checked to be a Files API URI of this key, nor bound to the session or caller. A client can name any URI the key's project can read (a Files API object uploaded by another visitor, if its name were known; the names are random, so enumeration is impractical, but nothing enforces ownership) and, depending on what the Gemini API accepts for `file_uri`, non-Files URIs (this review did not verify the vendor's current URI schemes; treat as unverified). The fetch is performed by Google, not by this server, so this is not an SSRF into the Railway network; it is anonymous use of the key to ingest arbitrary media outside the image-only and 5 MB rules.
3. `FILE_MISSING` detection is a boolean from request shape plus upstream status/message; the upstream message is never returned.
Recommend: in `request-schema.js` restrict `fileData.fileUri` to the Files API prefix of the Gemini endpoint (`https://generativelanguage.googleapis.com/v1beta/files/<id>`) and both `mimeType` fields to `image/png|jpeg|webp` for user-origin parts, leaving `thoughtSignature` and other passthrough fields alone. Cheap and does not touch the spec's passthrough intent. Cost exposure is otherwise bounded by the 30-requests-per-hour-per-IP limit on `/generate`.

### N-3: framework error page on malformed JSON

There is no error-handling middleware. A body that is not valid JSON makes `express.json` throw before any handler; Express' default handler answers `text/html` with the stack (probe: 400, `SyntaxError ... at C:\Work\Content-Swiss-Knife\node_modules\body-parser\...`). In production mode Express omits the stack, but nothing in the repo (no `NODE_ENV` in `server/`, `package.json` scripts or any deploy file present) sets it, so whether Railway runs with `NODE_ENV=production` is unverified. The same mechanism exists for every older route; this Story adds routes whose own contract (FR-61: every non-200 is `{ error: <closed code> }`) it breaks, and adds attacker-reachable ones. Recommend a route-scoped error middleware on `/api/image-studio` mapping parser errors to `INVALID_REQUEST` (400) without the stack.

On the reconciliation review's conclusion that this is not an FR-61 violation as written: **I agree.** FR-61's last sentence says an Express-default non-JSON error (its example is a 413 from `express.json`) is shown by the client as the generic non-retryable error (FR-52), so the Specification anticipates framework-originated non-JSON answers on these routes and `INVALID_REQUEST` is defined for body-validation failures, which a parser `SyntaxError` is not (FR-27 puts the parser before validation). My non-blocking rating never rested on an FR breach; it rests on the information-disclosure side (a stack trace with absolute server paths, whose presence depends on an unset `NODE_ENV`) and on attacker reachability. That residual is a hardening gap, not a requirement failure. This also protects the client, whose `errorField` parse falls back to a generic failure on an HTML body.

### N-4: upload route unthrottled, no BFF size or concurrency cap

`createUploadHandler` never consults the limiter (FR-66, by design). The 5 MB cap and the 2048 px rule are enforced only in the browser; the BFF accepts any base64 up to the 30 MiB body, decodes it into a `Buffer`, and uploads it to the Files API (retained there for the vendor's retention period) if it starts with a PNG/JPEG/WEBP signature. A looping anonymous caller can fill the Files API project storage or hold many 30 MiB buffers in memory at once. Recommend a decoded-size cap (about 5 MiB plus margin) returning `INVALID_REQUEST`/413 and either a separate limiter or a shared per-IP budget for uploads. v3: the T16 rework makes the retry of a timed-out upload run alongside the still-running earlier transfer (D-3), multiplying the memory and Files API traffic of one oversized request by up to 4 for about 407 s; this moves the recommendation to before merge.

### N-5: limiter key quality and an unverified assumption

`limiter.tryConsume(req.ip)`: (a) IPv6 clients can rotate within their /64 (billions of keys) and each fresh key gets a full 30-request window; the map then also grows and `sweep` is O(n) on every call, so many distinct keys make each request slower. Key IPv6 addresses by /64. (b) `trust proxy = 1` is correct only if exactly one trusted proxy appends the real client address. Behind Railway that is Specification assumption A-2; no check in the repository or the pre-implementation record verifies the hop count or that Railway appends rather than preserves a client `X-Forwarded-For`. If the assumption fails the effect is availability (everyone shares one bucket) rather than a bypass, except when the server is reached directly with no proxy (local `npm run server`), where the right-most `X-Forwarded-For` value is client-chosen and the limit can be evaded. Local-only; recorded for completeness.
