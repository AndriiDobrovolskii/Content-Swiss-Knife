## Re-verification of the v1 blocking findings

### B-1 (slot billing unit): RESOLVED

Checked against the code as it is:

- `server/image-studio/classify-response.js` `classifyResponse` returns `{ class: 'images', parts, imageCount }` where `imageCount = parts.filter(isValidImagePart).length` and `isValidImagePart` excludes `thought === true`. Only `candidates[0]` is read.
- `server/image-studio/handlers.js` line 211 prices `price(model, result.imageCount)`, writes one row at that cost and answers `costUsd` as the same number. This is the unit the unchanged handler uses.
- `test/image-studio/generate-handler.spec.ts` lines 220 to 233 pin it: two image parts give `price` called with `(FLASH, 2)` and `costUsd` about 0.06; a thought image plus a final image gives `(FLASH, 1)` and `parts` keeps the thought part.

Plan v2 section 5.0 defines the units explicitly (slot = one upstream call; `succeeded` = sum of the slots' `imageCount`; usage row = one successful call at `price(model, resolution, slot.imageCount)`; response `costUsd` = `price(model, resolution, succeeded)`; `granted` = calls; `requested` = images). That is the same rule the unchanged handler applies to its one call, so the pinned FR-70 and FR-84 cases hold with only the arity moving (plan 9.3 and breakdown OD-16 row owned by T3, "same counts"). Plan 5.2 steps 6 to 8, 3.2 (`batch` counters), 7.1 (`batch-outcome.ts` uses the same units), 9.2 and the traceability row for FR-9 all restate it consistently. Breakdown T7 (spec: a slot of two images has `imageCount` 2 and `succeeded` counts 2; a thought plus a final image counts 1 with the thought part kept), T8 (a slot of two image parts writes one row priced `price(model, resolution, 2)`; the response `costUsd` equals `price(model, resolution, succeeded)`), T9 (`succeeded` greater than `granted` parses; no ordering imposed on the counters), T15 (no clamping) and T23 carry the consequence. The earlier contradiction is gone: T8's acceptance check ("existing handler cases pass, only the arity changes") can now be met. The residual oddity (a call returning two images uses one limiter unit and bills two, so `succeeded` can exceed `granted` or `requested`) is stated, matches the existing behaviour and the pinned spec, and is covered by tests. Not a defect.

### B-2 (text-only slot cause): RESOLVED

The classifier's `text` class requires a non-thought text and `finishReason === 'STOP'` with no valid image part; anything else is `failed`. Plan v2 section 3.1 and 5.2 step 6 now map every non-success outcome into the closed list with no gap: `safety` to `safety`, `failed` to `empty`, `text` to `empty`, a file-missing error to `file_missing`, any other thrown error to `retries_exhausted`, in one function inside `fan-out.js`. The list gains no `text` member (FR-9 (a) enumerates four cause classes; the Specification's wording is respected, and the rejection is recorded in plan 15). The zero-image case is separately specified: the lowest-numbered slot's outcome is returned as a one-image request would return it, so an all-text batch still answers `kind: text` with no `batch`. The client side is real: `schemas.ts` today has `ImagesResponse` as a default `z.object` (no `batch`, so a server `batch` would be stripped silently, impact S2) and `parts` is refined to need at least one valid image part, which a mixed batch satisfies. T7 pins the five-outcome mapping table and the mixed case `failures: [{ cause: 'empty' }]`; T8 pins the 200 `images` answer billing only the image; T9 pins that the client's closed enum, read from the contract accessor, accepts every cause `reduceSlots` can produce. Complete.

## Non-blocking findings

- **N-1 (T7/T8, resolve the unit price lazily).** T7 says `reduceSlots` takes the unit price as a number and T8 says that number is `price(model, resolution, 1)`. If the handler computes it before `reduceSlots`, `price` is consulted on safety and text paths too. On the default path this is moot (T4's pre-call check consults `price` anyway and its four rows are rewritten). On the post-call branch that T8 Notes describe (T4 dropped), the unchanged rows at lines 240, 251 and 268 require `price` not to be consulted for a text or safety reply, and an eager call would fail them. Plan 5.2 step 8 does not need a separate unit price at all (row cost `price(..., slot.imageCount)`, response `price(..., succeeded)`). Suggest T7/T8 pass a price function, or compute `costUsd` after reduction, so it is called only when a slot succeeded.
- **N-2 (T3 acceptance wording).** "A grep shows no caller of `computeImageCost` or `getImagePrice` with the two-argument form" would match `generate-handler.spec.ts` line 285 (`pricing.computeImageCost('gemini-9-image', 1)`), inside a row T4 owns and which stays unchanged under a post-call ruling. The call still throws `PriceNotConfiguredError` (unknown model), so behaviour is fine. Scope the grep to non-spec product code.
- **N-3 (OD-16 over-claim).** Plan 9.3 and the breakdown add "the FR-27 order test" to the pre-call rows. The order test (lines 141 to 150) records `count`, `limiter`, `generate` in an `order` array; `price` is not in it and a pre-call price check does not reorder those three. The row will find nothing to change, and T39's "exactly the four T4 rows" may then not match literally. T4's text also says both "four" and "five" rows. Let TEST_WRITING confirm the table by reading the spec in full (the plan already says so); a new ordering case is additive.
- **N-4 (T31, plumbing detail).** Today `execute(session, buildInput, draftSnapshot)` derives `editOfVersion` and `inputFormat` from the draft snapshot (`draft.attachedVersion`, `draft.attachments`), not from `BuildInput`, `retry()` replays `retry.buildInput`, and `execute()` clears the composer text and restores it on failure. The plan says the derived action carries `editOfVersion` and `storedPrompt` through `BuildInput` and `execute()`, but `BuildInput` has neither field and T20 does not add one. The builder can solve this inside T31's store file, but `storedPrompt` must travel with the retry snapshot or a retried Upscale records an empty prompt, and a derived action must not discard unsent composer text. TEST_WRITING should add a retry-of-Upscale case and an unsent-text case.
- **N-5 (all-fail batch).** When no slot succeeds the lowest-numbered slot's outcome is returned, so the per-cause breakdown and failed count of FR-9 (a) (Proposed, OD-6) are not shown for an all-fail batch. Failure is shown and AC-5 holds; surface this to the owner with OD-6.
- **N-6 (carried from v1, unchanged).** N-2 sizing of T32, N-3 coupling of the component phase to SM-2 and the owner-supplied copy, N-5 (T39, T1, T40 are not deliverables), N-6 (the Per-task gate bends section 13, open point O-1), N-7 (characterization cases are now labelled in the breakdown), N-9 (vendor-fact timing deviation, G-1), N-11 (AC-10a hover is manual). None blocks.
- **N-7 (R-13 wording).** Under a post-call OD-15 ruling the exposure is N paid parallel calls with no record; the plan and breakdown now say so (R-13, T8 Notes). The owner should see this when ruling OD-15; it is not a plan defect.
