## Non-blocking findings

- **P3 re-entry has no marker (T9/T10).**
  - The breakdown has `so-builder` re-enter T9 when the executor records a failing light token value at T10, but the marker table has no line for it. The builder sees only that `EVIDENCE-COMPLETE: yes` is absent and cannot tell "waiting for the executor" from "re-enter T9".
  - Suggested: `TEST_WRITING`/OD-28 or the next planner revision adds a marker such as `LIGHT-VALUE-FAIL: <token>`. The prose rule "reads the failure record in the evidence file" works if the dispatch prompt says so.
  - A T10 failure other than a light value (FR-13 painting layer, FR-11 overlay geometry) has no stated route either. It would be recorded as not met and caught at `RECONCILIATION` (`changes_required` → `IMPLEMENTATION`).
- **Dispatch granularity.** `so-builder` says "one dispatch per task", while the breakdown says the builder is "dispatched for the whole `IMPLEMENTATION` stage" and works its tasks in order. The marker-then-`BLOCKED` rule works under either reading, but the dispatch prompt should state which one is used.
- **Expected `BLOCKED` holds.** `IMPLEMENTATION` will return `BLOCKED` at least at P1 (if T1/T2 are not done earlier), P2 and P3. `/so:status` will show `BLOCKED`, which "needs a human decision" in the vocabulary. The `blocking_issues` text should say "awaiting external evidence step Tn" so it is not mistaken for a defect, and `pipeline_status` should record the hold.
- **OD-29 timing (carried from v1, unchanged).** The Specification's wording has `ARCHITECTURE_PLANNING` measure the 1024 px fit "early". The plan did not, and the measurement stays at T1/T2 after plan approval, so a FAIL arrives after `TEST_WRITING` has spent its effort. Options for the human: run the no-code T1 measurement before approving (the breakdown allows it and already says T1 may be produced earlier), or reject to `ARCHITECTURE_PLANNING`. Note that if T1/T2 run before `TEST_WRITING`, the evidence slug is picked before OD-28 settles it. OD-28 should therefore be answered first, or the executor should use a slug that `TEST_WRITING` then adopts.
- **Gate verdict wording is now handled.** The baseline-relative pass rule (DD-12) is labelled "gate pass under the baseline rule", with `FR-16 met: NOT DETERMINED (U-1 pending product owner)` stated separately. U-1 itself still needs the product owner.
- **Plan text still says `lint` catches a missing `TRANSLATIONS` key (DD-3, DD-14 row 6).** The task breakdown corrects this (`ng build` and the component spec catch it), and the breakdown governs, but the plan text is inaccurate and could be fixed at the next plan revision.
- **The rail has no landmark name.** DD-3 leaves the `<nav>` without an `aria-label` because the FR-6 table has no copy for it. This is a product-copy question for the owner, and no string should be invented.
- **`TEST_WRITING` must carry the red-set rule.** It should record the by-design red set in `test_generation_report` so `QUALITY_GATE` and `so-builder` can tell by-design red from a regression, as the breakdown requires. The `so-test-writer` checklist line is worded for the ordinary case, and the breakdown, not the skill, is what authorises this exception.
- **`README.md` L127** ("at the bottom of the sidebar") stays true. Living docs are the archive stage's.
