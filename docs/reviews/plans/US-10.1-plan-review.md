## Focus point 6: does a scoped override satisfy "pin undici"?

Finding for the human, not a blocker (N-20). The recorded decision is only "pin undici, accepting the dependency change; version by live verification"; it does not say "direct dependency". The breakdown's paraphrase "pin undici in the dependencies" is the planner's wording, not the history's. A scoped override pins the one copy that the failure depends on (the copy `cheerio` loads, and so the process-wide dispatcher), changes only one new nested lock entry, adds no package and leaves `@angular/build` on its exact 7.28.0. The alternatives the breakdown rejects (direct dependency; global `overrides.undici`) are weighed with reasons, and the global form would break `@angular/build`'s exact pin. So the scoped form is consistent with, and the smallest reading of, the decision. What it is not: a top-level `undici` entry; `node_modules/undici` stays 7.28.0 and a future bare `import 'undici'` in `server/` would load the unpinned copy (guarded by case 6, deliberately). It does not contradict the recorded decision, so it does not block; the human should ratify the form when approving v4 (the history event does not mention it).
