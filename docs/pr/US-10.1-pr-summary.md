## What changed

Adds an Image Studio to the app: an operator uploads up to five product photos, describes the image in a chat with Gemini (Nano Banana, Flash or Pro), and refines the result through follow-up edits in the same session, then downloads, copies or ZIPs the versions. It adds the BFF routes `POST /api/image-studio/upload` and `POST /api/image-studio/generate` (single-shot Gemini image, Files API upload and `countTokens` methods; per-IP rate limit of 30 generations per hour; `Content-Length` body limit), the two image models in the shared catalogue, per-image pricing and a metadata-only usage row, and an Angular studio (composer, presets, version strip, session list, IndexedDB persistence for 7 days / 20 sessions) mounted lazily in `AppComponent`.

## Why

Operators currently go photo -> designer -> revisions to get a product visual. The Story replaces that loop with one tool and a multi-turn chat that keeps the context between edits. See `docs/stories/US-10.1-nano-banana-image-studio.md`.

## Security

0 blocking findings. Non-blocking, introduced by this change unless marked, **recommended before merge** where stated (`docs/reviews/security/US-10.1-security-review.md` v3; not softened here):

- **N-1 (recommended before merge; needs a SPEC decision, not an implementation-only fix).** `history` turns and parts are uncapped, and `countTokens` runs per turn before the rate limiter. Reproduced: one 1.06 MB anonymous request caused **20 001 upstream `countTokens` calls**; at the 30 MiB cap on the order of 500 000. They burn the shared `GEMINI_API_KEY` quota and the 30/hour limit never throttles them. FR-27 fixes the order and the spec sets no cap; FR-66's "zero upstream calls" wording is inconsistent with it.
- **N-2 (recommended before merge).** `fileData.fileUri`, both `mimeType`s and `inlineData` are forwarded to Gemini with no allow-list (verified by probe); the magic-byte gate exists only on `/upload`. FR-35 requires pass-through for `thoughtSignature`; restricting user-origin parts is small and compatible.
- **N-4, strengthened in v3 (recommended before merge).** `/upload` has no limiter and no decoded-size cap (a 15 MiB payload was accepted). With the working upload, a timed-out attempt cannot be cancelled while the retry loop starts the next, so one anonymous request can hold up to four overlapping transfers for about 407 s (about 140 MiB retained per request at the 30 MiB body limit, an estimate, not measured); a timed-out upload can double-upload (verifier F-8). Attach-time uploads have no client deadline or Cancel. Suggested: decoded-size cap about 5 MiB, a per-IP upload budget, and/or no retry of upload `TimeoutError`; each needs a human decision (the Specification is silent).
- **N-3.** Malformed JSON on the new routes returns Express' default HTML error page with a stack trace; whether Railway runs with `NODE_ENV=production` is unverified. Not an FR-61 violation as written.
- **N-5.** Limiter key is raw `req.ip`: IPv6 rotation within a /64 gets fresh buckets; `trust proxy = 1` rests on unverified assumption A-2; when reached directly (local), a client-chosen `X-Forwarded-For` selects the bucket.
- **F-8** (verifier): see N-4. **F-4:** a mid-upload session switch leaves a stuck `uploading` placeholder and drops the uploaded `fileUri`; removable by its x button.
- **D-1 (human-approved NFR-7 exception).** The scoped `overrides.cheerio.undici = 7.24.4` equals the `undici` bundled in Node v24.15.0, so the runtime fetch stack is unchanged, but relative to the hoisted 7.28.0 it **re-opens 7 advisories fixed in 7.28.0** (3 high: GHSA-vmh5-mc38-953g, GHSA-hm92-r4w5-c3mj, GHSA-vxpw-j846-p89q; 2 moderate; 2 low).
