## What changed

Image Studio gains seven capabilities. Each image tile has Upscale 4K and Variation actions; an Images selector (1, 2 or 4) makes one Generate press produce that many versions of one turn, by a server-side fan-out of N parallel single-image Gemini calls with a partial grant at the 30-per-hour limit and a per-cause failure report; each attached image can be tagged Product or Style ref (one Style ref per generation, outside the five-Product limit, with a fixed instruction sentence after it in the request); the prompt, ratio, resolution and model can be saved as a named user preset in `localStorage` (with a delete control); the header shows Today / month spend from Image Studio usage rows; and a pre-send estimate "about $X for N images" sits next to Generate. The server price table is now keyed by model and resolution, and an unpriced pair is refused before any paid call.

## Why

The design asks for these capabilities and the operator needs to see what a generation costs before and after pressing Generate. Several of them change the paid route: one request can now spend up to four image generations, and 4K is priced higher than 1K and 2K, so the price table had to know the resolution and be checked before the upstream call. Evidence: `docs/stories/US-10.6-image-studio-new-capabilities.md` (v2), `docs/specifications/US-10.6-spec.md` (v4), owner decisions in `docs/decisions/US-10.6-open-decisions.md` (v4), vendor facts in `docs/evidence/US-10.6-vendor-facts-evidence.md`.

Owner rulings this PR implements: server fan-out (one request carries `imageCount`, the BFF grants min(units, N) and runs that many parallel calls); Cancel discards the whole action (it does not keep partial images; the approved Specification text of FR-9 (c) still says "keeps" and is overtaken by this ruling); prices come from Google's list at the recorded pricing-page SHA-256 (OD-2); the recorded cost and the estimate count generated output images only and exclude vendor input charges (OD-18).

## Security

`docs/reviews/security/US-10.6-security-review.md` v2: PASS, 0 blocking. The five surfaces are clear: no key or secret in any added line (and none in tests), no new `bypassSecurityTrust*` or `innerHTML` (the Image Studio never uses the sanitizer pipe), TipTap not touched, no fetched-page content, CORS and `server/index.js` unchanged, error responses carry only a closed cause list, usage rows stay metadata-only. `imageCount` is validated to 1, 2 or 4 and the limiter grants atomically. Non-blocking findings introduced by this change, not softened:

- **NB-1 (worth a planner decision).** N parallel 4K Pro calls amplify memory and egress per request. One 4K Pro part is about 18.3 MB of JSON, so one 4K Pro request with `imageCount` 4 builds a single response of roughly 70 to 73 MB and can transiently need a few hundred MB of server memory; there is no response-size cap and no in-flight cap per process. The limiter still caps paid calls per IP at 30 per hour, so the per-IP aggregate is unchanged, but the shape (one request carrying 4x the memory) is new and the proxy is unauthenticated. Not measured. Suggested: an in-flight semaphore, and/or limit `imageCount` to 2 for Pro at 4K, and/or measure peak RSS in the T40 smoke.
- **NB-2.** A cancelled or disconnected batch keeps its limiter units and may already be paid, but writes no usage row, so the usage table and the new spend header can under-report real vendor spend ("recorded spend", not "billed spend"). A client could also use abort-after-dispatch to avoid the spend meter, though not the rate limit.
- **NB-3.** Log volume scales with N slots (up to 16 redacted lines per request); content is safe.
- **NB-4.** Stored user presets are not capped or enum-checked on load (the 60-character and 30-preset caps apply on create only); local to the user's own browser.
- **OD-18 (cost observability).** The recorded cost and the estimate count output images only and exclude vendor input charges, so they can understate the vendor invoice by owner ruling.
