### 3. BFF classification of the new error shapes (retry-loop.js / handlers.js, read in full)

`namedError(name, message)` returns an `Error` with only `name` set; no `status`.

- **AbortError (caller cancel).** `abortOnEarlyClose` aborts the handler's controller when the response closes unfinished. `uploadFile` rejects with `AbortError` (before the call: no SDK call is made; during the call: at once). In `runWithRetry`, `status` is undefined so it is not a non-retryable 4xx; the next line `if (signal?.aborted) throw failure` ends the run with no sleep and no new attempt. In `createUploadHandler` the catch calls `answerError`, whose first line is `if (signal.aborted) return`, so nothing is written to a closed response. Correct: not retried, no answer. Minor: `logged()` writes one "upload upstream call failed: status=none detail=The operation was aborted" log line per cancel (noise only, nothing secret).
- **TimeoutError (100 000 ms, `UPSTREAM_TIMEOUT_MS`).** No `status`, signal not aborted, so `runWithRetry` treats it as a transient failure and retries after 1000 / 2000 / 4000 ms (4 attempts); exhaustion rejects with `UPSTREAM_RETRIES_EXHAUSTED` carrying 502 (no usable status, P-3). Correct against FR-60/FR-61 and P-3. Nothing from the upstream error reaches the client.
- **Judgement on retrying a timed-out upload (F-8).** Double-upload: yes, possible. The SDK call cannot be cancelled, so a timed-out attempt keeps running in the background while the loop starts the next attempt; up to 4 transfers of the same bytes can overlap. Orphans: covered in the normal case. The `upload.then(...)` handler deletes any file whose upload resolves after the race was lost (`raceLost && file?.name` then `files.delete`, failure swallowed), and this is pinned for both abort and timeout by the corrected spec. Not covered: (a) a `files.delete` that fails (swallowed by design; the Files API object then lives until its own expiry); (b) an SDK promise that never settles, or settles without a `name`, after the server stored the file (no handle to delete); (c) a process restart before a late settle. Client side, read: `llm.service.ts#uploadImageFile` -> `postOnce` -> `runAbortable` (`http-abort.ts`) accepts an optional `signal` but sets no timeout; `studio-composer.component.ts#runIngest` calls `ingestImage` with `upload: (request, signal) => this.llm.uploadImageFile(request, signal)` and passes no `signal` in the deps (`image-ingest.ts` forwards only `deps.signal`, which the composer never sets); the only `AbortController` in studio code is the generation runner's 120 s deadline (`generation-runner.ts:112`), which covers generation only. So an attach-time upload has no client deadline, and removing an attachment or switching session does not abort the in-flight request, so the BFF abort path never ends the background-retry window. A persistent timeout therefore runs about 4 x 100 s + 7 s = 407 s before the 502, with background transfers still holding their Blobs, and uploads are not rate-limited (FR-66). The client `retryTransport` retries only requests that never reached the server, so it does not multiply this (a BFF 502 propagates untouched). This is bounded (4 per request) and is a robustness/cost finding, not a rule violation. Recommend: accept, or have the human decide whether upload timeouts should be non-retried. Not blocking.

### 4. Timer and listener hygiene in `uploadFile` (read line by line)

- `clearTimeout(timer)` and `signal?.removeEventListener('abort', onAbort)` are in a `finally` around `await Promise.race([upload, guard])`: cleared on success, SDK failure, abort and timeout. The pre-call abort returns before any timer or listener exists. The listener is also `{ once: true }`.
- No unhandled rejection: `guard` is observed by `Promise.race`, and after `finally` it cannot reject (timer cleared, listener removed); the SDK promise is observed by the race and by the explicit `upload.then(onOk, () => undefined)`, so a late SDK rejection is swallowed; the cleanup is `Promise.resolve().then(() => files.delete(...)).catch(() => undefined)`, so a synchronous throw or rejected delete is contained. The spec pins timer count 0 after every path and `unhandledRejection` empty for a late reject and a failing delete.
- A signal aborted after success does not delete the returned file (`raceLost` is only set by the timer or the abort listener, both removed). The only residual is the unavoidable timing race where the abort listener fires in the same turn the upload resolves; not reachable in practice.
