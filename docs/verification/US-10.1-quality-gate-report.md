## Worker-crash accounting (honest tally; the crash is mitigated, not fixed)

The `Worker exited unexpectedly` fault (exit code `0xC0000409`) is a known Node v24.15.0 / Windows runtime fault that hits the vitest fork worker when many short-lived loopback HTTP connections are opened (`pipeline_status` v9). It is not fixed by this Story; the shared keep-alive agent in `4723778` only lowers the connection count in the two loopback specs. The root-cause evidence (about 400 bare-`http` repros, Node 22 and Node 24.22.2 controls) is the builder's from v9; this stage did not reproduce it and does not vouch for it.

| Gate | Configuration | Full logic-runner runs | Crashes |
|---|---|---|---|
| v1 | `agent: false` | `npm test` 1, `test:coverage` 2 | 1 (coverage, attributed to `app-limiter.composition.spec.ts`) |
| v2 | `agent: false` | `npm test` 1, `test:coverage` 2 | 0 |
| v3 | `agent: false` | `npm test` 2, `test:logic` 1, `test:coverage` 2 | `npm test` 2 of 2 (same file by log diff); the other three 0 |
| v4 (this) | keep-alive agent (`4723778`) | `npm test` 2, `test:coverage` 2 | **0 of 4** |

**Did the mitigation hold in this gate's runs? Yes: 0 crashes in 4 full logic-runner runs (2 `npm test`, 2 `test:coverage`), and the two loopback specs logged all 8 and 10 tests each time.** Caveat, stated plainly: 4 green runs is weak evidence on its own. At the pre-mitigation rate the builder measured (near 1 in 9 per run), 4 green runs would occur by chance about 60% of the time. Adding the builder's own 3 green post-commit `test:logic` runs (`pipeline_status` v10, not re-run by me) makes 7, still not proof. The case for the mitigation rests on the builder's v9 controls (0 of 170 keep-alive crashes against about 7-10% for `agent: false`), which this gate did not re-run. The fault can recur on this runtime; a later red `npm test` with this signature is the same known fault, not a new defect, but it would still be a red gate and would be recorded as FAIL.
