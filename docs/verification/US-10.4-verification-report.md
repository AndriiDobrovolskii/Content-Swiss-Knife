## Check 6: Angular and server conventions: hold

- `AppComponent` is already a standalone, signal-based component. The additions use `signal`, `computed` and plain methods; no `NgModule`, no new `inject()` call, no RxJS added.
- No SDK import outside `server/providers/`; no prompt string in a service (no service touched; no string in the added `.ts` resembles a prompt).
- Secrets: nothing secret-like is added; no key, header, log line (`console.` has no hit) or response body is touched. `index.html` adds only a Tailwind `colors.shell` mapping to CSS variables.
- Storage: the new rail key `seo_gen_shell_rail_expanded` is read and written only through `readRailExpanded` / `writeRailExpanded`, which accept exactly `'true'` / `'false'`, use no `JSON.parse`, and swallow every storage failure (read: expanded by default; write: swallowed). This is deliberately unlike the neighbouring unguarded `seo_gen_dark_mode` reads, which I left unchanged. `server/usage/store.js` is untouched, so the no-migration point does not arise.
- The rail is a `<nav>`, and there is exactly one `<aside>` (the panel); `@if (hasPanel())` gates it at two spaces without re-indenting the `<aside>`, as plan DD-5 requires. `<ng-template #generatorForm>` is declared exactly once (count 1 before and 1 after), and a whitespace-insensitive comparison of its 227 lines before (at `91430f6`) and after is identical, so the hoist is a move and not an edit or a copy.
- Panel-less modes: the History overlay, Clear All, Process Images and the improvement-request block all live inside the gated `<aside>`; the AI Settings modal (`showModelSettings()`, line 1971) is outside both `<aside>` and `<main>`, so the rail's AI Settings control still works in `image-studio`, `html-editor` and `dashboard`.

The History overlay is anchored with `top-[var(--shell-header-h)]`, the same variable the strip uses (`h-[var(--shell-header-h)]`), replacing the old `top-[125px]`.
- Accent colour: `shell-accent` appears only as `border-shell-accent`, `ring-shell-accent` and, via `navIconClass`, `text-shell-accent` on the `<i>` icon of the active item. It is never applied to a label (AC-6).

The file is allowed, the change is tiny and visual only, and the product owner's permission is recorded in the evidence file ("M-0 gate 1 verdict", owner's chat ruling, with the remeasurement in phase 2). Two things for the reviewers who follow: (a) it touches a mode interior while the Specification's NFR-3 says interiors keep their markup, and the owner's justification borrows FR-18, which in the Specification governs unit-spec changes, not product markup; (b) the permission lives only in the evidence file and the pipeline status, not in an amended Story, Specification or breakdown. I do not treat this as a violation (the approval is a human owner decision and recorded), but `so-reconciliation-reviewer` and the PR description should state it, so the PR does not claim "mode interiors untouched" without this exception.
- **N3: allowed-file list.** `src/app/shell-nav.ts` (and its spec) is a non-component helper module outside the Story's literal surface line ("new components under `src/app/components/`"). It is named by the approved plan (DD-2, DD-6) and task T3, and the plan review confirms it, so it is in scope by the approved plan. `test/shell-evidence.spec.ts` is likewise not named in the task breakdown; the test strategy discloses it as new, and it is a test file authored at `TEST_WRITING`. Every other changed file (`index.html`, `types.ts`, `styles.css`, `app.component.*`) is in the Story's list. No file in the delta is outside the Story, plan or disclosed strategy.
