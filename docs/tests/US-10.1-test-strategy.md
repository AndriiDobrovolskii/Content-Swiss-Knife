**Revision note (v6, TEST_WRITING loop-back from IMPLEMENTATION (key `changes_required_tests`) after HUMAN_PR_APPROVAL was REJECTED; one spec file changed, `test/gemini-image-provider.spec.ts`; no implementation file, no other spec and no helper touched).** HUMAN_PR_APPROVAL was REJECTED for a real bug: uploading an image in the studio answered 404. `GeminiProvider.uploadFile` passed `config.httpOptions = { timeout }` to `ai.files.upload`; in `@google/genai` 1.52.0 `ApiClient.uploadFile` -> `fetchUploadUrl` REPLACES the resumable-upload start headers with a truthy `httpOptions` (even `{}`) instead of merging, so Google answers 404 with an empty message; and the upload path never reads `config.abortSignal`. Proven live by the orchestrator and the builder (builder report v6). The committed case `GeminiProvider.uploadFile (FR-16) :: FR-16: uploads the bytes as a Blob ... with abortSignal and a per-call timeout` asserted `config.httpOptions.timeout` > 0 and < the client floor, so the test pinned the broken mechanism. Specification FR-16, FR-21 and FR-60 require a single-shot upload, Cancel and a BFF retry loop; they never require `httpOptions` on the upload call. This is a test defect (over-specified mechanism), owned by TEST_WRITING. `countTokens` and `generateContent` are NOT affected (`ApiClient.request` merges per-call `httpOptions` and wires `timeout` and `abortSignal`), so their timeout assertions (generateImage case "DD-6: a per-call timeout is set", countTokens case "FR-40") are unchanged. **Change:** the `uploadFile` contract is now pinned as (a) `ai.files.upload({ file: Blob(bytes, type mimeType), config: { mimeType } })` with NO `httpOptions` key (asserted with `Object.hasOwn`) and no assertion on `config.abortSignal`; (b) `uploadFile` rejects promptly with an `AbortError`-named error, without an HTTP `status`, when the caller's signal is aborted before (no SDK call at all) or during the SDK call (SDK mock never answers; no clock advance needed); (c) it rejects with a `TimeoutError`-named error, without a `status` and without aborting the caller's signal, exactly at `UPSTREAM_TIMEOUT_MS` (fake timers, not at `UPSTREAM_TIMEOUT_MS - 1`), so the retry loop treats it like the generateImage timeout (a failure with no numeric status is retried as a transient 5xx-class failure, `retry-loop.js`) and treats the abort as a Cancel (`signal.aborted`); (d) an upload that resolves after the race was lost (abort or timeout) is removed with `ai.files.delete({ name })`, a late SDK rejection and a failing cleanup `files.delete` raise no unhandled rejection, and a successful upload is never deleted; (e) an SDK error is rethrown as the same object with its `status`, single-shot, never through `withRetry`. Defence in depth: the file's `@google/genai` mock now REJECTS `files.upload` with a 404 `ApiError` whenever `config.httpOptions` is truthy (mirroring the proven SDK behaviour; the check runs before any per-test implementation, plus a direct pin test of the mock), so any future code that passes `httpOptions` to `files.upload` fails the unit test. The mock also exposes `files.delete`. Implementation hints that follow from the tests (not requirements beyond them): the timeout must use the global `setTimeout` (the tests drive it with fake timers; `AbortSignal.timeout` would not be controllable) and must be cleared when the call settles (the tests assert no timer is left). Header comment of the spec corrected. The v5 case count of this file (13) becomes 25. **Red state:** 13 red / 12 green in this file; the whole logic runner changes by exactly one pre-existing test going from green to red (the FR-60 case that makes `uploadFile` fail with status 502, now answered 404 by the guard mock while `gemini.js` still sends `httpOptions`), the old FR-16 case removed (replaced) and 13 cases added; nothing else changed. See the generation report v6 section.

## Approach

- **Assertions are written from the Story/Specification text** (AC wording, FR failure paths, SD/D values, the Interface text table literals copied verbatim as expected values), never from the plan's proposed implementation and never from an actual run. Every `it()` title starts with the ids it proves (`FR-11 row 3: ...`, `AC-4 / D-7: ...`) so the AC matrix cites file plus exact title.
- **Ambient effects only through ports** (plan DD-15, NFR-14). The shared doubles are in `test/image-studio/helpers/fakes.ts`: fake clock and scheduler (time moves only when a test advances it), id source, recording `Announcer`, alert/confirm/clipboard/save ports, a synthetic raster byte format with a **fake `ImageCodec`** (honours `maxLongSide`, `quality`, `fillWhite`, drops EXIF/animation, can return a wrong MIME or an oversize output) and an **in-memory `SessionStorePort`** with real all-or-nothing batch semantics and a switch that makes writes throw (quota). `test/image-studio/helpers/handler-fakes.ts` (fake `req`/`res`, controllable `sleep`, stub Gemini), `test/image-studio/helpers/core-fixtures.ts` and `test/image-studio/helpers/studio-render.ts` (component harness) are the other doubles. All are boundaries, none is the unit under test.
- **Red for a usable reason.** The plan creates many brand-new modules, so a static import would make a whole file fail at collection with zero named tests (the matrix would then cite tests that never ran). Specs for modules that do not exist yet therefore load them at run time (`const load = (p) => import(/* @vite-ignore */ p)`, the precedent of `test/cors-policy.spec.ts`), giving one named failure per test (`Cannot find module '<the module under test>'`). Specs of modules that already exist (`model-support.js`, `pricing.js`, `gemini.js`, `llm.service.ts`, `model-catalog.ts`) use ordinary imports and fail by assertion or `is not a function`. `npx tsc --noEmit` therefore adds no diagnostic from any logic spec.
- **Soundness of the tests themselves.** Because "module not found" proves little about an assertion, the forks that wrote the server leaf, server handler, request-builder, apply-response and runner specs ran them against **throwaway reference implementations kept outside the repository** (results in the generation report) and deleted them. The store, component, ingest/format and text specs were argued by reading only; that is stated, not hidden.
- **No weakening.** The one existing spec edited, `src/prompt-core/model-catalog.spec.ts`, keeps every loop (including the server-parity `objectContaining({levels, maxOutputTokens})` test); `ALL_MODELS` is scoped to non-image entries and 14 tests are added. Its 48 pre-existing tests pass before and after. The breakdown (T2 Notes) assigns this edit to test writing.

## Findings for the plan owner and the human (also in the generation report)

1. **DD-20 order versus the `sentBytes` key.** The plan says store the sent bytes, then upload; the store key is `[sessionId, fileUri]` and the `fileUri` exists only after the upload; FR-16 also says the upload never depends on the store. `image-ingest.spec.ts` pins **upload, then store** (a store failure still never blocks the attachment). Storing before upload would need a client-generated key: a plan change.
2. **DD-28 g wording.** It lists `alert(` and `setTimeout(` literally, so interface members such as `alert(message: string): void` in `ports.ts` would trip scan g. The architecture spec treats a typed declaration and a call through an object as non-ambient (stated in its header); the plan wording should say so.
3. **T-17 timing.** The runner announces T-17 when it returns an `images` outcome, before the store commits; a quota failure at commit (SD-34) would leave a "version ready" announcement for a version that was not created. The Specification is silent; the tests assert neither order. A decision is needed (announce from the store after the commit).
4. **`init()` on an empty store creates one empty session** (FR-49 implies a current session exists; D-26 makes empty sessions rows). Pinned by `FR-49: with nothing stored init creates one empty session`; if the builder prefers lazy creation those tests change.
5. **T1 acceptance nuance** ("image IDs vs synthetic lists via `textModelsOf`") resolved: the T1 spec feeds synthetic lists to `textModelsOf` and asserts the lookup semantics at the data level, with baseline guards on the real catalogue; "`resolveImageModel` accepts an image ID" cannot exist before T2 adds the entries, so that case lives in `model-support.entries.spec.ts` (T2).
6. **Open spec points the tests pin without inventing a requirement** (each is a clear statement in the owning spec header): amount format of the cost line (only the number is asserted), the session-list order (newest last activity first), where per-version actions live (inside the full-view dialog), the error text for an invalid 200 (only "some `role=alert` and no version" is asserted), a bare 500 mapped to T-7 with Retry (FR-85), a first 410 `FILE_MISSING` as `reupload: true` with text `T-10`, T-22's six labels (no ids in the Specification; asserted as a set under keys starting `T-22`), Cancel is not a Retry candidate, `run()` throws `EmptyMessageError` for an empty message.
7. **Probe 0 (plan R12) result:** `AppComponent` renders in a clean clone with only `provideHttpClient()` and `provideHttpClientTesting()`; the FR-1 clear-all test is feasible; no escalation is needed.
8. **v2 (plan revision v3).** (a) The production token defaults (T36 for `Clock`, `Scheduler`, `IdSource`, `AlertPort`, `ConfirmPort`, `ClipboardPort`, `SavePort`; T39 for `SESSION_STORE_PORT` and `IMAGE_CODEC_PORT`) are untested by design of every spec, as plan_review N-17 says; no test was added because task_breakdown v3 lists none.
