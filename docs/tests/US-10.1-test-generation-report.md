### Defect (builder-proven, `docs/catalog/US-10.1-pipeline-status.md` v9)

On Node v24.15.0 / Windows the vitest fork worker is killed with exit code 0xC0000409 (native fast-fail, empty stderr, reported as "Worker exited unexpectedly") with a per-connection probability when many short-lived `agent: false` loopback `node:http` connections are opened. The app-limiter composition spec opened about 280 such connections; QUALITY_GATE's `npm test` failed about 1 run in 8 to 10. A bare http server plus an `agent: false` client reproduces it with no repository code; with a keep-alive agent the builder saw 0 of 170 on 24.15.0. **It is a Node runtime fault, not a defect of `createApp`, of the limiter or of these tests.** This change MITIGATES it for these two specs; it does not fix the runtime.

### Change (exactly the builder's specification, nothing else)

| Spec | Before | After |
|---|---|---|
| `app-limiter.composition.spec.ts` `post()` | `http.request({ ..., agent: false })` | `agent: agent!`, where `agent = new http.Agent({ keepAlive: true })` is created in `boot()` (one agent shared by every request of the test) and destroyed in `afterEach` |
| `create-app.spec.ts` `call()` | `http.request({ ..., agent: false })` | the same |
| both `afterEach` | `server.close()` | `agent.destroy()` first, then `server.closeAllConnections()`, then `server.close()` (so `close()` cannot wait on an idle keep-alive socket) |
| both | no comment | a header comment above `let agent` explaining the Node 24.15.0 Windows worker crash, so nobody reverts to `agent: false` |

Assertions: none added, removed or changed (diff is the option, the agent lifecycle and the comments). Checked that keep-alive changes nothing the tests assert: (a) the limiter is keyed per client IP from `X-Forwarded-For` (rightmost hop) or the socket peer; every request is loopback, so the key of the no-XFF case (127.0.0.1) is the same as before, and socket reuse does not enter the key; (b) the body-limit cases (413 / 411) send exactly what they sent: the `declareLength` helper path is the same `http.request` with `Content-Length: <declared>` and `flushHeaders()` and no body, then `req.destroy()` once the answer is complete - `destroy()` on a request that never finished writing destroys its socket, so a 413 never returns a half-written socket to the pool (the next request opens a fresh connection); the chunked 411 case ends its request normally, and Node's server drains the unread body after answering, so that connection stays valid or is closed by the server, which the agent handles; (c) no response in these specs depends on `Connection: close`; (d) every test boots its own server on port 0 and its own agent, so no socket survives from a previous test (the new `afterEach` destroys the agent before closing the server). Other loopback helpers: see "Left alone" below.

### Defect 2 - T45 flake: GC-dependent happy-dom MutationObserver (mechanism verified)

The flake `FR-61 / FR-83 / FR-74: '413 PROTECTED_HISTORY_EXCEEDS_LIMIT' -> one status update` (`announcements() = []` once, green on reruns) is a test-environment defect. `node_modules/happy-dom/lib/mutation-observer/MutationObserverListener.js` stores `callback: new WeakRef((record) => this.report(record))`; the arrow function is referenced by nothing else, so once the engine collects it the observer never reports again. Reproduced deterministically outside the repository (scratch script, `node --expose-gc`, bare happy-dom 20.10.6 `Window`): a mutation before `gc()` is reported (`["A"]`), a mutation after `gc()` is not (`["A"]` again); with `globalThis.WeakRef` swapped for a strong holder during `observe()`: `["A","B"]`. Whether a GC lands between `watchStatus()` and the flush depends on heap pressure, hence a one-off failure. The builder's coalescing hypothesis is not supported: a dead observer yields an empty list, which is exactly the observed signature. Fix: `observeMutations` pins the callback. Residual: the original rare failure was not reproduced inside the runner (GC timing); the fix removes the proven mechanism and the spec was green in three consecutive full runs. A flake with a different signature would be a new finding.
