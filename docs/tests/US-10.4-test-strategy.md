# Test strategy: US-10.4 (Redesign the app shell: grouped, collapsible navigation and restyled layout in light and dark themes)

Track: angular. Nothing in this Story generates content, touches a prompt, a store, a locale or a FROZEN file, so no generated-HTML (AGENTS.md section 4) test is written or weakened. The corpus fixtures in `test/fixtures/corpus/` are not used and no new fixture is created: the unit under test is the app shell, and the only doubles are the Image Studio fakes that `test/image-studio/helpers/fakes.ts` already provides (needed because "all 13 modes are reachable" includes entering Image Studio).

## 2. What is deliberately not unit-tested, and why

Tailwind is the Play CDN. It is not loaded by `ng test` and not by `vitest`, so no test here can see a class take effect. The following are therefore **not claimed** by any automated test and are covered by the manual evidence (section 5):

- Colours, the painting layer that makes `#0b1120` visible, light-theme counterparts, contrast ratios, accent never being a text colour (AC-5, AC-6; FR-13, FR-14, FR-15). The source pins in the shell-wiring spec check only that the tokens are declared once per theme with a light counterpart, that the dark values are the four specified, that `:root` keeps none of them, and that no opaque slate layer is left over `<body>` and `<main>`. That is "the marker is present", not "the page renders correctly".
- The 256 px / 64 px widths as pixels, the icon-only label hiding (`sr-only`), truncation, the 384 px main area and every other width consequence (AC-3 pixels, AC-6a; FR-4, FR-16). The component test asserts the Specification's own class names `w-64` / `w-16` on the rail, which is as far as the DOM goes.
- The History overlay's top edge equalling the panel header's bottom edge (FR-11). The source pin checks that both read one CSS variable and that neither `top-[125px]` nor `top-[64px]` remains; the pixel check is manual.
- Hover and focus-ring appearance (FR-15 states).
- Mode interiors (NFR-3): no mode form, result view or editor is retested; the "same main-area view" claim (FR-7) is checked through one stable marker per mode that has one.

## 4. Test-design rules applied (plan DD-14 and the impact analysis' silent-failure list)

- **Non-vacuous absence (hazard 2).** Every "not rendered in a panel-less mode" assertion in the component spec runs after `expect(panel).toBeNull()` for the same mode (AC-4e, AC-7), or is the panel-presence assertion itself (AC-4b). The kept `clear-all` assertions look the range control up in the whole app and assert the panel is absent.
- **The `aside` selector (F-2, hazard 1).** The panel is `container.querySelector('aside')`; the rail is found by `getByRole('navigation')`. A test fails if the rail were an `<aside>` (shell-wiring pin and the "only `<aside>`" component test).
- **`aria-current` counts select `[aria-current="page"]`** (hazard: `studio-session-list` uses the value `true`).
- **No CSS-only claims (hazards 6, 7).** Hidden items are asserted through the accessibility tree (`queryByRole`), which excludes `hidden`, `aria-hidden` and `display:none`; a class-only hide would leave the item in the tree and fail FR-2 (b), which is what the plan intends with `@if`. Unique names are asserted by counting the rail's buttons against the expected names, so a second hidden copy of an item would fail.
- **Rail state owned by `appMode()` (hazard 12).** A cancelled `confirm()` in HTML Editor must leave `aria-current` on HTML Editor; the test makes the editor report unsaved changes (existing member `htmlEditorRef`, set through `any`, as the clear-all spec does with `appMode`).
- **Storage doubles throw only for the rail key.** The AppComponent constructor reads and writes three other `seo_gen_*` keys unguarded (plan DD-6 note).
- **No new import of a not-yet-existing module in a spec that the component runner compiles.** `ng test` type-checks every file under `src/` in one program. `shell-nav.spec.ts` therefore loads `./shell-nav` with a dynamic, non-literal `import()` against a locally declared interface, so the module being absent makes only that spec red and leaves the component runner building. (A static import would have failed the build of every component spec; this is the one deviation from the `tab-descriptors.spec.ts` precedent, whose red component runner was accepted at the time.) The component spec imports no symbol this Story creates.
- **Determinism.** No sleep, no retry, no network, no wall clock, no unseeded randomness. `settle()` is the same promise flush as `studio-render.ts`. The fake clock and scheduler come from `fakes.ts`.

## 5. OD-28 settled here: the manual-verification procedure, slug and author

OD-28 was delegated to TEST_WRITING by the Specification (FR-19) and the task breakdown. It is decidable without a human, so it is decided here and does not block.

**File.** `docs/evidence/US-10.4-shell-manual-verification-evidence.md`. Registry kind `evidence` (`artifact-paths.yaml`: pattern `docs/evidence/{story_id}-{slug}-evidence.md`, owner `so-planner`, `external_ok: true`); slug `shell-manual-verification` (different from the clarification report's name, as the registry requires).

**Who writes it.** The **external executor** of tasks T1, T2, T7, T8 and T10: a human, or an agent that has been given a real Chromium. Neither `so-test-writer` (this stage writes the procedure, not measurements) nor `so-builder` writes it. The front matter carries `owner: so-planner` because `artifact-schema.md` requires the registered owner; the person or agent who ran each check is named in that check's `Run by:` line, never in `owner`. Registry owner and measuring person differ by design (the `external_ok` rule).

**When.** T1 and T2 need no plan, test or code and should be run **before** `IMPLEMENTATION` is dispatched, so that a FAIL costs nothing built (the plan review's open OD-29 timing finding; this strategy recommends it). Otherwise `IMPLEMENTATION` returns `BLOCKED` at pause P1 until the `GATE-1` line exists.

**Runner and browser.** A real Chromium (headed or headless), current stable, version recorded with its exact build. The app is served from a development build (`ng serve`, development configuration) with network access, because Tailwind (Play CDN) and Font Awesome load from CDNs. Viewports set exactly (DevTools device metrics or the automation tool's viewport call): 1024 x 768 for all width checks and 1024 x 720 for the rail's vertical fit. Tool versions (Chromium, Node, Angular CLI, any automation library) are recorded in every measured section.

**Matrices (the Specification's minimum, FR-19, stated as cells):**

| Check | Cells | Per cell, record |
|---|---|---|
| Colour, layers, contrast (FR-13, FR-14, FR-15) | theme {dark, light} x rail {expanded, icon-only} x mode {generator, image-studio} = 8 | computed background of `<body>`, the root container, `<main>`, and the colour actually visible behind the main content area (first opaque ancestor, alpha-composited if needed); rail surface and edge colour; group separators; the panel's outer surface, header strip and outer border (generator); the contrast ratio (WCAG 2.x relative luminance) of each shell text against the surface directly behind it: rail item label inactive, hover, active and `focus-visible`, group header text and count (expanded), app title (expanded), the Language code, the bottom controls' labels where visible; whether any shell text computes to `rgb(124, 58, 237)` (`#7c3aed`) |
| Light tokens (FR-14) | the `:root` custom properties read in the browser | every `--shell-*` value in both themes, and the confirmation that no shell surface computes to a dark token (`#0b1120`, `#111a2e`, `#26324a`) in the light theme |
| Overlay geometry (FR-11) | generator x rail {expanded, icon-only}, History open, 1024 x 768 | `getBoundingClientRect()` of the header strip's bottom and the overlay's top, raw numbers, tolerance 0.5 px |
| Fit (FR-16) | 13 modes x rail {expanded, icon-only} = 26 cells, at 1024 x 768 (and the rail's reachability at 1024 x 720), plus the unshifted 640 px baseline; phase 1 (T1) is the width proxy on the current build for the ten panel modes | columns (a) clipped, (b) needs horizontal scroll, and whether the rail and its four bottom controls are reachable; pre-existing (baseline) entries listed separately; seeded results as described in plan DD-12 |

**Required sections** (`## ` headings, exactly these): `M-0 phase 1`, `M-0 gate 1 verdict`, `M-0 phase 2`, `M-0 gate 2 verdict`, `FR-13 dark tokens and painting layers`, `FR-14 light theme values`, `FR-15 contrast`, `FR-11 overlay geometry`, `FR-16 fit summary`. A **measured** section (phase 1, phase 2, FR-13, FR-14, FR-15, FR-11) records, as `Label:` lines, `Method:`, `Browser:` (with tool versions), `Date:`, `Run by:` and the raw output or a pointer to screenshots. A **decision** section (the two gate verdicts and the fit summary) records `Date:`, `Run by:` and `Based on:` (the measured table it rests on); it has no browser of its own.

**Marker lines** (single lines at the start of a line; the task breakdown defines the first four, this strategy adds the last two):

- `GATE-1 (gate pass under the baseline rule): PASS` or `FAIL` (T2)
- `GATE-2 (gate pass under the baseline rule): PASS` or `FAIL` (T8)
- `FR-16 met: NOT DETERMINED (U-1 pending product owner)` until the product owner has read U-1 (T2, T8, T10)
- `EVIDENCE-COMPLETE: yes` (T10)
- `LIGHT-VALUE-FAIL: <token> <ratio>`: written by the executor for each light-theme token that fails FR-15 (or the light-theme colour check). It is the P3 re-entry signal the plan review left open: `so-builder` re-enters T9 and corrects the value in `src/styles.css` when it sees this line. It must not be present when `EVIDENCE-COMPLETE: yes` is written.
- `LIGHT-VALUE-RESOLVED: <token> <old ratio> -> <new ratio>`: written after the re-measurement that closes a `LIGHT-VALUE-FAIL`. (The builder's dispatch prompt for the P3 re-entry should mention both lines.)

A failed check is recorded with its measured value and is never omitted; the corresponding requirement is then not met (FR-19). A gate verdict is worded "gate pass under the baseline rule" and is never reported as "FR-16 met" (task breakdown, "Gate verdict wording").

`test/shell-evidence.spec.ts` checks the file's existence, front matter, the nine headings, the per-section field labels, the marker lines, that no FAIL gate verdict coexists with `EVIDENCE-COMPLETE: yes` and that no `LIGHT-VALUE-FAIL:` line is left open. It is red until the executor completes T10 (pause P3) and **no builder task turns it green**.
