### Differences from the task breakdown (non-blocking findings for `so-builder` and the orchestrator)

1. **T4 does not own every "names / reachability / theme / bottom controls" row.** The breakdown's T4 row lists AC-3 names, AC-4 reachability, AC-4a and AC-4c without distinguishing the rail state. Every variant that clicks or names the collapse control (all icon-only variants) is **T5**. The expanded-rail variants are T4. A builder at T4 who sees the icon-only variants red has not failed; the collapse control does not exist before T5.
2. **T6 owns more than "the panel gate".** Besides AC-4b presence, AC-4e and AC-7 rows (as the breakdown says), the `clear-all` DD-25 studio test and the `shell-wiring` gate pins are T6. The pre-result and post-result generator-form tests are **T4** (they already hold once the rail exists) and must **stay** green when T6 hoists `generatorForm`; the breakdown lists them under T6.
3. **T9 is not "no new failing test".** Seven `shell-wiring` source pins on the token declarations and painting layers are red until T9 (the breakdown anticipated this possibility: "if TEST_WRITING adds a source pin on the token mapping, it turns green here"). Between T3 and T8 the by-design red set therefore includes those seven.
4. **A fourth new spec, `test/shell-evidence.spec.ts`,** was added so that AC-9 has a real test row (the breakdown names three). It is red until the external executor completes T10; `so-builder` cannot satisfy it and must not be asked to. It belongs to the P3 hand-off, not to a builder task. It is not part of `npm run test` passing until P3, so **`QUALITY_GATE` must not run before P3** (which the breakdown already forces: `IMPLEMENTATION` returns `PASS` only after `EVIDENCE-COMPLETE: yes`).
5. **Two additional marker lines** (`LIGHT-VALUE-FAIL: <token> <ratio>` and `LIGHT-VALUE-RESOLVED: ...`) are defined in the strategy (OD-28) as the P3 re-entry signal the plan review left open. The builder's dispatch prompt for the P3 re-entry should name them.
6. **Contract shapes the plan left open** are pinned in the strategy, section 3 (notably `NavGroup = { id, modes }` and `groupOpen` as `Record<NavGroupId, boolean>`). If the builder needs a different shape, that is a `changes_required_tests` conversation, not an edit to `shell-nav.spec.ts`.

## 5. How the tests were proven satisfiable (honest account of the throwaway prototype)

A red suite proves nothing about whether the tests can ever pass. To avoid handing the builder tests with defects of their own, a **throwaway prototype of the plan** was built **outside the repository tree** (three temporary `git worktree`s in the session scratchpad, with `node_modules` junctioned; all removed afterwards, `git worktree list` shows only the two that existed before). It contained a minimal `shell-nav.ts`, the types, the translation keys, the rail, the panel gate, the hoisted template and the token declarations, written to the plan's markup rules. It is **not** part of the deliverable, was **discarded**, and no product file in the real tree was changed.

Results of the final spec files against the prototype:

- `npm run lint`: clean.
- `ng test`: **10 files, 270 tests, all pass** (80 shell + 7 clear-all included).
- `vitest run`: 272 files, 8761 passed + 23 failed + 3 skipped: only `test/shell-evidence.spec.ts` red (23), as designed, because it needs the evidence file. With a temporary sample evidence file holding the nine sections and the marker lines it passed 23/23; the sample was deleted immediately.
- All pre-existing wiring specs (`faq-layout`, `image-studio-wiring`, `export-guard`, `no-operator-notes`, `operator-notes-source-scan`) passed against the prototype with zero edits, which confirms the plan's claim that only two existing specs need adapting.

The per-test map of section 4 was checked empirically: the prototype was reduced to a "T4 state" (expanded rail only, constant `true`, no collapse control, panel always rendered). The component runner then failed exactly **37** tests: the 30 T5 tests, the 5 T6 tests and the 2 adapted `clear-all` tests; `shell-nav` and `template-wiring` were green and only the three T6 gate pins were red in `shell-wiring`. This matches the map.

Mutation check (three deliberate defects, against the shell component spec; each was caught):

| Mutant | Result |
|---|---|
| `writeRailExpanded` without its `try/catch` | 2 tests fail: "if writing the rail key throws ..." and "if both reading and writing throw ..." |
| `isNavItemShown` forgets to keep the active item when its group is collapsed | 3 tests fail: group toggling, "toggling a group never changes the active mode", "it holds with the active mode's group collapsed" |
| Dashboard carries `aria-current` whenever any mode is active | 4 tests fail: the 13-mode check, the collapsed-group check, the icon-only check, the cancelled-confirm check |

Two tests were corrected after the prototype run, and the reason is recorded here because one of them narrowed an assertion:

- **Narrowed: the header-strip text check** (AC-4b). It first asserted that no mode label appears anywhere inside the panel. The FAQ Generator form has its own interior heading "FAQ Generator" (`faqOnlyTitle`), a pre-existing interior (NFR-3). FR-9 and OD-22 constrain only the **header strip**, so the assertion now checks the strip, not the whole panel. The strip's text-empty assertion is unchanged.
- **Loosened to avoid a false red at T4: the "every rail button named and unique" check** no longer requires the collapse control (it counts it when present), and the "AI Settings opens the modal in a panel-less mode" test no longer asserts panel absence (AC-4b owns that). Both only change *when* a row turns green; neither removes a requirement. The collapse control's presence and name are asserted by the AC-3 / FR-4 rows, and panel absence by the AC-4b rows.

## 6. Coverage gaps found (not hidden)

1. **FR-13, FR-14, FR-15, FR-16 and the FR-11 pixel adjacency have no automated assertion** (AC-5 partial, AC-6, AC-6a). Cause: the Tailwind CDN is not loaded by either runner. The compensating controls are the manual evidence (strategy, section 5), the `shell-evidence.spec.ts` structure check, and the seven source pins. A reader of the matrix must not read AC-5 / AC-6 / AC-6a as automatically proven.
2. **`ng build` is the check for a `TRANSLATIONS` key used in the template but missing from a map**, not `npm run lint` (task breakdown T4 note). The component spec asserts every new string in both languages, which catches the same defect at run time.
3. **The hand-written rail markup is a second copy of `NAV_GROUPS`** (plan DD-2 honest limit); the guard is the component test that compares rendered order and count with the Specification's list.
4. **Icon-only label hiding (`sr-only`) and the `title` tooltip are CSS / presentational** and not asserted. The accessible-name tests cover the names in both rail states.
5. **No hover / `focus-visible` appearance test** (manual, FR-15).
6. **The corpus** (`test/fixtures/corpus/`, two items, same product across two stores) is not relevant to this Story; the known gap in `test/render-reconciliation.report.md` section 5 is unaffected.
7. **The build is the only compile-time check of the Angular template**; `tsc --noEmit` does not type-check templates.

## 7. Other non-blocking findings

- **IMPLEMENTATION will return `BLOCKED` at P1 unless T1 and T2 are done first.** With the slug and procedure now fixed (strategy, section 5), the external executor can create `docs/evidence/US-10.4-shell-manual-verification-evidence.md` and run T1 and T2 now, before `IMPLEMENTATION` is dispatched.
