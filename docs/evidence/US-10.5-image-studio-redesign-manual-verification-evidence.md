# Manual verification evidence: the Image Studio redesign (US-10.5)

This file is the evidence artifact of FR-31 / AC-14 and the output of task T42 (test strategy section 7). It records what the unit runners cannot see: contrast, the 1024 px layout, pointer drag, the mismatched-size compare frame, truncation, and the dark and light theme values.
A failed check is recorded with its measured value and is not omitted (FR-31). **One check failed on the first run: C-4 (amber "Retry" scrim, 3.19:1). It was fixed in commit `1601640` (T44, `bg-amber-700`) and re-measured at 5.02:1 (section C-4 addendum). Everything else passed.** The text below keeps the first-run values unchanged; the version-2 additions are the C-4 addendum and the summary.

## Method

- **Code under test:** branch `feature/US-10.5-image-studio-visual-redesign`, HEAD `16d82e7` ("harden stored-image handling (NB-1..NB-3)"), every product task T1-T37, T41 and T43 committed. The tree under `src/` was not modified by this run.
- **Server:** `ng serve` (development configuration, `http://localhost:4200/`, watch mode), already running; no backend (`npm run server`) was started and no image generation was triggered: no API key was entered or used.
- **Viewport:** a same-origin `<iframe>` of exactly 1024 x 768 CSS px loaded the app (the US-10.4 precedent), so the viewport-keyed Tailwind breakpoints saw a 1024 px viewport. The window resize of the browser tool did not change the 1920 px outer viewport, so the iframe is the 1024 px proxy. The app rail is expanded in every cell (the default state).
- **Seeding:** two sessions were written into the app's own IndexedDB (`cwk-image-studio`, stores `sessions` and `turns`, ids `seed-evidence-1` and `seed-evidence-2`) through the page's JavaScript: session 1 holds an edited turn (v1 400x300 PNG with preset `white-bg`, cost 0.04, 5200 ms; v2 240x400 PNG, `editOfVersion` 1, `inputRefs` to the attached v1, cost 0.04, 7800 ms) and session 2 holds one version with a 236-character prompt (truncation case). The images are canvas-generated gradients labelled with their size. These records and the one empty session created by the "New session" click were **removed again at the end of the run, on the user's explicit instruction** (2026-11-09): exactly the three sessions `seed-evidence-1`, `seed-evidence-2` and `4ac5fdee-3e60-48b2-a664-72a094c7fd38` and their 6 turn records were deleted by id; the user's pre-existing session `9db194dd-531c-48d6-a930-fa157c4a4097` (created 2026-11-08, no turns) was left untouched and is the only session remaining.
- **Contrast probe:** for every text node under `app-image-studio` (visible, non-zero box) the computed text colour and the effective background (ancestor backgrounds composited over the page background; colours normalised to sRGB through a 1x1 canvas, so oklch/oklab values are handled) give the WCAG 2.x contrast ratio `(L1 + 0.05) / (L2 + 0.05)` with `L = 0.2126 R + 0.7152 G + 0.0722 B` over linearised sRGB. A ratio below 4.5 is a failure.
- **Browser and tools:** Google Chrome 156.0.0.0 (Win32, device pixel ratio 1), driven by the Claude in Chrome automation tool with the harness JavaScript run in the page. Angular CLI via `ng serve` of the repository, Node.js 24, Tailwind Play CDN as loaded by `index.html` (the CDN generates a class only after it is added to the DOM, so the probes waited 1.2 s).
- **Date:** 2026-11-09.
- **Run by:** Claude (Claude Code, model Sonnet 5.5) acting as the external executor, at the user's explicit instruction ("запускай ... Проходь матрицю в Chrome автоматично").
- **Screenshots** (local, not committed; the raw probe output is in the sections below): `C:\Users\works\AppData\Local\Temp\claude-chrome-screenshots-10NqG2\screenshot-1794250017836-0.jpg` (dark, feed), `...-1794250058088-1.jpg` (light, feed), `...-1794250072691-2.jpg` (light, edited turn, strip, compare dialog), `...-1794250149689-3.jpg` (light, empty state).

## C-4 The two allow-listed colour patterns (FR-30, plan DD-15): one FAILED

Probe elements carrying exactly the classes of the shipped patterns were inserted into the studio at run time (in the page, not in any file) over a white image area and over the page surface, in both themes:

| Pattern | Dark | Light | Result |
|---|---|---|---|
| Status text `text-red-700 dark:text-red-300` on the page surface | `252,165,165` on `11,17,32` = **9.92** | `185,28,28` on `241,245,249` = **5.91** | PASS |
| Image scrim `bg-slate-900/70 text-white` over a white image (worst case) | white on `87,92,105` = **6.67** | **6.67** (7.00 over the light page) | PASS |
| **`bg-amber-600 text-white text-[10px] font-semibold` (the composer's attachment "Retry" scrim, `studio-composer.component.html` line 79)** | white on `217,119,6` = **3.19** | **3.19** | **FAIL (< 4.5)** |

The amber scrim is a 10 px semibold label, so it is normal-size text for WCAG 2.x AA and needs 4.5:1. It measures **3.19:1 in both themes**; FR-30 ("all studio text has a contrast ratio of at least 4.5:1") is therefore **not met for this element**. It appears only in the failed-upload state of an attachment thumbnail, which this run could not produce naturally (that needs a failing upload), so it was measured on a probe element with identical classes. The plan (DD-15) had exempted the pattern from the `--shell-*` colour rule; the exemption does not cover the contrast rule. This is recorded as a finding and was **not** fixed here (a Story or specification decision, or a one-class change such as a darker amber, belongs to the human).
