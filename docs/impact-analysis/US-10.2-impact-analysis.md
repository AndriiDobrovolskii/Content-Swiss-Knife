## TDD ordering hazards

1. **The red set is a function of the Running Node.** On `v24.22.2` (today) the unchanged tree makes seven guard cases red: 4(a), 4(b), 4(e) and FR-6 (cause C1), 4(c), 4(d) (cause C2) and FR-7 (cause C4, because the Pin `7.24.4` is not the bundled `7.30.1`). The record must print `node -v`, `process.versions.undici` and `npm -v`, and the red table must be taken on the Node actually running. A FR-7 that is green on `v24.22.2` against the unchanged tree is an unexpected outcome (FR-14).
2. **The 11 old cases must not be left in place.** On the new Pin, the old case 2 (`windowProblem`) fails for `7.30.1` ("at or above 7.26.0"), so it must be replaced in TEST_WRITING, before IMPLEMENTATION. 3. **A module-level throw destroys attribution.** Today the guard calls `readJson('package.json')` and `readJson('package-lock.json')` at import and `readJson` throws when a file is missing. A `.nvmrc` read that threw the same way would fail the whole file with one load error instead of seven attributable cases, which FR-14 treats as an invalid red (failure path: "a syntax error, a missing import, an unexplained red").

## Silent-failure risks (break without erroring)

1. **Skew reopens on production or on any other Node.** `engines` is advisory (human-decided OD-2, no `engine-strict`); `npm install` on another Node prints one `EBADENGINE` warning and continues. A deploy (Railway, production Node unknown) or a developer on another Node gets the nested undici `7.30.1` next to a different bundled copy: the upload route would again answer `502 UPSTREAM_RETRIES_EXHAUSTED`, caught only if someone runs `npm test` there (FR-6) or hits the route. Accepted limitation OD-9.
2. **The guard can pass vacuously on one Node.** On the pinned Node, FR-6/FR-7 pass by construction; the claim "a wrong Node fails" is proven only by the pure decision's synthetic cases (FR-5, accepted OD-11). If the decision exercised by the synthetic cases and the check made by the real case were different code, the synthetic proof would say nothing about the real case (FR-5 states the comparisons "are expressed as a pure decision", which is the property that closes this).
3. **`.nvmrc` is read with the wrong normalisation.** CRLF or BOM or trailing whitespace in a Windows-created `.nvmrc` would make `24.22.2\r` not equal `engines.node`, or a stricter parser accept `24.22.2\n` silently (NFR-9).
4. **A passing live check that measured the wrong thing.** FR-17 is only meaningful if `node server/index.js` really loaded `cheerio`'s nested copy at the Pin (it does: `fetcher.js` imports cheerio at startup); FR-18 is only meaningful if the scratch tree has no nested cheerio undici (validity condition). A scratch tree installed from the original lockfile "measures nothing".
5. **Stale living docs.** `docs/knowledge/project-state.md` keeps saying "no `engines`/`.nvmrc`" and "7.24.4 equals Node 24.15.0" until archive; AGENTS.md lines 332 and 405-407 keep naming the old pair until a human edits them. An agent reading those after merge reads wrong numbers, with no failing test.
6. **`npm audit` shape.** The nested undici leaves the flagged range while the hoisted `7.28.0` and `node-gyp`'s `6.27.0` stay flagged (OD-13: non-goal). The count changes without any assertion noticing.
7. **Accidentally committed or retained secrets and scratch.** The live runs use the shared `GEMINI_API_KEY` (NFR-3); scratch copies, the server log and the uploaded Files API object are real side effects with no test. The server log is deleted after counting; the object is deleted by name derived from `fileUri` only.
8. **A late `package-lock.json` churn.** If npm rewrites line endings or metadata, `git diff` is clean after normalisation but the FR-13 diff must be a parsed key diff (hazard D above).
