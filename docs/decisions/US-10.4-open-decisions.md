## Carried forward and answered (OD-1..OD-21)

### OD-1 - Clear All in Image Studio
- **Question.** Where does "Clear All" live in Image Studio once the input panel is gone, or are the existing behaviour and specs retired with approval?
- **Evidence (carried).** The "Actions Footer" (`app.component.html` line 892 to the `</aside>` at line 1082) is inside the `<aside>`; in studio mode it renders only Clear All and the feedback block (the studio branch at line 1019 is empty). `clearAll()` has `case 'image-studio': break;` (`app.component.ts` line 1164) and no case for html-editor or dashboard (cases at lines 1067-1164, verified again this run), so Clear All is a no-op in those three modes. `app.component.clear-all.component.spec.ts` asserts Clear All is present in studio mode and that clicking it leaves stored sessions unchanged.
- **Answers (human, 2026-11-08, chat).** Interim: move Clear All into the Image Studio header (v2). **Final, in Story v4: Clear All is removed entirely from `image-studio`, `html-editor` and `dashboard`; the Image Studio assertions of `src/app/app.component.clear-all.component.spec.ts` are approved for removal; no header is created for Image Studio inside US-10.4.** The interim answer is superseded.
- **Status: ANSWERED (final).** Blocking: false. Transcribed as AC-4e and AC-8. What exactly the approval covers is OD-30; the dead code it leaves behind is OD-31.

### OD-2 - History button position and overlay anchor
- **Question.** Where does the History (clock) button live after the panel header loses its controls, and what does the overlay anchor to?
- **Evidence (carried).** The button is `@if (appMode() === 'generator')` in the old panel header (`app.component.html` line 33, `title="History"`). The overlay is `@if (showHistory() && appMode() === 'generator')`, `absolute inset-0 top-[125px]` inside the `<aside>` (lines 139-140). The old header holds the title row and the 13-button mode switcher; its height was not measured, but 125 px is plausibly less than that header's height, so today's overlay is not "directly under the header".
- **Answers (human, 2026-11-08, chat).** Two interim readings ("move History into the studio header"; "a History button in all modes") are **both superseded** by the final answer in Story v4: the History button and its overlay stay exclusively in `generator` mode, in the header of the input panel; not added to any other mode; the overlay is anchored to that same panel header (example `top-[64px]`, or the new header height).
- **Status: ANSWERED (final).** Blocking: false. Transcribed as AC-4d. Residue: what the panel header contains and how its height is defined, OD-22.

### OD-22 - Story Q3: panel header contents, app title/logo, header height

AC-4d requires an overlay "directly under that same panel header, whatever the new header height is". Owner gave `top-[64px]` only as an example. No source (Story, owner answers, AGENTS.md) places the logo. In every panel mode other than generator the header would hold nothing but, possibly, the title.
- **Why it cannot be inferred.** The owner's answers move controls out of the header but do not say what stays or where the title goes.
- **Impact if unresolved.** The Specification writer chooses the logo's home and the header's content. AC-4d is still writable structurally (the overlay is positioned from the header's own box, with no hard-coded pixel offset); a hard-coded `64px` would silently break if the header height differs.
- **Blocking: false.** A Specification design choice, ratified at HUMAN_SPEC_APPROVAL. Needed by: SPECIFICATION (record the choice), HUMAN_SPEC_APPROVAL.

### OD-23 - Story Q4: active item, collapsed groups, icon-only rail, `aria-expanded`, Dashboard `aria-current`

### OD-24 - Story Q5: group-state persistence, keys, unavailable storage
- **Question.** Is the open/closed state of each group persisted (the owner's earlier answer said "state is persisted"; AC-3 persists only the rail), under which key or keys, and what happens when `localStorage` is unavailable or holds a malformed value?

- **Why it cannot be inferred.** The word "state" in the v2 answer is ambiguous between rail only and rail plus groups; the Story took the narrow reading. The failure behaviour is unspecified.
- **Impact if unresolved.** The writer decides between persisting groups or not, and between crash, default-expanded or in-memory on storage failure. A guess toward "not persisted" may contradict what the owner meant.
- **Blocking: false.** AC-3 and AC-1 are literal enough to write: rail persisted, groups default-expanded, and the fallback is an NFR choice. Needed by: SPECIFICATION (record), HUMAN_SPEC_APPROVAL.
