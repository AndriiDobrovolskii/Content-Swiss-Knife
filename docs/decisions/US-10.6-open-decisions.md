## OD-1 - Gemini 4K image-to-image edit and multi-candidate support (Story Q1)

- **Question.** Does the Gemini image API accept (a) an image-to-image edit with `imageSize` 4K on the Pro model, and (b) several candidate images per `generateContent` call - and what happens to AC-1 / AC-3 if either answer is no?
- **Why it cannot be inferred.** Checked: `server/providers/gemini.js` `generateImage` sends only `responseModalities` and `imageConfig: { aspectRatio, imageSize }` (no candidate count anywhere); `src/prompt-core/model-catalog.json` lists 4K only for `gemini-3-pro-image` (its `resolutions`); `server/image-studio/request-schema.js` accepts 4K only for a model whose catalogue entry lists it; US-10.1 pre-implementation checks (`docs/evidence/US-10.1-pre-implementation-checks.md`) record V-1..V-10 but no candidate-count and no 4K-edit check; no upscale code exists. The Story points to "US-10.3 holds the live-verification pattern", but US-10.3 is `NOT_STARTED` in `docs/catalog/stories.yaml` and `test/` holds no Image Studio live spec; the only opt-in live spec in the repository is `test/doc-generation-live.spec.ts` (`LIVE_DOC_TEST`, AGENTS.md section 5). So that pattern has not been built for Image Studio.
- **Impact if unresolved.** The specification writer cannot say whether AC-3 is "one call, N candidates" or "N calls", and cannot promise AC-1 at all. A wrong guess ships a feature whose first real call fails (the US-10.1 `files.upload` precedent in AGENTS.md section 6 item 9). Also: Upscale is Pro-only, so what the session does when its model is Flash is OD-7.
- **Needed from the owner / evidence.** A recorded live check (method, tool and runtime versions, date, who ran it, raw output - the `evidence` artifact rules in `artifact-paths.yaml`), and a decision on whether the Specification should be written with both outcomes (as the Story's decision "N parallel calls if the API limits a request to one image" already allows) or wait for the check.
- **blocking: false.** The Story itself provides the fallback for (b); (a) has no fallback and AC-1 must be revised if it fails, which the Story already states.

## OD-2 - Per-resolution prices (Story Q2)

- **Question.** What is the price in dollars per generated image for each (model, resolution) pair the catalogue allows - Flash 1K/2K and Pro 1K/2K/4K - and from which source?
- **Why it cannot be inferred.** Checked: `server/usage/pricing.js` `IMAGE_PRICES` is keyed by model only (`gemini-3.1-flash-image` 0.03, `gemini-3-pro-image` 0.06); no resolution dimension exists in the repository. The recorded source (V-5 of `docs/evidence/US-10.1-pre-implementation-checks.md`) gives one flat price per model and names the Pro model as `gemini-3.1-pro-image-preview`, while the catalogue, price table and presets use `gemini-3-pro-image` - the evidence does not state the price of the id the code actually bills. The requester said only "for example 2x or 4x" for 4K. AC-14a requires only "4K costs more than the same model's 1K and 2K"; it does not say whether 1K and 2K are equal or different.
- **Impact if unresolved.** AC-13, AC-14 and AC-14a cannot name numbers, so tests cannot assert an expected cost and the estimate (OD-14) and the recorded cost cannot be equal by construction. A guessed multiplier mis-bills every 4K Upscale and under- or over-states the spend totals (AC-12).
- **Needed.** The prices from the official Gemini pricing, recorded as evidence with the exact model id each applies to, and a ruling on whether 1K and 2K differ.
- **blocking: false.** The Specification can fix the table's structure and the AC-14a ordering rule and cite the evidence for the values; the values must exist before TEST_WRITING.
- **Status (v2): ANSWERED** by the owner ruling of 2026-11-14 recorded in "Owner answers" below (prices and the 1K/2K question). The question text above is unchanged from v1. The ruling's scope limits are listed there; the input-image part is carried as OD-18.

## OD-3 - Image Studio row marker and the spend query (Story Q3)

- **Question.** (a) May the Image Studio writer set `mode` on new rows? (b) How do existing rows (written with `mode` null) get counted? (c) How does the client select Image Studio rows from `GET /api/usage`?
- **Why it cannot be inferred.** Checked: `server/image-studio/usage-row.js` writes `mode: null` and `taskLabel: 'image-studio|<presetId|none>|<resolution>'`; `queryUsage` in `server/usage/store.js` filters by `from`, `to`, `store`, `productName` (LIKE) and `taskLabel` by **exact** match, so a `image-studio|` prefix is not queryable; US-10.1 FR-72 / OD-35 deliberately decided "No stable marker is added to the `mode` column" and the dashboard test "with mixed old and new rows". `mode` is not a discriminator that is unique to Image Studio: the Story's own AC-12 says "`mode` being null", which text rows may also have (not verified here - the text-provider write path was not read).
- **Impact if unresolved.** AC-12 can be built three ways with different server and test consequences: client-side prefix filter over everything returned for the month; a new server filter / aggregate endpoint; or a `mode` value on new rows plus a rule for old rows. Under the third, rows older than the change are miscounted unless handled. This also reverses an earlier recorded decision (FR-72), which the Story does not mention.
- **blocking: false.**
- **Status (v4): ANSWERED** by the batch ruling recorded in v4 under "Owner answers" (batch of 2026-11-14), items G-8 (OD-3: marker = `taskLabel` prefix, `mode` null, client selects rows from the existing `GET /api/usage`). The question text above is unchanged.

## OD-4 - Who fans out N calls, and the contract (AC-3, AC-4, AC-5)

- **Question.** For Images = 2 or 4, does the client send N separate `POST /api/image-studio/generate` requests, or does the BFF accept one request and make N upstream calls (or one call with N candidates, subject to OD-1)? What is the response shape, including partial success?
- **Why it cannot be inferred.** Checked: the Story says "the generator makes N parallel calls if the API limits a request to one image, otherwise one call" without naming the layer. Today `createGenerateHandler` handles one request = one upstream call; the response is a union on `kind` (`images`, `text`, `safety`) with one `costUsd`; `trimRequest` runs `k+1` `countTokens` calls per request; the limiter is consulted once per request; one 120 s client deadline covers the whole user action (US-10.1 FR-21/FR-22, SD-30); `retryTransport` never applies to generate calls (CF-5).
- **Impact if unresolved.** The two designs differ in: the wire contract and `image-studio-contract.json`; where the limiter unit is taken (OD-5); how often history is trimmed and counted (N times the `countTokens` traffic if the client fans out); how partial failure is reported (N independent answers vs one union with a partial variant); where Cancel acts; and the size of every test. The wrong guess changes the API both runtimes read.
- **blocking: false.** Recommended to answer before SPECIFICATION.
- **Status (v4): ANSWERED** by the batch ruling recorded in v4 under "Owner answers" (batch of 2026-11-14), items G-2 A (server fan-out, one request carries `imageCount`). The question text above is unchanged.

## OD-5 - Rate-limit unit, partial grant and failed images (AC-4)

- **Question.** (a) How is one limiter step per image taken - a count argument to `tryConsume`, or one step per call? (b) Does an image whose upstream call failed (safety block, empty response, retries exhausted) still use one of the 30, as today ("a counted request is every one that reached the Gemini call, whatever its outcome", US-10.1 FR-66 as amended by OD-13)? (c) When zero units remain, is the whole request refused with the existing 429 `RATE_LIMIT_EXCEEDED` and `Retry-After`? (d) Is "Generated 2 of 4 images." computed by the BFF or the client?
- **Why it cannot be inferred.** Checked: `server/image-studio/rate-limiter.js` `tryConsume(key)` adds exactly one and refuses atomically; handlers call it once outside the retry loop; AC-4 gives the 28-used / request-4 / yields-2 example only. The Story says "each image counts separately" and, in AC-5, "recorded cost covers only those 2" for failures - it does not say whether failed images were also counted against the limit.
- **Impact if unresolved.** Limiter semantics decide whether a run with failures can lock the operator out earlier than they expect, and whether the limiter test (`test/image-studio/rate-limiter.spec.ts`, `app-limiter.composition.spec.ts`) changes. The partial-grant is a change to the atomic "check-and-increment" guarantee (FR-66) and needs an explicit rule for concurrent requests.
- **blocking: false.**
- **Status (v4): ANSWERED** by the batch ruling recorded in v4 under "Owner answers" (batch of 2026-11-14), items G-8 (OD-5: one limiter unit per image; a failed image that reached the call still counts; zero left = existing 429), with G-2 A (counts from server numbers) and SM-9. The question text above is unchanged.

## OD-6 - Partial failure, Cancel, billing granularity, announcements (AC-5, AC-16)

- **Question.** (a) How is each failed image shown (per slot, or one message), and with what text when the causes differ (safety, empty response, exhausted retries, file missing)? (b) Is Retry per failed slot or for the whole action? (c) What does Cancel do to images already returned - kept and billed? (d) Is there one usage row per image or one per response, and does `PRICE_NOT_CONFIGURED` for one image fail the whole action? (e) What is announced when some images succeed and some fail?
- **Why it cannot be inferred.** Checked: AC-5 says only "the failure is shown, never silent"; US-10.1 FR-74 / OD-21 defines exactly two `role="status"` announcements for a success and exactly one for any end without a version, with the highest version number for multi-image responses (OD-30 C-30.5); SD-22 / CF-6 treat a response arriving after Cancel or after the session is gone as a discarded paid response; FR-71 / SD-22 define how cost is added; US-10.1 FR-83 uses `role="alert"` for errors. None of these covers a mixed outcome.
- **Impact if unresolved.** AC-16 (exactly one `role="status"`) and AC-5 can contradict each other in the mixed case; the cost total and the `usage_log` sum diverge differently under per-image vs per-response rows; tests for the mixed case cannot be written.
- **blocking: false.**
- **Status (v4): ANSWERED** by the batch ruling recorded in v4 under "Owner answers" (batch of 2026-11-14), items G-8 (defaults of FR-9 (a)(b)(d)(e) and FR-24) and G-2 A (Cancel discards the whole action; Proposed FR-9 (c) does not hold), with SM-9. The question text above is unchanged.

## OD-13 - Header spend: refresh, failure display, format, relation to the session total (AC-12)

- **Question.** (a) When is the figure fetched and refreshed (open, after each generation, on an interval)? (b) What shows while loading and on error? (c) Number format (decimals, locale)? (d) Is the existing per-session running total (US-10.1 FR-71) kept alongside it? (e) Is "today" the UTC day for an operator in a UTC+2/+3 timezone?
- **Why it cannot be inferred.** Checked: the Story states UTC for both boundaries ("Decisions taken") and "global, not the 7-day client cache", so (e) is decided; FR-71 says the session total is "explicitly not authoritative: it is not derived from `GET /api/usage`" and the header today (`studio-header.component.html`) shows no cost; `/api/usage` returns every matching row (no limit or aggregation); Image Studio rows carry no client identity, so "global" includes every operator.
