- **Why it cannot be inferred.** Checked: `npm view @google/genai versions` shows 2.32.0 and 3.0.0 to 3.3.0 are published (so (c) is consistent at the registry level), and `npm view @google/genai@2.32.0 engines` gives `node >=20.0.0`; installed version is `1.52.0` (`node_modules/@google/genai/package.json`), `package.json` has `^1.43.0`. The Story itself says the version and behaviour claims "were not verified against Google's pages when recorded". Not checked, and not checkable from the repo: the 2.x changelog or the Gemini 4 documentation. The repo code encodes 1.52.0 internals: `server/providers/gemini.js` carries three load-bearing comments about them (the `retryOptions` loop at `dist/node/index.mjs:13305`; `files.upload` replacing resumable-upload headers with `config.httpOptions` and answering an empty 404; `files.upload` ignoring `config.abortSignal`). - **Impact if unresolved.** AC-13 says every pre-existing Gemini provider, retry and Image Studio spec "passes against the upgraded SDK", but those specs use fakes, and the same fakes hid the `files.upload` 404 (memory: genai files.upload timeout 404, US-10.1). ## OD-3 - Timeout semantics under SDK continuation (Story Q9)

- **Question.** On `@google/genai >= 2.32.0`, when one `generateContent()` call issues two sequential HTTP requests, does `config.httpOptions.timeout` bound each request or the whole call?
- **Why it cannot be inferred.** Checked: `server/utils/timeouts.js` (`DEEP_TIMEOUT_MS` 1,200,000; `VISION_TIMEOUT_MS` 600,000; `FAST_TIMEOUT_MS` 120,000) and its call sites in `gemini.js` (`timeoutForMode(mode)` in `generate`, `VISION_TIMEOUT_MS` / `FAST_TIMEOUT_MS` in `analyzeImage`, `FAST_TIMEOUT_MS` in `extractFromPdf`); the installed SDK is 1.52.0 which has no continuation, so the behaviour cannot be read from `node_modules` today. The Story marks Q9 as unanswered and the owner's note as "a request to check, not a finding". The Scope lists `timeouts.js` as "verify only".
- **Impact if unresolved.** The Specification cannot say whether the Surface stays "verify only". If the timeout covers the whole call, a Carbon call that needs a second hop in the Fast slot (120 s) could abort although each hop is within budget, and `withRetry` would retry it as a transport failure (up to the retry budget), which is costly on a paid model. If it is per hop, nothing changes.
- **Needed.** Evidence from the `2.32.0` source or one real continuing call (see OD-5), and, if the answer is "whole call", a ruling on whether `timeouts.js` joins the Surface.
- **blocking: false.** The Specification can carry both branches; the Surface must be settled before ARCHITECTURE_PLANNING.

## OD-4 - AC-4 "selecting a model sets its default level" vs existing model-switch behaviour

- **Question.** In the model dropdown, does selecting a model reset the slot's level to that model's `defaultLevel` (Carbon `medium`, Hydrogen `high`) as AC-4 literally says, or does it keep carrying the current level across with a clamp, as `setDeepModel` / `setFastModel` do today? If the former, for all models or only the two new ones?
- **Why it cannot be inferred.** Checked: `src/services/model-settings.service.ts` `setDeepModel` / `setFastModel` call `clampLevel(provider, spec.id, currentLevel)` ("Carry the current level across if the new model accepts it") and never read `defaultLevel`; only `setDeepProvider` / `setFastProvider` set `spec.defaultLevel`; the dropdown template (`model-settings.component.html` lines 52 and 121) calls `setDeepModel` / `setFastModel`. So with the current code, switching the Deep slot from Sonnet 5.5 at `high` to Carbon via the dropdown yields `high`, not `medium`. AC-7 describes the provider switch (which does set `defaultLevel`) separately, so AC-4 is not just AC-7 restated. AC-3 says Anthropic behaviour is "the same as before this Story", and the Out of scope list does not mention changing model-switch semantics.
- **Impact if unresolved.** Three buildable readings with different consequences: (1) change `setXModel` to reset to `defaultLevel` for every model, silently altering the Anthropic and Gemini 3.x switch behaviour and existing specs (`model-settings.service.spec.ts`); (2) special-case only the two new models, an inconsistent rule; (3) read AC-4 as the provider-switch path only, leaving AC-4 untestable on the dropdown. A wrong guess either fails AC-4's literal test or ships an unrequested behaviour change.
- **Needed from the owner.** Which of the three readings, in one sentence.
- **blocking: false.** SPECIFICATION can present a Proposed block, but this is the Open Decision most likely to be built wrong; answering it first is recommended.

## OD-6 - Usage and cost accounting across continuation hops and Gemini 4 usage fields

- **Question.** When SDK continuation stitches a response from two HTTP requests, does the returned `usageMetadata` sum both hops (prompt, candidates, thoughts, cached tokens), and are the field names `promptTokenCount`, `candidatesTokenCount`, `thoughtsTokenCount`, `cachedContentTokenCount` the same for Gemini 4 and for SDK 2.x?
- **Why it cannot be inferred.** Checked: `GeminiProvider#usage` in `server/providers/gemini.js` reads exactly those four fields from one response and returns cost inputs; `computeCost` in `server/usage/pricing.js` multiplies them; `server/index.js` line 83 stores the result. Nothing in the repo shows a two-hop response, and the installed SDK 1.52.0 has no continuation. The Story's value statement includes "see correct cost for what I run", and AC-9 only tests `getPrices`, not the usage read.
- **Impact if unresolved.** If hop-1 tokens are dropped, every continued Carbon call under-reports cost (the largest, most expensive calls); if prompt tokens are counted twice the cost is over-reported; a renamed cache field zeroes `cacheReadTokens` and overstates input cost by up to 20x on cached prefixes. The Specification has no requirement to write against, and AC-9 would pass either way.
- **Needed.** The SDK's documented or observed usage semantics for a continued call, as evidence (OD-2), and a ruling on whether a usage-read requirement and test belong in this Story.
- **blocking: false.**
