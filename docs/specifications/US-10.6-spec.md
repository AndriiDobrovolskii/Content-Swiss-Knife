# Specification: US-10.6 - Add the new Image Studio capabilities from the design - Upscale 4K, Variation, several images per generation, Style ref, saved presets, spend totals and pre-send estimate

## Summary

When this is done every generated image in Image Studio has an "Upscale 4K" and a "Variation" action, the composer has an "Images" selector (1, 2, 4), a Product / Style ref role per attached image and a "+ Save current as preset" control with deletable user presets, and the studio shows "Today $X · month $Y" in its header and "≈ $X for N images" next to Generate. One turn can hold several images, each image counts separately toward the 30-per-hour limit and toward cost, a partial result is shown and billed only for the images that exist, and one price table (model and resolution) is the single source of both the estimate and the recorded cost. Everything Image Studio already does keeps working, except the two amendments the Story names (AC-3 as AC-8, AC-42 as AC-4).

## Background

US-10.6 is part 3 of 3 of the Image Studio redesign (US-10.4 app shell and US-10.5 visual layer are `ARCHIVED`). US-10.5 deliberately rendered none of these controls (its AC-4 and AC-10), so nothing yet specifies where they sit or what they say (OD-11).

Inputs and their authority:

- **Story v2** (DRAFT). Its "Decisions taken (2026-11-08)" are the base text of this Specification; its three Open questions Q1, Q2, Q3 are OD-1, OD-2, OD-3.
- **Open Decisions v1** (OD-1..OD-17, **none blocking**) and **clarification report v1** (verdict "Ready for Specification", conditional on every OD becoming an explicit requirement or a marked Proposed block). The log has no "Owner answers" section yet: **no Open Decision has an owner ruling**.
- **Specification review v1** (CHANGES_REQUIRED), addressed in the revision notes above.
- AGENTS.md sections 3 to 7, 9, 11.

How the Open Decisions are handled. This Specification resolves none. Where the Story or an AC fixes a point, the point is a base requirement and cites the AC. Where the Story is silent, the requirement states only what the AC already requires and the gap is a block headed **Proposed (OD-n)**: a reviewable assumption for HUMAN_SPEC_APPROVAL, not a decision. A Proposed block is not a requirement until the owner rules on it. The two vendor facts (OD-1, OD-2) are not choices and cannot be closed by a Specification: they are stated as preconditions in FR-1, FR-5 and FR-22 and as an evidence obligation in NFR-7.

Facts about the current code that the requirements rest on (read by the clarification and review stages, not designed here): one generate request makes one upstream call and the limiter is consulted once per request (`tryConsume(key)` adds exactly one, atomically); the response is a union on `kind` with one `costUsd`; the price table is keyed by model only (`gemini-3.1-flash-image` 0.03, `gemini-3-pro-image` 0.06), the cost of an image answer is `unit * count` with **no rounding** (`computeImageCost`), `costUsd` is stored and returned as that unrounded number, and an unknown model throws `PRICE_NOT_CONFIGURED` (500) after the paid call; 4K exists only for `gemini-3-pro-image`; request validation rejects a model/resolution pair that is absent from the catalogue with `INVALID_REQUEST` (400) before any upstream call; the usage row of Image Studio has `mode` null and `taskLabel` `image-studio|<presetId|none>|<resolution>`; `GET /api/usage` filters only by `from`, `to`, `store`, `taskLabel` (exact match) and `productName`; the Gemini call sets no candidate count; `Version` stores its own `resolution`; a `Part` is forwarded to Gemini as stored, unknown fields included; when a generation ends (the in-progress state goes from true to false) the studio moves focus to the prompt field if it is enabled, whatever element had focus (US-10.1 FR-76).

Observations by the specification writer (recorded, not decided):

1. **Numbering clash in AC-1.** AC-1 says "running it on version `v{N}` creates a new version `v{N+1}`". If N is not the session's highest version, `v{N+1}` already exists. FR-1 therefore states the new number as "the next number after the session's highest" and marks that reading Proposed (OD-7, OD-9).
2. **Three markers for "Image Studio row".** AC-12 says `mode` is null, US-10.1 FR-72 deliberately wrote no marker in `mode`, and `GET /api/usage` cannot filter by a `taskLabel` prefix. FR-18 states the AC and leaves the selection mechanism Proposed (OD-3).
3. **AC-5 and AC-16 can contradict** in a mixed outcome (some images fail) because AC-16 fixes exactly one `role="status"`. FR-9 and FR-24 state both and the mixed case is Proposed (OD-6).
4. **AC-14 is stated for "one successful generation"** only. Whether the estimate also applies to Upscale and Variation is not stated (OD-14b); FR-20 is limited to Generate.
5. **AC-16 says focus "stays" in the prompt field.** For Upscale and Variation, which start from a button on an image, focus is on that button, not in the prompt field, when the action starts. FR-24 reads AC-16 as "focus is in the prompt field when the action ends", which is how US-10.1 AC-48 is implemented today.
6. **The vendor facts are verified after approval.** The Open Decisions log and the clarification report put the OD-1 and OD-2 evidence before ARCHITECTURE_PLANNING, a stage after HUMAN_SPEC_APPROVAL. The human therefore approves a Specification whose AC-1 depends on a vendor fact that has not been checked. This Specification states that plainly (FR-1, NFR-7, Open questions) instead of requiring the check before approval; whether to run it earlier is the owner's choice.
7. **The 5-image limit can be broken by a role change, not only by attaching.** A newly attached image is Product (AC-6), so the state "five Product uploads and one Style ref" is reachable (attach four, mark one Style ref, attach a fifth Product). Changing that Style ref upload back to Product would hold six Product uploads, which US-10.1 AC-3 (kept by AC-15) forbids. The attached "Edit this" version is outside the five today (US-10.1 FR-10) and stays so. FR-12 states the behaviour and the paths it covers.

## Functional requirements

### FR-1: Upscale 4K action creates one new 4K version

Each generated image has an "Upscale 4K" action (AC-1). When the operator runs it on version `v{N}`, the session gains one new version whose resolution label is 4K, produced by an image-to-image edit call to the Pro model in which the chosen version is sent as the input image with resolution 4K (Story, Decisions taken). The usage record written for that call carries resolution 4K and the model used (the model id and the resolution segment of the existing `taskLabel`). The new version is billed as a 4K generation from the price table (FR-22).

Precondition (OD-1, vendor fact): this requirement holds only if the Pro model accepts an image-to-image edit with resolution 4K. The live check is due before ARCHITECTURE_PLANNING (NFR-7), which is after HUMAN_SPEC_APPROVAL; the Specification is therefore approved with this precondition unverified (observation 6). If the recorded check shows the edit is not accepted, AC-1 is not satisfiable as written: the Story must get a new version that revises AC-1, and this Specification must be revised from it, before any later stage continues. The Specification supplies no fallback. The owner may instead require the check before approval.

**Proposed (OD-7): new number.** The new version takes the next consecutive number after the highest version number in the session, so it is `v{N+1}` when `v{N}` is the latest and does not overwrite or renumber an existing version otherwise. Rationale: the literal AC-1 reading collides when N is not the latest (observation 1).

**Failure path:** if the call fails (safety block, empty response, upstream retries exhausted, file missing, rate limit), the session gains no new version, no usage row is written for a call that produced no image, the failure is shown to the operator and is not silent, and the source version is unchanged. The same error handling and codes as a failed generation apply (no new error code is introduced by this requirement). When the call is refused by the hourly limit, FR-8 applies. When the action cannot run for the model and resolution of the source version, FR-2 (c) applies.

### FR-2: Upscale request content and availability (Proposed only)

This requirement has no base obligation of its own: the base obligation for AC-1 is FR-1. The Story fixes only that the chosen version is sent as the input image with resolution 4K. The following are not fixed and are written as assumptions for the owner to rule on at HUMAN_SPEC_APPROVAL:

- (a) **Proposed (OD-7).** The request carries the chosen version's image, the version's aspect ratio and resolution 4K; it carries no session history and no attachments of the original turn.
- (b) **Proposed (OD-7).** If the request needs an instruction text, that text is Image Studio prompt text and lives in a non-frozen file in `src/prompt-core/` or `src/prompts/` (AGENTS.md section 3 Rule 3, section 7.4; see Scope "Home of new prompt text"), in a form the owner approves before TEST_WRITING (AGENTS.md section 1: prompt-text changes are proposed, never taken unilaterally). The Specification does not write it.
- (c) **Proposed (OD-7, shared with OD-8): the model of a derived action.** An Upscale needs the Pro model, because 4K exists only there. When the session's selected model is Flash, the action stays present on the image (AC-1 requires that every generated image has the action) and one of two behaviours applies, which the owner chooses: (i) the action is disabled, and the reason is available to the operator as text (an accessible description or visible hint); or (ii) the call is made to Pro without changing the session's selected model. Under neither option does a Flash session send a 4K request to Flash, and under neither is the action absent. The option "hide the action" is not offered, because it would make AC-1 false for those images and would need a Story revision first. The same rule applies to a Variation whose output pair is not valid for the model that would be used (FR-3).
- (d) **Proposed (OD-7).** For a version that is already 4K the action is present and disabled, with its reason available as text.
- (e) **Proposed (OD-7).** The upscale is stored as a new model turn after a user turn so that history keeps the alternating, even-length shape the request validation requires; the shape of the user turn is the owner's ruling.
- (f) **Proposed (OD-7).** The usage row of an Upscale is distinguishable from a generation only by what AC-1 requires (resolution and model); no extra marker is added.

**Failure path:** as FR-1. For (c) (i), pressing a disabled action sends nothing and writes nothing.

### FR-3: Variation action creates K new versions

Each generated image has a "Variation" action (AC-2). When the operator runs it on version `v{N}`, the request sent to the model contains `v{N}` as a reference image together with the turn's original prompt, and with the Images selector at K the session gains K new versions with consecutive numbers (FR-7). Each of the K images counts separately toward the hourly limit and toward cost (FR-8, FR-9).

**Proposed (OD-8), awaiting the owner.** "The turn's original prompt", the model, the resolution and the attachments are not defined by the Story:

- (a) "Original prompt" is the prompt text the source turn was sent with. For a turn that was sent without text (images-only or chip send), the Variation request carries `v{N}` and no prompt text, and is still sent.
- (b) The turn's original attachments and its Style ref are not resent; only `v{N}` is the reference.
- (c) No session history is sent beyond the Variation turn itself.
- (d) **Resolution, aspect ratio and model.** The aspect ratio is that of `v{N}`. The resolution is that of `v{N}`, so a Variation of a 4K version is a 4K generation priced as 4K. The model is chosen by the owner from: the session's selected model at the moment the action is pressed, or the model that produced `v{N}`. Whichever is chosen, the pair (model, resolution of `v{N}`) must be one the catalogue allows. The case that breaks this is a 4K version in a session whose model is Flash (the model was switched after the 4K image was made): request validation rejects a 4K / Flash pair. That case follows the same ruling as FR-2 (c): the action is either disabled with a reason available as text, or it runs on the model that supports the resolution, without changing the session's selected model. Under neither option is a request sent that validation would reject, and under neither is the output resolution silently changed to fit the model.
- (e) K is the value of the Images selector at the moment the action is pressed; changing the selector later does not alter a request in flight.

**Failure path:** if every one of the K images fails, no version is added, no usage row is written, and the failure is shown (FR-9). A partial result follows FR-9. A refused request follows FR-8. A (model, resolution) pair that cannot be used follows (d): nothing is sent, nothing is written, and the operator can see why.

### FR-4: Images selector

The composer has an "Images" selector with the values 1, 2 and 4; the default is 1 (AC-3). No other value can be chosen. The selected value applies to Generate and to Variation.

**Proposed (OD-11):** the value is part of the composer draft and resets to 1 on a new session; its placement and label text are in FR-25.

**Failure path (Proposed, OD-11):** a value outside {1, 2, 4} that reaches the selector from a stored draft or from code is treated as 1 and is never sent as a count. The Story does not state this boundary; it is written here so a test has a defined expected value, and the owner can rule otherwise.

### FR-5: Generating N images adds N consecutive versions to one turn

Choosing N in the Images selector and pressing Generate adds N versions with consecutive numbers to the same turn (AC-3). The Story fixes the means: if the image API limits a request to one image, N parallel calls are made; otherwise one call returns N images (Story, Decisions taken). Which of the two is true is a vendor fact (OD-1) and is a precondition: the Specification states both outcomes and requires the observable result to be the same.

Observable result in both branches: after the action ends, the turn shows between 0 and N new images; the successful ones have consecutive version numbers; the cost and the hourly-limit count follow FR-8 and FR-9.

**Failure path:** FR-9.

### FR-6: Where the N calls are made and the wire contract (Proposed only)

This requirement has no base obligation of its own: the base obligation for AC-3 is FR-5. The Story does not say which layer makes the N calls. **Proposed (OD-4), awaiting the owner, recommended to be answered before approval.** The constraints the owner's ruling must satisfy are:

- (a) The hourly-limit decision (FR-8) and the partial-success report (FR-9) are made in one place, atomically. The two options the owner chooses between are: the client sends one request that carries the image count and the server fans out, or the client sends N requests. This Specification does not choose, and the planner is not bound by either option until the owner rules.
- (b) Whichever layer fans out, the existing 120 s client deadline for the user action, the Cancel behaviour of US-10.1 and the discarded-paid-response rule of US-10.1 (a response arriving after Cancel or after the session is gone) stay valid; how they combine with N calls is the owner's ruling.
- (c) Any contract change is reflected in the shared contract file both runtimes read; a field that exists on one side only is a defect.

**Failure path:** n/a, a contract shape has no failure of its own; FR-9 covers the outcomes.

### FR-7: Version numbering is deterministic (Proposed only)

This requirement has no base obligation of its own: AC-3 and AC-2 require consecutive numbers (FR-3, FR-5), not the order in which they are given when calls finish at different times. **Proposed (OD-9), awaiting the owner.**

- (a) The numbers are given in slot order (the order the images are requested), not in completion order, and only to images that succeed, with no gaps among the successful ones. A test that makes the second call finish before the first must see the same numbers as one that does not.
- (b) The N results are stored in one model turn when the stored history stays valid for the next request, including any thought signature a result carries, which is echoed back exactly as received (US-10.1 FR-35). If merging cannot keep the history valid, the owner decides how the results are stored; the requirement that the version numbers are consecutive and in the same turn does not change.

**Failure path:** if a stored turn could not be reused as valid history, the next request must not fail because of the new turn's shape; this is checked by the test for FR-5.

### FR-8: Each image counts toward the 30-per-hour limit

Each generated image counts as one generation toward the 30-per-client-per-hour limit (US-10.1 AC-42; AC-4). When fewer units remain than images requested, the request is not rejected as a whole: it generates as many images as units remain and shows the warning "Rate limit reached. Generated 2 of 4 images." for the example of 28 units already used and 4 images requested (2 generated of 4). Only the images generated are billed.

The Story fixes the example only. The general rule written here is the one the example implies: with U units remaining and N requested, `min(U, N)` images are generated and the warning reads "Rate limit reached. Generated {generated} of {requested} images." with the numbers filled. The unit consumption and the grant of a partial allowance are one atomic check-and-increment: two concurrent requests cannot together exceed 30 (the guarantee of US-10.1 FR-66 is kept).

**Proposed (OD-5), awaiting the owner:**

- (a) Whether an image whose upstream call failed (safety block, empty response, retries exhausted) still uses one of the 30. Today "a counted request is every one that reached the Gemini call, whatever its outcome" (US-10.1 FR-66 as amended by its OD-13). Proposed: the same rule per image, so a failed image that reached the call counts. AC-4 itself says "each generated image counts", so this goes beyond the Story's wording; the owner should see that it can lock the operator out earlier than the number of images shown suggests (for example, four images requested, two blocked, still consumes four units).
- (b) When zero units remain, the whole request is refused with the existing `RATE_LIMIT_EXCEEDED` (429) and `Retry-After`, and no image is generated.
- (c) The "Generated {generated} of {requested}" text is composed from numbers the server reports, not from client arithmetic. Its UA text is in FR-25.
- (d) An Upscale (one image) and a Variation (K images) use the same per-image count.

**Failure path:** zero units remaining is the failure path; as (b). A warning that cannot be displayed must not hide the images that were generated.

### FR-9: Partial failure shows the successes and bills only them

When some of the N requested images fail, the turn shows the images that succeeded, the recorded cost covers only those images, and the failure is shown and never silent (AC-5). Example from the Story: 2 of 4 fail, the turn shows 2 images and the recorded cost is that of 2 images. When all N fail, the turn shows no image, the cost is zero and the failure is shown.

**Proposed (OD-6), awaiting the owner:**

- (a) The failure is shown in an element with `role="alert"` (the existing error convention of US-10.1 FR-83) that states how many images failed and, when causes differ, one line per cause class (safety, empty response, retries exhausted, file missing). An upstream rate-limit answer on one call is the cause class "retries exhausted" for that image only. The UA and EN texts are in FR-25.
- (b) A Retry applies to the whole action, not to a single failed slot; images already shown are kept and a Retry that succeeds adds new versions after them.
- (c) Cancel keeps the images already returned and bills them, because they were paid for upstream; images not yet returned are not added (the discarded-paid-response rule of US-10.1 applies to a response that arrives after Cancel).
- (d) Cost is recorded one usage row per successful image, each at the price of its model and resolution (FR-22). If the price for the pair is not configured, nothing is shown as success and nothing is recorded for that action (FR-22).
- (e) The "Today / month" total (FR-18) and the existing session running total are both computed from the images that succeeded only.

**Failure path:** the requirement is itself the failure path. If recording the cost of a successful image fails, the successful image is still shown (the existing rule "a row-write failure does not change the 200").

### FR-10: Role selector on an attached image

Each attached image has a "Product" / "Style ref" selector (AC-6). A newly attached image has the role Product.

**Failure path:** a two-value selector with a fixed default has no invalid input of its own. The one change it can refuse is a change to Product that would leave more than five Product uploads attached; that case is FR-12.

### FR-11: At most one Style ref per generation

At most one attached image can have the Style ref role per generation. Marking a second image as Style ref is rejected with an explanatory message and the first stays marked (AC-7). The rejection does not clear, move or change the role of any other image.

**Proposed (OD-11):** the message is shown in an element with `role="alert"` and, for the Story's wording, it names the reason (only one Style ref is allowed per generation); the texts are in FR-25. It does not use the single `role="status"` of FR-24. The rejection of a role change to Product under the 5-image limit (FR-12) uses the same channel.

**Failure path:** the rejection is the failure path; removing the Style ref image makes the role available again, which a test must assert.

### FR-12: A Style ref image is outside the 5-image limit, the attached version stays outside it, and the limit holds when roles change

A Style ref image does not count toward the 5-image limit of US-10.1 AC-3 (AC-8). One Style ref image plus five Product uploads can be attached together (six uploads in all); attaching a sixth Product upload is rejected exactly as today; with five Product uploads and no Style ref nothing changes. The attached "Edit this" version (`attachedVersion`) is outside the five exactly as today (US-10.1 FR-10: 5 uploads plus one attached version are accepted, a 6th upload is rejected); this Story does not change that. Any other limit that exists today (accepted image type, request body size, file size) applies to the Style ref image unchanged.

**Invariant.** At every moment the composer holds at most five Product uploads and at most one Style ref image (FR-11). The attached "Edit this" version is not an upload and is not counted in the five, as today. No path may leave it otherwise.

**Changing a role.** Because a newly attached image is Product (FR-10), the state "five Product uploads and one Style ref image" is reachable. When the operator changes an upload's role from Style ref to Product while five Product uploads are already attached, the change is rejected: the image stays Style ref, no other image changes, and an explanatory message is shown. The message is shown in an element with `role="alert"`, the channel of FR-11 and not the single `role="status"` of FR-24; it states that at most five Product uploads can be attached; its UA and EN texts are in FR-25. Removing a Product upload makes the change possible again, which a test asserts. A change from Product to Style ref never raises the Product count, so it is governed by FR-11 only.

**Every path that sets or changes a role.** The same invariant applies to each of these, and a test covers each:

- (a) the role selector of an attached image, in both directions (the case above and FR-11);
- (b) attaching a new image (it is Product, so the existing limit applies as today);
- (c) removing an image (it frees capacity and never causes a rejection);
- (d) attaching the "Edit this" version (`attachedVersion`): it stays outside the five-image limit exactly as today (US-10.1 FR-10; the existing count rule counts uploads only), so attaching it neither raises the upload count nor is refused by the limit, and 5 uploads plus an attached version are accepted while a 6th upload is rejected. Whether it shows a Product / Style ref selector, and whether it can be a Style ref, is not ruled (FR-14, OD-10 (d));
- (e) re-uploading an expired file (FR-14), which keeps the image's role and adds no image, so it neither raises the Product count nor is blocked by the limit;
- (f) restoring a role from storage (FR-14): a stored value that is not Style ref is treated as Product, and a restore never turns a Style ref image into a Product image beyond the limit.

**Failure path:** a Style ref image that fails the existing type or size checks is rejected with the existing message for that check. A role change refused by the limit is the failure path of the "Changing a role" paragraph: nothing is sent, nothing is stored, and the operator sees why. A message that cannot be displayed must not let the change through.

### FR-13: Style ref instruction in the request

The request sent to the model contains, for the Style ref image, the instruction "Use this image purely as a stylistic reference, do not copy the product from it" (AC-9). The text is exactly this sentence (quoted from AC-9); it is Image Studio prompt text and lives in a non-frozen file in `src/prompt-core/` or `src/prompts/`, not in a service (AGENTS.md section 3 Rule 3, section 7.4). The FROZEN files in those directories (`task-a.ts`, `task-b.ts`, `task-c.ts`, `master-system-prompt.ts`) are not a home for it (AGENTS.md section 9). A request with no Style ref image does not contain the sentence.

**Proposed (OD-10), awaiting the owner:**

- (a) The instruction is a text part placed immediately before or after the Style ref image part in the same user turn; the choice of side is the owner's ruling.
- (b) The sentence is sent in English regardless of `uiLanguage`.
- (c) The role tag is not placed on a part that is forwarded to Gemini, because parts are forwarded with unknown fields intact and an unknown field can make Gemini answer 400.

**Failure path:** if a Style ref image is the only image and there is no prompt text, the owner decides whether the send is allowed (OD-10e); until ruled, the send follows the existing "something to send" rule of the composer.

### FR-14: History keeps the role tag

The stored history keeps the role of each attached image, so after a reload or a reopened session the image is still shown with its Product or Style ref role (AC-9). A session saved before this Story has no role tag; every image in it is treated as Product and the session loads without being discarded.

**Proposed (OD-10), awaiting the owner:** the tag is part of the stored session shape (the optional field the US-10.5 stored-session validation passes through), and is not sent to Gemini (FR-13c). On a later turn of the same session the Style ref instruction is not repeated for an image that was a Style ref on an earlier turn unless that image is attached again; the expired-file re-upload keeps an image's role; history trimming drops images by the existing rule and does not treat a Style ref image differently. The attached "Edit this" version (`attachedVersion`) stays outside the five-image limit exactly as today (US-10.1 FR-10); the invariant of FR-12 is at most five Product uploads and at most one Style ref. Whether the Product / Style ref selector is shown on the attached version, and whether it can be a Style ref, is not ruled (OD-10 (d)) and is left to the owner; by default it is Product, as a newly attached image is (AC-6).

**Failure path (Proposed, OD-10):** a stored role value that is neither Product nor Style ref is treated as Product and the session is not discarded; the Story does not state this.

### FR-15: Save the current settings as a user preset

"+ Save current as preset" saves the current prompt, aspect ratio, resolution and model as a user preset under a name the user types (AC-10). The name is stored exactly as typed and is not localized. The preset appears in the preset row, survives a page reload (it is kept in `localStorage`; the Story forbids a backend), and when chosen it applies exactly like a registry preset (US-10.1 AC-15): it fills the prompt, aspect ratio, resolution and model the way a registry preset does and is shown as checked in the same way.

**Proposed (OD-12), awaiting the owner:**

- (a) A user preset gets an id generated by the client that matches the pattern a registry preset id must match (`^[a-z0-9][a-z0-9-]{0,63}$`) and contains no `|`, never the typed name, so a name containing `|` or non-ASCII text cannot corrupt the `taskLabel` or fail request validation. The typed name is the display text only. When a user preset is checked, the usage row's preset segment carries that id.
- (b) The saved prompt is the composer text as it is at the moment of saving, literal. It is not turned into a `{product}` template.
- (c) An empty or whitespace-only name is not saved and the control reports why. A name equal to an existing user or registry preset name is not saved silently over it. A maximum name length and a maximum number of user presets are fixed by the owner; the Specification invents neither value, and TEST_WRITING needs both.
- (d) If `localStorage` is unavailable, full, or holds data that does not parse, the studio still works, registry presets remain usable, and a save that cannot be stored reports that it was not saved; data that does not parse is ignored, not partly applied, and is not deleted by merely loading it.
- (e) When a user preset is applied and its model is no longer in the catalogue, or its resolution is not allowed for its model (for example 4K with a Flash model), the preset is not applied silently as saved: the owner decides whether it falls back to the model's default resolution or the application is refused with a message.

**Failure path:** as (c), (d) and (e).

### FR-16: Delete a user preset

A user preset has a delete control (a trash or cross icon) that is visible on hover and on keyboard focus (AC-10a). Deleting removes the preset from the row and from `localStorage`. Registry presets have no delete control. The control has an accessible name that includes the preset's name.

**Proposed (OD-12f), awaiting the owner:** deletion is immediate with no confirmation; if the deleted preset is the one currently checked, it is unchecked and the composer fields keep their current values.

**Failure path (Proposed, OD-12d):** if removing from `localStorage` fails, the preset is not shown as deleted and the failure is reported; the Story does not state this.

### FR-17: Registry presets are unaffected

Registry presets in `PROMPT_PRESETS` are unaffected by saving or deleting user presets (AC-11): `PROMPT_PRESETS` is not mutated, registry presets keep their order, texts and ids, and saving, deleting or failing to read user presets never adds, removes or changes a registry preset in the row.

**Failure path:** n/a, no failure path of its own; FR-15 (d) covers storage failure.

### FR-18: Header shows today's and this month's spend

The studio header shows "Today $X · month $Y" (AC-12), where X and Y are the sums of the cost of Image Studio usage rows only, taken from `GET /api/usage` (global, not the 7-day client cache) for the current UTC day and the current UTC month. Text-generation rows are not included. An Image Studio row is a row the usage store marks as such: today a `taskLabel` starting with `image-studio|` with `mode` null. A month with no Image Studio rows shows `$0.00`.

**Proposed (OD-3), awaiting the owner.** How the rows are selected is not stated by the Story (it reverses the "no marker in `mode`" decision of US-10.1 FR-72 if a `mode` value is added):

- (a) The marker stays the `taskLabel` prefix `image-studio|`, with `mode` null, as AC-12 describes it; no `mode` value is written for new rows, so rows written before and after this Story are counted by one rule and no old row is miscounted.
- (b) Because `GET /api/usage` can filter a `taskLabel` only by exact match, the selection of the prefix is made after the rows are returned, on the client or by a new server filter; which one is the owner's ruling. Whichever is chosen, rows of text generation are excluded and a test with mixed old and new rows asserts it.

**Proposed (OD-13), awaiting the owner:**

- (c) The totals are fetched when the studio opens and again after each generation, Upscale or Variation that ends with at least one image.
- (d) While loading and after a failed fetch the header shows a neutral placeholder and no figure; a failed fetch does not block or hide any other part of the studio and does not show a wrong number such as `$0.00`.
- (e) Amounts show two decimals with a dot separator and a leading `$`. Under the first comparison rule of FR-21 this is display formatting only: X and Y are summed from the stored, unrounded `costUsd` values and rounded once, for display. Under the second rule of FR-21 the stored values are already rounded and the sums are of rounded values.
- (f) The existing per-session running total (US-10.1 FR-71) is kept; the session total is explicitly not authoritative and is not replaced by the header totals.

**Failure path:** as (d).

**Note for the planner (not a requirement).** The month figure needs every usage row of the month, text-generation rows included, because the filter is applied after the rows are returned (OD-3b) and `GET /api/usage` has no aggregation or limit. The volume grows with usage and no requirement here bounds it; this is recorded so the plan can decide whether a server-side filter or aggregate is warranted.

### FR-19: Spend day and month are UTC

The "today" and "month" boundaries are in UTC (Story, Decisions taken): "today" is from 00:00:00 UTC of the current UTC date and "month" is from 00:00:00 UTC of the first day of the current UTC month, both up to now. The boundaries do not depend on the operator's time zone. A row written at 23:30 UTC counts for that UTC day, not for the next day of an operator in UTC+2.

**Failure path:** n/a, a boundary computation has no failure path of its own; the clock is injectable so a test can fix it (NFR-5).

### FR-20: Pre-send estimate next to Generate

The pre-send estimate "≈ $X for N images" is shown next to Generate and equals the price-table cost of the selected model and resolution multiplied by N (AC-13). It updates when the image count, the resolution or the model changes. It is computed on the client from the price table (Story, Decisions taken) and needs no request.

**Proposed (OD-14), awaiting the owner:**

- (a) The estimate is shown for Generate only; Upscale and Variation show none (AC-13 names Generate only).
- (b) The comparison and rounding rule is the one chosen in FR-21 (rule A or rule B). The server does not round a cost today, so there is no existing server rule for the estimate to copy; the estimate follows whichever rule the owner picks in FR-21. How many decimals the text shows when a price has more than two decimals is the owner's ruling under the same choice, and TEST_WRITING needs it before it can assert the text; AC-13 fixes no base format (unlike the spend figures of FR-18 e). It is linked to the row granularity of FR-9 (d); see FR-21.
- (c) For N = 1 the text follows the language's singular form; the UA plural forms for N = 1, 2 and 4 are in FR-25.
- (d) When the estimate exceeds the remaining hourly allowance (FR-8) the estimate is still shown and the number of images that can be generated is not part of it.

**Failure path (Proposed, OD-14):** if the selected (model, resolution) pair has no price in the table, no estimate number is shown (no number is invented); whether Generate is also disabled for that pair is the owner's ruling.

### FR-21: Estimate and recorded cost come from one price table

The estimate and the recorded cost use the same price table, so for one successful generation they are equal (AC-14): for a model M, resolution R and N successful images, the estimate shown before sending and the cost recorded for the same generation are the same number, produced by one expression over one unit price. A test asserts this over every (model, resolution) pair the catalogue allows. Today the server computes `unit * count` with no rounding and stores `costUsd` unrounded; there is no server rounding rule.

**Proposed (OD-14c), awaiting the owner: the comparison rule.** The Story does not state a rounding rule. The owner chooses one:

- **Rule A (matches the code as it is; no server change).** Neither the estimate value nor the recorded `costUsd` is rounded. The estimate for N images is `unit * N` and the recorded cost is the same expression. Equality is asserted exactly on the numbers: for each pair, the estimate for N equals `unit * N` computed as the server computes it, and every usage row written for an image carries `costUsd` equal to the unit price of its pair. Rounding to two decimals happens only when text is displayed (FR-18 e, FR-20). Limitation: if cost is recorded one row per image (FR-9 d), the floating-point sum of N rows can differ from `unit * N` in the last bit; the test therefore compares per image and against the shared expression, and does not assert an exact sum of rows. **Linked rulings.** This per-image wording rests on the row granularity of FR-9 (d) (OD-6), and the number of decimals of the estimate text (FR-20 b) rests on the rounding rule; if the owner rules one row per response with cost `unit * count` as today, the Rule A test is worded against that instead. The owner is asked for the three together (OD-14 and OD-6).
- **Rule B (a server change, not in the Story).** One rounding rule (to the cent, or to a stated number of places) is applied by the server to every recorded `costUsd` and by the client to the estimate, so that totals of rounded values are exactly comparable. This changes the stored values and the AC-12 sums, and `image-pricing.spec.ts` and any other spec that pins an unrounded cost would change, so each must be named in the closed list of FR-23 (OD-16).

**Proposed (OD-14a), awaiting the owner: one source.** The price values are read by the server cost and by the client estimate from one source, so they cannot drift; the price table is server-only today, and this Specification does not choose between a shared contract file and an endpoint. The existing consistency check between the price keys and the catalogue is extended to the resolution dimension.

**Failure path:** n/a, an equality has no failure path of its own; a pair without a price is FR-22.

### FR-22: Price table by model and resolution

The server price table prices an image by model and resolution (AC-14a). A 4K image costs more than the same model's 1K image and than the same model's 2K image. An unknown model/resolution pair is rejected before any usage row is written, as an unknown model is today: no row exists for a request whose price is unknown.

Precondition (OD-2, vendor fact): the price of each pair is taken from the official Gemini price list and recorded as evidence with the exact model id each applies to. The Specification names no number: the Story gives none, the repository holds none, and the one recorded source (V-5 of the US-10.1 evidence) names a different Pro id than the code bills. The numbers must exist in recorded evidence before TEST_WRITING and the model-id question must be answered before ARCHITECTURE_PLANNING; both fall after HUMAN_SPEC_APPROVAL (observation 6). If the official list shows that 4K is not more expensive than 1K or 2K for a model, AC-14a is not satisfiable as written and the Story must be revised.

**Proposed (OD-2), awaiting the owner:** whether the 1K and 2K prices of a model are equal or differ is the owner's ruling; AC-14a requires only that both are below 4K.

**Proposed (OD-15), awaiting the owner:** "rejected before any usage row is written" is read as: the pair is checked against the price table before the paid upstream call, and an unknown pair answers with the existing `INVALID_REQUEST` (400) or `PRICE_NOT_CONFIGURED` (500) code without any upstream call (which code is the owner's ruling). The alternative reading, which keeps the check after the paid call as today, leaves a paid call with no usage row and a 500; if the owner keeps it, the step order of US-10.1 FR-27 is unchanged.

**Failure path:** the rejection is the failure path; no upstream call (under the Proposed reading) and no usage row.

### FR-23: Existing Image Studio behaviour is preserved

The pre-existing Image Studio specs pass without their behavioural assertions being weakened (AC-15). US-10.1 AC-1 to AC-48 stay valid. Two are amended and only as the Story states: US-10.1 AC-3 (the 5-image limit) is amended only as FR-12 says, and US-10.1 AC-42 (30 per client per hour) is amended only as FR-8 says. "Not weakened" means: no assertion is deleted, skipped, commented out, loosened to `toBeTruthy()`, or made to accept both the old and the new value, and no coverage threshold or coverage include is changed (AGENTS.md section 7.7, 7.9).

**Proposed (OD-16), awaiting the owner at HUMAN_SPEC_APPROVAL.** The price table, the shared contract and the limiter change shapes that existing specs pin, and AC-15 allows only the two amendments above. Candidates, not read in full by the clarification stage: `image-pricing.spec.ts`, `image-model-consistency.spec.ts` (asserts the price keys equal the catalogue ids), `rate-limiter.spec.ts`, `app-limiter.composition.spec.ts`, `generate-handler.spec.ts` (injects `price(model, count)`), `usage-row.spec.ts`, `request-schema.spec.ts`, and the Angular specs under `src/app/components/image-studio/` and `src/services/image-studio/`. The proposal: before TEST_WRITING a closed table lists each existing spec whose assertion must change because of FR-8, FR-12, FR-21, FR-22 or the contract change of FR-6, with the old and new assertion and the requirement that forces it, as US-10.5 did; an assertion not in the table may not change, and a change not in the table stops the stage for the owner.

**Failure path:** a needed change to an existing assertion that is not in the table is a stop, not a silent edit.

### FR-24: One status element and focus after an action ends

Exactly one `role="status"` element remains in the studio (AC-16, US-10.1 AC-46). This holds after a single-image success, a multi-image success, an Upscale and a Variation. The new controls (selector, role selector, preset save and delete, spend, estimate) add no second `role="status"`.

**Focus.** AC-16 and US-10.1 AC-48 are read as: when an action ends, focus is in the prompt field. Generate, Upscale and Variation are all actions of this kind, and each ends the same way: on success, on a partial result, on error, on Cancel and on the 120 s timeout. Upscale and Variation start from a button on an image, so when they start focus is on that button and not in the prompt field; at the end focus is moved to the prompt field. This does not depend on which control started the action or on where focus was during the wait, including when the operator moved it elsewhere in the studio, and matches the existing behaviour of US-10.1 FR-76 (the studio moves focus to the prompt field when the in-progress state ends). If the prompt field is disabled at that moment, the existing rule of US-10.1 FR-76 and SD-37 applies unchanged. The new controls do not take focus away from the prompt field when an action ends. A test asserts that the focused element after each of the five endings above (success, partial result, error, Cancel, 120 s timeout) is the prompt field, for an action started from the Generate button and for one started from an image action button; the partial result applies to Generate and Variation only, because an Upscale produces one image.

**Proposed (OD-6e), awaiting the owner:** in a mixed outcome (some images succeed, some fail) the single status announces the success with the highest version number, as for a multi-image response today, and the failure is announced by the `role="alert"` of FR-9, not by a second status.

**Failure path:** an action that ends with no version keeps the existing single announcement of US-10.1 FR-74.

**Proposed (OD-11), awaiting the owner and the human at HUMAN_SPEC_APPROVAL.** The Story defers layout to US-10.5, which rendered none of these controls, and gives no UA text. Not invented here:

## Non-functional requirements

- **NFR-1 (Provider independence, AGENTS.md section 3 Rule 1, section 7.3).** The Gemini image call, including any candidate count or 4K edit parameter, is made only in `server/providers/`. The Angular code reaches it only through the Express proxy. No behaviour in this Specification depends on which text-generation provider is active.
- **NFR-2 (Prompts out of code, Rule 3, section 7.4; FROZEN files, section 9).** The Style ref sentence (FR-13) and any Upscale or Variation instruction (FR-2, FR-3) are not string literals inside a service; they live in a non-frozen file in `src/prompt-core/` or `src/prompts/`. None of the five FROZEN files may hold or change them. That directory is not on the Story's surface list (Scope; OD-17). Prompt-text changes are proposed to the owner and not taken unilaterally (AGENTS.md section 1).
- **NFR-3 (Retrieval separation, Rule 2).** Not touched. No search or page fetch is added; there is no automated check for this rule, so this line records that review must confirm the diff adds none.
- **NFR-4 (Secrets, Rule 4, section 7.2).** No key, price source credential or Gemini setting reaches the browser bundle. The client estimate (FR-20) reads prices, never keys. No API key and no full request payload is logged.
- **NFR-5 (Determinism, AGENTS.md section 5).** Spend boundaries (FR-19), version numbering (FR-7) and the partial grant of the hourly limit (FR-8) are testable without wall-clock dependence, without unseeded randomness, without a sleep and without network: the clock and the call completion order are injectable.
- **NFR-6 (Atomic limiter).** The partial grant of FR-8 keeps the check-and-increment atomic. Two concurrent requests never together obtain more than 30 units in the window.
- **NFR-7 (Live verification of vendor calls, AGENTS.md section 6 item 9).** A change that adds or modifies a call into the Gemini API under `server/providers/` is not done on mocks alone. One real call through the real route (or an opt-in spec gated by an environment variable, the pattern of `LIVE_DOC_TEST`) records the real response shape and status for the 4K image-to-image edit and for the candidate count (OD-1), and anything the call created is deleted. If it cannot be run, the report says so and does not claim the call verified. **Timing:** the OD-1 evidence (method, tool and runtime versions, date, who ran it, raw output) exists before ARCHITECTURE_PLANNING, which is after HUMAN_SPEC_APPROVAL. A negative result for the 4K edit re-opens the Story (AC-1) and this Specification (FR-1); a negative result for the candidate count selects the N-parallel-calls branch of FR-5 and needs no revision. The owner may require the evidence before approval instead.
- **NFR-8 (No usage-store migration, AGENTS.md section 2).** The `usage_log` table gains no column. A new column on a populated database would be silently ignored by `CREATE TABLE IF NOT EXISTS`.
- **NFR-9 (Test discipline, AGENTS.md sections 5 and 7.7).** Tests are written before the implementation and are observed failing; the coverage thresholds and the coverage include list are not changed; component specs are named `*.component.spec.ts`; tests assert behaviour, not existence.
- **NFR-10 (Persistence of presets).** User presets are kept in the browser only (`localStorage`), per browser; they are not synchronized, shared or stored on the server (Story, Out of scope).
