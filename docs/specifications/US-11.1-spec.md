# Specification: US-11.1 — Replace Gemini 3.6 Flash and 3.7 Flash with Gemini 4 Carbon and Gemini 4 Hydrogen in the model settings, migrate stored choices, and price the new models

## Summary

When this is done, Gemini 4 Carbon and Gemini 4 Hydrogen are selectable Gemini models in the AI
Model Settings (Gemini 3.1 Pro and Gemini 3.8 Flash stay), and Gemini 3.7 Flash and Gemini 3.6
Flash are no longer selectable. A browser that stored either retired model, and a server that
still receives either retired id, both land on Gemini 3.8 Flash with a valid level. Hydrogen has
its own cost tier and badge, both new models are priced from their own entries (Carbon with a
date-dependent price), and the Gemini provider runs on the upgraded `@google/genai` major version
and refuses to return a response that ended in `CONTINUATION`.

## Background

The product owner asked (`Knowledge/Requests/R1/r1.md`, Story v1) to swap the two older Flash
models for the two Gemini 4 models. Today the Gemini provider lists Gemini 3.1 Pro, 3.8 Flash,
3.7 Flash and 3.6 Flash as text models (plus two image models that are not part of the text
slots). The Deep and Fast defaults do not change (`anthropic` / `claude-sonnet-5-5` at `high`;
`gemini` / `gemini-3.8-flash` at `low`). Precedent for a model swap: US-4.1.

Provenance of the facts this Specification states as requirements (Open Decisions OD-1, OD-2):
the model ids, prices, the Carbon promo end date, `minimal` being rejected with HTTP 400,
implicit-only caching and ignored sampling parameters are the owner's confirmation against
`ai.google.dev` as of 2026-11-15. No evidence artifact records the vendor pages yet, and this
Specification did not re-verify any vendor page. The `@google/genai` version and continuation
behaviour claims are also the owner's and are unverified. Values that depend on those facts
(FR-2, FR-3, FR-20 to FR-25, FR-29 to FR-32) are stated as owner-confirmed; OD-1 says an evidence
record is needed before the price numbers are frozen in tests.

Scope boundaries that the clarification round settled and this Specification only restates:
`xhigh` is not registered for Hydrogen; the third cost tier is named `balanced`; the Carbon price
cutover is `2026-12-01T00:00:00Z` (UTC); the SDK range is capped below 3.0.0.

## Functional requirements

### Catalog

### FR-1: Gemini text-model list, order and retirements

In `model-catalog.json` the text models of provider `gemini` are, in this order,
`gemini-4-carbon`, `gemini-3.1-pro-preview`, `gemini-4-hydrogen`, `gemini-3.8-flash`.
`gemini-3.7-flash` and `gemini-3.6-flash` are absent from the catalog. Because the browser and
the server read the same catalog file, the same list and order hold in both runtimes.

**Failure path:** a catalog that contains either retired id anywhere, lists the four text models
in another order, or lists any other text model for `gemini`, fails the catalog test.

### FR-2: `gemini-4-carbon` catalog entry

The catalog entry `gemini-4-carbon` has `levels` exactly `["low","medium","high"]`,
`defaultLevel` `"medium"` and `maxOutputTokens` 65536. Its `levels` contain neither `minimal`
nor `xhigh`. Its `tier` is `premium` (see Notes, N-1).

**Failure path:** an entry with a different `levels` set or order, a different `defaultLevel`, or
a `levels` array containing `minimal` or `xhigh` fails the catalog test.

### FR-3: `gemini-4-hydrogen` catalog entry

The catalog entry `gemini-4-hydrogen` has `levels` exactly `["low","medium","high"]`,
`defaultLevel` `"high"`, `maxOutputTokens` 65536 and `tier` `"balanced"`. Its `levels` contain
neither `minimal` nor `xhigh`.

**Failure path:** an entry with a different `levels` set or order, a different `defaultLevel`,
`maxOutputTokens` or `tier`, or a `levels` array containing `minimal` or `xhigh` fails the catalog
test.

### FR-4: Entries that stay unchanged

The two image models (`gemini-3.1-flash-image`, `gemini-3-pro-image`), every entry of provider
`anthropic`, and the catalog entries `gemini-3.1-pro-preview` and `gemini-3.8-flash` keep exactly
the values they have before this Story. The image models are not text models and are not listed
in either slot's model dropdown.

**Failure path:** any changed field on one of these entries fails the catalog test.

### FR-5: `balanced` is a valid tier in the type

The `tier` field of a text model (`ModelSpec`) and of an image model (`ImageModelSpec`) is typed
`'premium' | 'balanced' | 'fast'`, in both places the type is declared. `npm run lint` accepts a
catalog entry with `tier` `balanced`. No image model uses `balanced`.

**Failure path:** if either declaration still admits only `'premium' | 'fast'`, the `balanced`
entry of FR-3 fails type-checking.

### Settings UI

### FR-6: Model dropdown contents

With provider `gemini` selected in the Deep slot, the Deep model dropdown lists exactly four
entries in this order: Gemini 4 Carbon, Gemini 3.1 Pro, Gemini 4 Hydrogen, Gemini 3.8 Flash.
With provider `gemini` selected in the Fast slot, the Fast model dropdown lists the same four
entries in the same order. Neither "Gemini 3.7 Flash" nor "Gemini 3.6 Flash" appears in either
dropdown.

**Failure path:** a dropdown that lists a retired model, omits one of the four, or orders them
differently fails the component test, for either slot.

### FR-7: Cost/speed badge text

The badge shown beside the selected model reads `$$$` for Gemini 4 Carbon and Gemini 3.1 Pro,
`$$ ⚡` for Gemini 4 Hydrogen and `$ ⚡` for Gemini 3.8 Flash. The badge for every Anthropic
model reads exactly as before this Story.

**Failure path:** a `balanced` model whose badge reads `$ ⚡` or `$$$`, or an Anthropic badge that
differs from its pre-Story text, fails the component test.

### FR-8: `balanced` badge colour set

The badge of a `balanced` model uses a sky colour class set that has a light variant and a dark
variant, and that class set differs from both the premium set (amber) and the fast set (emerald).
The `premium` and `fast` badges keep their existing class sets.

**Failure path:** a `balanced` badge that reuses the amber or emerald set, or has only one of the
two theme variants, fails the component test.

### FR-9: `minimal` is not offered for three Gemini models

The thinking-level control offers, for Gemini 4 Carbon, Gemini 4 Hydrogen and Gemini 3.8 Flash,
exactly the three levels `low`, `medium` and `high`, and does not offer `minimal`.

**Failure path:** a level control for one of these models that offers `minimal` (or any level
outside the model's `levels`) fails the component test.

### FR-10: `clampLevel` maps `minimal` to `low` for the same three models

`clampLevel('gemini', M, 'minimal')` returns `low` for each `M` in
`gemini-4-carbon`, `gemini-4-hydrogen` and `gemini-3.8-flash`. The Story names `clampLevel`
without saying which implementation; a browser module and a server module of that name exist and
read the same catalog, so this holds in both (see Notes, N-2).

**Failure path:** a clamp that returns `minimal`, or anything that is not a member of the model's
`levels`, fails the catalog test, in either runtime.

### FR-11: Deep provider switch to `gemini`

Switching the Deep slot's provider to `gemini` selects `gemini-4-carbon` at level `medium`, and
persists that choice.

**Failure path:** a switch that selects any other model, or a level other than `medium`, fails the
settings-service test.

### FR-12: Fast provider switch to `gemini`

Switching the Fast slot's provider to `gemini` selects `gemini-3.8-flash`. The new `balanced` tier
does not move the Fast pick onto Gemini 4 Carbon or Gemini 4 Hydrogen.

**Failure path:** a Fast-slot switch that lands on Carbon or Hydrogen fails the settings-service
test.

### FR-13: A selected model always carries a valid level

After a model is selected in a slot through the model dropdown, that slot's level is a member of
the selected model's `levels`. (Which level it is — carried over from the previous model with a
clamp, or the model's `defaultLevel` — is Open Decision OD-4; see P-4.)

**Failure path:** a slot left on a level that is not in its model's `levels` after a model change
fails the settings-service test.

### Restore and defaults

### FR-14: Retired Gemini models migrate to `gemini-3.8-flash` on restore

When stored settings are restored, a slot whose model is `gemini-3.7-flash` or `gemini-3.6-flash`
becomes provider `gemini` / model `gemini-3.8-flash`. This holds for the Deep slot and for the
Fast slot, each tested separately, and for each of the two retired ids. The slot's provider is
`gemini` whether the payload carries it on the slot or only as the legacy top-level `provider`
(the single-provider payload shape the service still reads).

**Failure path:** restore must not throw, and must never leave a slot with a model id that is not
in the catalog, for any stored payload including one carrying a retired id. A stored payload in
which the retired id sits next to a non-`gemini` provider is not specified here (OD-9, P-9a).

### FR-15: Level of a migrated slot

The restored level of a migrated slot is a member of `gemini-3.8-flash`'s `levels`: a stored
`minimal` becomes `low`; a stored `low`, `medium` or `high` is kept. A migrated slot with no
stored level is not specified here (OD-9, P-9b).

**Failure path:** a migrated slot whose restored level is `minimal`, or any value outside
`["low","medium","high"]`, fails the settings-service test.

### FR-16: The corrected settings are persisted once

After a restore that migrated at least one slot, the corrected settings are persisted, so a second
restore from the stored payload performs no migration.

**Failure path:** if the second restore migrates again (or re-persists as a migration), the
persistence is wrong and fails the settings-service test.

### FR-17: The Sonnet 4.6 migration still works

Restoring a slot stored as `claude-sonnet-4-6` still yields `claude-sonnet-5-5`, with the level
handling it has before this Story. Adding the Gemini migration does not change that outcome.

**Failure path:** a regression in this migration fails the existing settings-service test.

### FR-18: Defaults and reset

With no stored settings, and after "Reset to defaults", the Deep slot is `anthropic` /
`claude-sonnet-5-5` at `high` and the Fast slot is `gemini` / `gemini-3.8-flash` at `low`. Both
models are in the catalog, and each default level is a member of its model's `levels`.

**Failure path:** a default model that is absent from the catalog, or a default level that is not
in its model's `levels`, fails the settings-service test.

### Server model resolution

### FR-19: `resolveSlot` remaps the retired ids

`resolveSlot('gemini', { model, level }, tier)` with `model` equal to `gemini-3.7-flash` or
`gemini-3.6-flash` returns model `gemini-3.8-flash` for both the `deep` and the `fast` tier. The
returned level is the requested level clamped to a member of `gemini-3.8-flash`'s `levels`, and
the returned `maxOutputTokens` is 65536. The call logs exactly one warning, and that warning
names the retired id.

**Failure path:** a model id that is not a retired id and is not in the catalog still falls back by
tier exactly as before this Story (`premium` falls to the first premium model, `fast` to the first
fast model). The tier-fallback behaviour, and the fall-through for an unknown id, must not change.
A retired id used with a provider other than `gemini`, and a retired-id slot with no level, are not
specified here (OD-9, P-9a, P-9b).

### Gemini provider request shape and SDK

### FR-20: `thinkingLevel` equals the slot level

A request the Gemini provider builds for `gemini-4-carbon` and for `gemini-4-hydrogen`, at each
level in that model's `levels`, has `thinkingConfig.thinkingLevel` equal to that level.

**Failure path:** a request whose `thinkingLevel` differs from the requested in-range level, or is
`minimal`, fails the provider test.

### FR-21: No cache reference and no caller-set sampling parameters

A request the Gemini provider builds for `gemini-4-carbon` and for `gemini-4-hydrogen` contains no
`cachedContent` / `cached_content` reference, and contains no `temperature`, `topP` or `topK`
field. Caching for these models is implicit only.

**Failure path:** a request carrying any of those fields fails the provider test.

### FR-22: Non-streaming calls; 65536 on the text-generation path

The Gemini provider's text-generation calls (the `generate()` path) for `gemini-4-carbon` and
`gemini-4-hydrogen` are non-streaming `generateContent` calls carrying `maxOutputTokens` 65536,
the resolved slot's catalog value. The image-caption call (`analyzeImage`) and the PDF-extraction
call (`extractFromPdf`) are not part of the 65536 clause: they keep their existing caps
(`analyzeImage` carries the lower of 8000 and the slot's `maxOutputTokens`, which is 8000 for both
models; `extractFromPdf` carries 8192), and this Story does not change them. No streaming call is
introduced on any of the three paths.

**Failure path:** a `generate()` call for these models that streams or carries a `maxOutputTokens`
other than 65536 fails the provider test; a streaming call on the `analyzeImage` or `extractFromPdf`
path fails the provider test; an `analyzeImage` or `extractFromPdf` call whose cap differs from the
existing value (8000, 8192) for these models is a change this Story does not make and fails the
provider test.

### FR-23: `CONTINUATION` is an unfinished generation

`GeminiProvider`'s response reader treats `finishReason === 'CONTINUATION'` as an unfinished
generation: it throws an error that names the model, as it does for `MAX_TOKENS`, and never
returns the partial text.

**Failure path:** a `CONTINUATION` response that yields text to the caller (to the validator, the
repair gate or a route) instead of an error fails the provider test. This is a guard for the
abnormal case; on a conforming SDK it is not expected to fire (Story Q8).

### FR-24: `@google/genai` dependency range and lock

`package.json` requires `@google/genai` as `^2.32.0` (at least 2.32.0, below 3.0.0).
`package-lock.json` resolves it to a `2.x` version that is `>= 2.32.0`. No `3.x` version is
installed.

**Failure path:** a range that admits 3.x, or a lock that resolves to 1.x or to a `2.x` below
2.32.0, fails the dependency check.

### FR-25: Existing SDK-dependent specs pass on the upgraded SDK

Every pre-existing Gemini provider, retry and Image Studio spec that imports the SDK passes against
the upgraded SDK, so the upgrade does not regress the text slots or Image Studio. These specs use
fakes; whether green fakes are sufficient evidence for a major-version upgrade is Open Decision
OD-2/OD-5 (see P-2, P-5).

**Failure path:** any pre-existing spec of those three families that fails after the upgrade is a
defect of the upgrade, not a reason to weaken the spec (AGENTS.md §5).

### Pricing

### FR-26: Gemini 4 Hydrogen price

`getPrices('gemini-4-hydrogen')` returns `{ in: 1.50, out: 7.50, cw: 0, cr: 0.075 }` for every
date.

**Failure path:** `getPrices` for this id must never return `FALLBACK_PRICE` and must never
resolve to another Gemini model's entry.

### FR-27: Gemini 4 Carbon price, date-dependent and per lookup

`getPrices('gemini-4-carbon')` returns `{ in: 2.00, out: 10.00, cw: 0, cr: 0.10 }` for any instant
before `2026-12-01T00:00:00Z`, and `{ in: 4.00, out: 20.00, cw: 0, cr: 0.20 }` from that instant on
(the boundary instant itself returns the later price). The instant is evaluated on every lookup,
not at module load.

**Failure path:** `getPrices` for this id must never return `FALLBACK_PRICE` and must never
resolve to another Gemini model's entry, at any instant. A price chosen once at module load fails
the pricing test (a test that moves the injectable clock across the boundary observes both
prices).

### FR-28: Existing Gemini prices unchanged

`getPrices('gemini-3.8-flash')` and `getPrices('gemini-3.1-pro-preview')` return the same values
as before this Story, for the same instants.

**Failure path:** any change of those two results fails the pricing test.

### FR-29: Retired models have no price entry

`server/usage/pricing.js` has no entry and no helper for `gemini-3.6-flash` or
`gemini-3.7-flash`. What `getPrices` returns for a retired id after the removal is not specified
here (OD-9, P-9c).

**Failure path:** a price entry or a price helper for either retired id fails the pricing test.

### Docs and existing specs

### FR-30: Active docs and sources do not offer the retired models

`README.md`, `.env.example` and the other active (non-archived) docs and sources do not name
`gemini-3.7-flash`, `gemini-3.6-flash`, "Gemini 3.7 Flash" or "Gemini 3.6 Flash" as a selectable or
default model. (The exact closed list of files this covers is Open Decision OD-8; see P-8.)

**Failure path:** a remaining mention of a retired model as selectable or default in an active doc
or source fails the active-docs test.

### FR-31: Existing specs that referenced the retired models are updated

The existing specs that referenced the retired models are updated to the new catalog: after the
change none of them asserts that a retired model is in the catalog, selectable or priced, and
none of them fails for lack of a model it expected. Updating must not weaken what a spec asserts
(AGENTS.md §5). Whether a spec that uses a retired id only as an arbitrary fixture is rewritten
to a current id or may keep the retired id as a deliberate fixture is Open Decision OD-8 (P-8).

**Failure path:** a spec that still expects a retired model in the catalog, in a dropdown or in the
price table fails, and is a defect to fix in the spec's expectation, not by deleting the assertion.

### Gate

### FR-32: Commands pass

`npm test` (both runners), `npm run lint`, `npm run build` and `bash arch-guard.sh` pass. (Full
Definition of Done, AGENTS.md §6, is NFR-8.)

**Failure path:** any non-zero exit of those commands means the Story is not done.

## Proposed requirements pending Open Decisions

Nothing below is a decision. Each block states what the Specification would require under the
proposed reading, so the owner can rule on it at HUMAN_SPEC_APPROVAL. No block is binding until
the owner has answered and the Specification is revised. None of the nine Open Decisions is
`blocking: true`. The binding part of each ambiguous acceptance criterion is already written above
(FR-13, FR-14, FR-15, FR-19, FR-29, FR-30).

### P-1 (OD-1): Vendor facts need a recorded source before the numbers are frozen

Proposed: the vendor facts behind FR-2, FR-3, FR-20, FR-21, FR-26 and FR-27 (ids, prices, the
Carbon promo end date, `minimal` rejected with HTTP 400, implicit caching only, sampling
parameters ignored) are recorded in an evidence artifact (`docs/evidence/US-11.1-*-evidence.md`,
owner `so-planner`), or the owner rules that their confirmation is the accepted source, before
TEST_WRITING freezes the price numbers. Owner to rule: evidence file, or accept the confirmation.

### P-2 (OD-2): The 1.x to 2.x SDK major upgrade is checked beyond mocked specs

Proposed: before ARCHITECTURE_PLANNING relies on FR-24, a recorded check of the `2.32.0` package
covers the four owner claims (continuation default from 2.29.1 and full support from 2.32.0;
`CONTINUATION` stop at 32,768 tokens on older versions; `3.x` changes the default API version and
needs Node 22 or newer; nothing the repo relies on in 1.52.0 changes), and the three SDK-internal
behaviours that the Gemini provider's source comments record for 1.52.0 (the `retryOptions` retry
loop that is dormant unless the option exists; `files.upload` replacing resumable-upload headers
with `config.httpOptions`; `files.upload` ignoring `config.abortSignal`). If any no longer holds,
the corresponding code is a change inside this Story's Surface only after the owner rules on it.
Owner to rule: whether this check is required, and whether a failed check widens the Surface.

### P-3 (OD-3): Timeouts when SDK continuation issues two HTTP requests

Two branches, to be chosen once evidence exists:

- **Per HTTP request:** the per-call timeouts (`DEEP_TIMEOUT_MS`, `VISION_TIMEOUT_MS`,
  `FAST_TIMEOUT_MS`) bound each request; `server/utils/timeouts.js` stays verify-only and no
  requirement is added.
- **Whole call:** the timeouts bound the whole `generateContent` call. Then a Gemini 4 call whose
  continuation needs a second request, with each request within the slot's budget, must not be
  aborted by the slot's timeout, `timeouts.js` joins the Surface, and the Story's "verify only"
  wording changes.

Owner to rule: which branch, after evidence from the 2.32.0 source or one real continuing call.

### P-4 (OD-4): Level after selecting a model in the dropdown

AC-4 says "Selecting Gemini 4 Carbon in a slot sets that slot's level to `medium`; selecting
Gemini 4 Hydrogen sets it to `high`". The existing dropdown selection carries the current level
across with a clamp and never reads `defaultLevel`; only a provider switch sets `defaultLevel`
(FR-11, FR-12). A provider switch can land only on Carbon (Deep) or Gemini 3.8 Flash (Fast), so
Hydrogen's `high` is reachable only through the dropdown (or a restore with no stored level). Three
readings:

1. Selecting any model in the dropdown resets the level to that model's `defaultLevel`. This also
   changes Anthropic and Gemini 3.x behaviour and the existing settings-service tests.
2. Selecting `gemini-4-carbon` or `gemini-4-hydrogen` in the dropdown sets their `defaultLevel`
   (`medium` / `high`); every other model keeps carry-over with a clamp. Smallest change that
   satisfies the AC text literally; the rule is inconsistent across models.
3. AC-4's selection clause applies to the provider-switch path only (FR-11); the dropdown keeps
   carry-over with a clamp. The Hydrogen-`high` clause is then not testable on any selection path.

Proposed: reading 2, because it satisfies the AC text without altering the Anthropic and Gemini
3.x behaviour that AC-3 says stays "the same as before". Owner to rule: 1, 2 or 3. Until ruled,
only FR-13 binds the dropdown.

### P-5 (OD-5): Live smoke for a changed vendor call

AGENTS.md §6 item 9 requires one real call against the vendor from the running server path for any
change under `server/providers/`; this Story changes the SDK major version and the models behind
the Gemini provider, and its Out of scope excludes live-API verification. The Specification does
not read the Story's exclusion as a waiver of item 9. Two options: (a) the owner waives item 9 for
US-11.1, recorded in the Specification and the Pull Request; (b) an opt-in live spec (the
`LIVE_DOC_TEST` pattern, §5) joins the Surface. Absent a ruling, item 9 is checked as AGENTS.md
writes it. Owner to rule: (a) or (b), by HUMAN_SPEC_APPROVAL.

### P-6 (OD-6): Usage and cost across a continued call

Proposed (conditional on the evidence of P-2): the usage that the Gemini provider returns for one
call equals the tokens billed for that call across all of its HTTP requests (input, output
including thinking, cache-read), read from the field names the Gemini 4 and SDK 2.x responses
actually use. A continued call must not drop the first request's tokens, count prompt tokens
twice, or report a renamed cache field as zero. FR-26 and FR-27 test prices only, not the usage
read. Owner to rule: whether a usage-read requirement and test belong in this Story.

### P-7 (OD-7): Whether the single-request output limit applies to Hydrogen

The Story states the 32,768-token single-request limit for Carbon only. FR-22 and FR-23 are
written for both models (as AC-13 and AC-14 are), and no requirement depends on the limit being
specific to one model. If the limit applies to Hydrogen, P-3 and P-6 apply to it as well. Owner to
answer, or the evidence of P-1 to settle: does the limit apply to Hydrogen, and is
`maxOutputTokens` 65536 valid for Hydrogen on the same terms?

### P-8 (OD-8): What FR-30 scans, and which existing specs change

Proposed closed list for FR-30: `README.md`, `.env.example`, `AGENTS.md` (the set
`test/active-docs-models.spec.ts` scans), plus the comments in the active sources named by the
Story's Surface (the model-settings component and service comments, the catalog, `pricing.js`).
Archived Story artifacts (for example the US-4.1 set), `docs/catalog/stories.yaml` and
`Knowledge/Requests/R1/r1.md` are historical and are not scanned. A retired id may appear where
the behaviour is to recognise it: the browser restore migration table, the server remap, and the
tests of FR-14, FR-15 and FR-19. Existing specs found by search that use a retired id or label
(non-exhaustive, from the clarification report): `test/gemini-provider.spec.ts`,
`test/llm-routes.spec.ts`, `test/call-log.spec.ts`, `test/pricing.spec.ts`,
`test/active-docs-models.spec.ts`, `test/image-studio/model-support.entries.spec.ts`,
`test/image-studio/model-support.image-blind.spec.ts`, `src/prompt-core/model-catalog.spec.ts`,
`src/services/model-settings.service.spec.ts`. Some (the fallback assertions around
`test/gemini-provider.spec.ts` lines 401 to 403, and `test/llm-routes.spec.ts`) change behaviour
under FR-19. Owner to rule: the closed list for FR-30, and for FR-31 whether every spec that uses
a retired id as an arbitrary fixture is rewritten to a current id, or named fixtures may keep it.

### P-9 (OD-9): Remap edge cases

- **P-9a, provider gating.** Proposed: the remap applies when the slot's resolved provider is
  `gemini`. A retired Gemini id next to a non-`gemini` provider is an unknown id for that
  provider and falls back by tier as before (browser: `validateSlot` re-derives the provider;
  server: `resolveSlot('anthropic', …)` does not remap). The literal AC-5 and AC-12 wording
  covers only the `gemini` case.
- **P-9b, absent level.** Proposed: not specified until ruled. The remapped slot's level is
  `clampLevel(…, model.defaultLevel)` today, which is `high` for `gemini-3.8-flash`, while the
  Fast default and the Fast fallback use `low`. Owner to rule which is intended; FR-15 and FR-19
  bind only that the level is a member of `levels`.
- **P-9c, price of a retired id.** Proposed: no requirement. After FR-29 a retired id resolves to
  `FALLBACK_PRICE` in `getPrices`; the only caller resolves the provider model first (FR-19), so
  it should not be reached by new usage rows. Owner to confirm that this needs no requirement.

## Non-functional requirements

- **NFR-1 — Provider independence (AGENTS.md §3 Rule 1).** The vendor SDK is imported only in the
  Gemini provider layer under `server/providers/`; the server remap (FR-19) lives in that layer;
  no browser or orchestrator code branches on the active provider because of this Story.
- **NFR-2 — Retrieval separation (§3 Rule 2).** Search and page fetch are untouched. This rule has
  no automated check; the implementation verifier checks the diff.
- **NFR-3 — Prompt caching economics (§3).** `systemBlocks` stay in the Gemini request's
  `systemInstruction` and are not collapsed into `userContent`; Gemini 4 caching is implicit only
  (FR-21), so no `cachedContents` is created.
- **NFR-4 — Secrets (§3 Rule 4).** No API key reaches the browser bundle. The catalog file is
  shared by the browser and the server and contains no secrets. `.env.example` gains no new
  setting; it is updated only to stop naming the retired models (FR-30).
- **NFR-5 — Behavioural compatibility (§3 Rule 5).** The retry/backoff wrapper stays
  provider-independent, and the SDK-level retry loop stays off after the upgrade (see P-2): the
  pre-existing retry specs of FR-25 are the check available on fakes.
- **NFR-6 — Single catalog source.** The model list, levels, tiers and output ceilings exist once,
  in `model-catalog.json`; the browser and the server read the same file (FR-1, FR-10).
- **NFR-7 — Determinism.** The Carbon price depends on the instant of the lookup (FR-27), so the
  tests must drive an injectable clock, never the wall clock, to observe both sides of
  `2026-12-01T00:00:00Z`. Nothing else in this Story uses unseeded randomness.
- **NFR-8 — Definition of Done (§6).** In addition to FR-32, the full AGENTS.md §6 applies:
  `npm run test:coverage` thresholds hold, the new behaviour has tests that were written first and
  observed failing, the Rule 2 diff read, and — subject to P-5 — one real vendor call from the
  running server path or the owner's recorded waiver.

## Out of scope

- Changing the default Deep or Fast model, or any Anthropic model.
- Changing the Gemini provider's same-provider fallback models (3.1 Pro for Deep, 3.8 Flash for
  Fast); they stay as they are and remain compatible with Carbon or Hydrogen as the primary model.
- Explicit context caching (`cachedContents`) and any cache-storage billing.
- Batch, Flex, Priority and Contributor-tier pricing; Vertex AI regional pricing; the Google
  Search / Maps grounding fee.
- The Gemini 3.1 Pro above-200K-token price tier (already noted as unmodeled in `pricing.js`).
- Re-pricing past `usage_log` rows; cost stays as computed at insert time. The dashboard's model
  badge colouring and the readability of historical rows with retired ids need no change.
- Changing prompts, schemas or generated HTML; no FROZEN file is touched.
- Evaluating the quality of Gemini 4 output for any locale, including the uk-UA master.
- Live-API verification against Google as a deliverable of this Story, unless the owner rules for
  option (b) of P-5. Acceptance is by unit tests with mocked SDKs; AGENTS.md §6 item 9 is not

- Moving the Gemini provider to streaming calls.
- Changing the `maxOutputTokens` caps of the image-caption (`analyzeImage`) and PDF-extraction

- Changing the model-switch semantics of models other than those named in P-4, unless the owner
  rules for reading 1 of P-4.

## Notes

- **N-1 — Carbon's tier.** The Story fixes the `tier` value only for Hydrogen (`balanced`). Carbon's
  `$$$` badge (FR-7) and its selection as the first `premium` model by a Deep provider switch
  (FR-11) are both satisfied by `premium`, which is the existing tier for Gemini 3.1 Pro that also
  shows `$$$`. No other `tier` value for Carbon satisfies FR-7 and FR-11 together, so this is a
  consequence of the acceptance criteria, not a new decision.
- **N-2 — Two `clampLevel` implementations.** The browser module and the server module both define
  `clampLevel` over the same catalog (the server's own comment says it mirrors the browser's).
  The Story names the function once. FR-10 reads that as covering both, since AC-8's
  `thinkingLevel` is produced by the server's one.

- **N-3 — Scope of the 65536 clause (revision 2, plan-review finding B-1).** Story AC-13 says the
  Gemini provider's calls for `gemini-4-carbon` and `gemini-4-hydrogen` "stay non-streaming
  `generateContent` calls carrying `maxOutputTokens` 65536". Read literally for every provider call,
  that is untrue of the unchanged code: `analyzeImage` carries `Math.min(8000, slot cap)` and
  `extractFromPdf` carries 8192, deliberately lower caps for a short caption and a mechanical
  transcription, and no AC changes them. FR-22 therefore scopes the 65536 clause to the
  `generate()` text path and states that the other two paths keep their caps; the non-streaming
  clause stays on all three paths. This is a scope clarification, not a new requirement and not a
  raise of any cap. The Story text of AC-13 is unchanged and remains broader than FR-22; the
  approver confirms the reading at HUMAN_SPEC_APPROVAL. If the owner instead wants those caps
  raised, that is new scope that needs its own ruling and Specification revision.
