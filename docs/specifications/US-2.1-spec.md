# Specification: US-2.1 — Migrate product descriptions to the v4.0 UA content schema

## Summary

When this is done, every new product description generated by the pipeline conforms to the v4.0
UA content standard (`Knowledge/Schemas/product_description_schemas_v4_ua.md`): the v4 hook, the
merged Killer Specs + Key Benefits list, the v4 functionality section, applications, conditional
compatibility and package-contents sections, the v4 spec-table markup, the v4 CTA, and v4 number
separators. Every newly generated document carries `schemaVersion: '4.0'`; documents already
cached as `'3.0'` remain parseable and renderable under their own rules. The v4 word volumes are
enforced for the native uk-UA master only; every other locale keeps v4 structure without
word-count validation.

## Background

The v4.0 UA schema was approved on 2026-09-18 and supersedes
`Knowledge/Schemas/product_description_schema_v3_ua.docx`. The generator still encodes v3: the
product-description domain schema pins `schemaVersion: z.literal('3.0')` and the generation
prompts carry v3 rules. There is no v3 → v4 changelog — "Журнал змін" appears in the v4 contents
but no such section exists in the document — so per OD-1 the whole v4 document is the delta and
v4 is the single source of truth. No diff of the v3 `.docx` is required or attempted.

Eleven Open Decisions (OD-1..OD-11, `docs/decisions/US-2.1-open-decisions.md` v2) were settled by
the human on 2026-09-19; none is blocking. This Specification is built on those settled decisions
and does not re-open any of them.

**One Story, three delivery phases (OD-7).** The human explicitly confirmed this is a single
Story and named three phases for it: (1) domain and Zod schema updates, (2) generation-prompt
updates, (3) render-template and transform updates. Phase ordering, decomposition and per-task
assignment belong to ARCHITECTURE_PLANNING and IMPLEMENTATION_PLANNING; the phases are recorded
here because OD-7 asked the Specification to carry them.

## Functional requirements

### FR-1: The hook is a single paragraph with the fixed opening form

The generated description opens with exactly one `<p>` element as its hook. Its text begins with
`<b>{product name}</b> —` followed by the product type or category (v4 §1, "Незмінний старт"). In
the `uk-UA` master, the hook's rendered text measures 40–85 words.

**Failure path:** a hook that is not a single `<p>`, that does not open with the bolded product
name followed by an em dash, is a structural defect and the generation is rejected by structural
validation. A `uk-UA` hook outside 40–85 words is **not** rejected — see FR-18.

### FR-2: The hook carries 2–4 technical values

The hook contains 2–4 of the product's most important technical values (v4 §1, "Обов'язковість
ключових цифр"). Values repeated later in the Killer Specs list or the spec table serve a
different function at each place and are not treated as duplicates.

**Failure path:** the count is a property of prose, not of a collection, so it carries no automated
check under FR-17. A hook with fewer than 2 or more than 4 technical values is a prompt-level miss
and a review finding; it is not a validation failure and does not reject the generation.

### FR-3: `killerSpecs` holds 3–4 items in `<b>lead</b> — benefit` form

The `killerSpecs` collection holds **3–4** items. Each is rendered as `<b>{short lead containing
the figure and parameter}</b> — {concrete benefit or technical explanation}` (v4 §2). A bare
restatement of the value without a benefit clause does not satisfy the item format
(v4 §2, «а не простий перефраз значення»).

**What is and is not enforced.** The **item count** is a collection length and is validated — see
FR-17. The **benefit-clause requirement is a property of prose**: distinguishing a benefit clause
from a restatement is a judgement no validator makes, so it carries no automated check. It is a
prompt instruction and a review criterion; a bare restatement is a prompt-level miss and a review
finding, not a validation failure, and it does not reject the generation. This is the same honest
split FR-2 states for the hook's technical-value count.

**Failure path:** an item count outside 3–4 fails schema validation and enters the repair loop
(this bound is already pinned in the domain schema and is restated here so the v4 migration does
not relax it). A weak benefit clause has no failure path in the system — see the paragraph above.

### FR-4: The Killer Specs + Key Benefits block is one H2 over a single list of at most 8 items

The block is a single `<h2>` followed by one `<ul>`. The **combined** rendered list — the
`killerSpecs` items of FR-3 plus the Key Benefits items that follow them — contains **at most 8
`<li>` items in total**, of which 3–4 are the FR-3 Killer Specs. The block contains no `<table>`
(v4 §2, "mobile-First UX (жодних таблиць)"). In the `uk-UA` master the block's rendered text
measures 90–300 words.

**Composition of the §2 block (resolves spec-review finding 2).** For a document carrying
`schemaVersion: '4.0'`, §2 renders **exactly one `<h2>` and exactly one `<ul>`, and nothing else**.
Between the §2 heading and the end of its list there is no paragraph, no figure, no video embed
and no second list. The three non-`bullets` Block kinds that the Key Benefits collection admits
today — `paragraph`, `figure` and `video` — are therefore **not legal inside §2 of a `'4.0'`
document**. The grounds are the text of the criterion and of v4 itself, not a preference:

- AC-3 requires "one H2 followed by a `<ul>` of at most 8 items";
- v4 §2 (`:283`) specifies the section as «Ненумерований список (`<ul><li>`) до 6–8 пунктів
  (90–300 слів)» and (`:293`) as «дві частини в **єдиному потоці**» — one list under one H2, of
  which the first 3–4 items are the Killer Specs;
- v4 §2 names no prose lead-in, figure or video for this section at all.

Consequences this Specification states rather than leaves to inference:

1. **Figure and video content is not lost.** Figures and video embeds continue to be carried by
   the v4 sections whose shape admits them — §3 functionality (FR-27) and §4 applications — and
   the §4 media criteria of FR-23 and FR-24 continue to apply to them wherever they land. This
   Specification does not require a particular destination section for any individual figure; it
   requires only that §2 is not one.
2. **A `'3.0'` document is unaffected.** Under OD-2's dual support, a `'3.0'` document keeps its
   existing Key Benefits shape, including all four Block kinds, and keeps rendering under its own
   rules. This restriction is scoped to `'4.0'` exactly as FR-10's string-only spec value is.
3. **The first-image rule is in play.** Moving figure content out of §2 changes rendered document
   order, which is the input to the §4 first-image-eager criterion — see FR-23.
4. **The §3 bullets floor is in play.** Content relocated out of the Key Benefits collection
   (bullets floor 2) toward the functionality collection (bullets floor 3) crosses a deliberate
   floor difference — see FR-29.

*How the `'4.0'` restriction is expressed in the domain schema — a narrowed Block union for §2, a
version-conditional refinement, or a separate collection shape — is an ARCHITECTURE_PLANNING
decision and is deliberately not specified here. The behaviour above is not.*

**Reconciliation of the lower bound (OD-9 residual).** AC-3 states a maximum of 8 items and no
minimum. v4 §2 reads "до 6–8 пунктів" — an upper bound of 8 with 6 as the recommended target.
Accordingly: the enforced ceiling is 8 items on the combined list; **no new minimum is introduced**
beyond the 3-item floor FR-3 already places on `killerSpecs`; v4's target of 6 is carried as a
prompt instruction under OD-1, not as a validation floor. The 8-item ceiling is a property of the
combined list, not of either collection independently — a ceiling applied to only one of them
would admit a rendered list of more than 8 items and violate AC-3. How that combined ceiling is
actually checked is FR-17.

**Failure path:** a combined list exceeding 8 items fails validation and enters the repair loop
(FR-17, FR-30). A §2 block in a `'4.0'` document that renders a paragraph, figure, video or a
second list between its `<h2>` and the end of its `<ul>` is a structural defect and fails
validation. A `uk-UA` block outside 90–300 words is not rejected — see FR-18.

### FR-5: The applications section is one H2 over a list of 4–8 items

The applications section is a single `<h2>` followed by one `<ul>` of **4–8** `<li>` items. Each
item names an industry or usage scenario and explains in 1–2 sentences how the product solves a
task in that context, rather than naming the industry alone (v4 §4).

**What is and is not enforced.** The **item count** is a collection length and is validated — see
FR-17. Whether an item "explains how the product solves a task" rather than naming the industry
alone is **a property of prose and carries no automated check**, exactly as in FR-2 and FR-3. It is
a prompt instruction and a review criterion; a bare industry name is a prompt-level miss and a
review finding, not a validation failure.

In the `uk-UA` master the section's rendered text measures 80–250 words.

**Failure path:** an item count outside 4–8 fails schema validation and enters the repair loop. A
`uk-UA` section outside 80–250 words is not rejected — see FR-18. A weak scenario explanation has
no failure path in the system — see the paragraph above.

### FR-6: Compatibility and package contents appear only when the source data contains them

The compatibility section (v4 §5) and the package-contents section (v4 §6) are emitted **only**
when the source description or datasheet supplied as input contains that data. When the input does
not contain it, the section is absent from the output entirely. Neither section's content may be
assumed or invented.

When package contents are emitted, the section is an `<ol>` under the heading "Що в коробці?" for
a single product or "Що входить до набору?" for a set in `uk-UA`, and under the corresponding
heading for the document's own locale in every other locale.

**The localized headings have a source of truth, and it is not the model.** For every locale in
`STORE_REGISTRY`, both heading strings resolve from a **code-resident per-locale table**, the same
class of source the repository already uses for `DELIVERY_REGION_PHRASES`
(`src/prompt-core/constants.ts:97`) and `FIGCAPTION_TEMPLATES` (`src/utils/video-figure.ts`, cited
by AGENTS.md §4 and quoted in FR-24). The model does not author these headings, and a heading for
the same locale does not change between regenerations of the same product. The rationale is the
one already recorded at `constants.ts:97`: left to the model, a fixed commercial string comes back
differently worded on each run, and a v4 section heading is that same class of string. Without a
named source a test would have to invent the expected heading for `pl-PL`, `de-DE`, `es-ES`,
`pt-PT`, `en-GB`, `en-US`, `en-ES`, `es-MX` and `ru-UA`.

*Where that table lives, and whether it extends an existing constant or adds a new one, is an
ARCHITECTURE_PLANNING decision. That it is code-resident rather than model-authored is not.*

This requirement governs the §5 and §6 sections named above and no others.

**Failure path:** a compatibility or package-contents section present in the output without
corresponding input data is a fabrication defect and fails review; an absent section where the
input carried no such data is correct output, not a miss. A package-contents heading that does not
match the table entry for the document's locale is a defect.

### FR-7: The specs section uses one H3 and one table per category

When the specs section is emitted, it presents **one `<h3>` and one `<table>` per logical
parameter category**. The table is wrapped in a `<div class="table-responsive">` and carries
`class="table table-bordered table-striped"` (v4 §7). Categories are not merged into one large
table, and units live in the value column rather than in the parameter name.

**Failure path:** a category rendered without its own H3 and table, or a merged multi-category
table, is a structural defect and fails validation.

### FR-8: No spec value cell contains a list or a line break

No value cell in the specs section contains a `<ul>`, an `<ol>` or a `<br>` (v4 §7). The rendered
value is plain text.

**Failure path:** a value cell containing any of those tags is a structural defect and fails
validation.

### FR-9: A multi-value parameter is comma-joined into one row

A parameter that has several values (supported nozzle diameters, file types, compatible materials,
certificates) presents all of them comma-separated in a **single row** (v4 §7). The row count
therefore equals the input parameter count — see FR-22.

For a `'4.0'` document the spec value is a single string, and the model is instructed to join
multiple values with a comma into that one string rather than emitting a collection for the
renderer to join (OD-4).

**Failure path:** a parameter emitted as several rows, or as a collection in a `'4.0'` document,
fails validation and enters the repair loop.

### FR-10: The spec-value string-only rule is scoped to version 4.0

The removal of the collection form from a spec row's value applies to `'4.0'` documents. A
document carrying `schemaVersion: '3.0'` continues to parse with its existing value form (single
string **or** non-empty collection of strings) and continues to render under its own rules
(OD-2 × OD-4). Applying the string-only rule unconditionally would reject the cached `'3.0'`
documents that OD-2 exists to preserve.

**Failure path:** a cached `'3.0'` document that fails to parse after this change is a regression
against OD-2's stated rationale, not an acceptable side effect.

*How this version-scoping is expressed (discriminated union, version-conditional refinement, or a
parse-time upcast) is an ARCHITECTURE_PLANNING decision and is deliberately not specified here.*

### FR-11: The CTA is a single paragraph under a localized commercial H2

The description ends with a CTA section: one `<h2>` reading "Чому варто купити {product name} в
{store name}?" in `uk-UA`, and the corresponding heading for the document's own locale elsewhere,
followed by exactly one `<p>` (v4 §8). In the `uk-UA` master the CTA paragraph measures 50–100
words.

**The heading template has a source of truth, and it is not the model.** The heading is assembled
from a **code-resident per-locale template**, into which the product name and the store name are
interpolated; the store name itself resolves from `STORE_REGISTRY` (NFR-6). For every locale in
`STORE_REGISTRY` the template is fixed in code and does not vary between regenerations of the same
product. This is the same sourcing requirement FR-6 states for the package-contents headings, and
the same pattern FR-24 inherits through AGENTS.md §4's citation of `FIGCAPTION_TEMPLATES`. v1 of
this Specification sourced the store *name* but not the surrounding template, which left a test
with no expected string to assert for nine of the ten locales.

*Where the template table lives is an ARCHITECTURE_PLANNING decision; that it is code-resident is
not.*

**Failure path:** a missing CTA, a CTA spanning more than one `<p>`, a heading that is not the
localized commercial H2 form, or a heading that does not match the template for the document's
locale, fails validation. A `uk-UA` CTA outside 50–100 words is not rejected — see FR-18.

### FR-12: The description body contains no `<h1>`

The generated description body contains no `<h1>` element at any position. The page H1 is emitted
by the CMS from the product-name field; a manual `<h1>` in the description duplicates it (v4 §0).

**Failure path:** an `<h1>` anywhere in the description body fails validation and the generation is
rejected.

### FR-13: The FAQ is produced separately and is never embedded in the description

When a FAQ is produced, it consists of **3–5 question/answer pairs**, each answer 2–4 factual
sentences, and it is delivered as a separate artifact for the CMS FAQ module. FAQ HTML never
appears inside the description body (v4 §9).

The **trigger is unchanged**: a FAQ is produced only when supplemental content is supplied. v4 §9
is "Рекомендовано", not mandatory, and this Story does not make the FAQ unconditional and does not
change the call architecture (OD-10). The v4 FAQ rules (3–5 pairs, 150–400 words) are carried into
the FAQ generation prompt for consistency.

**Failure path:** FAQ markup found inside the description body is a defect regardless of its own
correctness. A generation with no supplemental content and therefore no FAQ is correct output, not
a miss.

### FR-14: The hook pattern is selected deterministically before the prompt is built

For each product, a hook structural pattern is selected by the **service layer**, before the
prompt payload is built, by a deterministic index computed over the product's `name` and its
`website` (OD-3). The selected pattern is passed into the generation prompt as an explicit
instruction naming which of the v4 §1 patterns to use. At least 4 distinct structural patterns are
available for selection (v4 §1, "Антиконвеєр").

The same `name` + `website` pair always yields the same pattern; the same product under a
different store may draw a different pattern, and that was accepted.

**The index distributes; it is not merely deterministic.** The selected pattern is a function of
the **whole** `name` + `website` pair, and the selection **varies with its input**: over a set of
distinct `name` + `website` pairs, every one of the available patterns is reachable, and the
selection is not constant, not a function of `website` alone, and not a function of any single
character of `name`. This clause exists because determinism alone does not deliver the rotation:
a constant selector returning pattern 1 for every product would satisfy the paragraphs above and
NFR-5 in full — it is deterministic, service-side, pre-prompt, and draws from a set of at least 4
patterns — while making AC-9 unachievable for **any** fixture batch. The distribution property is
what a test asserts against the system rather than against a curated fixture.

**Failure path:** a pattern chosen by the model rather than by the service, an index that varies
between runs for the same `name` + `website`, or an index that does not vary across distinct
`name` + `website` pairs, defeats the rotation and is a defect. Generation is stateless per
product, so the model cannot rotate patterns by itself.

*This requirement deliberately does not assert that no two consecutive products draw the same
pattern. A distributing deterministic index gives coverage of the available patterns across the
catalogue, not a guarantee about consecutive pairs; that property is satisfiable for a curated
fixture batch and is a test-design matter — see Open questions.*

### FR-15: Every new generation emits `schemaVersion: '4.0'`, and `'3.0'` remains accepted

Every new LLM generation emits a document with `schemaVersion: '4.0'`. The domain schema accepts
both `'3.0'` and `'4.0'`. Rendering branches on the version: a `'3.0'` document keeps the previous
handling rules wherever they differ, a `'4.0'` document gets the v4 rules (OD-2). Existing cached
documents are neither rejected nor mass-migrated.

**Failure path:** a new generation emitting `'3.0'`, or a cached `'3.0'` document being rejected at
parse or render, is a defect. A generation that cannot produce a valid `'4.0'` document does not
fall back to `'3.0'` — see FR-30.

### FR-16: Number separators follow three locale groups, and es-MX belongs to group 1

Decimal and thousands separators are applied per locale — in running text, headings, captions and
spec-table value cells alike — in exactly three groups (OD-11):

| Group | Locales | Decimal | Thousands | Example |
|---|---|---|---|---|
| 1 | `en-US`, `en-GB`, `en-ES`, **`es-MX`** | dot `.` | comma `,` | 1,234,567.89 |
| 2 | `uk-UA`, `ru-UA`, `pl-PL` | comma `,` | non-breaking space | 1 234 567,89 |
| 3 | `de-DE`, `es-ES`, `pt-PT` | comma `,` | non-breaking space | 1 234 567,89 |

**es-MX (the decision's explicit either/or, now closed).** OD-11 left the Specification to either
place `es-MX` in a group or scope the separator clause to locales with an explicit rule. This
Specification **places `es-MX` in group 1**, on two cited grounds: `src/prompt-core/constants.ts`
already assigns `es-US / es-MX` "decimal dot, thousands comma (US market, CLDR)", and v4's Appendix
§4 gives the CLDR rationale for the Spanish-in-the-US locale explicitly. `es-MX` is live on
`Expert-3DPrinter`, whose other locales are `en-US` and `uk-UA`. Two consequences follow: there is
**no code delta for `es-MX`**, and **AC-10's separator clause is not scoped down** — every
`STORE_REGISTRY` locale now has an explicit rule.

**Group 3 is a behavioural change.** The current rule block gives `de-DE` and `es-ES` "thousands
dot (or space)"; group 3 fixes the non-breaking space, and `pt-PT` has no rule today and gains one.
Groups 1 and 2 already match the decision.

**This table governs where the v4 Appendix is silent or permissive, and AC-10's "of the Appendix"
is read accordingly.** AC-10 says separators "follow the locale rules of the Appendix". The
Appendix has **no `pt-PT` rule at all** — its Spain section covers `es-ES`, `en-ES` and `uk-UA`
only — and it offers `de-DE` / `es-ES` a dot *or* a space for thousands. For those locales the
three groups above **supersede** AC-10's "of the Appendix" wording: `pt-PT` gains a rule the
Appendix does not state, and the `de-DE` / `es-ES` either/or is closed on the non-breaking space.
Both moves are what OD-11 settled; this clause states in so many words that they are intended
rather than a drift from AC-10.

**Existing-test constraint on the rule block (carried from the clarification report, note 4).**
The separator rules reach the prompt through `NUMBER_FORMAT_RULES`
(`src/prompt-core/constants.ts:489-501`), which is **not** FROZEN and is only interpolated into
FROZEN `master-system-prompt.ts:83`. Group 2 is **unchanged** by this Story, and
`src/prompt-core/ua-translation-style-guide.spec.ts:49` asserts the exact substring
`'uk-UA / ru-UA: decimal comma, thousands non-breaking space'` against that constant. The change
required here is therefore a targeted one — group 3 corrected, `pt-PT` added — and it **must not
alter the group-2 line**: a wholesale rewrite of the block fails an existing test that exists to
keep `NUMBER_FORMAT_RULES` and the UA translation style guide from contradicting each other inside
the same system prompt. This is a constraint on the change, and it is also a planning hazard routed
to ARCHITECTURE_PLANNING (see Open questions) so it is not rediscovered by a failing test.

Only the separator punctuation localizes; digits and units are never changed — see FR-21.

**Failure path:** a number formatted with another locale's separators, or a localization that
alters the digits or the unit, is a defect. A `NUMBER_FORMAT_RULES` edit that changes the group-2
line is a regression against an existing test, not a stylistic choice.

### FR-17: Item counts are validated, the combined §2 ceiling is a cross-collection check, word volumes are prompt-only

Per OD-9, constraints split by kind. This requirement states which check each v4 number gets, and
what shape that check has.

**1. Single-collection lengths, expressed directly by the schema.** `killerSpecs` 3–4 (FR-3) and
applications items 4–8 (FR-5) are lengths of one collection each, expressible as a minimum and a
maximum on that collection, and they are validated. A miss is a schema failure the existing repair
loop corrects locally and cheaply.

**2. The combined §2 ceiling of 8 (FR-4) is not a collection length.** It is a **document-level
cross-collection invariant**, and no single maximum expresses it. v1 of this Specification
described it as a schema-enforced collection length, which was inaccurate:

- `killerSpecs` is bounded at 3–4 items (`src/domain/description-doc.schema.ts:160`);
- the Key Benefits collection is bounded only below — `z.array(RelaxedBlockSchema).min(1)`
  (`:162`) — with **no maximum on the number of Blocks**;
- each `bullets` Block within it is bounded at 2–8 items (`:100`, via `makeBlockSchema(2)`).

Today's bounds therefore admit 4 + 8 + 8 + … rendered `<li>` items in §2 while every existing
bound holds. The FR-4 ceiling is consequently a **new** check whose subject is the rendered §2
list as a whole: the count of `killerSpecs` items plus the items every §2 Block contributes, summed
across Blocks, must not exceed 8. OD-9 settled *that* item counts are validated rather than left to
the prompt, and this ceiling is validated on that authority; OD-9 did not settle the shape of this
particular check, which is why the Specification states it here.

Two consequences follow, and they are why the distinction is not cosmetic:

- **Repair is not local.** A single-collection miss has an obvious cheapest repair — that one
  collection. A combined-ceiling miss does not name a field, so the repair ladder has no
  single-field target for it. See FR-30.
- **It is a `'4.0'` rule.** Like FR-4 and FR-10, this ceiling applies to `'4.0'` documents; a
  cached `'3.0'` document is not retro-validated against it (OD-2).

*Where this check lives — a document-level schema refinement, the output validator, or both — is an
ARCHITECTURE_PLANNING decision. That it is a validated cross-collection invariant rather than a
per-collection maximum is not.*

**3. Word volumes are prompt-only.** The word volumes — 40–85, 90–300, 80–250, 50–100 — are
enforced by **prompt instruction only** (OD-9). So are the prose-judgement clauses of FR-2, FR-3,
FR-5 and FR-28, each of which says so in its own text.

**Failure path:** a single-collection length outside its bound fails validation; a combined §2 list
of more than 8 rendered items fails validation. A word volume outside its range does not — see
FR-18.

### FR-18: No generation is rejected for a word-count miss

The validator does not reject a generation because a section's word count falls outside its v4
range. A hook of 86 words where v4 says 40–85 is accepted output (OD-9).

This is a negative requirement stated on its own because it is the clause most easily violated by
adding a well-intentioned length check.

**Failure path:** a validation rule that rejects, repairs or retries a generation on word count
alone is a defect against this requirement, whatever its intent.

### FR-19: Word-volume ranges are measured on rendered uk-UA text and apply to no other locale

Where a word volume is stated (FR-1, FR-4, FR-5, FR-11), it is counted on the **rendered text
nodes** of the generated HTML for that section, in the `uk-UA` master only. The translation path is
not constrained by numeric word limits for any other locale, and translated output is **not
word-count validated at all** — there is no tolerance band and the translate path needs no numeric
range change (OD-5).

v4 §3 states no word volume of any kind (FR-27), so this requirement has nothing to measure there
in any locale.

**Failure path:** a word-count constraint applied to any non-`uk-UA` locale contradicts OD-5 and is
a defect.

### FR-20: v4 structure is preserved in every locale

The v4 heading hierarchy (H2/H3), section order, list shapes and table shapes are preserved in
every locale produced by the translation path. Structure preservation is the v4 obligation that
fans out from the `uk-UA` master; word volume is not.

The v4 heading hierarchy this requirement preserves is the one v4 states section by section,
including §3's H2/H3 rule as stated in FR-27. A translated locale reproduces the master's H2 and
H3 levels as they stand; it does not promote an H3 to an H2, collapse two H2 groups into one, or
introduce a heading level the master does not have.

**Failure path:** a translated locale that drops, merges or reorders a v4 section, changes a
heading's level, or converts a list into prose, is a defect even though its word count is
unconstrained.

> **FR-27..FR-30 are new in v2.** They are appended here rather than inserted in v4 section order
> so that FR-1..FR-26 keep the numbers v1 gave them and downstream traceability is not churned.
> FR-21..FR-26 follow below in the AGENTS.md §4 section, where v1 put them.

### FR-27: The functionality section (v4 §3) is mandatory and is structured in H2 groups with optional H3 sub-groups

Every generated `'4.0'` document contains the v4 §3 functionality section, and it is structured as
v4 states.

> `Knowledge/Schemas/product_description_schemas_v4_ua.md:349-351`:
> `## § 3 Функціональність` — *Без обмеження обсягу | Блоки H2/H3 | **Обов'язково***

Three rules follow from the v4 text, and each is a requirement here:

1. **Mandatory.** The section is «Обов'язково» (`:351`). A `'4.0'` document with no functionality
   content at all is incomplete. The existing domain shape already agrees — `functionality` is a
   non-empty collection of subsections (`src/domain/description-doc.schema.ts:163`) — so this
   requirement **preserves** current behaviour rather than changing it.
2. **H2 for a group, H3 only when a group has 2+ distinct sub-functions.** v4 `:364-366`:
   «H2 — для широкої функціональної групи. H3 — тільки якщо в групі 2 і більше окремих підфункцій,
   що заслуговують на власний заголовок.» A single sub-function does not get its own H3, and the
   hierarchy is two levels deep — the existing domain shape already caps nesting at two levels, so
   this too is a preservation, not a change.
3. **No volume limit.** v4 `:355`: the volume is set by the breadth of the product's functionality —
   2–3 H2 blocks for a simple device, as many H2/H3 sections as a complex machine needs —
   «Ліміт не встановлюється». §3 therefore has **no word range and no section-count range**, in
   any locale. FR-18 and FR-19 have nothing to measure here, and no minimum or maximum number of
   §3 sections is introduced by this Story. The v4 recommended H2 order (`:380-388`: Технологія →
   Конструкція → ПЗ → Безпека → Сертифікація) is «**Рекомендований**» in v4's own words and is
   carried as a **prompt instruction** under OD-1, not as a validated ordering — the same handling
   FR-4 gives v4's recommended target of 6 §2 items.

**Failure path:** a `'4.0'` document with no functionality section fails validation. A functionality
group that opens an H3 for a single sub-function, or that introduces a third heading level, is a
structural defect (the third level is already rejected by the two-level shape). A section order
that differs from v4's recommended order is **not** a failure — it is a recommendation, and no
check rejects a generation for it.

### FR-28: Each functionality group covers a distinct technical aspect and does not restate another section

The functionality section does not duplicate, repeat or paraphrase the same characteristics,
functions or values from one block to another; each section covers a new, distinct technical
aspect (v4 §3, `:359`: «Суворо заборонено дублювати, повторювати або перефразувати одні й ті самі
характеристики, функції чи значення з блоку в блок»). Figures already stated in the Killer Specs
list are either not repeated here or are expanded with the context behind them, not restated bare
(v4 §3, `:396`). Each H2 group carries at least 2 sentences, and shortening a group "for the sake
of brevity" is not permitted (v4 §3, `:394`, `:359`).

**What is and is not enforced.** Every clause in this requirement is a **property of prose** —
whether two passages paraphrase each other, and how many sentences a passage contains, are
judgements no collection-length check makes. Under OD-9's split they are therefore **prompt
instructions and review criteria only**, exactly as FR-2, FR-3 and FR-5 state for their own prose
clauses. This requirement introduces no validation rule and no word or sentence count that can
reject a generation, consistent with FR-18.

**Failure path:** duplicated or padded functionality prose is a prompt-level miss and a review
finding; it does not fail validation and does not reject the generation. No automated check is
created by this requirement.

### FR-29: v4 §3 changes no item-count bound, and the §2 merge is recorded as an interaction with the existing floors

v4 §3 states no list-item count anywhere (FR-27 point 3). This Story therefore **changes no
item-count bound on the functionality section**, and in particular does not change the existing
bullets floor that applies inside it.

The Specification records the interaction rather than leaving ARCHITECTURE_PLANNING to rediscover
it. The two collections in play have deliberately different bullets floors:

- Key Benefits uses the **relaxed floor of 2**, and the relaxation is evidence-based: a live run on
  2026-08-17 shipped a `bullets` Block with only 2 items, the repair ladder had no cheaper repair
  than a full document regeneration, and the budget ran out before a valid document was produced
  (`src/domain/description-doc.schema.ts:82-95`).
- Functionality stays at the **strict floor of 3**, which the same comment calls "a DELIBERATE,
  ACCEPTED GAP, not an oversight … Revisit immediately if this same crash recurs on
  functionality", noting that the prompt-level mitigation (use a paragraph Block rather than an
  under-filled bullets Block) already applies there.

FR-4 moves non-list content out of §2, which is the relaxed-floor collection, and §3 is the
section whose shape admits that content with the stricter floor. This Specification does **not**
change either floor, and does not predict a failure; it states the interaction so that the repair
behaviour of FR-30 and any floor decision are taken knowingly rather than by default.

**Failure path:** n/a as a behaviour — this requirement asserts that an existing bound is unchanged
and creates no new check. A change to the functionality bullets floor made as a side effect of this
Story, without the evidence the schema comment asks for, is a defect against this requirement.

### FR-30: An exhausted repair budget fails the generation loudly and never downgrades the document

When a `'4.0'` generation cannot be made valid within the repair budget, the generation **fails**:
an error naming the unresolved schema failures is raised and **nothing is saved** for that product.
No partial, invalid or empty description is persisted, and the pipeline does **not** fall back to
emitting a `'3.0'` document — FR-15 requires every new generation to emit `'4.0'`, so a downgrade
would be a silent violation of it rather than a graceful degradation.

This restates existing behaviour rather than introducing it: the Doc path already refuses to let an
empty artifact leave, on the stated grounds that persisting an empty description is "a silent data
loss that surfaces days later as 'why is this product blank', with no trace of the cause"
(`src/render/doc-schema-issues.ts:144-174`). It is stated here because this Story adds a constraint
of a class the repair ladder has already failed on once (FR-29) and one that no single-field repair
can target (FR-17 point 2), so what happens at exhaustion must be a requirement rather than an
assumption.

**Failure path:** a run that persists an empty or schema-invalid description, or that emits a
`'3.0'` document because the `'4.0'` document could not be repaired, is a defect. A run that fails
with a message naming the unresolved schema failures is correct behaviour, not a miss.

## Generated-HTML requirements (AGENTS.md §4)

This Story changes generated HTML, so the §4 criteria below are requirements of this
Specification. Each is quoted verbatim from AGENTS.md §4.

### FR-21: Unit spacing and value fidelity

> "Space between number and unit: `1.75 mm`, `200 °C` (not `1.75mm`)."

> "Spec count on output = spec count on input. Don't change values or units."

**Preserved, and it bounds FR-16.** Separator localization changes punctuation only; it never
changes a digit, a unit, or the spacing between them.

### FR-22: Spec-count parity under comma-joining

> "Spec count on output = spec count on input. Don't change values or units."

**Preserved by FR-9.** Comma-joining several values of one parameter into a single row keeps the
row count equal to the input parameter count; it does not reduce the spec count.

### FR-23: Figure structure and lazy-loading

> "Each image wrapped in a `<figure>` with a `<figcaption>` (figcaption sourced from the manifest
> caption). First image's `<img>` — without `loading="lazy"`; every subsequent one — with it;
> `decoding="async"` on all. No orphan images (each `<figure>` is preceded by a `<p>` lead-in).
> The lead-in `<p>` must not duplicate the `<figcaption>`; `alt` must not duplicate the
> `<figcaption>`."

> "Images wrapped in `<figure>` (inline style `display: block; width: fit-content; max-width:
> 100%; margin: 4px auto;`) with a `<figcaption>` (a `<b>` lead-in label distinct from the alt +
> description) and `decoding="async"`. First image — without `loading="lazy"`; every subsequent
> one — with it. No `<figure>` nested inside `<p>`. No orphan images (each is preceded by a `<p>`
> lead-in)."

**Preserved.** The v4 Appendix image markup agrees with both criteria: the first image's `<img>`
carries no `loading="lazy"` and every later one does; `decoding="async"` is on all. Both bullets are
quoted because each pins something the other does not; neither is merged or deduplicated here.

**Where the v4 Appendix figure markup differs from AGENTS.md §4, §4 governs.** Specifically, the
`<figure>` inline style is `width: fit-content` as §4 states, not the `width: max-content` the v4
Appendix sample shows. AC-10's instruction to use the v4 Appendix markup does not weaken a §4
criterion.

**What the §2 merge does to the first-image rule (resolves spec-review finding 3).** FR-4 removes
figure content from §2, which changes where the first figure of a document falls. The criterion is
**preserved, and it is preserved as a property of the rendered document, not of the input**:

- The eager image is whichever `<img>` comes **first in the rendered document order** of the
  generated description; every `<img>` after it carries `loading="lazy"`. That is the criterion,
  and this Story does not change it.
- Because a `'4.0'` document carries no figure in §2, its first image is the first figure of the
  first later section that carries one. **Which source image occupies the LCP slot may therefore
  differ between a `'3.0'` and a `'4.0'` rendering of the same input.** This Specification accepts
  that: no requirement here pins *which* source image must be the eager one, and §4 does not
  either. A differing choice is not a §4 violation as long as exactly the first image in rendered
  document order is eager and every later one is lazy.
- **The position walk must see every section that can carry a figure.** This is the known failure
  mode, and it is recorded in the repository: a figure the position walk never visits resolves to
  position 0 — the LCP slot — and ships without `loading="lazy"`, which `output-validator` flags as
  `lcp-image-lazy` (`src/render/render-description.spec.ts:664-669`, the test that exists because
  §4 applications was once missed). Relocating figure content out of §2 is exactly the kind of
  change that trips it.

**Boundary case — a product with no images.** A document whose input manifest carries no image
emits no `<figure>` and no `<img>`, and satisfies this requirement vacuously. The absence of an
eager image in an image-less document is correct output, not a miss.

**Failure path:** an `<img>` other than the first in rendered document order without
`loading="lazy"`, or a first image that carries it, fails validation. A figure emitted in a
position the first-image determination does not account for is a defect against this requirement
even when the markup of the figure itself is correct.

### FR-24: Video survival and iframe markup

> "**A video embed present in the input is present in the output.** A YouTube/Vimeo `<iframe>` in
> the source description must survive into every generated language version. Losing it is a bug,
> not a stylistic choice — see `src/utils/video-manifest.ts`."

> "Video iframes (YouTube/Vimeo) wrapped in `<figure>` (aspect-ratio on the `<figure>`) with a
> `<figcaption>` in the artifact's own language (`Відеоогляд [Product]` for uk-UA, "Video review
> of [Product]" for en-*; see `FIGCAPTION_TEMPLATES` in `src/utils/video-figure.ts`); `src`
> preserved with `rel=0` ensured; `loading="lazy"` + the standard
> `allow`/`referrerpolicy`/`allowfullscreen` set; no `<figure>` nested inside `<p>`."

**Preserved.** The iframe `title` and the `<figcaption>` are in the artifact's own language in every
locale. FR-4 removes video embeds from §2 for a `'4.0'` document; survival is a property of the
document, not of §2, so a video present in the input is still present in the output — in a section
whose v4 shape admits it.

**Boundary case — a product with no video.** Most products have no video, the video manifest is
then empty and the prompt's video block is omitted; a document with no video embed satisfies this
requirement vacuously. Emitting no `<iframe>` when the input had none is correct output, not a
miss; losing an `<iframe>` the input did have is the bug this criterion names.

**Failure path:** a video embed present in the input and absent from any generated locale's output
is a defect, whatever the rest of that output looks like.

### FR-25: Markup discipline

> "HTML only, no Markdown. No `<br>` for spacing; `<hr>` after each `</section>`."

**Preserved.** This also reinforces FR-8's prohibition on `<br>` inside spec value cells.

### FR-26: Standing criteria that must remain true

> "**Forbidden** `itemtype="https://schema.org/Product"` in the description body (the CMS already
> emits Product via JSON-LD; a duplicate = a critical error in GSC). Allowed only: `PropertyValue`,
> `FAQPage`, `HowTo`."

> "SEO: meta_title ≤ 55 chars; meta_description ≤ 155, ends with CTA ➔. **No currency symbol** —
> price is not available at the Task B stage, and `task-b.ts` forbids inventing one;
> price/priceCurrency ship via Schema.org Offer microdata instead. `output-validator.ts`'s
> `meta-description-currency` rule is therefore deliberately never armed — see
> `src/services/seo-currency-wiring.spec.ts`."

> "Non-EN languages: no anglicisms ("друк" not "прінт", "ПЗ" not "софт")."

**Preserved unchanged.** v4 changes nothing about SEO metadata; the SEO generation step is not
touched by this Story (OD-8). The `meta-description-currency` rule **stays disarmed** — it is a
deliberate, load-bearing decision and must not be "fixed" while making the validator accept
`'4.0'`.

## Non-functional requirements

- **NFR-1 — Prompt caching separation.** `systemBlocks` must not be collapsed into `userContent`
  (AGENTS.md §3). The per-product hook-pattern index of FR-14 is **dynamic input**: it must not be
  injected into a cached prompt block, or prompt caching breaks. Where it is placed instead is an
  ARCHITECTURE_PLANNING decision.
- **NFR-2 — Provider independence.** No behaviour specified here may depend on which LLM provider
  is active (AGENTS.md §3 Rule 1).
- **NFR-3 — Retrieval separation.** Web search and page fetch stay out of generation (AGENTS.md §3
  Rule 2). This rule has no automated check; a green arch-guard is not evidence that it holds.
- **NFR-4 — Secrets.** No API key reaches the Angular bundle (AGENTS.md §3 Rule 4).
- **NFR-5 — Determinism.** The pattern index of FR-14 is a pure function of `name` + `website`:
  no unseeded randomness, no wall-clock dependence, no run counter. The same input yields the same
  pattern on every run. Determinism alone is not sufficient — FR-14 also requires the selection to
  distribute across the available patterns.
- **NFR-6 — `STORE_REGISTRY` is the only source of locales, currency and store names.** The locale
  groups of FR-16, the store name in the FR-11 heading and the locale keys of the FR-6 and FR-11
  heading tables are resolved from the registry; no language list, currency symbol or store name is
  hard-coded elsewhere (AGENTS.md §3).
- **NFR-7 — FROZEN-file discipline.** No FROZEN file is edited without explicit per-file human
  approval, and `.arch-guard-checksums` is re-baselined in the same commit as the edit
  (AGENTS.md §9).
- **NFR-8 — Cache preservation.** The change must not force regeneration of already-cached
  documents; preserving them is OD-2's stated rationale.
