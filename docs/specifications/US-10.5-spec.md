# Specification: US-10.5 - Restyle Image Studio to the new design - header, session list, results feed, composer and empty state - without adding new capabilities

## Summary

When this is done Image Studio shows a header (title, "New session", saved-session count), a session list with per-row name, date and cost, a results feed whose turns show input thumbnails, prompt, chips, a summary line and "Reuse prompt", images labelled `v{N} · {width}×{height}` with one-click native "Download" and "Edit this →", an "Edit of v{N}" chip with a before/after Compare slider in the full-view dialog, a "Download all (N) .zip" with a timestamped name, the version strip under the main image, a restyled composer (preset check mark, quick-edit chips above the prompt, "Generate" with Ctrl+Enter) and an empty state with three starter cards read from `PROMPT_PRESETS`. The stored session shape gains optional per-turn fields so the new displays have data, and sessions saved before this Story still load. Every studio surface follows the `--shell-*` tokens in a dark and a light theme, and everything the studio already does, except the three owner-approved departures and the small departures of the owner's rulings (Story v5 Context), keeps working. The points on which Specification v3 offered alternatives (the images-only send, the preset id after an edit, model text parts, the feed container, the removed spec tests, the duration end point, and what counts as an edit) were ruled by the owner on 2026-11-08 and are base requirements here; the points that still await the human are Proposed blocks.

## Functional requirements

Terminology. "The studio" is Image Studio. "A turn card" is the results-feed entry of one generation: the prompt sent and the images (versions) it produced. "Source version" is the version an edit was made from. "Stored turn" is the persisted conversation record. "Old session" is a session saved before this Story: its turns lack `cost`, `durationMs`, `presetId`, source version and input references. "The composer" is the input area with the prompt field, attachments, presets, ratio, resolution, model and Generate. "Retained version" is a version the session currently holds.

Plural forms. Where a count is shown in a sentence, English uses the singular for exactly 1 and the plural otherwise (including 0). Ukrainian uses the CLDR cardinal rule for `uk`: the "one" form when N mod 10 = 1 and N mod 100 ≠ 11; the "few" form when N mod 10 is 2 to 4 and N mod 100 is not 12 to 14; the "many" form otherwise (N mod 10 = 0, or 5 to 9, or N mod 100 is 11 to 14). So 1, 21, 101 take "one"; 2-4, 22-24 take "few"; 0, 5-20, 25-30 take "many".

### Header and session list

#### FR-1: Studio header

The studio header shows the title "Image Studio" (UA "Студія зображень") and a "New session" button (UA "Нова сесія") followed, on the same line, by the saved-session count in the form "· history (N)" (UA "· історія (N)"). The header shows no spend total of any kind (no today, month or session cost). Activating "New session" does what the list's "New session" button did before (it moves to the header; US-10.1).

**Failure path:** a spend total in the header, or a second "New session" button left in the session list, is a defect; the header renders without error whatever the number of saved sessions.

**Proposed (OD-6b, OD-6c), for HUMAN_SPEC_APPROVAL.** With no saved sessions the header shows "history (0)". N is the number of sessions in the session list, so it equals the N of "N sessions" (FR-2); "history (N)" is plain text, not a control. The existing "Start a new session?" confirmation (US-10.1 T-23) is kept when "New session" is activated from the header, because the Story moves the button and changes no behaviour.

#### FR-2: Session list rows and count

The session list shows the line "N sessions" (UA "N сесій") and no search hint. Each row shows (a) the session name, which is the last prompt entered in that session, (b) the date of the session's last activity as `dd.MM · HH:mm` (24-hour, device local time), and (c) that session's own cost (its stored session cost). Selecting a row selects that session as before. The overall estimated-cost line ("Estimated cost: {amount}", US-10.1 X-10) is not rendered anywhere in the list.

**Failure path:** a row whose session has no prompt yet still renders (date and cost) and does not throw. A cost line "Estimated cost" anywhere in the list is a defect.

**Proposed (OD-6a, OD-6d, OD-6e, OD-5), for HUMAN_SPEC_APPROVAL.** (i) A row with no prompt shows no name text (date and cost only); a long name is truncated to one line with an ellipsis. (ii) The per-row cost uses the existing studio format: `$` and two decimals (for example `$0.12`). (iii) The date shape is numeric and fixed in both UI languages (the Story fixes the shape), in local time. (iv) Count forms: EN "1 session" / "N sessions"; UA "1 сесія" (one), "2 сесії" (few), "5 сесій" (many), chosen by the plural rule above (the owner supplied only "N сесій", the "many" form).

### Results feed - turn cards

#### FR-3: Turn card content

Each turn card that produced at least one image shows: (a) thumbnails of the input images the generation was made from, (b) the prompt text, (c) a chip for the preset used, if any, (d) chips for the aspect ratio, resolution and model, (e) the summary line of FR-4, and (f) a "Reuse prompt" button (UA "Використати промпт"). The preset chip (c) and the thumbnails (a) are read from the stored turn.

(g) The model text parts of an `images` response (shipped by US-10.1 FR-20 and pinned today by `image-studio.component.spec.ts`, L383-400: `FIRST-TEXT`, image, `SECOND-TEXT`, image) are shown inside the turn card, interleaved with the image tiles in the order the API returned them (owner ruling SQ-3-A, OD-31; Story Context).

(h) The feed container keeps `role="log"`, `aria-live="off"` and the accessible name X-26 ("Conversation" / "Розмова" in the studio's existing texts), and holds the turn cards, the version strip and the events. Assertions that count generated tiles select the tiles, not the strip thumbnails: the strip's thumbnails use the prompt as their `alt`, so the existing assertion that counts the images of the log whose `alt` equals the prompt (L394-395: exactly 2) is narrowed to the image tiles, and its expected count of generated tiles stays 2 (owner ruling SQ-4-i, OD-32; FR-32 (d)).

These rules also hold with (g) and (h):

1. The image tiles of one turn card appear in the order in which the API returned their images.
2. Model text parts add no image, no version and no unit to the N of the summary line (FR-4); text parts never change the number of tiles.
3. Neither the presence of text parts nor the container raises an error, hides a tile, or changes which versions the version strip lists (FR-13).
4. Every generated image tile appears in the feed container exactly once.

**Failure path:** for an old session (a turn lacking the stored fields) the card omits the preset chip and the thumbnails without an error and without a placeholder error state; the remaining parts still render. A thumbnail whose image bytes are no longer available is omitted without an error.

**Proposed (OD-12, OD-17a), for HUMAN_SPEC_APPROVAL.** Replies that yield no image (a text-only reply, a safety block, a failure with Retry) keep their existing content and behaviour, restyled only; the summary line and "Reuse prompt" are required for turns that produced at least one image. Thumbnails cover both uploaded attachments and an attached earlier version.

#### FR-4: Summary line

A turn card that produced images shows the summary line "N images · $cost · T s", where N is the number of images that turn produced, `cost` is the stored cost of that generation in USD, and T is the stored duration in seconds. For an old session the summary line is omitted entirely.

**Failure path:** a turn with only one of `cost` and `durationMs` stored omits the missing segment and its separator; a turn with neither shows no summary line (FR-3's omission rule); a missing value never renders as `NaN`, `undefined` or `$0.00`. A stored value that is present but invalid is treated as missing (FR-23).

**Proposed (OD-25, OD-5), for HUMAN_SPEC_APPROVAL.** Cost uses `$` and two decimals (the existing format); T is shown with one decimal (for example `12.4 s`). EN "1 image" / "N images"; UA "1 зображення" (one), "2 зображення" (few), "5 зображень" (many), chosen by the plural rule above, and the seconds unit "с". The UA string is proposed copy, not owner-supplied.

#### FR-5: "Reuse prompt"

Activating "Reuse prompt" on a turn card puts that turn's prompt text, aspect ratio and model into the composer and moves focus to the prompt field. It does not send a generation request and does not start any other request.

**Failure path:** if the restored model does not offer the composer's current resolution, the composer must not be left in a state the resolution rule forbids (US-10.1 AC-9: 4K needs the Pro model); no request is sent in any case.

**Proposed (OD-19, OD-7), for HUMAN_SPEC_APPROVAL.** The restored prompt text replaces what was in the field. The resolution is not restored (the Story lists three fields). When the restored model does not offer the current resolution, the resolution changes to the nearest lower resolution that model offers. The button is disabled whenever the prompt field is disabled (for example while a generation runs) and is not shown on a turn that has no stored prompt text.

### Results feed - images

#### FR-6: Image tile label and actions; native one-click download

Each generated image shows the label `v{N} · {width}×{height}` and the actions "Download" (UA "Завантажити") and "Edit this →" (UA "Редагувати →"). "Edit this →" behaves as "Edit this version" did before (US-10.1 AC-22). "Download" saves that image in its native format in one click, with no format choice. The download-format selector (US-10.1 X-7, "Download format") is not rendered anywhere in the studio.

**Failure path:** if saving fails, the existing failure behaviour of single-image download is unchanged. A format selector anywhere in the studio is a defect.

**Proposed (OD-24), for HUMAN_SPEC_APPROVAL.** "Native format" is the format the image is held in, and the saved file's extension follows it. Because no selector exists, the archive of FR-11 and FR-12 also contains each image in its native format. Copy to clipboard keeps its existing behaviour. This Story deletes no code or spec behind the removed selector (the transcoding path, the stored `inputFormat` and `downloaded` fields, `output-format.spec.ts`, `zip.spec.ts` are left as they are; whether they become dead code is for a later Story).

#### FR-7: Render-time image size

`{width}×{height}` in the label of FR-6 is computed when the image is rendered, from the image bytes through the `ImageCodec.probe` port, and is not stored in the session.

**Failure path:** if the probe has not resolved, or rejects because the bytes cannot be decoded, the label shows `v{N}` alone, no error is shown and no exception reaches the user.

**Proposed (OD-23), for HUMAN_SPEC_APPROVAL.** The probe result is obtained once per image and reused while the image stays on the page; re-rendering the feed does not decode the image again (observable as: the number of probe calls for N distinct images stays N across any number of feed re-renders).

#### FR-8: Capabilities that are not rendered

The studio renders none of: "Upscale 4K", "Variation", "Alt text", Ctrl+K session search or its hint, a Today or month spend, "Save current as preset", the Product / Style ref role selector, the "Images 1/2/4" selector, a pre-send cost estimate.

**Failure path:** any of these appearing, even disabled, is a defect. (US-10.6 adds some of them; they are out of this Story.)

### Results feed - edits and compare

#### FR-9: "Edit of v{N}" chip and "Compare with v{N}" control

An image that edits an earlier version shows the chip "Edit of v{N}" (UA "Редакція v{N}") and a control "Compare with v{N}" (UA "Порівняти з v{N}"), where v{N} is the stored source version of that image. Both are read from the stored source version.

An image has a stored source version only when it was generated with an earlier version attached to the composer at the time of the send (the attachment made by "Edit this →", US-10.1 AC-22); its stored source version is that version's number (owner ruling SQ-7-A, OD-35; Story AC-5). A quick-edit chip send (US-10.1 AC-18) and a typed follow-up with nothing attached store none, and neither does an image of a session's first generation (no earlier version exists); such images show neither the chip nor the control. "An image that edits an earlier version" in this requirement means exactly the images that have a stored source version.

**Failure path:** an image with no stored source version (every image of an old session, and every image not generated by an edit) shows neither the chip nor the control, without an error. A stored source version that is present but invalid is treated as absent (FR-23).

**Proposed (OD-9), for HUMAN_SPEC_APPROVAL.** The control is shown for each image that has a stored source version, and compares that image (After) with its source version (Before). When the source version v{N} is no longer in the session (the stored value is valid but the version is gone), the Compare control is not shown and the chip stays. Story AC-5 words the chip and control per turn; the Story lets the stored source version live on the version or on the turn, so this Specification states the display per image, which agrees with AC-5 for a turn with one image and, for a turn with several images, shows the chip and control on each image that edits an earlier version (a sharpening of AC-5, not a new behaviour).

**Proposed (OD-35 remainder), for HUMAN_SPEC_APPROVAL.** The rule above is evaluated at the moment of the send. If the user detaches the attached version before pressing Send, the send has no attached version, so it stores no source version and its images show neither the chip nor the control. (The composer holds at most one attached version, so a single source number is representable.)

#### FR-10: Before/after slider in the full-view dialog

Activating "Compare with v{N}" opens, inside the existing full-view dialog (not inline in the feed), a before/after slider that shows the source version labelled "Before (v{N})" (UA "До (v{N})") and the edited image labelled "After (v{M})" (UA "Після (v{M})"). The slider has `role="slider"` and is operable from the keyboard alone: at minimum, ArrowLeft decreases and ArrowRight increases its value (`aria-valuenow`), Home sets its minimum (`aria-valuemin`) and End sets its maximum (`aria-valuemax`). The dialog closes as it does today (Escape and its existing close control) and the existing dialog actions are kept.

**Failure path:** if either image cannot be displayed, no uncaught error reaches the user and the studio stays usable.

**Proposed (OD-9), for HUMAN_SPEC_APPROVAL.** If either image cannot be displayed, no broken slider is shown: the user stays on the feed or sees the existing single-image view. The slider starts at 50; ArrowLeft and ArrowRight move it by 5 on a 0-100 scale (the key map in the base text is the minimal reading of "operable by keyboard"; the start value and step size are proposed); it has an accessible name. When the two images differ in size or aspect ratio, both are fitted uncropped and undistorted into one frame.

### Results feed - archive and strip

#### FR-11: "Download all" control

The results feed shows the control "Download all (N) .zip" (UA "Завантажити все (N) .zip") where N equals the number of retained versions in the session (US-10.1 AC-35), and keeps the SynthID notice. The control lives in the feed (not in the version strip). The control is disabled when the session retains no version (N = 0) and while a delivery action (a single-image download, a copy, or an archive build) is in progress; activating it while disabled saves no file and starts no action. A generation in progress does not disable it. This is the behaviour of the current "Download all versions" button, pinned by the existing spec SD-28, and the Story changes only its label, its place and its archive name.

**Failure path:** a conversion or archive failure keeps its existing behaviour (an alert, no partial archive, nothing flagged downloaded; US-10.1).

**Proposed (no OD; spec review B2, rendering part only), for HUMAN_SPEC_APPROVAL.** Where the control is rendered when N = 0: it is rendered disabled, reading "Download all (0) .zip", in a feed that is shown; it is not rendered while the empty state of FR-18 is shown (no turns, so no feed).

#### FR-12: Archive name

The archive saved by "Download all" is named `{timestamp}-{sessionName}.zip`, where:

- `{timestamp}` is UTC in the format `YYYYMMDD-HHMMSS`;
- `sessionName` is the session's last prompt (the same value as the session name in FR-2), transliterated, with special characters and spaces replaced by hyphens (kebab-case), and capped at 40 characters: a name longer than 40 characters is cut before the last hyphen that lies within its first 41 characters, so that the result has at most 40 characters, or at 40 characters if there is no such hyphen.

This is the owner's rule as written in Story v5 AC-6 (cut rule: owner ruling on Story Q5, OD-26: keep 40 characters). Story AC-6's example `20261108-181530-red-sneakers-on-white.zip` follows it: the name part `red-sneakers-on-white` is 21 characters and is not cut.

**Failure path:** the name is always a valid file name; a prompt that yields an empty name part after stripping does not produce an empty, hyphen-only or `undefined` name part.

**Proposed (OD-15 remainder: the normalisation order), for HUMAN_SPEC_APPROVAL.** The cut rule above is the owner's. The Story does not say in what order kebab-case is applied relative to the count, so this Specification proposes that the cut rule is applied to K, the kebab-case string, computed in this order: transliterate (item (iii) below), lower-case, replace every run of characters outside `a-z0-9` by one hyphen (a run of hyphens collapses to one), and remove leading and trailing hyphens (trimming). The limit of 40, the window of the first 41 characters and "the last hyphen" are all counted on K, that is after transliteration and normalisation (a transliterated letter can take several Latin characters). K has no leading or trailing hyphen, so a cut never leaves an empty name part, and `sessionName` never ends in a hyphen.

Test vectors under the ruled rule and this K (computed for this Specification; K is the kebab string):

| Prompt | `sessionName` | Length | Why |
|---|---|---|---|
| `Red sneakers on white` | `red-sneakers-on-white` | 21 | K is not longer than 40: no cut |
| `A red sneaker on a white background with a soft shadow` | `a-red-sneaker-on-a-white-background-with` | 40 | the last hyphen within the first 41 characters is at position 41: cut before it, 40 characters |
| `Red sneakers on a white background with a soft shadow` | `red-sneakers-on-a-white-background-with` | 39 | the last hyphen within the first 41 characters is at position 40 (position 41 is `a`): cut before it |
| `Leather hiking boots with waterproof membrane and red laces` | `leather-hiking-boots-with-waterproof` | 36 | the last hyphen within the first 41 characters is at position 37 |
| `Pneumonoultramicroscopicsilicovolcanoconiosisextra shoes` | `pneumonoultramicroscopicsilicovolcanocon` | 40 | no hyphen within the first 41 characters: hard cut at 40 |

The owner's earlier example `20261108-181530-a-red-sneaker-on-a-white-backgrou.zip` is not a test vector: its name part `a-red-sneaker-on-a-white-backgrou` (33 characters) is a mid-word cut that the ruled rule cannot produce (the rule ends a name at a whole word, or at exactly 40 characters when the first 41 characters hold no hyphen), and the example's prompt is not given. The owner's ruling on Q5 supersedes it.

**Proposed (OD-15, remaining parts), for HUMAN_SPEC_APPROVAL.** (i) The timestamp is the UTC time of the moment "Download all" is activated, read through the existing `Clock` port (so tests control it). (ii) Lower-casing is part of kebab-case (the Story's example is lower case; the rule text does not say so). (iii) Transliteration of Ukrainian Cyrillic follows the Ukrainian national transliteration (Cabinet of Ministers resolution No. 55, 2010), including its position-dependent letters; for example `Червоні кросівки` gives `chervoni-krosivky`; a character with no Latin mapping is treated as a special character. (iv) When K is empty after stripping (or the session has no prompt), the file is named `{timestamp}-image-studio-versions.zip` (the old constant name's stem). (v) Two archives created in the same second are not renamed by the studio; a collision is left to the browser's own de-duplication.

#### FR-13: Version strip placement

The version strip (US-10.1 AC-23) is displayed under the main generated image in the results feed, where "the main generated image" is defined in the Proposed block below. Clicking a thumbnail in the strip opens the full view, as before.

**Failure path:** a session that retains no version renders no strip and no empty frame in its place, and raises no error; the strip's existing single-version behaviour is unchanged.

**Proposed (OD-27; Story AC-7 wording, found by the Specification review as B1), for HUMAN_SPEC_APPROVAL.** The Story does not define "the main generated image", and today the strip is one session-wide element rendered after the whole feed. This Specification proposes:

1. **Definition.** The main generated image is the image with the highest version number among the retained versions of the session (the newest image), as displayed in the image tile of the turn card that produced it. If that turn produced several images, each has its own tile and the main one is the tile of the highest version number.
2. **One strip per session.** There is exactly one strip, not one per turn; it lists every retained version (US-10.1 AC-23 unchanged). It is displayed directly below the image tiles of the turn card that holds the main image: in document and visual order it follows that tile and precedes any feed entry that comes after that turn card, and it is not rendered inside any other turn card.
3. **Boundary cases.** No retained version: no strip (see the failure path). One version: one thumbnail, under that image. Several turns: under the newest image only; earlier turn cards have no strip. While a new generation is running the strip stays under the current main image, and moves under the new image once that version is retained. If the turn card of the main image is not in the feed (for example its turn was dropped from the history), the strip is displayed at the end of the feed. An old session follows the same rules.

(Item 2 above is approved text and stands unchanged: the feed container of FR-3 (h) holds the strip, and the strip's thumbnails are not image tiles; owner ruling SQ-4-i, OD-32.)

### Composer

#### FR-14: Preset row selected mark

The preset row marks the selected preset with a check mark. The check mark disappears as soon as the user edits the prompt text. No "Save current as preset" control is rendered (FR-8). Choosing a preset sets prompt, aspect ratio, resolution and model exactly as before (US-10.1 AC-15).

Three values follow a picked preset: (w) the `presetId` sent in the generation request, which also forms the usage row label `image-studio|<presetId>|<resolution>`; (r) the `presetId` stored in the turn (FR-23), which is the preset the card shows as its chip (FR-3 (c)); (c) the preset that carries the check mark. When the prompt text was edited after a preset was picked, the request still carries the picked preset id (as today; the usage row label and the request are unchanged), the stored turn records no preset, and the check mark is cleared (owner ruling SQ-2-A, OD-30; OD-18 RESOLVED). The sent preset id is kept apart from the check mark: clearing the check mark does not change (w). In order:

1. Without any edit of the prompt text after the pick, (w), (r) and (c) are the picked preset.
2. With no preset picked, none of the three exists.
3. A quick-edit chip send has none of the three (as today, a chip send clears the preset).
4. (c) clears as soon as the prompt text is edited (AC-8). (r) is the preset whose check mark was showing when the prompt was sent: if the user edited the prompt after picking a preset, no preset is recorded and no preset chip appears (FR-3).
5. The stored `presetId` is never part of the content resent to the model API (FR-23).

**Failure path:** a check mark that remains after the prompt text was edited, or one on two presets at once, is a defect.

**Proposed (OD-13), for HUMAN_SPEC_APPROVAL.** (i) The selected state is conveyed programmatically as well as by the glyph (WCAG 1.4.1: not by a glyph alone). (ii) This Story specifies no other lifecycle for the check mark (on send, on a new session): the existing behaviour is kept.

#### FR-15: Quick-edit chips placement

The quick-edit chips (US-10.1 AC-18) are displayed directly above the prompt field, and only once the session holds at least one generated version.

**Failure path:** with no generated version the chips are not rendered.

#### FR-16: Aspect ratio, resolution and model controls

The aspect-ratio control is the existing native `<select>` and offers every value of `image-studio-contract.json`: 1:1, 4:3, 3:4, 4:5, 16:9, 9:16. The resolution and model controls keep their current options. The rule that 4K needs the Pro model (US-10.1 AC-9) holds.

**Failure path:** a composer state with 4K and a model that does not offer it is a defect; selecting such a combination is prevented exactly as before.

#### FR-17: Generate button and Ctrl+Enter

The send button is labelled "Generate" (UA "Згенерувати"; replaces "Send" / "Надіслати", US-10.1 X-1) and shows the hint "Ctrl ↵". The button is enabled exactly when the existing send rule `canSend()` (US-10.1 FR-18) is true, so a send with a blank prompt and a ready upload or an attached earlier version (the "images-only send") still works as before; "Write a prompt to start" shows only when there is nothing to send (owner ruling SQ-1-B, OD-29; Story AC-11). In order:

1. **One rule for click and chord.** Pressing Ctrl+Enter submits the prompt exactly when a click on the button would send; it never sends while the button is disabled.
2. **Enablement.** The button is enabled exactly when `canSend()` is true. It is disabled when `canSend()` is false: no session, a generation running, an attachment uploading, a blocked session, or nothing to send.
3. **Nothing to send.** When the prompt text is blank (empty or whitespace only) and the composer holds no ready upload and no attached version, the button is disabled and its label reads "Write a prompt to start" (UA "Напишіть промпт для початку").
4. **Generate.** The label reads "Generate" whenever the prompt text is not blank and whenever the button is enabled.
5. **The request is unchanged.** A send that occurs produces the same generation request, the same stored role and parts; the FR-23 fields are the only additions. Enablement and label are all this requirement changes about sending. Retry and Cancel are not affected.

**A v4 change to an approved block (reviewer note N2; owner ruling SQ-1-B).** The approved v3 Proposed block for OD-13 said that in every disabled state other than the empty prompt the label stays "Generate", and its bracketed sentence added that a blank prompt with another reason for being disabled reads "Write a prompt to start". Under rules 3 and 4 the label follows the draft, not the reason the button is disabled. The visible effect: while a generation is running (or an attachment is uploading, or the session is blocked) and the draft is blank with nothing attached, the disabled button reads "Write a prompt to start"; with the prompt text not blank it keeps "Generate".

**Failure path:** Ctrl+Enter while the button is disabled (nothing to send, generation running, attachment uploading, blocked session) sends nothing.

**Proposed (OD-13 remainder), for HUMAN_SPEC_APPROVAL.** When the prompt text is blank, the composer holds a ready upload or an attached version, and the button is disabled for another reason (for example while a generation is running), the Story states neither label; "Generate" is proposed, because the Story gives the other label only for "nothing to send". The chord is handled in the prompt field; Cmd+Enter on macOS is not specified by the Story and is not required.

### Empty state

#### FR-18: Empty state content and timing

A session with no turns and no generation in progress shows the headline "Your images will appear here", an explanatory sentence, and three starter cards "Product on white" (1:1), "Lifestyle scene" (4:5), "Category banner" (16:9), each with its description (FR-22). The empty state is shown only while the session has no turns and no generation is in progress.

**Failure path:** the empty state is not shown once any turn exists, and not while the first generation runs.

**Proposed (OD-5, OD-12), for HUMAN_SPEC_APPROVAL.** If the first generation fails and no turn is stored, the literal rule above applies and the empty state is shown again. Copy with no source in the owner's answers: explanatory sentence EN "Describe the image you want, or start from one of the templates below." / UA "Опишіть потрібне зображення або почніть з одного з шаблонів нижче."; UA headline "Тут з'являться ваші зображення"; UA card titles "Товар на білому тлі", "Лайфстайл-сцена", "Банер категорії". The state before any session exists, and the blocked-session state, keep their existing presentation, restyled only.

#### FR-19: Starter cards fill the composer

Choosing a starter card fills the prompt, aspect ratio, resolution and model exactly as selecting the corresponding preset does (US-10.1 AC-15), and leaves the prompt editable. Choosing a card has the same effect on the preset check mark and the recorded preset as choosing the preset in the preset row (FR-14).

**Failure path:** choosing a card never leaves the composer in a state forbidden by FR-16 and raises no uncaught error.

#### FR-20: Progress during the first generation

During the first generation of a session (no turns, generation in progress) a progress indicator or skeleton is shown in place of the empty state.

**Failure path:** if that generation ends without a version, the progress indicator is removed and FR-18 applies.

**Proposed (OD-22), for HUMAN_SPEC_APPROVAL.** The indicator is presentational and carries no `role="status"` (it may be hidden from assistive technology): the studio's existing single status region remains the announcement path, so FR-33 holds.

### Presets and stored shape

#### FR-21: Preset registry

`PROMPT_PRESETS` holds exactly five presets - `white-bg`, `lifestyle`, `banner`, `social`, `detail-closeup` - and passes `validatePreset`. The names of `white-bg`, `lifestyle` and `banner` (UA and EN) are the card titles of FR-18 ("Product on white", "Lifestyle scene", "Category banner" and their UA forms), and their default aspect ratios are 1:1, 4:5 and 16:9; `lifestyle` defaults to 4:5 (was 4:3). The prompt templates of all five presets are unchanged. `social` and `detail-closeup` are unchanged. The EN titles and ratios are fixed by the Story; the UA titles are the proposed copy of FR-18 (OD-5) until ratified.

**Failure path:** a preset that fails `validatePreset` is a registry-test failure, never a runtime error (existing contract).

#### FR-22: Preset description and cards read the registry

`PromptPreset` gains an optional `description`, bilingual like `name`. The three cards show it: `white-bg` EN "Perfect for e-commerce listings" / UA "Ідеально для товарних карток"; `lifestyle` EN "Product in a realistic setting" / UA "Товар у реалістичному оточенні"; `banner` EN "Wide format with space for text" / UA "Широкий формат із місцем для тексту". The three starter cards are read from `PROMPT_PRESETS`, not hard-coded in the component: a change to a preset's name, ratio or description in the registry changes its card with no component change. `PROMPT_PRESETS` is the single source of truth for the preset names, ratios and descriptions the studio displays.

**Failure path:** a preset without a `description` renders no description text and no empty element (`social` and `detail-closeup` have none).

#### FR-23: Stored session shape

The stored session shape and its `schemas.ts` validation gain these fields, all optional on read: on the turn, `cost` (USD) and `durationMs` and `presetId`; the source version number of an edit (on the version or on the turn: placement decided in ARCHITECTURE_PLANNING); and references to the attachments the image was generated from (the thumbnails of FR-3). Width and height are not stored (FR-7). A stored value written by the studio survives a reload.

**Failure path (absent fields):** the validation accepts a stored session in which none of these fields is present and does not reject a session because a field is absent. A property of a stored turn or version that this Specification does not list ("an extra value") is preserved as stored and ignored; it never causes rejection (the stored shape already passes unknown keys through).

**Failure path (present but invalid), Proposed (OD-28, related to OD-17c; found by the Specification review as B5), for HUMAN_SPEC_APPROVAL.** A new field that is present but invalid does not reject the session and does not raise an error: the session loads and the invalid field is treated as absent, so the parts that depend on it are omitted exactly as FR-3, FR-4 and FR-9 omit them for an old session. Other valid fields of the same turn are still used (for example, a turn with an invalid `cost` and a valid `durationMs` shows only the duration segment, FR-4). Validity:

| Field | Valid | Present but invalid (treated as absent) |
|---|---|---|
| `cost` | a finite number, zero or greater | a string such as `"abc"`, a negative number, `NaN`, infinity |
| `durationMs` | a finite number, zero or greater | the same set |
| source version | an integer of 1 or more that is lower than the image's own version number | zero, negative, non-integer, non-numeric, or equal to or greater than the image's own number |
| `presetId` | the id of a preset in `PROMPT_PRESETS` | an unknown id (for example one removed from the registry later), a non-string |
| attachment references | each reference identifies an attachment of the session | a reference to an attachment that does not exist (dangling) is dropped on its own; the remaining thumbnails still render |

This differs on purpose from the existing rule that a stored record failing its schema is ignored (P-9): that rule protects the core fields; rejecting a whole session because an optional display field is malformed would hide the user's data.

**Proposed (OD-17, OD-3), for HUMAN_SPEC_APPROVAL.** Which turn of a generation's user/model pair carries each field, and the exact form of the thumbnail reference, are left to ARCHITECTURE_PLANNING (the Story delegates the source-version placement). The observable requirements are: the fields are persisted and read back; they are not included in the content resent to the model API (a turn is the resend payload, see Background; sending the new fields would change the request, which the Story forbids by "existing behaviour does not change"); and the save path does not drop them.

#### FR-24: Measuring cost and duration

`cost` is the USD cost of the generation response that produced the turn. `durationMs` is the time from the "Send" click (or the "Retry" click) to the moment the response is handed to the persistence port for storing, in non-negative milliseconds; the write itself and the attachment upload are not included, because a send cannot start while an upload runs (owner ruling SQ-6-A + SQ-6-U1, OD-34; Story AC-13a). A Retry restarts the clock: `durationMs` of the retried generation runs from the Retry click, not from the original Send. Both are recorded in the stored turn.

**Failure path:** a response that stores no turn (a text-only reply, a safety block, a failure) stores neither field.

**Proposed (OD-3b), for HUMAN_SPEC_APPROVAL.** `cost` equals the amount that response adds to the session's running cost (the same number the session list shows per row after summation). The clock is read through the existing `Clock` port, so tests control it.

#### FR-25: Old sessions keep loading

A session saved before this Story loads without error and works as before: selecting it, adding turns, editing a version and downloading all behave normally. For its turns the summary line, preset chip, "Edit of v{N}" chip, Compare control and thumbnails are omitted. Turns added to an old session after this Story carry the new fields and display them.

**Failure path:** an old session that shows an error, a blank feed, or a placeholder for the missing parts is a defect; a session with a mix of old turns (no fields) and new turns (fields) renders each according to its own stored fields.

#### FR-33: Single status region; focus stays in the prompt

The studio has exactly one `role="status"` element (US-10.1 AC-46). After a generation finishes, focus remains in the prompt field (US-10.1 AC-48).

**Failure path:** a second `role="status"` element (for example from the progress indicator, FR-20), or focus leaving the prompt field when a generation finishes, is a defect. (US-10.1 also keeps focus in the prompt after an error, Cancel or timeout; that is preserved.)

Not in play. This Story changes the studio's interface only: no prompt, renderer or generated product HTML changes. No §4 criterion is restated and none is weakened: no requirement above concerns spec-count parity, figure/figcaption structure, image loading attributes, video, `meta_title` or `meta_description`.

## Non-functional requirements

- **NFR-1 (provider independence, retrieval separation, secrets: AGENTS.md §3 Rules 1, 2, 4):** the change touches no LLM call, retrieval path, proxy, prompt or secret; no new network request is added; nothing is added to the browser bundle that would carry a key. No server change.
- **NFR-2 (prompts out of code: AGENTS.md §3 Rule 3):** no component holds preset prompt text or card text for presets; preset names, ratios and descriptions live in `PROMPT_PRESETS` (FR-22). The preset prompt templates are unchanged (FR-21).
- **NFR-3 (no new capability):** behaviour not listed in FR-1..FR-33 is unchanged; no capability of FR-8 is added.
- **NFR-4 (determinism: AGENTS.md §5):** tests control time: the archive timestamp, the stored duration and the local `dd.MM · HH:mm` date are tested with a controlled clock and a controlled time zone, no wall clock and no unseeded randomness. The archive-name derivation (transliteration, kebab-case, cut rule) is a pure function of the prompt and the instant. Tests assert what a user observes (role and text), not that something merely exists.
- **NFR-5 (localisation):** every new user-visible label, accessible name and hint exists in both the `en` and `uk` forms of the studio texts, in the same way as the existing studio texts. The "Ctrl ↵" hint is language-neutral.
- **NFR-6 (no data loss):** old sessions are never rewritten in a way that loses data; the new fields are additive and optional on read (FR-23, FR-25).
- **NFR-7 (FROZEN files, AGENTS.md §9):** no FROZEN file is modified.

## Out of scope

- Ctrl+K session search and the "Alt text" action: dropped from the project for now; not planned.
- The preset prompt templates, any prompt change, FROZEN files, any server change, any change to what is sent to a model.

- A mobile layout (the minimum supported width is 1024 px).
- Any other app mode (generator, optimizer, Image Tools, HTML Editor, Dashboard, and so on).
- Rendering performance targets for very long sessions: no budget is set by the Story (the once-per-image probe rule of FR-7 is the only related requirement).
