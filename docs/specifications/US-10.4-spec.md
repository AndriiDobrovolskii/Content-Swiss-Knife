# Specification: US-10.4 - Redesign the app shell: grouped, collapsible navigation and restyled layout in light and dark themes

## Summary

When this is done the app has one global left navigation rail that groups the 12 content modes under three expandable groups (SEO & Text, Images, Code), keeps Dashboard, Language, Theme and AI Settings at its bottom, and collapses to a 64 px icon-only rail whose state survives a reload. The per-mode input panel is rendered only in the nine text modes and Image Tools; it is gone, together with Clear All, History and the improvement-request button, from Image Studio, HTML Editor and Dashboard. The shell is restyled with the design's dark tokens and a derived light theme, meets WCAG AA text contrast, stays usable at 1024 px, and the manual verification of all of that is recorded under `docs/evidence/`.

Story v4 transcribes the product owner's answers of 2026-11-08 (OD-1..OD-21 in the Open Decisions log, all answered and treated here as settled requirements). ## Functional requirements

Terminology: "the rail" is the global left navigation. "The panel" is the per-mode input panel (today's `<aside>`). "Panel modes" are the nine text modes (generator, ua-generator, optimizer, translator, seo-generator, copywriter, readability, slug-generator, faq-generator) plus `image-tools`. "Panel-less modes" are `image-studio`, `html-editor` and `dashboard`. There are 13 `AppMode` values: the 12 content modes and `dashboard`.

### FR-1: Grouped navigation content

The rail lists the 12 content modes under three group headers. EN interface: "SEO & Text · 9", "Images · 2", "Code · 1". UA interface: "SEO та Текст", "Зображення", "Код", each followed by the same count in the same " · N" form as the EN headers. SEO & Text holds, in this order: generator, ua-generator, optimizer, translator, seo-generator, copywriter, readability, slug-generator, faq-generator. Images holds, in this order: image-tools, image-studio. Code holds html-editor. The number shown in each header equals the number of mode items in that group. Each mode item is a button whose accessible name is the mode's existing label from the current interface language's `TRANSLATIONS` map (for example "Image Studio" / "Студія зображень", "Image Tools"); no mode item is renamed.

**Failure path:** n/a for a static structure; if the interface language changes, group headers and item names re-render in the other language, and no EN text remains in the UA interface for the group names.

**Ratified design choice (OD-25, UA count form), human ratification at HUMAN_SPEC_APPROVAL, 2026-11-08.** The UA headers use the " · N" form stated above (the specification's reading of the Story's "with the same counts").

**Open (later stage):** whether the counts are static or derived (OD-25, ARCHITECTURE_PLANNING) and the exact UA count string within the ratified " · N" form (OD-25, TEST_WRITING).

### FR-2: Groups expand and collapse; all expanded by default

Each group header is a control that toggles that group between expanded (its items rendered) and collapsed (its items not shown, except the active mode's item as in (a) below). On first load, with no stored state, all three groups are expanded. Toggling a group does not change the active mode.

**Failure path:** n/a, no failure path: toggling is an in-memory UI state with no external dependency.

**Ratified design choice (OD-23), human ratification at HUMAN_SPEC_APPROVAL, 2026-11-08.** AC-2 must hold at all times, so a collapsed group never removes the active item:
- (a) Collapsing a group hides all of its items except the active mode's item, if the active mode is in that group. The active item stays rendered, visible and focusable.
- (b) Items hidden by a collapsed group are not focusable and are not exposed to assistive technology (and therefore carry no `aria-current`).
- (c) Each group header is a button that exposes `aria-expanded` ("true" when expanded, "false" when collapsed); its accessible name is its visible text (name and count).
- (d) In the icon-only rail (FR-4) group headers are not shown as toggles; all 12 mode items are rendered as icon buttons, with a decorative separator between groups. The per-group expanded/collapsed state is kept in memory and applies again when the rail is expanded.

**Ratified design choice (OD-24, group persistence), human ratification at HUMAN_SPEC_APPROVAL, 2026-11-08.** The expanded/collapsed state of each group is **not** persisted; every page load starts with all groups expanded. Reason: AC-1 fixes "expanded by default" and AC-3 persists only the rail.

### FR-3: Exactly one item carries aria-current="page"

The navigation item of the active mode carries `aria-current="page"` and no other control in the shell does. This includes the bottom controls: Language, Theme and AI Settings never carry it. It holds in every rail state (expanded, icon-only) and with the active mode's group collapsed (FR-2 (a)).

**Ratified design choice (OD-23, Dashboard), human ratification at HUMAN_SPEC_APPROVAL, 2026-11-08.** The Dashboard rail control is a navigation item like the others: it carries `aria-current="page"` when `dashboard` is the active mode and then no mode item carries it. This is the literal reading of AC-4, which counts Dashboard as a mode.

**Failure path:** the number of elements in the shell with `aria-current="page"` is exactly 1 for every one of the 13 modes, in the expanded rail, in the icon-only rail, and with the active group collapsed; zero or two is a defect.

### FR-4: Rail collapse control and widths

A collapse control reduces the rail to an icon-only rail and expands it back. The expanded rail is 256 px wide (Tailwind `w-64`); the collapsed rail is 64 px wide (`w-16`). In the collapsed rail every mode item and every bottom control remains operable by click and keyboard. The rail is expanded when no stored preference exists. Selecting a mode in either rail state shows that mode and does not change the rail state.

**Failure path:** n/a, no failure path for the toggle itself; persistence failure is FR-5.

### FR-5: Rail collapse state persisted and restored

The rail's expanded/collapsed state is written to `localStorage` on every change and read once at start-up. After a reload the rail is in the state it was left in.

**Ratified design choice (OD-24, key, value and fallback), human ratification at HUMAN_SPEC_APPROVAL, 2026-11-08.** (i) One key holds the rail state, and the key is `seo_gen_shell_rail_expanded`. The value is the string `true` when the rail is expanded and the string `false` when it is collapsed (the string format the existing `seo_gen_dark_mode` key uses). (ii) If reading throws, the key is absent, or the stored value is anything other than "true" or "false", the rail starts expanded and no error reaches the user. (iii) If writing throws (storage unavailable or full), collapsing and expanding still work for the rest of the session and no exception propagates out of the click handler. The existing `seo_gen_*` reads and writes are unguarded, so there is no precedent to follow; this is a deliberate choice.

**Failure path:** as in (ii) and (iii) above: default expanded, no crash, no user-visible error.

### FR-6: Accessible names, translated per the localisation map

Every icon control in the rail has an accessible name, and the names are taken from the en/uk `TRANSLATIONS` maps for the current interface language (not hard-coded English `title` attributes). In both rail states the name of each mode item is the mode's label (FR-1), unique among the rail's buttons, so that a role-and-name lookup such as `getByRole('button', { name: /Image Tools/ })` or the exact name "Image Studio" finds exactly one button. In the icon-only rail the visible text of mode items is hidden but the accessible name stays. The Language control's accessible name contains its visible text, the code "EN" or "UA" of the current interface language (WCAG 2.5.3, Label in Name): the name is that visible code, then a comma and space, then the translated name.

**Ratified design choice (OD-26: copy), human ratification at HUMAN_SPEC_APPROVAL, 2026-11-08.** Existing wording is reused where it exists; the new Ukrainian wording is as follows. The Language row is the ratified change (visible text included in the name):

| Control | EN | UA |
|---|---|---|
| Collapse control, rail expanded | Collapse navigation | Згорнути навігацію |
| Collapse control, rail icon-only | Expand navigation | Розгорнути навігацію |
| Dashboard | Cost Dashboard (existing `dashboardTooltip`) | Дашборд витрат (existing `dashboardTooltip`) |
| Language | EN, Switch Language (visible text "EN"; "Switch Language" is today's title) | UA, Змінити мову (visible text "UA") |
| Theme | Toggle Dark Mode (today's title) | Перемкнути темну тему |
| AI Settings | AI Model Settings (today's title) | Налаштування моделі ШІ |
| Mode items | existing mode labels | existing mode labels |
| Group headers | the header text of FR-1 | the header text of FR-1 |

TEST_WRITING pins the final strings from this table.

**Failure path:** a control with no accessible name in either interface language, two rail buttons with the same name, or a Language control whose accessible name does not contain its visible "EN" / "UA" text, is a defect.

### FR-7: Everything reachable today stays reachable; same main-area views

After the redesign each of the 12 content modes and the Dashboard can be selected from the rail; the UA/EN language toggle and the AI model settings are reachable in every mode, expanded or collapsed rail, including the panel-less modes (the AI settings modal does not depend on the panel). Selecting a mode shows the same main-area view that mode showed before this Story. The only intentional differences are the removals of FR-9, FR-12 and FR-17 in panel-less modes. No mode interior (inputs, outputs, editors) is redesigned.

**Failure path:** a mode that cannot be selected, or a control (language, AI settings, Dashboard) that cannot be reached in some mode or rail state, is a defect.

### FR-8: Theme toggle in the rail

The dark-mode toggle is an icon button at the bottom of the rail, showing a moon icon in the light theme and a sun icon in the dark theme, with an accessible name (FR-6). Activating it switches the theme exactly as the existing toggle does (the `dark` class on the document root, and the existing persisted preference).

**Failure path:** n/a, no failure path beyond the existing toggle behaviour, which this Story does not change.

### FR-9: Input panel presence by mode

The panel is rendered, to the right of the rail, in each panel mode: the nine text modes (generator and ua-generator included before any result exists, because the panel holds their Generate and Clear buttons) and image-tools. The panel is not rendered at all (absent from the DOM, not merely hidden) in image-studio, html-editor and dashboard. In every mode the old in-panel mode switcher is gone; the rail replaces it. In panel-less modes the main area uses the width the panel no longer takes. Removing the panel from html-editor and dashboard is an intentional behaviour change (owner's answer; Story AC-4).

**Failure path:** rendering the panel in a panel-less mode, or omitting it in a panel mode, is a defect; a mode switcher remaining in any panel is a defect.

**Ratified design choice (OD-22: panel header and logo), human ratification at HUMAN_SPEC_APPROVAL, 2026-11-08.** The app title and cube logo (`uiLabels().appTitle`) sit at the top of the rail: in the expanded rail the logo and title, in the icon-only rail the logo only. The panel has a header strip with a height that does not depend on the mode. The strip does not show the mode label; it is empty except, in generator mode only, for the History button of FR-11. No mode label or other new text appears in the panel header, so a text lookup for a mode label does not find a second match inside the panel header.

**Failure path (header):** a mode label, or any text other than what FR-11 specifies for the History button, in the panel header strip is a defect.

### FR-10: Bottom controls of the rail

The bottom of the rail holds, in this order from top to bottom: Dashboard, Language toggle, Theme toggle, AI Settings. Each is reachable in both the expanded and the icon-only rail, and keeps its existing behaviour (Dashboard selects the dashboard mode; Language toggles the interface language; Theme per FR-8; AI Settings opens the model settings modal).

**Failure path:** a bottom control missing or out of order in either rail state is a defect.

### FR-11: History button and overlay: generator only, anchored to the panel header

In generator mode the History (clock) button is in the header of the panel and toggles the Generation History overlay. The overlay is positioned directly under that same header: its top edge is the header's bottom edge, with no overlap and no gap, whatever the header height is; its position is not a fixed pixel offset unrelated to the header (the old `top-[125px]`, and the owner's example `top-[64px]`, are not requirements). No History button and no overlay exist in any other mode, including panel modes other than generator; if the history flag is set and the user leaves generator mode, no overlay is rendered. The history flag itself is not changed by leaving generator, as today, so returning to generator shows the overlay again if it was open.

**Failure path:** a History button or overlay outside generator mode is a defect; an overlay that overlaps the header or leaves a gap is a defect. Pixel geometry is checked manually (FR-19); that the button is generator-only and toggles the overlay is checkable in a component test.

### FR-12: Clear All gated with the panel

The "Clear All" button is not rendered in image-studio, html-editor and dashboard. In every other mode it is rendered in the panel and behaves exactly as before. No header, and no replacement Clear All, History or improvement-request control, is added to Image Studio by this Story.

**Failure path:** a Clear All button in a panel-less mode, or a changed Clear All effect in a panel mode, is a defect.

### FR-13: Dark theme shell tokens

In the dark theme the shell renders with: page background `#0b1120`, rail surface `#111a2e`, shell borders `#26324a`, accent `#7c3aed`. Mode interiors keep their existing `slate-*` colours. The page background `#0b1120` is applied to the global `<body>` or the global wrapping `<main>` (Story wording); whichever element carries it, the colour visible behind the main content area is `#0b1120`.

**Failure path:** a shell surface that shows a different colour in the dark theme, or a page background that is set but hidden by an opaque layer above it, is a defect (see the next block). Verified manually (FR-19).

**Ratified design choice (OD-27: surfaces and layer), human ratification at HUMAN_SPEC_APPROVAL, 2026-11-08.** The shell surface list that the manual check covers is: (1) the visible page background behind `<main>` and `<main>` itself, `#0b1120`; (2) the rail surface, `#111a2e`; (3) the panel's own chrome, that is its outer surface, its header strip and its outer border, which use the shell tokens (surface `#111a2e`, border `#26324a`) so that rail and panel read as one look; (4) the shell borders the check covers are the rail's own edge, the separators between groups, and the panel's outer border, all `#26324a`. Everything inside the panel (mode forms, inputs, buttons, footer actions) is an interior and keeps its `slate-*` colours. The painting layer matters: today an opaque root container (dark slate) sits between `<body>` and `<main>` and `<main>` is translucent over it, so `#0b1120` set on `<body>` alone would not be visible; the implementation must make the colour visible. The accent is used only for the active item's icon, the active-item border and focus rings.

### FR-14: Light theme

A light theme exists for the whole shell. Each dark token of FR-13 has a light counterpart derived from the same design tokens; the light values are chosen by the developer, meet FR-15, and are recorded in the evidence artifact (FR-19). When the `dark` class is absent no shell surface (page background, rail, panel chrome, borders) keeps a dark-theme colour. The theme toggle (FR-8) switches between the two themes.

**Failure path:** any shell surface still showing a dark-theme token in the light theme is a defect. Verified manually (FR-19).

### FR-15: Contrast of shell text

In both themes, and with the rail expanded and collapsed, all navigation and shell text (rail item labels, group header text and counts, the app title, the visible Language code, and the active, hover and focus states of these) has a contrast ratio of at least 4.5:1 against the surface directly behind it. The accent `#7c3aed` is never a text colour anywhere in the shell; it is used only for active icons, borders and focus rings. Text is high-contrast (for example white or light grey in the dark theme).

**Failure path:** any shell text below 4.5:1, or any shell text rendered in `#7c3aed`, is a defect. Verified manually; the measured ratios are recorded (FR-19).

### FR-16: Usable at 1024 px

At a viewport width of 1024 px, in each of the 13 modes, with the rail expanded and with the rail collapsed, no content is clipped off-screen so that it becomes unreachable (no horizontal scrolling is required to reach anything, and nothing is cut off by an `overflow-hidden` ancestor), and the navigation is fully usable. Widths below 1024 px are not supported (desktop-first; no mobile layout).

**Failure path:** content that cannot be reached at 1024 px in any mode and rail state is a defect. If meeting this is impossible without changing a mode interior (out of scope) or the panel width, that is not resolved by widening this Story silently: it goes back as a Story amendment (see Open questions, OD-29). Verified manually (FR-19).

### FR-17: Improvement-request control

The shell adds no new "Suggest an improvement" control. The existing improvement-request button, shown only when `environment.feedbackForm.baseUrl` is set, keeps working unchanged in every mode that renders the panel, and is not rendered in image-studio, html-editor and dashboard.

**Ratified design choice (OD-3 / report F-9), human ratification at HUMAN_SPEC_APPROVAL, 2026-11-08.** The Story names "the button"; in the markup it is one block of three elements: the button, the rename-editor pen, and the popup-blocked notice. The three are one unit that follows the button: rendered together in panel modes when `baseUrl` is set, absent together in panel-less modes.

**Failure path:** when `baseUrl` is not set nothing of the block is rendered in any mode (as today); an added control in the rail or elsewhere is a defect.

### FR-18: Existing unit specs keep passing; permitted changes only

Every unit spec that passes on `main` before this Story still passes after it, with no behavioural assertion weakened. The only permitted changes to existing `*.spec.ts` files are: (a) selector or markup updates; (b) adapting old layout checks (for example the FAQ-button-next-to-UA-button check) to the new grouping; (c) removing the Image Studio assertions of `src/app/app.component.clear-all.component.spec.ts` (the product owner's explicit approval); the Image Tools assertions of that spec are kept. Each spec change is listed in the implementation report. A retained spec that locates the input panel must find the panel and not the rail.

**Failure path:** a previously passing spec that fails, or a spec change outside (a)-(c), is a defect; a change outside (a)-(c) needs a new approval from the product owner, not an interpretation by the builder.

**Ratified design choice (OD-30: scope of "the Image Studio assertions"), human ratification at HUMAN_SPEC_APPROVAL, 2026-11-08.** Only the assertions that AC-4e makes false are removed. Per-test disposition for `src/app/app.component.clear-all.component.spec.ts`:

| Test | Disposition |
|---|---|

| FR-1 / SD-12: Clear All in Image Studio leaves stored sessions unchanged (EN and UA) | Remove. It needs the Clear All button, which does not exist in the studio (FR-12). |
| DD-25 / R16: no Process Images, no Image Tools range control, Clear All present in studio mode (EN and UA) | Keep the two assertions that Process Images and `input[type="range"]` are absent in studio mode, adapted so that a missing panel does not make the lookup throw (the old `querySelector('aside')` would return null). Remove only the assertion that Clear All is present. |

**Ratified design choice (OD-31: wiring pins), human ratification at HUMAN_SPEC_APPROVAL, 2026-11-08.** `src/app/app.component.image-studio-wiring.spec.ts` passes with its assertions unchanged. As the Story's and the clarifier's description of its pins, they include: an `image-studio` branch in the panel's Actions Footer placed before the final `@else`, an explicit `image-studio` case in `clearAll()` that touches no studio symbol, and a rail/nav button that selects `image-studio`. Panel gating makes the first two unreachable at runtime; this Story does not remove them, because that spec is not named in the owner's approval.

**Ratified design choice (OD-32: relocated markup), human ratification at HUMAN_SPEC_APPROVAL, 2026-11-08.** Three specs read `app.component.html` as text (`image-studio-wiring`, `template-wiring`, `faq-layout`). If the rail or panel markup moves into another file, pointing such a pin at the new location counts as a "selector or markup update" under (a) only when the property it asserts is preserved unchanged in the new location. How the markup is split is a planning matter, not specified here.

### FR-19: Manual verification recorded under docs/evidence/

The result of the manual verification of FR-13, FR-14, FR-15 and FR-16 (AC-5, AC-6, AC-6a) is recorded as an artifact under `docs/evidence/`, of the registered `evidence` kind: it carries the artifact front matter, and each recorded check names its method, the browser and tool versions, the date, who ran it, and the raw output or a pointer to screenshots. The artifact records the light-theme token values chosen in FR-14, the measured contrast ratios of FR-15, and the pixel geometry check of FR-11 (overlay under the header). A failed check is recorded with its measured value and is not omitted; the corresponding requirement is then not met. Who writes the artifact and at which stage is settled with the verification procedure (OD-28, TEST_WRITING).

**Failure path:** a verification without the recorded artifact does not satisfy AC-9; a cell of the executed matrix missing from the artifact is a defect.

**Proposed minimum for the matrix (OD-28 stays open; the full procedure is fixed by TEST_WRITING).** Contrast and colour (FR-13 to FR-15): both themes, rail expanded and collapsed, in at least one panel mode (generator) and at least one panel-less mode (image-studio). Fit (FR-16): all 13 modes with the rail expanded and collapsed, at a 1024 px width. Runner and browser are left to TEST_WRITING; the artifact records which were used.

## Generated-HTML requirements (AGENTS.md §4)

Not in play. This Story changes the app shell only; no prompt, renderer or generated product HTML changes, so no §4 criterion is restated and none is weakened. No functional requirement above concerns spec-count parity, figure structure, image loading attributes, video, `meta_title`, or `meta_description`.

## Non-functional requirements

- **NFR-1 (provider, retrieval, secrets: AGENTS.md §3 Rules 1, 2, 4):** the change touches no LLM call, retrieval path, proxy, prompt or secret. No new network request is added; nothing is imported into the browser bundle that was not already there.
- **NFR-2 (no new capability):** no mode gains a capability (in particular no History button outside generator, FR-11). Behaviour not listed in FR-1..FR-19 is unchanged.
- **NFR-3 (mode interiors untouched):** inputs, outputs and editors of every mode keep their markup and `slate-*` colours; `src/app/components/image-studio/**` is not modified.
- **NFR-4 (tests: AGENTS.md §5):** every new component under `src/app/components/` has its sibling `*.spec.ts`; tests render the component, interact, and assert what a user observes, querying by role and text. Tests that touch persistence use a controlled storage double and no wall clock.
- **NFR-5 (localisation):** every new user-visible label and accessible name exists in both the `en` and `uk` `TRANSLATIONS` maps.

## Out of scope

- Redesigning the inside of any mode (inputs, outputs, editors), and Image Studio itself (US-10.5, US-10.6).
- New capabilities of any mode, including a History button in any mode other than generator.
- A header for Image Studio, and any Clear All, History or improvement-request control in Image Studio (the studio's own header is US-10.5).
- A mode label or any other new text in the panel header (OD-22, ratified).
- Recolouring the `slate-*` interiors of the existing modes.
- A "Suggest an improvement" feature or control.
- Prompts, FROZEN files, store profiles, generated HTML, `STORE_REGISTRY`.
- Mobile or sub-1024 px layouts.
- Non-text contrast (icons, borders): the Story requires text contrast only (FR-15).
- Persisting the expanded/collapsed state of individual groups (OD-24, ratified).
