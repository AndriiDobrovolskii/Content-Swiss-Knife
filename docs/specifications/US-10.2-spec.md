# Specification: US-10.2 - Pin the Node runtime and the undici override together

## Summary

When this is done the repository names exactly one Node release (`24.22.2`) in both `.nvmrc` and `package.json` `engines.node`, the scoped
`overrides.cheerio.undici` equals the `undici` that exact Node bundles (measured, expected `7.30.1`), and `test/undici-pin.spec.ts` fails the
moment any of those three drift apart or the running Node is not the pinned one. The pair has been shown to work on the real Gemini Files API
through a real `node server/index.js`, the full gate and ten consecutive `npm run test:logic` runs are green on the pinned Node, and the live
evidence is recorded in a registered `evidence` artifact.

## Background

US-10.1 shipped `overrides.cheerio.undici = 7.24.4`, chosen to equal the `undici` bundled in Node v24.15.0, because a newer npm copy made the
Gemini Files API upload fail with `UND_ERR_INVALID_ARG` (502 `UPSTREAM_RETRIES_EXHAUSTED`). The defect is a version skew between the npm copy and the
Node-bundled copy, so the pin is correct for one runtime only, and the repository has no `engines` and no `.nvmrc`. AGENTS.md section 7 item 10
now requires such a pin and the runtime pin to land in the same change. The human instructed the move to Node 24.22.2 with a mandatory live check
(Story v2, "Human instruction"). The guard today encodes a verified window `[7.24.4, 7.26.0)` that cannot accept the new pin.

Facts used (observations at a date, not constants - every recorded check prints its own `node -v`):

- Version 1 of this Specification was written when the build machine ran `v24.15.0` (`process.versions.undici` `7.24.4`, npm `11.13.0`; clarification report v2, environment facts).
- Observed on this machine by read-only commands on 2026-11-02 (revision 2, and independently by SPEC_REVIEW): `node -v` = `v24.22.2`, `node -p process.versions.undici` = `7.30.1`, `npm -v` = `11.13.0`.
  The repository tree is still unchanged: `overrides.cheerio.undici` = `7.24.4`, no `.nvmrc`, no `engines` (so the guard's bundled-undici comparison already differs on this Node).
- The Pinned Node is therefore already installed here. Consequently every behaviour below is stated as a **function of the Node that is running at that moment and of the tree**, never of one
  fixed Node; `v24.15.0` survives only as the other branch of that function (FR-14) and as the example of a wrong Node (FR-6).
- That Node 24.22.2 bundles `undici` `7.30.1` is the human's figure, the Node v24.22.2 source tag, and now one local observation; the committed value is still the one **measured** at IMPLEMENTATION (FR-10).

## Definitions

- **Pinned Node** - the exact version `24.22.2` (OD-1, PROPOSED DEFAULT - awaiting human at HUMAN_SPEC_APPROVAL; if the human picks a newer 24.x,
  every `24.22.2` literal and the expected `7.30.1` below are rewritten and re-measured, nothing else changes).
- **Pin** - the string value of `package.json` `overrides.cheerio.undici`.
- **Bundled undici** - the output of `node -p process.versions.undici` under the Pinned Node.
- **The guard** - the existing `test/undici-pin.spec.ts`, run by `npm run test:logic` (`vitest.config.ts` includes `test/**/*.spec.ts`).
- **Base commit** - `6b377a5`, the HEAD of this branch and its merge-base with `origin/main` when the Specification was written (the local `main` ref is stale); "unchanged tree" means the working tree with no US-10.2 edit to
  `package.json`, `package-lock.json`, `.nvmrc` (the tree simply has no `.nvmrc`, no `engines` and the old Pin yet; no stash, checkout or other git state change is needed to obtain it).
- **Running Node** - the Node that executes the command being recorded (`node -v` printed in the same record).
- **Cause (of a red case)** - exactly one of: **C1** `.nvmrc` missing/empty/not exact; **C2** `engines.node` missing/not exact; **C3** the Running Node differs from the `.nvmrc` version
  (evaluable only when `.nvmrc` exists and is exact); **C4** the Pin differs from the Bundled undici of the Running Node; **C5** `.nvmrc` and `engines.node` differ from each other. A red case is
  **attributable** when its failure message names exactly one cause and the file or field at fault. If two preconditions are missing, the case names the first one in the order `.nvmrc`, `engines.node`.
- **Relevant change set** (FR-22) - the files that `npm run test:logic` reads or loads: everything under `src/`, `test/` and `server/` that the tests import or read, `package.json`, `package-lock.json`,
  `.nvmrc`, `vitest.config.ts` and the `tsconfig*.json` files it uses.

## Functional requirements

Group A - the runtime pin.

### FR-1: `.nvmrc` names the pinned Node exactly

A file `.nvmrc` exists at the repository root. Its content, with surrounding whitespace and line endings (including CRLF) trimmed and one optional
leading `v` removed, is exactly `24.22.2` - a three-part `MAJOR.MINOR.PATCH` of a stable release, not a range, alias (`lts/*`, `node`, `24`),
partial version or prerelease.

**Failure path:** a missing `.nvmrc`, an empty one, or one whose trimmed content is not that exact form is a defect that FR-4 turns into a failing guard
case which names `.nvmrc` and quotes the offending content (or says the file is missing).

### FR-2: `engines.node` is the exact pinned version and equals `.nvmrc`

`package.json` has `engines.node` equal to the string `24.22.2` - exact, no range operator, no `v` prefix, no tag (human-decided OD-2). The version in
`.nvmrc` (after FR-1 normalisation) and `engines.node` are the same string. Because `engines.node` is exact, "`.nvmrc` is inside `engines.node`" is decided
by plain string equality (OD-12 closed by consequence of OD-2).

**Failure path:** `engines` missing, `engines.node` missing, not a string, not exact, or different from `.nvmrc` fails the guard (FR-4) naming the field.

### FR-3: The runtime pin is advisory in npm and adds nothing else

`engines` contains exactly one key, `node`. `.npmrc` is byte-identical to the base commit (no `engine-strict`, human-decided OD-2); so `npm install` on another Node
only prints an `EBADENGINE` warning and **the guard (FR-6, FR-7) is the only enforcement**. No `engines.npm` is added (OD-14, PROPOSED DEFAULT - awaiting human at
HUMAN_SPEC_APPROVAL).

**Failure path:** an `engines.npm` key, any other `engines` key, or any `.npmrc` byte change is a scope violation found by the recorded diff of FR-13.

Group B - the guard (`test/undici-pin.spec.ts`).

### FR-4: File-agreement cases, one case per cause

The guard contains separate test cases, each failing for exactly one named cause and each with a message that names the file or field:
(a) `.nvmrc` is present; (b) `.nvmrc` content is an exact `MAJOR.MINOR.PATCH` (after FR-1 normalisation); (c) `package.json` `engines.node` is present;
(d) `engines.node` is an exact `MAJOR.MINOR.PATCH` string; (e) the `.nvmrc` version equals `engines.node`. A case whose precondition file or field is
missing fails with a message naming the missing file or field, never with a version mismatch.

**Failure path:** these cases are the failure path of FR-1 and FR-2; each is shown non-vacuous by FR-5.

### FR-5: The comparisons are a pure decision, proven on synthetic inputs (OD-11, PROPOSED DEFAULT - awaiting human at HUMAN_SPEC_APPROVAL)

The guard's runtime and file-agreement comparisons are expressed as a pure decision that receives its inputs as plain values (the `.nvmrc` content, `engines.node`,
the running Node version, the bundled undici, the Pin) and reads neither `process.version`, `process.versions` nor any file itself. For every failing condition of
FR-4, FR-6 and FR-7 the guard contains a synthetic case that makes it fail, and for each a synthetic case that makes it pass, so a runtime case is proven to be able
to fail and to pass on **any** Node. Synthetic failing inputs include: `.nvmrc` missing; `engines.node` missing; `.nvmrc` = `24`, `lts/*`, `node`, `24.22`, `^24.22.2`,
`24.22.2-rc.1`, empty; `engines.node` = `>=24.22.2 <25`, `v24.22.2`, a number; `.nvmrc` `24.22.2` vs `engines.node` `24.22.1`; running Node `24.15.0` vs pinned `24.22.2`;
bundled `7.24.4` vs Pin `7.30.1`; Pin `7.24.4` vs bundled `7.30.1`.

**Failure path:** if a synthetic failing input is accepted, the non-vacuity case fails (so a guard that cannot fail is itself red). If the human rejects the proposed
default (OD-11 option C), the runtime cases can only be proven on the Pinned Node and AC-3/AC-7 must be re-traced at HUMAN_SPEC_APPROVAL.

### FR-6: The running Node must be the pinned Node (human-decided OD-5)

A real-runtime guard case compares the running Node (`process.version`, leading `v` removed) with the `.nvmrc` version. It passes only when they are equal. On any other
Node it **fails** - it is not skipped, not marked todo, not downgraded to a warning - with a message that names the pinned Node, the running Node and the files that name
the pin. When `.nvmrc` is missing or not exact, this case fails with a message naming `.nvmrc` as the cause (not a version mismatch).

**Failure path:** the case's red state on a wrong Node is the specified behaviour. Consequence accepted by the human: `npm test` is red for this file on every Node that is not
`24.22.2` (for example `v24.15.0`) until the Pinned Node is running (OD-3). On this machine the Running Node is already `v24.22.2`, so here the case is red only while `.nvmrc` is absent (cause C1) and
is the second, mechanical enforcement of the FR-16 precondition once `.nvmrc` exists.

### FR-7: The bundled undici must equal the Pin (AC-4)

A real-runtime guard case compares `process.versions.undici` with the Pin. It passes only when equal. When they differ it fails with a message that names the Pinned Node
(from `.nvmrc`, or states that `.nvmrc` is unavailable), the Pin and the bundled undici (and also the running Node). The verdict of this case depends only on the Pin and the
bundled undici, so a missing `.nvmrc` does not change its outcome; a missing or non-exact Pin fails it naming `overrides.cheerio.undici`.

**Failure path:** a Pin that differs from the bundled undici fails with the three values in the message; it is a different cause from FR-6 and is reported by its own case.

### FR-8: No version is hard-coded in the guard and the old window is gone (AC-5)

The pinned Node is read from `.nvmrc`/`engines.node`, the Pin from `package.json`, the bundled undici from the runtime. The constants and assertions that encode the window
`[7.24.4, 7.26.0)` (lower bound, upper bound, the "at or above 7.26.0, the first release that failed" and "below the verified window" checks) do not exist in the guard. Version
literals appear only as **synthetic inputs** of non-vacuity cases. A Pin of `7.30.1` (or whatever FR-10 measures) equal to the bundled undici is accepted; a Pin that
differs from the bundled undici is rejected, whatever its value.

**Failure path:** a leftover window bound is found by the recorded source search (AC-test matrix) and by the synthetic case "Pin `7.24.4`, bundled `7.30.1` is rejected".

### FR-9: The other guard checks survive, each with its non-vacuity proof (AC-6)

The guard still asserts, each as a case with its existing non-vacuity proof, now against the new Pin: the Pin is an exact `MAJOR.MINOR.PATCH` string (no range operator, tag,
prerelease, wildcard, whitespace or `v`); `package-lock.json` has `node_modules/cheerio/node_modules/undici` at exactly the Pin with `resolved` (the registry tarball of that
version) and `integrity`; the `undici` resolved from cheerio's directory is that nested copy at the Pin, and an absent `node_modules`, `cheerio` or `undici` fails and never skips;
`undici` appears in no `dependencies`/`devDependencies`/`optionalDependencies`/`peerDependencies` and the only override path naming it is `cheerio > undici`; no file under `server/`
imports, requires or dynamically imports the bare specifier `undici`. The tree-root seam of the existing guard stays available for scratch trees and stays unset in the gate. The
hoisted `node_modules/undici` and `node_modules/node-gyp/node_modules/undici` are still deliberately not asserted.

**Failure path:** each check fails (not skips) with a message naming the file, key or path at fault.

Group C - the override.

### FR-10: The Pin is the measured bundled undici of the Pinned Node (AC-4)

`overrides.cheerio.undici` is an exact string equal to `node -p process.versions.undici` executed under the Pinned Node. `7.30.1` is the **expected** value only; the **measured**
output is the Pin. If the measurement differs from `7.30.1`, the measured value is used and the difference is recorded in the evidence (FR-20). The measurement is taken before the
Pin is written, with `node -v` printed in the same record.

**Failure path:** if the Pinned Node is not available, no Pin is written from the expectation: IMPLEMENTATION is BLOCKED (FR-16). If, after the Pin is applied, FR-17 fails on the Pinned
Node, the change is not done and the failure is reported, not worked around (human-decided OD-4 keeps the override; AGENTS.md section 6 item 9).

### FR-11: The scoped override is kept and stays the only undici override (human-decided OD-4)

`overrides.cheerio.undici` stays in `package.json`; it is not removed, relaxed to a range, hoisted to a top-level override or moved under another parent. No other override path names
`undici`; `node-domexception` and `fetch-blob` overrides are unchanged. The outcome of FR-18 cannot change this shape inside this Story.

**Failure path:** any other shape fails FR-9 (override-path case) and the AC-9 diff of FR-13.

Group D - the installed tree.

### FR-12: Lockfile and `node_modules` are regenerated consistently on the Pinned Node (AC-8)

After the change, on the Pinned Node, `npm install` has been run so that: `package-lock.json` is npm-generated (never hand-edited); a **second** `npm install` leaves `package-lock.json`
unchanged (compared by content hash before and after, both recorded); `npm ls undici` exits 0 (its output recorded); and `node_modules/cheerio/node_modules/undici` in the lockfile and in the
installed tree is the Pin (with `resolved` and `integrity`).

**Failure path:** a lockfile that changes on the second run, a non-zero `npm ls undici`, or a nested copy that is not the Pin means the change is not done; the real output is reported and the
lockfile is not patched by hand.

### FR-13: Nothing else in the dependency surface changes (AC-9)

Against the base commit, a recorded diff of keys shows: `dependencies`, `devDependencies` and `optionalDependencies` values byte-identical; `overrides` differs only in `cheerio.undici`;
`package.json` gains only `engines` (FR-3); in `package-lock.json` no package other than `cheerio`'s nested `undici` changes version, `resolved` or `integrity`, and the root package entry
gains only the matching `engines`. Formatting or metadata churn caused by the npm version that ships with the Pinned Node (observed here: `npm -v` = `11.13.0` under `v24.22.2`, the same as under
`v24.15.0`, so churn is not expected; the allowance applies only if the recorded `npm -v` differs from the npm that produced the base commit's lockfile) is allowed provided the
recorded diff shows it carries no version, `resolved`, `integrity` or key change for any package (OD-14, PROPOSED DEFAULT - awaiting human at HUMAN_SPEC_APPROVAL).

**Failure path:** any other version/key change fails AC-9; the builder reports it and does not hand-edit the lockfile to hide it.

Group E - test-first order (AGENTS.md section 5; section 7 items 6, 7 and 10).

### FR-14: The guard is written first and recorded red against the unchanged tree (AC-7)

TEST_WRITING updates `test/undici-pin.spec.ts` **before** any change to `package.json`, `.nvmrc` or `package-lock.json`, then runs it against the unchanged tree on the Running Node (whatever it is at that
moment; `node -v`, `process.versions.undici` and `npm -v` printed in the record) and records the real output as a per-case table (case name, outcome, failure message, and for each red case its single Cause C1..C5).
The expected outcome is a **function of the Running Node and the tree**. On the unchanged tree (no `.nvmrc`, no `engines`, Pin `7.24.4`):

| Case | Expected on the unchanged tree | Cause named |
|---|---|---|
| FR-4 (a) `.nvmrc` present; (b) `.nvmrc` exact; (e) `.nvmrc` equals `engines.node` | red on every Node | C1 `.nvmrc` missing (for (e): the first missing precondition) |
| FR-4 (c) `engines.node` present; (d) `engines.node` exact | red on every Node | C2 `engines` / `engines.node` missing |
| FR-6 Running Node equals `.nvmrc` | red on every Node, because `.nvmrc` does not exist; it can name C3 only once `.nvmrc` exists | C1 on the unchanged tree (never reported as a mismatch) |
| FR-7 Bundled undici equals Pin | **depends on the Running Node**: Running Node `v24.15.0` (bundled `7.24.4`) - green (`7.24.4` = `7.24.4`), not a cause of the red run; Running Node `v24.22.2` (bundled `7.30.1`) - **red** (Pin `7.24.4` is not the Bundled undici); any other Node - red exactly when its bundled undici is not `7.24.4`, and the record says so | C4 (message names the Running Node, the Pin and the Bundled undici) |
| FR-9 survivors and every synthetic non-vacuity case (FR-5) | green on every Node | none |

So the expected red set is: on `v24.22.2` (the Node installed on this machine at the time of writing) the seven cases (a)-(e), FR-6 and FR-7, with causes C1, C1, C2, C2, C1, C1 and C4; on `v24.15.0` the six
cases (a)-(e) and FR-6, FR-7 being green. Any other red case, and any green case from the red list, is an unexpected outcome and must be explained in the record. **Attributable** means the definition in
Definitions: each red case's message names its own single cause and the file or field; the TEST_WRITING record lists each red case with its cause for the Node actually running at that moment. The red
run is taken on the unchanged tree as it stands (it has no `.nvmrc`, no `engines` and the old Pin); no implementation file is changed before this record exists.

**Failure path:** a red run in which any red case has no single nameable cause from the table (for example a syntax error, a missing import, an unexplained red, or a message naming two causes) is not a valid TDD
red and the test is fixed before the builder starts. A red FR-7 on `v24.22.2` is **not** invalid; a green FR-7 on `v24.22.2` on the unchanged tree is an unexpected outcome (the Pin or the comparison is wrong) and is explained or fixed.

### FR-15: Implementation follows the red record; green is proven on the Pinned Node (AC-7)

Only after FR-14, IMPLEMENTATION changes `package.json` (`engines`, `overrides.cheerio.undici`), creates `.nvmrc`, and regenerates `package-lock.json`, as **one change set**
(AGENTS.md section 7 item 10). On the Pinned Node the guard is then run and every case passes; the real output is recorded as a second per-case table next to the red table, and
the guard file is not weakened between the two runs (no `skip`/`only`/`todo`, no deleted or loosened assertion - section 7 item 7).

**Failure path:** a case that is still red on the Pinned Node is a defect of the change or of the test, reported with its message; it is not skipped or deleted.

Group F - the pinned Node on the machine.

### FR-16: IMPLEMENTATION holds until the Pinned Node is running (OD-3, PROPOSED DEFAULT - awaiting human at HUMAN_SPEC_APPROVAL)

The human installs Node `24.22.2` as the global Node; no agent installs, replaces or downloads a Node. **OD-3 is satisfied on this machine**: it already runs `v24.22.2` (Facts used). IMPLEMENTATION (the Pin
measurement of FR-10, any write to `package.json`, `.nvmrc`, `package-lock.json`, `npm install`, and every proof that needs the Pinned Node: FR-12, FR-15 green, FR-17, FR-18, FR-21, FR-22) does not start until

output recorded; it must be `v24.22.2`, otherwise the task returns BLOCKED with the printed value". This check is made and recorded at the start of that task even though the machine currently satisfies it.
FR-6 (the guard fails on any other Node) is the second, mechanical backstop.

**Failure path:** `node -v` printing anything else is BLOCKED, never "proceed and note it".

Group G - the live verification (AGENTS.md section 6 item 9).

### FR-17: A real upload on the Pinned Node returns 200 with a `fileUri` (AC-10)

**Procedure.** With `node -v` printing `v24.22.2` and the Pin applied, the following are done in this order from the repository root and recorded:

1. *Server.* A real `node server/index.js` (not `createApp` in a test, not a stub) is started on a spare, free, non-default port (the `PORT` environment variable). The server reads the key itself
   (`dotenv` reads the repository `.env`, the existing mechanism); no agent reads it. Its stdout and stderr are both captured to **one log file in the session scratchpad / operating-system temporary
   directory, outside the repository** (for example `<temp>/us-10.2-live-server.log`), and the process id of that exact process is recorded.
2. *Request.* A valid 1x1 PNG, base64-encoded, is sent as JSON `{ "data": "<base64>" }` to `POST /api/image-studio/upload`. The real status and the body shape are recorded; the route answers only
   `{ fileUri, mimeType }`.
3. *Log check.* The captured log is searched for `UND_ERR_INVALID_ARG` and `UPSTREAM_RETRIES_EXHAUSTED`; the match counts are recorded (if there is a match, the matching lines, after the NFR-3 secret search).
4. *Identify the created object.* The object name is derived from the `fileUri`: the path suffix starting at `files/` (that is `files/<id>`). Only the object created by this request is claimed. The Files API
   listing is project-wide and the key is shared, so it may hold objects of other people; nothing is ever deleted or claimed by listing, prefix, age or count, and a listing is not used to select a deletion.
5. *Delete and confirm.* A throwaway script, piped on standard input (`node --input-type=module -`, so no file is written in the repository), is run **from the repository root**. It loads the key with
   `dotenv` from the repository `.env`, builds the `@google/genai` client the way `server/providers/gemini.js` does, takes the object name as its only (non-secret) argument, calls `ai.files.delete({ name })`,
   then calls `ai.files.get({ name })`, and prints only the delete outcome and the status of the follow-up read. It never prints the key, the client configuration or the environment. **Pass:** the delete
   resolves without an error and the follow-up `get` fails with the API's not-found answer (its status and message recorded verbatim). The script text, which holds no secret, is recorded in the evidence.
6. *Stop and dispose.* The server is stopped by the recorded process id (never by image name). The log file is **deleted** at the end of the check; the evidence keeps only the counts of step 3 (and any
   matching lines under the rule above), never the log itself.

The key is never printed, logged or written (NFR-3). The status and body shape, with the `fileUri` identifier and without any key, are recorded.

**Failure path:** any non-200 status, a missing `fileUri`, or `UND_ERR_INVALID_ARG` in the log means the change is **not done**; the real output is reported and the pin is not worked around.
`UND_ERR_INVALID_ARG` is a defect of the pair and is never retried. A non-200 whose log names a transient cause instead (`429`, a timeout or a network error; the server's retry loop can turn these into a final
`502 UPSTREAM_RETRIES_EXHAUSTED`) and names no `UND_ERR_INVALID_ARG` is **"not verified"**, not "failed": exactly **one** re-run is allowed, both runs are recorded, the re-run decides, and a second transient
result leaves AC-10 "not verified" and the Story not reportable as done. (This one re-run is specific to the live check and is not a retry-until-clean; FR-22 has none.) If the call cannot be run at all (no
key, no quota, no network), the report says "not verified" and the call is not claimed verified (section 6 item 9). If the delete or the confirmation fails, the object name is reported for manual deletion.

### FR-18: The same upload without the override is recorded as a measurement (AC-11, OD-10 PROPOSED DEFAULT - awaiting human at HUMAN_SPEC_APPROVAL)

**Procedure.** On the same Pinned Node, the upload of FR-17 (same request, same steps 2-6, same object identification and deletion) is repeated against a server started from a scratch copy of the repository
located **outside** the repository directory (in the operating-system temporary directory, not under `.tmp.driveupload/`). The scratch copy is made from the repository's tracked files only: it holds no
`.env`, no `node_modules` of the real tree, and `overrides.cheerio.undici` is removed from its `package.json`; the tree is then installed there (a scratch-only `npm install`, which may regenerate the
scratch lockfile). The real repository's `package.json`, `package-lock.json` and `node_modules` are not used or touched by the scratch install.

**Validity condition (the run counts as a measurement only if it holds).** The recorded `npm ls undici` of the scratch tree shows `cheerio` resolving the **hoisted** `undici` copy - there is no
`node_modules/cheerio/node_modules/undici` in the scratch tree - and the version printed for it is **not** the Pin. If cheerio still resolves a nested copy at the Pin (for example because the scratch was
installed from the original lockfile), the run measures nothing: one correction of the scratch tree is allowed (regenerating the scratch lockfile and reinstalling), recorded; if the condition still fails,
the evidence says "not measured" with that cause.

**Key handling for the scratch run (PROPOSED DEFAULT - awaiting human at HUMAN_SPEC_APPROVAL; refines OD-7).** The key is never copied into the scratch tree. The scratch server is started from the scratch

## Non-functional requirements

- **NFR-1 (determinism):** the guard reads files and the running runtime only - no network, no clock, no randomness; it is unaffected by the order of other specs.
- **NFR-2 (no escape hatch):** the guard's failures on a wrong Node, a missing file or a drifted pin are failures - never `skip`, `todo`, `only`, a warning, or a loosened assertion (AGENTS.md section 7 item 7). No test is deleted to reach green.
- **NFR-3 (secrets):** the shared `GEMINI_API_KEY` is never printed, logged, committed, placed in the evidence, in a scratch copy that survives, or in a bundle (AGENTS.md section 3 rule 4; `.env` is not read into any artifact).
- **NFR-4 (scope of dependencies and config):** no new dependency, no `devDependencies` change (so no `semver` import), no CI file, no `.npmrc` change, no `engines.npm`, no change to `@types/node` (AGENTS.md section 7 item 8; the
  `overrides`/`engines` edit is covered by the human's recorded instruction).
- **NFR-5 (same change set):** the guard, `package.json`, `.nvmrc` and `package-lock.json` land together, so `main` never carries the override without the runtime pin (AGENTS.md section 7 item 10; section 13 commit discipline).
- **NFR-6 (honest evidence):** every recorded check is real output from a command that was run; a check that was not run is reported "not verified" (AGENTS.md section 6 and section 6 item 9).
- **NFR-7 (no product-code change):** no file under `server/`, `src/`, `tools/`, `angular.json`, `arch-guard.sh`, `vitest.config.ts` or `tsconfig*.json` changes; `server/index.js`, `server/image-studio/*` and `server/providers/gemini.js` are exercised read-only by the live check.
  Provider independence (section 3 rule 1), retrieval separation (rule 2), prompt caching and the store registry are therefore unaffected (section 6 item 6: checked by reading the diff).
- **NFR-8 (FROZEN files):** none of the five section 9 files is modified; `bash arch-guard.sh` frozen-file section is unchanged (section 6 item 5).
- **NFR-9 (platform):** `.nvmrc` normalisation tolerates CRLF and a trailing newline (git on Windows converts line endings); the Windows-specific proof is FR-22 only.
