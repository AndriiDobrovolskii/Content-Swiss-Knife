# Specification: US-10.1 — Nano Banana Image Studio

## Summary

A new Image Studio mode lets an editorial operator upload product photos, describe the wanted visual in a multi-turn chat with
Gemini image models (Nano Banana 2 "Flash", Nano Banana Pro "Pro"), refine it with follow-up edits in the same session, and download
any retained version. Image generation runs only through the Express BFF, with the Gemini key held server-side, with bounded
request sizes, bounded history, a per-IP rate limit, a per-image cost estimate and an accessible interface. The mode adds no
generated product-description HTML and touches no FROZEN file.

This Specification takes the Story (v1) as amended by the cumulative Story-text overrides and the numbered conditions of the Open
Decisions log (v8). Where an override replaces Story wording, the override wins and the traceability matrix says so. The log has no
blocking Open Decision (`open_decisions_blocking: false`); its one open entry, OD-50, is a list of labelled proposals that this
Specification carries under the labels D-23 to D-35, SD-41, SD-42 and W-2 and that the human confirms or replaces at
HUMAN_SPEC_APPROVAL (AGENTS.md section 11: nothing is decided for the human). Version 5 embeds the decisions the log now records
(OD-5, OD-6, OD-12, OD-14, OD-15, OD-16, OD-18, OD-20, OD-21, OD-25 and OD-36 to OD-49, see "Decisions of the approval comment" and "Decisions recorded in Open Decisions log v8") as
requirements tagged HUMAN-DECIDED, each with the id of the log entry that records it.

## Definitions

- **Session**: the persisted conversation of one operator (client side, IndexedDB), one row of the session list (FR-49). A model
  switch and a blocked-state exit each create a new session (OD-17); there is no branch inside a session. Every session has its own
  turn-id space and its own version numbers.
- **Turn**: one entry of the history, a **user turn** (text, optional attached images) or a **model turn** (the response parts
  exactly as the API returned them, including service fields such as `thoughtSignature`). Every turn has a stable id (FR-43).
- **History**: the retained sequence `U1 M1 U2 M2 ... Un Mn` of accepted image turns, followed in a request by the **new user turn**.
  A text-only reply, a safety block, a failed turn and a Cancel never enter it (FR-36).
- **Version**: one generated image, labelled v1, v2, ... (FR-23). A version belongs to a model turn; a model turn may hold several.
- **Seed**: the input image with which a new session begins after a model switch (FR-50) or a blocked-state exit (FR-47). It is an
  input, not a version.
- **Retained turn**: a turn still stored in the session. The stored list and the list sent to the model are the same list.
- **Protected set**: the first user turn `U1` (the originals; in a seeded session it also holds the seed) and the model turn `Mn`
  holding the **latest version**, defined as the last image, in API order, of the last accepted model turn in the history being sent
  (not the version being edited under FR-37). A model turn holding several images is protected whole (OD-30 C-30.3). The **new user
  turn** (text and any attachment) is outside trimming and counts toward every size.
- **Non-history event**: a UI-only event (a text-only reply, a safety block) shown in the chat and never sent back (FR-36).
- **Failed turn**: a generate attempt that ended in any non-200 response, a Cancel, a timeout, a response failing FR-24, or an empty
  or truncated response (FR-26). It never enters the history (FR-64).
- **Counted request**: a request that counts toward the rate limit (FR-66).
- **Sent bytes** (SD-24): the exact bytes the client hands to `/api/image-studio/upload` for one uploaded image, that is, the image
  after any downscale (FR-11) and after the EXIF-removing re-encode (FR-13), which keeps the format of the user's file (OD-38). The user's raw file is never stored and never
  re-uploaded (**HUMAN-DECIDED, recorded as OD-12 C-12.2**: only the sent bytes are sent and kept for re-upload). Keeping them is best effort: if the store fails the attachment is still sent (FR-16, OD-37). The copy kept in IndexedDB (FR-16) and the bytes re-sent after a `FILE_MISSING` 410 (FR-17) are the sent bytes.
- **Size units** (1024-based, as the existing `'50mb'` parser setting; the 5 MB value is SD-25, directly confirmed by the human, OD-48 C-48.6): 5 MB = 5 242 880 B,
  18 MB = 18 874 368 B, 20 MB = 20 971 520 B, 30 MB = 31 457 280 B. Every "5 MB" in this Specification, including the AC-4 and AC-7
  size limits, means 5 242 880 B: a file of exactly 5 242 880 B is "at most 5 MB"; one of 5 242 881 B is "over 5 MB". A file of
  5 000 000 B is therefore at most 5 MB.
  - **30 MB measure**: the declared `Content-Length` of a client-to-BFF request (JSON body, images as base64).
  - **18 MB measure** (OD-27 C-27.1): the length in bytes of the serialized JSON request the BFF would send to Gemini for the
    generate call, in which each inline image (a retained generated version, the version attached under FR-37, a session seed) counts
    as its base64 text, each `file_uri` part counts as only its own serialized part (a few hundred bytes, **not** the size of the
    file it names), and text counts as its UTF-8 length. This is the quantity the vendor's 20 MB inline cap is assumed to apply to.
    Whether the vendor measures decoded or encoded bytes, and whether referenced content counts toward the vendor cap at all, are
    checks V-6 (i) and (ii); if V-6 contradicts this convention the convention is a new decision for the human, not a Specification
    choice (the OD-27 re-open trigger).
  - **Token measure**: the sum of the per-turn `countTokens` results (FR-40), compared with 80% of the model's input token limit.
- **Successful generation**: a generate request answered with HTTP 200 whose body is the `images` variant of FR-24 (at least one
  image).

- **uiLanguage** (OD-14, HUMAN-DECIDED): the application's existing UI-language signal, `'en' | 'uk'` (`uiLanguage` in
  `src/app/app.component.ts`; persisted in `localStorage` under `seo_gen_ui_lang`; **default `'en'`**; toggled by the existing header
  control). The human's "EN/UA" means `'en'` / `'uk'`. A **studio text** is any user-visible string of the Image Studio (messages,
  error texts, preset names, chip labels, announcements, notices, control labels). Each studio text exists in both languages (Interface
  text table) and is resolved when it is rendered or announced, from the `uiLanguage` value at that moment, so a toggle re-renders
  every text on screen.
- **Text convention**: wherever this Specification quotes a Ukrainian literal (`Помилка API`, T-1 to T-10, the FR-47 message, the
  FR-68 text, the chips, the AC-46 announcements), the literal is the `uk` value of that text; its `en` value is in the Interface text
  table. A requirement that says "shows T-n" means "shows T-n in the current `uiLanguage`".
- **Thought part**: a response part whose `thought` field is `true` (`Part.thought`, `@google/genai` typings, `genai.d.ts` line 8873).
  An interim rendering or reasoning part of the model, not a final result (FR-84).
- **Last activity** (OD-16, SD-32): the time stamp stored with a session, set at creation and updated only by the events SD-32 lists
  (an exhaustive list); the 7-day retention (FR-48) and the eviction order of the cap (FR-86) are measured from it.
- **Stored session** (OD-36): a session record held in IndexedDB. The cap of 20 (FR-86) counts stored sessions; the session list shows
  every stored session.
- **Input format** and **target format** (OD-18, HUMAN-DECIDED follow-up): the *input format* of a generated version is the format
  (PNG, JPG or WEBP) fixed by the rule of FR-82; the *target format* of a version is the format of the file a download of that
  version produces, initially its input format and changed only by the operator's selector choice (FR-55, FR-82).

## Functional requirements

### Mode and configuration

#### FR-1: The studio is an `AppMode`, not a route

The application offers an Image Studio mode as a new value `'image-studio'` of the existing `AppMode` type, switched through the
existing `appMode()` mechanism. There is no URL route, deep link or router (AGENTS.md section 2: the app has no router). Entering the
mode does not require selecting a store. The tool-label map has a non-empty entry for the new value (asserted by the existing
template-wiring spec pattern), and the clear-all switch has an explicit case for it that leaves stored Image Studio sessions
unchanged (SD-12; a test invokes clear-all in the mode and reads the same sessions afterwards). The selected mode is not persisted by
this Story, so a reload lands on the Generator while the session itself survives (FR-48).

**Failure path:** n/a for the switch itself. Existing modes behave exactly as before (NFR-6).

#### FR-2: Image models are catalogue entries

The shared model catalogue (`src/prompt-core/model-catalog.json`, read by both runtimes) contains two Gemini image entries,
appended **after** all existing Gemini entries so that neither is `models[0]` and the default text model is unchanged:
`gemini-3.1-flash-image` (label Nano Banana 2, Flash) and `gemini-3.1-pro-image-preview` (label Nano Banana Pro, Pro). These IDs
are human-supplied and unverified: check V-3 must confirm the exact strings before implementation, and every place that spells an
ID (catalogue, pricing key, tests, fixtures) uses the one verified spelling. Each image entry carries `modalities: ["image"]` and
the shape of SD-8. Model IDs live in configuration, not in code. No environment override is introduced and the catalogue is the
single source of the IDs (OD-31).

**Failure path:** if V-3 shows a different ID, the catalogue and the pricing key change together (FR-70) and the per-model price
test fails until they do.

#### FR-3: Text paths never select an image model; the image path only selects one

On the server and the client, every path that selects a text model ignores any entry whose `modalities` include `image`: the
`findModel` step, the tier fallback and `defaultModel` in `resolveSlot`, `clampLevel`'s `findModel ?? defaultModel`, and the
client's settings computeds (`deepModels` / `fastModels`) and `model-catalog` helpers. The image routes accept only a model whose
`modalities` include `image`. Their request schema accepts a user turn that has images and no text (FR-18, FR-19; OD-46 C-46.4).

**Failure path:** a crafted text request that names an image model ID does not use it (it is treated as not found and takes the
existing fallback); a crafted image request that names a text model ID is rejected with status 400, `error` equal to
`INVALID_REQUEST`, and nothing is generated.

#### FR-4: Catalogue invariants stay intact for text models

The catalogue spec keeps every existing invariant for text models: non-empty `levels`, a `defaultLevel` inside `levels`, the
`clampLevel` probes, and the pinned default Gemini text model. It is changed only by being **scoped to non-image entries** and by
adding assertions: every image entry has `modalities` containing `image` and the fields of SD-8. Making `levels` optional for all
models, or skipping the loops, is not permitted (AGENTS.md section 7.7).

**Failure path:** a text model with empty `levels`, or an image entry missing `modalities`, fails the catalogue spec.

#### FR-5: A missing Gemini key yields a hard 501

When `GEMINI_API_KEY` is absent, any `/api/image-studio/*` call that needs it returns HTTP 501 with `error` equal to
`GEMINI_KEY_MISSING` in the `{ error: string }` envelope. The BFF does not retry it, the UI shows no Retry button, and the client's
`retryTransport` does not retry it. The UI text is T-11 ("Gemini API key is required for Image Studio" in `en`, its `uk` counterpart in the Interface text table; OD-14, HUMAN-DECIDED) and contains neither the literal `GEMINI_API_KEY` nor any other environment-variable name (FR-65). An upstream 501 is
never read as this signal (FR-61). The 501 is not a counted request (FR-66).

**Failure path:** the 501 is itself the failure path; nothing is generated, billed, counted or logged.

#### FR-6: Image generation lives behind the existing provider abstraction and ignores `LLM_PROVIDER`

Image generation is a new method on the existing LLM provider abstraction: implemented by the Gemini provider on the server
(`server/providers/`) and exposed on the client's `LlmProvider` interface and its implementer. The mode uses Gemini whatever
`LLM_PROVIDER` is set to (including `anthropic`; a test runs the image route with `LLM_PROVIDER=anthropic`). No vendor SDK import
is added under `src/`. The method's contract is FR-25, not the illustrative `generateImage(prompt, images, options)` signature.

**Failure path:** FR-5 when the key is absent.

#### FR-7: `.env.example` and the Story Scope line

`.env.example` keeps its existing `GEMINI_API_KEY` entry. No image-model environment variable is added: the Story Scope line
"`.env.example` (new/required `GEMINI_API_KEY` usage, model IDs)" is overridden by OD-31 for its "model IDs" part (see the Story-text
overrides table), and the log records no `.env.example` change because the key is already documented. A comment on the existing entry
saying that the key is required by Image Studio (it is otherwise optional, AGENTS.md section 3 Rule 4) is permitted by the Story
Scope's "required `GEMINI_API_KEY` usage" and is not required by this Specification. A review check reads the file and finds no
image-model variable.

**Failure path:** n/a.

### Upload

#### FR-8: Three ways to attach images

The operator can attach images by a button, by drag and drop, and by clipboard paste (Ctrl+V). All three feed the same attachment
list and the same validation (FR-9 to FR-15).

**Failure path:** a pasted or dropped item that is not a supported image is rejected under FR-15 and does not alter the images
already attached.

#### FR-9: PNG, JPG and WEBP only, verified by magic bytes on the BFF

PNG, JPG and WEBP are accepted. The BFF verifies the type from the file's leading bytes, never from the name or extension, at every
`/api/image-studio/*` endpoint that receives user-supplied image bytes (at least the upload endpoint, FR-16). **HUMAN-DECIDED (OD-12 C-12.1):** the check runs on the already cleaned or re-encoded bytes (the sent bytes). Under SD-24 the BFF only ever receives the sent bytes, on the first upload
and on the re-upload alike, and the same check applies to both because both go through the same endpoint. **Accepted (OD-40 C-40.1):** the BFF's checks on the upload endpoint are the magic bytes (415) and the 30 MB body cap (FR-51) only; it does not check the 5 MB size, the pixel size or the EXIF, and it holds no image code and no image dependency. AC-2 holds for images added through the Image Studio UI; a direct API call can bypass the client rules (the accepted limitation of FR-12).

**Failure path:** a file named `.png` whose bytes are not PNG is rejected by the BFF with status 415 and `error` equal to
`UNSUPPORTED_IMAGE_TYPE`, and the client shows reason T-1 (SD-13); the file is not attached or sent to the model. A file that cannot be decoded on the client is rejected there with T-1 and never reaches the BFF (FR-11, CF-19); a decodable file with a false extension is re-encoded and accepted, because the extension is never used. The rejection is
not a counted request.

#### FR-10: At most five uploads per message; the attached version is outside the five

At most 5 images **uploaded by the user** can be attached to one message (clipboard and drag and drop included). A 6th upload is
rejected with T-3 whether or not a version is attached under FR-37; 5 uploads plus one attached version are accepted (OD-28 C-28.1).
Tests: 5 uploads plus an attached version accepted; 6 uploads rejected.

**Failure path:** the 6th is rejected with the "count" reason and the five already attached remain (FR-15).

#### FR-11: Client-side downscale of an upload whose long side is over 2048 px

FR-11 governs one condition only: an uploaded image whose **long side is greater than 2048 px** is downscaled on the client to a long
side of 2048 px before it is sent, whatever its file size (this is the AC-4 downscale; the AC-4 "or larger than 5 MB" branch is the
size rule of FR-12, not a second downscale trigger). AC-4 applies to uploads only; a generated version attached under FR-37 is sent
as it is, including a 4K one, without downscaling or re-encoding (OD-28 C-28.3).

**HUMAN-DECIDED (N-7, OD-48 C-48.5; OD-12 C-12.4):** the file is decoded first. A file that cannot be decoded (so that its long side cannot be determined) is rejected with T-1 whatever its size, before any row below is applied.

**Client pipeline and order (OD-39 C-39.2).** Every image added through the UI, whatever its size or format, goes through the same steps in this order: decode (failure: T-1) -> downscale when L is over 2048 px -> draw on a canvas -> encode in the format of the user's file (FR-13; OD-38 C-38.1) at the quality of SD-42 -> compare the type of the encoder's output with the required format (FR-13, D-31) -> the 5 MB check on the result -> upload. L and "source dimensions" mean the as-displayed (orientation-applied) dimensions (D-32, OD-50 P-12, awaiting confirmation). The encoder is behind an injectable seam (FR-13, NFR-14).

The single rule for every (long side, size) combination, with "5 MB" = 5 242 880 B (SD-25), "S" the size of the file the user
supplied and "L" its long side in px (the decision table is exhaustive and the rows are mutually exclusive):

| Row | L | S | Outcome |
|---|---|---|---|
| 1 | at most 2048 | at most 5 MB | Not downscaled. The EXIF-removing re-encode of FR-13 applies. The sent bytes are then checked (D-7, last line of this table). |
| 2 | at most 2048 | over 5 MB | Rejected on the client with reason T-2 (FR-12). Not downscaled, not re-encoded, not sent. |
| 3 | over 2048 | at most 5 MB | Downscaled to a long side of 2048 px, then the EXIF-removing re-encode of FR-13. The sent bytes are then checked (D-7). |
| 4 | over 2048 | over 5 MB | Downscaled to a long side of 2048 px, then the EXIF-removing re-encode of FR-13. The sent bytes are then checked (D-7). |

D-7 check (rows 1, 3 and 4): the sent bytes must be at most 5 MB; if they are over 5 MB the file is rejected with reason T-2 and
nothing is sent (**HUMAN-DECIDED, OD-12 C-12.3, D-7**). The boundary tests are: L = 2048 and L = 2049; S = 5 242 880 B and S = 5 242 881 B;
S = 5 000 000 B (at most 5 MB); and each of the four rows once; a test with the injected encoder returning more than 5 242 880 B for a source of at most 5 MB asserts T-2 and no upload request (OD-38 C-38.5).

**Failure path:** an image that cannot be decoded for the downscale or the EXIF-removing re-encode is not sent and is rejected on the client with T-1 (FR-15), whatever its size, decode failure being checked before size (N-7, HUMAN-DECIDED). Visible consequence of D-7 (CF-20): a file of at most 5 MB whose EXIF-free re-encode is over 5 MB is rejected with T-2.

#### FR-12: An oversize upload is rejected on the client, never silently re-encoded

Row 2 of the FR-11 table: a file whose long side is at most 2048 px and whose size exceeds 5 MB (5 242 880 B) is rejected on the
client with reason T-2; it is never re-encoded to fit and the other attached files stay attached (OD-8 C-8.1, C-8.4). FR-12 is the
only rule that governs that combination: FR-11 does not apply to it. **HUMAN-DECIDED (OD-12 C-12.3), D-7:** the sent bytes of rows 1, 3 and 4 are
checked as they will be sent; a result over 5 MB is rejected by the same rule, so no upload over 5 MB is ever sent. Enforcement is on
the client only (OD-40 C-40.1): the BFF does not check the size, so a direct API call can send an image over 5 MB, up to the 30 MB body cap (FR-51); this is an **accepted limitation** (OD-40 C-40.2, listed under the accepted limitations). No BFF test asserts a size rejection, and the AC-4 row of the matrix says "client-side" (OD-40 C-40.3). The EXIF re-encode of FR-13 must not be used to shrink a file.

**Failure path:** the rejection is FR-15; no request is sent.

#### FR-13: No EXIF or GPS metadata reaches the model (uploads)

EXIF metadata, including GPS, is removed from every **uploaded** image added through the Image Studio UI before it is sent to the
model, including images that FR-11 would otherwise leave untouched (AC-5 narrowed to uploads, OD-28 C-28.1, and to the UI, OD-40
C-40.3; a generated version is not uploaded and is assumed to carry no EXIF, an assumption not verified in the repository).

**Mechanism (HUMAN-DECIDED, OD-39 C-39.1).** The client draws each such image on a native HTML5 canvas and takes it out again with
`toBlob` (or `toDataURL`), whatever its size. No library and no dependency is added (AGENTS.md section 1) and no image code is added
to the BFF (OD-40 C-40.1). The order of the steps is that of FR-11 (OD-39 C-39.2).

**Format (HUMAN-DECIDED, OD-38 C-38.1, C-38.2).** The re-encode outputs the same format as the user's file, identified by its magic
bytes as supplied (D-19): PNG to PNG, JPG to JPG (`image/jpeg`), WEBP to WEBP. It never forces PNG and never converts between
formats; the alpha of PNG and WEBP is preserved. An animated WEBP is re-encoded to a single-frame WEBP holding its first frame; it is
not rejected. **D-30 (OD-50 P-10, awaiting confirmation):** the first frame is taken silently, with no notice text; an animated PNG
has PNG magic bytes and takes the same path, so it also becomes its first frame; GIF is not an accepted format and is rejected by the
magic-byte rule.

**Quality (SD-42, OD-50 P-9, awaiting confirmation).** The JPG and WEBP re-encodes use the quality value of SD-42; PNG is lossless and
takes none. The value is named in this Specification and is not left to the browser default.

**Output type (D-31, OD-50 P-11; OD-38 C-38.4, reading awaiting confirmation).** The type of the encoder's output (the returned Blob
type and the magic bytes) is compared with the required format. A mismatch (for example a browser whose canvas cannot encode WEBP and
returns PNG) is a re-encode failure: the file is rejected on the client with T-1 and nothing is sent. Sending the fallback type under
the original name is not allowed. T-1 reads "Allowed formats: PNG, JPG, WEBP", which would mislead in this case; V-8 (ii) decides
whether that is acceptable.

**Orientation (D-32, OD-50 P-12; OD-39 C-39.3, reading awaiting confirmation).** "Source dimensions" in the FR-11 and FR-13 tests and
the long side L of FR-11 mean the as-displayed (orientation-applied) dimensions; a fixture with an orientation tag belongs to check
V-8 (i), not to the gate.

**Side effects accepted with the mechanism (D-33, OD-50 P-13; OD-39 C-39.6, awaiting confirmation).** The colour profile (ICC) is
dropped and wide-gamut pixels may be converted to sRGB; every ancillary chunk and segment (EXIF, GPS, XMP, PNG text) is dropped.

**Tests (OD-39 C-39.4; AGENTS.md section 5; neither runner has a working canvas).** The re-encode sits behind an injectable encoder
seam (NFR-14). The gate tests assert the plumbing: the raw file's bytes never reach the upload endpoint or IndexedDB, only the
encoder's output does; the encoder is called for every accepted upload, including an image of at most 2048 px and at most 5 MB; a
decode or encode failure ends in T-1 with nothing sent; an encoder output of the wrong type ends in T-1 with nothing sent (D-31); an
encoder returning more than 5 242 880 B for a source of at most 5 MB ends in T-2 with no upload (OD-38 C-38.5); for an animated WEBP
fixture the sent bytes produced by the (fake) encoder contain no animation chunks and hold the first frame (OD-38 C-38.2). The
verification fixture is a JPG containing GPS EXIF: the bytes handed to the upload endpoint are the encoder's output, **and** the same
holds on the re-upload path: the copy stored in IndexedDB and the bytes re-sent on a `FILE_MISSING` 410 are the sent bytes (SD-24,
Definitions), so a test that forces a `FILE_MISSING` for the fixture's `file_uri` asserts that the bytes of the second upload request
are identical to the bytes of the first (OD-12 C-12.5). The statement "the sent bytes contain none of the GPS EXIF" is asserted in the
gate only on bytes produced by the fake encoder; that a real canvas output carries no EXIF or GPS is a browser fact, verified by
check V-8 (iii), and the AC-5 row of the traceability matrix says so (proposed waiver W-2, awaiting confirmation). The gate does not
claim the stronger statement (AGENTS.md section 6).

**Accepted limitation (OD-40 C-40.2).** A direct API call can send an image over 5 MB (up to the body cap), not downscaled and with
its EXIF and GPS metadata, to the model; AC-4 and AC-5 hold for images added through the UI.

**Failure path:** if the metadata cannot be removed from an image (it cannot be decoded, the canvas fails, or the output type is
wrong), that image is not sent and is rejected on the client with T-1 (FR-15; N-10, OD-48 C-48.5, OD-12 C-12.4).

#### FR-14: Thumbnails before sending, removable

Thumbnails of the attached images are shown before sending and each thumbnail can be removed individually.

**Failure path:** removing a thumbnail leaves the other attachments in place.

#### FR-15: Rejection explains the reason and keeps the rest

A rejected file shows its reason (format T-1, which also covers a file that cannot be decoded, one whose EXIF cannot be removed and one whose re-encode output has the wrong type (FR-13); size T-2; count T-3). The other attached files remain attached and the message can
still be sent with them.

**Failure path:** n/a, this requirement is the failure path of FR-8 to FR-14.

#### FR-16: First upload to the Files API, one image per request

The BFF sends user-uploaded images to the Gemini Files API once and the history stores the returned `file_uri`, not base64 (AC-28
narrowed to user uploads: the version attached under FR-37 is sent inline and never uploaded, OD-27, OD-28 C-28.4). The first-upload
path is `/api/image-studio/upload` (SD-6): one image per request, JSON body with base64, response carrying the `file_uri`. The BFF
holds no image bytes after the call. The client keeps the **sent bytes** of each uploaded image (Definitions, SD-24: downscaled and EXIF-free, never the raw
file) in IndexedDB, at most 5 MB each (5 242 880 B, guaranteed by FR-11 and FR-12 because nothing over 5 MB is ever sent, under the HUMAN-DECIDED D-7); they are
the only source for FR-17. Storing them is best effort (OD-37 C-37.1, C-37.3): a quota failure while storing is announced by the alert of FR-81, and the attachment stays attached, is uploaded to the Files API and is sent normally; it is neither rejected nor flagged as failed, the other attachments are unaffected (FR-15), and the upload request and the send never wait on, or depend on, the success of the store. The history entry stores the `file_uri` only: no base64 and no marker (AC-28 is amended: transparent recovery holds only while the sent bytes could be stored). The endpoint is part of the `/api/image-studio/*` surface, so FR-51 applies to it, and it is not a counted request
(FR-66). An upload follows the retry loop and error taxonomy of FR-60 and FR-61.

**Failure path:** a non-retryable upload failure shows `Помилка API` with no Retry button; an exhausted 429 or 5xx shows T-7 with a
Retry button; in both cases nothing is attached to the history (FR-64).

#### FR-17: An expired file is re-uploaded by the client, transparently

When the request carried at least one `file_uri` and the upstream response itself indicates a missing file, the BFF answers HTTP
410 with `error` equal to `FILE_MISSING`. The recognition rule is the conjunction of: the request carried a `file_uri`; the upstream
error is of the class check V-2 establishes for a missing file; and the error itself names a file resource (for example the
`file_uri` or the Files API). It is not "any 404". A model-not-found error, or a "Files API" mention in an unrelated error (for
example a 400), is passed through under FR-61: no 410, no re-upload, no retry. The recognizer is pinned to the V-2 result and tested
against both a file-missing fixture and a model-not-found fixture.

On a `FILE_MISSING` 410 (status **and** code) the client re-sends the stored **sent bytes** (SD-24; "the originals" of the Story are
the images as the user uploaded them through FR-11 and FR-13) from IndexedDB to `/api/image-studio/upload` without a second
downscale or re-encode, replaces the stored `file_uri`s and repeats the request, at most once per user action (SD-4). "Unmodified" in FR-35 means
unmodified except the `file_uri` after expiry. The BFF keeps no bytes. The automatic repeat is a new client request and counts again
toward the rate limit (FR-66). A test feeds an upstream 410 that is not the file-missing class and asserts no re-upload (OD-29
C-29.2).

**Failure path:** a second `FILE_MISSING` after a re-upload shows T-10 and is not retried again; so does a re-upload for which the
stored sent bytes are not in IndexedDB (never stored because the store hit the quota, OD-37 C-37.2; or cleared by the browser): the turn
is a failed turn (FR-64), T-10 is shown, no upload request is made and nothing is retried. For an attachment whose sent bytes were not
stored this happens at the **first** `FILE_MISSING`, not the second. The sequence writes at most one usage row (FR-69). It runs inside
the single 120 s deadline (SD-30, HUMAN-DECIDED OD-5).

**Aftermath of T-10 for the session (D-27, OD-50 P-6 / OD-37 C-37.6, awaiting confirmation; a literal consequence of the decided
rules, not a new rule).** The retained first user turn `U1` (the originals, with their `file_uri`) is protected and is resent on every
send (FR-35, FR-42). After a Files API file has expired, that stored `file_uri` is dead, and with no stored bytes the client cannot
replace it; so every later send in that session meets `FILE_MISSING` again and shows T-10. Adding the image again puts a new
`file_uri` into the new turn only; it does not repair `U1`. What still works in that session: viewing, the strip, downloads, copy,
"New session" and, while a version exists, a model switch that seeds a new session with the latest version (a seed is inline, FR-37,
FR-50). A new session with a new upload recovers. T-10 reads "Add the images again" (a confirmed text), which does not by itself repair
the session. Alternatives named in OD-50 P-6 and not applied: a re-added image replaces the dead references in the retained turns (in
tension with AC-21 "unmodified"); a changed T-10 text that says a new session is needed; another rule.

### Chat and generation

#### FR-18: Text only, text plus images, or images only

A message has one of three valid forms (HUMAN-DECIDED, OD-46 C-46.1; AC-8 is extended by the third): **text only** (text-to-image),
**text plus images** (edit or composition), or **images only** (no text). The Send action is enabled when the text has at least one
non-whitespace character or the message has at least one image. **D-34 (OD-50 P-14, awaiting confirmation):** whitespace-only text
counts as empty, and an image is an uploaded image **or** the attached version of FR-37, so "Edit this version" with no text is a
valid message. An images-only turn carries its image parts and no text part; no filler text is invented. Whether the live API accepts
such a turn is check V-9. Tests: an images-only message is accepted and sent, and the outbound user turn holds image parts and no text
part; a whitespace-only message with no image is rejected and not sent; an attached-version-only message is accepted (D-34).

**Failure path:** a message whose text is empty or only whitespace and that has no image is not a valid message and is not sent (the
Send action is disabled, and the BFF rejects a request with such a new user turn, FR-19). If V-9 shows that the API rejects an
images-only turn, what the client sends in its place is a new decision for the human (Pre-implementation checks).

#### FR-19: Aspect ratio and resolution are chosen before sending

Before sending, the operator selects an aspect ratio from 1:1, 4:3, 3:4, 4:5, 16:9, 9:16 and a resolution from 1K, 2K and, only in
Pro mode, 4K. Defaults are 1:1 and 1K. The generate request schema accepts a new user turn that has images and no text (FR-18; OD-46 C-46.4).

**Failure path:** 4K is not selectable for Flash; a request that names a resolution not allowed for its model, an aspect ratio
outside the list, or a new user turn with neither non-whitespace text nor an image part (FR-18), is rejected by the BFF with status 400 and `error` equal to `INVALID_REQUEST`, nothing is generated and the
request is not a counted request.

#### FR-20: Response rendered in API order

The model response is rendered in the chat as text and images in the order the API returned them (the `images` variant of FR-24
carries the ordered parts).

**Failure path:** FR-24 (an invalid response is an error), FR-26, FR-62 and FR-63.

#### FR-21: Progress, input lock and Cancel

While a generation runs, a status indicator and a Cancel button are shown and the input field is locked. "The rest of the UI stays
responsive" has no threshold in the Story (recorded as a Story wording defect); this Specification gives the observable condition:
while a generation runs, the Cancel button, the version strip and its full view, every download and copy action, the session list,
"New session" and the mode switch stay enabled and respond to input; the composer input and the Send action are disabled, and the
model switch is inactive (**PROPOSED DEFAULT D-4**, FR-50). Because the session list and "New session" stay enabled, the response is
applied only to the session that sent the request (SD-22). Cancel aborts the upstream call to Gemini on the BFF (AbortController; a test with a stubbed Gemini asserts the
abort signal reaches the stub). A Cancel is a failed turn: it produces no version, adds no turn to the history, writes no usage row,
adds no cost and applies no cut (FR-64). The content of the cancelled turn returns to the composer (**PROPOSED DEFAULT D-5**) and the cancel notice T-18 is shown (FR-83). A
Cancel after the Gemini call started is a counted request (FR-66); a Cancel before it (for example during `countTokens`) is not.
**HUMAN-DECIDED (approval comment 2026-11-01, OD-5, PD-5):** Cancel is valid at every moment of the user action, including `countTokens`, an upload, the FR-17 repeat and a backoff wait; it aborts the upstream call when one is in flight, and no further upstream call is made after it (a test with an injectable clock cancels in the middle of a backoff wait and asserts that no upstream call follows); the BFF aborts the upstream call when the client disconnects. Recorded as OD-5 C-5.2 and C-5.3.

**Failure path:** if the abort is not honoured by the upstream, the client still returns to the editable state and ignores any late
response.

#### FR-22: 120 s timeout with Retry

A request that exceeds 120 s times out and shows T-6 with a Retry button; the timed-out turn is a failed turn (FR-64).
**HUMAN-DECIDED (OD-5, RESOLVED-WITH-CONDITIONS; PD-5 accepted; C-5.1 to C-5.4):** the 120 s is one overall deadline for the whole
user action, including the `countTokens` calls (FR-40), the upload requests made after Send or Retry, the FR-17 repeat and the backoff
retries (FR-60); it does not restart per attempt. Cancel is valid at every moment including backoff (FR-21), and the upstream call is
aborted when the client disconnects. The client's `retryTransport` never applies to a generate call (OD-5 C-5.4; FR-85, SD-31), and in
every case never retries a response that carries the `{ error: string }` envelope. Anchor, reach and who measures it: SD-30. A test
with an injectable clock asserts that T-6 appears at 120 000 ms after Send, also when the clock stands inside a backoff wait, and that
the upstream call is aborted then.

**Failure path:** a timed-out turn adds nothing to the history (FR-64); Retry re-sends the same turn (FR-36).

#### FR-23: Versions are numbered per session and labelled

Each generated image gets a version number (v1, v2, ...) and a label with the model and the resolution. Numbers are per session,
start at v1 in every session (including a seeded one) and are never renumbered: after a cut (FR-44) surviving numbers may be
non-contiguous (for example v1, v5), the next number is the highest number ever assigned in the session plus one, and a failed,
cancelled or non-history turn consumes no number (OD-17 C-17.3, **PROPOSED DEFAULT D-3** for the gap rule). A response with several
images numbers each image consecutively in API order (vN, vN+1); the `images` variant lists them as separate versions in the strip,
the ZIP and "Edit this version" (OD-30 C-30.2, C-30.3). A seed is not a version and consumes no number (OD-17 C-17.2); a thought part consumes no number (FR-84).

**Failure path:** a response with no image creates no version (FR-62, FR-63, FR-26).

#### FR-24: The BFF response is validated before it enters application state

The generate response is validated against a Zod schema before it enters application state. The schema is a union discriminated by
the closed field `kind` (SD-1): `images` (the ordered response parts with at least one image, `costUsd` a finite non-negative number,
the token usage, `trimmedTurnIds`), `text` (the text, `trimmedTurnIds`) and `safety` (the reason string of SD-23, `trimmedTurnIds`), all three
HTTP 200, each produced only by the classification of FR-26; `trimmedTurnIds` is an array of non-empty strings never longer than the number of turn ids the request carried, always
present. Every failure is a non-200 `{ error: string }` (FR-61). A 200 that matches none of the variants is an invalid response.
A 200 `safety` or `text` variant is not an invalid response. An invalid response is surfaced as an error and never rendered as an
empty image. **PROPOSED DEFAULT D-6:** a malformed or guard-violating `trimmedTurnIds` makes the whole response an error (the literal
AC-14 reading), including a paid image that is then not shown; the alternative "drop the list, keep the image" is not specified.

**Failure path:** the error is shown as a failed turn (FR-64); nothing is added to the history or session cost and nothing is
deleted (FR-44).

#### FR-25: The generate contract

A generate request carries: the retained history as turns, each with its stable id (FR-43) and its parts exactly as stored; the new
user turn (the text when present, uploads by `file_uri`, and the attached version inline; a turn that has images may have no text, FR-18); the model ID; the aspect ratio; the resolution; and the
preset ID when a preset was used. A successful (HTTP 200, `kind` = `images`) response carries the ordered response parts,
`costUsd`, `trimmedTurnIds` and the token usage. Image generation runs only on the BFF.

**Failure path:** every non-200 response uses the `{ error: string }` envelope (except an Express-parser 413 without a JSON body,
FR-52) and carries no `trimmedTurnIds` and no cost.

#### FR-26: Response classification

The BFF classifies the Gemini answer into exactly one of four response classes, in this order (OD-30 C-30.1), using the closed sets
of SD-23 (sourced from the installed `@google/genai` typings). The first candidate is the one read; "usable candidate" means the
response has at least one candidate. A "valid image part" is an inline image part that passes the schema (AC-14); "text only" means
at least one non-empty text part and no image part.

1. **Safety** (HTTP 200, `kind` = `safety`): the candidate's `finishReason` is in the candidate safety set (SAFETY, BLOCKLIST,
   PROHIBITED_CONTENT, SPII, IMAGE_SAFETY, IMAGE_PROHIBITED_CONTENT), whatever parts the candidate holds (an image part of a
   safety-finished candidate is dropped, not shown, and no cost is recorded or shown for it (N-2: what the vendor bills is not asserted)); **or** the response has no usable candidate and
   `promptFeedback.blockReason` is in the prompt-level safety set (SAFETY, BLOCKLIST, PROHIBITED_CONTENT, IMAGE_SAFETY, MODEL_ARMOR,
   JAILBREAK).
2. **Images** (HTTP 200, `kind` = `images`): not class 1, and the candidate holds at least one valid image part (a thought part is not one, FR-84), whatever its finish
   reason is. **PROPOSED DEFAULT D-10:** an image together with an abnormal finish reason is still `images`, because billing is per
   image and the image is usable.
3. **Text** (HTTP 200, `kind` = `text`): not class 1 or 2, the candidate is text only and its `finishReason` is the normal finish
   STOP.
4. **Empty-response failed turn** (HTTP 502, `error` equal to `EMPTY_RESPONSE`, SD-15): everything else, namely: no candidate and
   no prompt-level safety `blockReason` (including `blockReason` OTHER, which the human decided is abnormal (N-5), BLOCKED_REASON_UNSPECIFIED or an unknown value); a candidate
   with no parts or only empty text; text only with an abnormal finish reason (MAX_TOKENS, RECITATION, LANGUAGE, OTHER and the other
   abnormal values of SD-23, an absent `finishReason` included); a candidate with parts of neither kind; a body that is malformed,
   cut off or fails the schema before classification. It writes no usage row, has no cost, is a counted request (the call reached
   Gemini, FR-66) and shows the Retry button.

The decision table, applied top to bottom, the first matching row deciding (every row is a stubbed-Gemini test; a further parametrised
test (N-1) iterates over **every member** of the installed `FinishReason` enum crossed with each part shape (a valid image, text only, nothing or other parts) and with candidate presence, and over every member of `BlockedReason` with no usable candidate, and asserts that each combination maps to exactly one class of this table: for example STOP with an image is class 2, STOP with text only class 3, STOP with nothing class 4, and a `BlockedReason` is read only when there is no usable candidate; a value outside the enums maps to the abnormal finish or the abnormal block reason):

| # | Candidate present | `finishReason` | Parts | `promptFeedback.blockReason` | Class |
|---|---|---|---|---|---|
| 1 | yes | in the candidate safety set | any | any | 1 safety |
| 2 | no | n/a | n/a | in the prompt-level safety set | 1 safety |
| 3 | yes | not in the candidate safety set (STOP or abnormal) | at least one valid image part | any | 2 images |
| 4 | yes | STOP | text only | any | 3 text |
| 5 | yes | abnormal | text only | any | 4 failed turn |
| 6 | yes | not in the candidate safety set | no valid image part and not text only (empty, other part kinds) | any | 4 failed turn |
| 7 | no | n/a | n/a | not in the prompt-level safety set, or absent | 4 failed turn |
| 8 | the body is malformed, cut off or fails the schema | n/a | n/a | n/a | 4 failed turn |

The class decides the history (class 1 and 3 are non-history events, class 4 a failed turn, FR-36, FR-64), the usage row (only
class 2 writes one, FR-69), the cost (only class 2), the Retry button (offered for classes 1, 3 and 4, FR-62, FR-63, FR-64) and the
rate-limit record (all four are counted, FR-66). Each class has a stubbed-Gemini test.

**Precedence (N-11, HUMAN-DECIDED):** a class-2 answer for which no price resolves is not answered as HTTP 200: FR-70 turns it into the HTTP 500 `PRICE_NOT_CONFIGURED`, which takes precedence over the class-2 outcome (no row, no cost, no history entry; it is a counted request).

**Failure path:** class 4 is the failure path (FR-64).

#### FR-27: Order of checks on the generate route

For a generate request the BFF applies, in this order: the CORS middleware; the body-limit middleware (FR-51); the body parser; body
validation (model, ratio, resolution, ids, `INVALID_REQUEST`); the key check (501); the size trim and protected-remainder byte test
(FR-39, FR-46); the token trim and protected-remainder token test (FR-40, FR-46); the atomic rate-limit step (FR-66); the Gemini
generate call. A read-only rate-limit pre-check earlier in the sequence is permitted to avoid wasted `countTokens` calls, but the
atomic step decides (OD-13 C-13.1). The limiter is never inside a retry-wrapped operation (FR-66).

**Failure path:** the first check that fails answers the request; the later checks do not run and the later steps are not counted.

### Prompt presets

#### FR-28: Picking a preset fills the form; the text stays editable

Before the first message the operator can pick a preset. Picking one fills the prompt template, the aspect ratio, the resolution and
the model; the prompt text stays editable before sending. What fills the `{product}` placeholder is FR-79 (the product-name field, HUMAN-DECIDED). Editing the text for one send does not change the registry.

**Failure path:** a preset whose default resolution is not allowed for its model is a registry error caught by the registry test
(FR-29), not a silent clamp.

#### FR-29: Presets are data in a `PROMPT_PRESETS` registry

Presets are data in a separate registry named `PROMPT_PRESETS` (modelled on `STORE_REGISTRY`), not code in a component. Each preset
has `id`, a UA name, an EN name, a prompt template with a `{product}` placeholder, and defaults (aspect ratio, resolution, model).
Adding a preset is a configuration change only: a test adds a registry entry and the preset appears with no component change. The
registry and the quick-edit instructions (FR-31) are prompt text and so live outside services and components (AGENTS.md section 3
Rule 3); the file is `src/prompt-core/prompt-presets.ts` (FR-78, HUMAN-DECIDED). The displayed name follows `uiLanguage` (FR-30, FR-77) and no system instruction is sent (FR-80).

**Failure path:** a malformed entry (missing field, unknown aspect ratio or resolution, 4K on Flash) is rejected by the registry
test, not at runtime.

#### FR-30: The MVP registry contains exactly five presets

The registry contains exactly these presets, with these ids and names (OD-26) and these AC-17 defaults:

| id | UA name | EN name | Aspect | Resolution | Model | Template directive (AC-17) |

| `white-bg` | Білий фон | White background | 1:1 | 2K | Flash | clean #FFFFFF, soft shadow, product centred |
| `lifestyle` | Лайфстайл | Lifestyle | 4:3 | 2K | Pro | product in a real environment (workshop, office, classroom) |
| `banner` | Банер | Banner | 16:9 | 2K | Pro | free area reserved for text, the model does not draw text |

The UI shows the `uk` name when `uiLanguage` is `'uk'` and the `en` name when it is `'en'` (OD-14, FR-77); both names are stored. Each template is the literal of SD-21 and contains `{product}` and the directive listed for it; the registry test asserts the literal
text, the placeholder and the directive words for each. The ids are stable keys that appear in `usage_log.task_label` (FR-32) and in dashboard buckets, so renaming one changes historical grouping.

**Failure path:** a sixth entry, a missing entry, a changed id, name or default fails the registry test (OD-26 note 4).

#### FR-31: Quick-edit chips after v1

After v1 exists, quick-edit chips "Прибрати фон", "Світліше", "Тінь м'якша", "Інший ракурс" are shown. Each sends a predefined
follow-up instruction. The labels above are the `uk` values; the chip labels shown are the T-15 texts of the current `uiLanguage` (FR-77). The instruction texts are the literals of SD-21, registry-held prompt text in `src/prompt-core/prompt-presets.ts` with the presets (FR-29, FR-78; OD-42 C-42.1); the instruction sent to the model is the single-language English literal whatever the UI language (CF-3).

**Failure path:** before v1 exists the chips are not shown; while a generation runs they are not actionable (FR-21).

#### FR-32: The preset is recorded for successful generations (AC-19, server half)

For each successful generation the usage row's `task_label` records the preset used and the resolution in the SD-7 format. A text-only,
safety-blocked, failed or cancelled attempt writes no row and so leaves no preset record (OD-4, OD-19 C-19.5, OD-22 C-22.1 (i)).

**Failure path:** n/a.

#### FR-33: The "downloaded" flag is a per-device client flag (AC-19, client half)

The client stores, per version, a boolean "downloaded" flag in the IndexedDB session state. It is set on a completed single-file
download, on a completed ZIP download (every version included in the ZIP is flagged) and on a completed copy to the clipboard
(FR-57), not on the click; the success signals are SD-17. A failed save or a failed clipboard write leaves it unset. Nothing is sent
to the BFF: no new endpoint, no new table, no schema change. The flag lives in the session record and is deleted when its version is
trimmed (FR-44) or its session expires (FR-48). What the UI does with the flag is not required and not invented. **Accepted
limitation (OD-22):** the flag is invisible to the server (`usage_log`, `GET /api/usage`), cannot be joined with the preset record
and cannot be aggregated; the Story's "the log records ... whether the image was downloaded" is waived to this flag. A test covers the
three triggers and the unset-on-failure case.

**Failure path:** a failed save or clipboard write leaves the flag unset.

### Session memory and iterative edits

#### FR-34: A text-only correction edits the latest version

Given a session that holds v2, a text-only correction sends a request that contains v2 (as the model turn's image) and the new text.
The version returned is stored as v3. The gate verifies the request shape with a stubbed Gemini. "The rest of the composition
preserved" is a model-quality property that no deterministic gate can assert (AGENTS.md section 5); AC-20 is verified manually only (**HUMAN-DECIDED (approval comment 2026-11-01, OD-20)**; see "Automated-test waivers"). The request-shape and numbering assertions in this requirement stay automated.

**Failure path:** if v2 is no longer retained (cut by FR-44), it is not in the request, and FR-42 defines what is.

#### FR-35: Every request carries all retained turns unmodified

Every request carries all retained turns (AC-21 narrowed by OD-23): texts, user-uploaded images (as `file_uri`) and model responses,
including every service field the API returned (for example `thoughtSignature`), unmodified except a `file_uri` replaced after
expiry (FR-17). A test with a stubbed Gemini whose response carries service fields asserts that the next request contains them
unchanged. The history is always `U1 M1 ... Un Mn` (accepted image turns only) followed by the new user turn (OD-19 C-19.1).

**Failure path:** a retained turn that cannot be sent unmodified is not repaired by the client; the request ends as a failed turn
(FR-64).

#### FR-36: Non-history events, Retry and what a failed turn keeps

A text-only reply and a safety block are non-history events: shown in the chat as UI-only events (FR-62, FR-63), never sent back,
and **not stored in IndexedDB** (**PROPOSED DEFAULT D-5**), so a reload shows only the accepted turns. A failed turn's text and
attachments stay available: they are restored to the composer. The Retry action re-sends the **same** user turn (same text, same
attachment references, with re-upload after expiry as in FR-17, same ratio, resolution, model and preset); it is offered only while
the composer still holds exactly that content (SD-18); an edited message is a new turn. A Retry is a new request and counts again
(FR-66); a repeated safety block is counted every time (OD-19 C-19.7).

**Failure path:** n/a.

#### FR-37: "Edit this version" has three states

Every retained version has an "Edit this version" action. The reading below is derived (not separately asked) and flagged as
**PROPOSED DEFAULT D-3**:

| Situation | What happens |
|---|---|
| Normal state | The action attaches that version to the next message of the **same** session; no new session; AC-22 is unchanged. |
| Blocked state (FR-47) | The same action creates a **new session** (a new row in the session list) seeded with the chosen version; it is offered on **every retained version**. |
| Model switch Flash <-> Pro (FR-50) | A new session seeded with the latest version, only while the composer is empty of unsent content. |

In the normal state the attached version is shown as a thumbnail in the composer's attachment list, the same element as FR-14, and can be removed there; in the blocked state the effect (a new session) is stated by the T-14 message that is on screen (FR-47). A test asserts that, after the action in the normal state, the attachment list holds the version's thumbnail and that removing it leaves the message without the attachment (N-3). The attached version is sent **inline** in the new user turn, never through
the Files API, without downscaling or re-encoding, and does not count toward the five uploads (FR-10). At most one version is attached
at a time; a second "Edit this version" replaces the first (**PROPOSED DEFAULT D-9**). **PROPOSED DEFAULT D-8:** the attached copy stays
in the stored user turn and is resent inline while that turn is retained, so a version attached once is carried twice (as its model
turn and in the user turn) until trimmed. Versions removed by FR-44 are permanently gone and have no action. A seed is inline in the
protected first user turn `U1`, is not a version (not in the strip or ZIP, not numbered), is not counted toward the five and counts
toward the 18 MB inline measure for the whole life of its session (OD-17 C-17.2, OD-27 C-27.6).

**Failure path:** the attachment is subject to the size checks of FR-39 to FR-46.

#### FR-38: A strip of retained versions with a full view

A strip above the input field shows thumbnails of all retained versions of the current session; clicking one opens a full view.
Versions removed by FR-44 are absent, and earlier sessions' versions are not shown.

**Failure path:** n/a.

#### FR-39: Size trim at 18 MB

Before each call the BFF computes the 18 MB measure (Definitions) of the request it would send to Gemini. Above 18 MB it removes the
oldest trim units (FR-42) until the request is at most 18 874 368 B or only the protected set and the new user turn remain.
Originals (the first user turn) and the latest version are never removed. `file_uri` originals weigh their reference only, so this
limit bounds inline data (generated versions, the attached version, a seed); the practical bound on originals is the token limit
(FR-40).

**Failure path:** if the protected remainder plus the new user turn still exceeds 18 MB, FR-46 applies.

#### FR-40: Token trim at 80% of the input limit

After the size trim (size first, then tokens, OD-7 C-7.5), the BFF counts tokens with `countTokens`: **one call per retained turn
separately, plus one for the new user turn (k + 1 calls)**, where **k is the number of turns still retained after the size trim of
FR-39** (turns the size trim removed are not counted; when the size trim removed nothing, k is the number of turns in the request),
made concurrently with at most 4 in flight (SD-10, **PROPOSED DEFAULT
D-11**), and sums the counts. Above 80% of the model's input token limit (`inputTokenLimit`, SD-8) it removes the oldest trim units
(FR-42) until the sum is at most 80% or only the protected set and the new user turn remain. The sum is an estimate of the
whole-request count (system or per-request overhead, per-image accounting); the 20% margin is the buffer; if V-7 (iii) shows the gap
exceeds the margin that is a new decision for the human, not a guess (OD-32 C-32.3). The calls are made by the BFF, are not counted
requests (FR-66), add nothing to `usage_log`, and each follows the retry loop and taxonomy of FR-60 and FR-61. One call failing
after its retries, or failing non-retryably, ends the action with no generate call, no row and no count: an exhausted 429 or 5xx
shows T-7 with the Retry button, a non-retryable 4xx shows `Помилка API` without one (OD-29 C-29.4). Originals and the latest version
are never removed. The trim is a pure function of the request body plus the counts: a test with a stubbed `countTokens` asserts the
same input yields the same `trimmedTurnIds`, and a test asserts exactly k + 1 calls, with k counted after the size trim (a request whose size trim removed one pair makes two calls
fewer than the same request without the trim), and never more than 4 simultaneously.

**Failure path:** if the protected remainder plus the new user turn still exceeds 80%, FR-46 applies.

#### FR-41: The image-token estimate is a placeholder verified under V-7

The estimate `IMAGE_TOKEN_ESTIMATE` is a configuration value with a recorded source, initially 258 tokens, marked "human-supplied
example, unverified, from older documentation; not supported by anything in this repository" (**PROPOSED DEFAULT D-13**, OD-34
C-34.1). Its final value (per model, possibly per resolution or media-resolution setting, and for inline, `file_uri` and generated
images separately if V-7 shows they differ) comes from V-7 (i), recorded before IMPLEMENTATION. It applies only if V-7 shows that
`countTokens` rejects or ignores image and `file_uri` parts; the choice is made once from the V-7 result and recorded, not decided at
run time. When it applies, the estimate is added per image part and per `file_uri` part to the text count of each turn within the
FR-40 scheme. An underestimate can let a request exceed the real input limit (the 20% margin is the buffer; a vendor rejection ends
as `Помилка API` without Retry); an overestimate trims versions earlier than needed, which is a permanent deletion (FR-44). A test
runs the arithmetic with the placeholder replaced by a fixture value. If V-7 shows `countTokens` accepts the parts but the count
cannot be used, that is a new decision for the human.

**Failure path:** if V-7 fails and no recorded selection exists, IMPLEMENTATION does not start (Pre-implementation checks).

#### FR-42: Trim units, boundaries, determinism and fallback

The history is the alternating sequence `U1 M1 U2 M2 ... Un Mn`, where `U1` is the first user turn and `Mn` is the model turn
holding the latest version; no turn can follow `Mn` (FR-36). A trim unit is the pair `(M_i, U_i+1)` for i from 1 to n-1, removed
oldest first. After every removal the retained sequence still begins with `U1`, still contains `Mn` and still alternates roles, and
both halves of every removed pair are listed in `trimmedTurnIds` (FR-43). The pair removes the user turn and any images that user
turn carried; the human confirmed this is intended (OD-23 confirmation 1). A model turn with several images is removed whole
(OD-30 C-30.3). This pairing is the one derivable from the protected set and the measured remainder of FR-46 and is flagged for the
human (SD-9). The trim is a deterministic function of the request body plus the token counts (no clock, no randomness), because
replay after a lost response (FR-44) relies on it.

Primary strategy: pair removal, with the remaining parts' `thoughtSignature` unchanged. Fallback if check V-1 shows the live API
rejects gaps (the human's): collapse all old history to the first user turn (originals) and the latest generated version. The V-1
result, recorded before implementation, selects exactly one strategy; tests cover the selected one with a stubbed Gemini (no live
API in the gate). "Edit this version" of an older version is not broken by the collapse, because the attached version travels in the
new user turn.

**Failure path:** if no unit can be removed and the limits are still exceeded, FR-46 applies.

#### FR-43: Every 200 reports exactly what was trimmed

Every turn in a request carries a stable id (SD-20), persisted in IndexedDB; the BFF only echoes ids it received and never invents or
renumbers one. A seeded session reuses no id of any other session. Every HTTP 200 response of the generate route (all three `kind`
values) carries `trimmedTurnIds`, always present, an empty array when nothing was removed, listing exactly the turns removed by FR-39
to FR-42 (turns, not versions). A test per rule (size, tokens, both, and the V-1 fallback) asserts the list equals the removed turns
and that equal input gives an equal list.

**Failure path:** a non-200 response carries no list and nothing is deleted.

#### FR-44: The client applies the cut atomically and guards it

On receiving a valid 200 for a session that still exists (SD-22; otherwise the response is discarded and nothing is applied), the
client appends the new model turn (for `kind` = `images`) and deletes the listed turns in that session in a **single**
IndexedDB transaction, and updates in-memory state only after the commit. The cut is applied on every 200 that carries the list,
including the `text` and `safety` variants that create no version (**PROPOSED DEFAULT D-6**, flagged: a loss with no new version to
show for it). The client ignores ids that are not in its local session and never deletes the first user turn or the latest model
version even if a response lists them. "The first user turn" and "the latest model version" are evaluated against the session **as
it was when the request was built, before the new model turn is appended** (SD-27); this is the history the BFF protected, so a
valid response never lists them, and the new model turn (whose id is not in that session) cannot be deleted by the same response.
A response that lists a protected turn is handled as an invalid response (FR-24) and logged. Deleting a turn deletes
its versions and the downloaded flags (FR-33).

**Failure path:** a response that is not applied (Cancel, abort, reload, offline, schema failure, commit failure including quota)
leaves the session exactly as before, so the next request is a safe replay of a body that was already within the cap. A quota failure on the commit is shown by the native alert of FR-81 (SD-34). Two tabs on one session can race a cut: the last write wins and there is no synchronisation (OD-43 C-43.1, an accepted limitation); each tab's commit remains one atomic transaction (OD-43 C-43.2).

#### FR-45: The trim notice states the permanence and what was removed

When a request removed turns, the user is shown the T-9 message (SD-13): the removed versions and messages, with the images those
messages carried, are **permanently deleted from this device**, with the counts V, M and I computed from `trimmedTurnIds`. A test
asserts the counts equal those of the removed turns. No download is offered before removal (the human confirmed this, OD-23
confirmation 2). The notice is shown with `role="alert"` or as plain visual text (HUMAN-DECIDED, OD-21; FR-83). It is computed from the one `trimmedTurnIds` list of the response (FR-43), so a response shows one notice even when both limits removed turns. In the FR-46 state this notice is replaced by the
FR-47 message. The notice is T-9 in the current `uiLanguage`. The strip, "Edit this version" and "Download all versions" cover retained
versions only.

**Failure path:** no message is shown when `trimmedTurnIds` is empty.

#### FR-46: A protected remainder over the limits ends in a terminating 413

The measured remainder is the first user turn (originals, as their references) plus the latest model version plus the new user turn
with its attachments (OD-24 C-24.1, OD-27 C-27.1). If it exceeds 18 MB (the byte test sees only inline content), or exceeds 80% of
the token limit (the token test sees the originals through `countTokens`), checked in that order, the BFF stops before any Gemini
generate call and returns HTTP 413 with `error` strictly equal to `PROTECTED_HISTORY_EXCEEDS_LIMIT`. Nothing is generated, billed,
logged or counted. The 413 is not retried by `retryTransport` or by the BFF, and a test asserts exactly one request is made. It adds
no turn and deletes nothing (FR-64, FR-44). The text and attachments of the rejected message stay in the composer.

**Failure path:** n/a, this requirement is the terminating failure path of FR-39 and FR-40.

#### FR-47: The blocked state and its single exit

On a 413 whose `error` equals `PROTECTED_HISTORY_EXCEEDS_LIMIT`, the UI shows the literal "Сесія занадто велика. Будь ласка, почніть
нову сесію з останньої версії" instead of the trim notice, with no Retry button. While the state holds, sending a text message in
the current session is disabled; viewing, the strip, download, copy and "New session" stay available. The state is stateless
(**PROPOSED DEFAULT D-12**): it is not a persisted flag and the next send re-creates it. "Edit this version" is the only action that
re-enables sending: it creates a **new session** seeded with the chosen version, offered on **every retained version** of the blocked
session (OD-17 (g)); the old session keeps its history for viewing and download until it expires (FR-48) or is evicted as the least recently active of the 20 stored sessions (FR-86), never by this exit (OD-36 C-36.4). In the blocked state "Edit this version" is **not**
subject to the composer guard of FR-50 (**PROPOSED DEFAULT D-4**); the rejected text and attachments stay in the old session's composer.
The new session does not carry the old originals. The seed plus the first new turn is itself subject to FR-46. The message is T-14 in the current `uiLanguage` and uses `role="alert"` (FR-83). Only Send is disabled in this state; the composer input stays enabled and focusable (SD-37).

**Failure path:** a seed that alone exceeds the limits ends in the same 413; the UI stays in the blocked state, "New session" remains
available, and the exit does not loop (the new session has no retained version, so no further exit is offered from it). The creation of the new session follows FR-86 (OD-36 C-36.1): at the cap it silently evicts another stored session, never the blocked source session, and is never refused.

#### FR-48: A session survives a reload for seven days

A session survives a page reload (IndexedDB on the client) and is kept for 7 days **from its last activity** (**HUMAN-DECIDED (approval comment 2026-11-01, OD-16)**; this amends the
Story's AC-25 "kept for 7 days", which gave no reference point). What survives is the retained session (turns, versions, the sent
bytes, the downloaded flags, the running cost total). "Activity" is SD-32 (committed writes, not viewing). Stale sessions are deleted
when the stored sessions are initialised or loaded (page load, and each later load of the list), never by a timer; the boundary is
strictly more than 604 800 000 ms since the last activity (SD-33). Deleting a session deletes its whole record (turns, versions, sent
bytes, flags, cost total); the Gemini Files API files it referenced are not touched (FR-49). A test with an injectable clock covers
age 604 799 999 ms (kept), 604 800 000 ms (kept) and 604 800 001 ms (deleted), a write that renews the stamp, and a load that
deletes. Every model switch and blocked-state exit adds a session row (OD-17 C-17.6), within the cap of FR-86. The 7 days are an upper bound: a session also ends by eviction at the cap (FR-86, OD-36). "Activity" is the exhaustive list of SD-32 (the FR-16 sent-bytes store and an unsent composer change are not activity; OD-44 C-44.2). Two tabs on one session: the last write wins, with no synchronisation, lock or notice (OD-43 C-43.1, an accepted limitation); a session expired or evicted by one tab stays visible in the other until its next load (SD-33), a trim deleted by one tab may still be sent by the other, and two tabs creating sessions at once can leave more than 20 stored sessions until the next creation (D-25). Recorded as OD-16 C-16.1 and OD-44 (SD-32 to SD-34 confirmed).

**Failure path:** IndexedDB being unavailable or full is FR-81 (the native alert); the atomicity of FR-44 holds either way.

#### FR-49: "New session" with confirmation and a session list

A "New session" button clears the current history after a confirmation; the previous session remains available in the session list (until it expires, FR-48, or is evicted as the least recently active of the 20 stored sessions, FR-86; never in the same action that leaves it, OD-36 C-36.4)
with its own history, cost total and downloaded flags; nothing is carried into the new session. Declining the confirmation changes
nothing. Every model switch (FR-50) and every blocked-state exit (FR-47) adds a row; no parent link is required (OD-17 C-17.6).
The confirmation text is T-23. The list obeys the 7 days of FR-48 and the cap of FR-86. "New session" creates a row even when the current session holds no turn (D-26, OD-50 P-5, awaiting confirmation: repeated confirmations then push real sessions out with empty ones; reusing an empty session instead would be a new behaviour that the human has not decided). "New session" leaves the Gemini Files API files the previous session referenced where they are: the BFF makes no delete call, and the files expire on Google's side (**HUMAN-DECIDED (approval comment 2026-11-01, OD-16)**; a test with a stubbed Files API asserts that no delete call is made). Recorded as OD-16 C-16.5; the creation at the cap is FR-86 (OD-36 C-36.1).

**Failure path:** n/a.

#### FR-50: Switching Flash and Pro starts a new session

Once the session holds at least one version (SD-19), switching between Flash and Pro creates a **new session** (a new row in the
session list) seeded with the latest version as an attached image in the new session's composer; history is not mixed between
models; numbering restarts at v1 (OD-17). The model-switch control is inactive while the composer holds unsent text or new uploads;
**PROPOSED DEFAULT D-4:** an unsent attachment of FR-37 and a failed turn awaiting Retry also count as unsent content, and the control is
also inactive while a generation runs. The strip (FR-38), the ZIP (FR-58), the file names (FR-56) and the cost total (FR-71) cover
the current session only; the cost of earlier sessions is not added to a new session's total; two sessions may each produce a
`..._v1_...` file for the same product name, and a single ZIP never mixes sessions (OD-17 C-17.4). A seed that alone exceeds the
limits ends in FR-46. The creation follows FR-86: at the cap it silently evicts another stored session, never the source session of the seed, and the seed is read from its source before any deletion (OD-36 C-36.1, C-36.4; D-24).

**Failure path:** with unsent content the control is inactive and no session is created.

#### FR-51: A 30 MB body limit on image-studio routes only

A body limit of 30 MB (31 457 280 B) applies to `/api/image-studio/*` routes only, implemented as a `Content-Length` check in a
middleware mounted **after `cors()` and before the global `express.json`**, so rejections carry CORS headers and the browser can read
them. The global `express.json` limit stays `50mb`. A body-bearing request (POST, PUT, PATCH) to `/api/image-studio/*`, including the
upload endpoint, with a declared `Content-Length` over the limit gets HTTP 413 with `error` equal to `REQUEST_BODY_TOO_LARGE`
(SD-2, SD-3), and one with no `Content-Length` (chunked) gets HTTP 411 with `error` equal to `CONTENT_LENGTH_REQUIRED`. Body-less
requests (GET, HEAD, OPTIONS) are not rejected. Neither rejection is a counted request, and the middleware runs before the limiter.
Tests: a 31 MB declared body is rejected on an image-studio route; the same body is accepted by an existing route; a missing
`Content-Length` yields 411; existing routes are otherwise unchanged (the global parser order and its 50 MB limit). Check V-4 must
show that a browser `fetch()` POST's `Content-Length` reaches the BFF through Railway; if Railway re-chunks request bodies the 411 rule
would reject legitimate requests and the human is told before implementation.

**Failure path:** a lying `Content-Length` (smaller than the real body) is still bounded by the unchanged 50 MB parser cap.

#### FR-52: The client dispatches on status and code, never on status alone

The client treats a 413 whose `error` equals `PROTECTED_HISTORY_EXCEEDS_LIMIT` as the protected-history state (FR-47), and any other
413 (`REQUEST_BODY_TOO_LARGE`, or Express's own non-JSON 413) as a generic non-retryable error showing T-8: no Retry button, the
failed turn does not enter the history, nothing is deleted, "New session" remains available. This generic handling is **HUMAN-DECIDED (approval comment 2026-11-01, OD-25, PD-25 accepted)**: the standard error without a Retry button, and the turn does not enter the history. Recorded as OD-25. A 413 is not in the status set `retryTransport` retries, and a test asserts that. Both
413 cases are tested side by side. The client re-uploads only on the 410 that carries `FILE_MISSING`, and treats a 429 with
`RATE_LIMIT_EXCEEDED` differently from a 429 with `UPSTREAM_RETRIES_EXHAUSTED` (FR-68).

**Failure path:** n/a, this requirement is the failure path of FR-46 and FR-51.

#### FR-53: No legitimate request may exceed the cap; the headroom is shown, not assumed

No request to `/api/image-studio/*` may legitimately exceed 30 MB: first upload is one image per request (SD-6), so five uploads of
up to 5 MB (each sent as base64) do not form one over-cap body, and the generate body carries `file_uri` references for
originals. The Specification-level inequality, in the Size units of the Definitions, is:

`R + G + N + H <= 31 457 280 B`

where `R` is the retained history after trim (inline versions, the attachment copies of FR-37 under **PROPOSED DEFAULT D-8**, a seed,
`file_uri` references and text), `G` is the largest total image size of one generated response (all images of the response, OD-30
C-30.4; no cap on images per response is invented), `N` is the largest new user turn (including an attached inline version) and
`H` is 1 048 576 B (SD-11). The numeric instantiation needs `G` for 1K, 2K and 4K and the size of a 4K version resent inline; both are
the measured result of check V-6 (iii) and are **not assumed here**. If the inequality cannot be shown for a 4K response with the
human's 18 MB and 30 MB, or a 4K version breaks the Story's "7 MB per base64 image", no number is chosen by the Specification: that is
a new Open Decision for the human (the cap, the trim target or the 4K allowance changes). A test over a simulated long session with
deterministic maximum-size versions taken from the V-6 record keeps every request body at or below `31 457 280 - 1 048 576` B on every
turn and fails if the inequality is broken.

**Failure path:** the residual case (a body rejected despite this) is FR-52 and OD-25.

### Download

#### FR-54: One-click download at native resolution

Every retained version downloads in one click at the native pixel dimensions returned by the API; the image is never resized. The one-click
download delivers the version in its target format (FR-82, **HUMAN-DECIDED (approval comment 2026-11-01, OD-18 follow-up)**): the API bytes unchanged when the API format
equals the target format, a client conversion otherwise. AC-31's "without re-compression" therefore holds exactly when the two formats
are equal; where a conversion happens the clause is waived by the human's decision (CF-16). A test with a stub returning PNG for a
PNG-input version asserts the downloaded bytes equal the returned bytes.

**Failure path:** a version whose bytes are unavailable shows an error and downloads nothing.

#### FR-55: Selectable download format

The download format is selectable: PNG, WEBP or JPG (quality 90), converted on the client when the API format differs; the conversion keeps the
native pixel dimensions. The selector stays (**HUMAN-DECIDED (approval comment 2026-11-01, OD-18 follow-up (e))**): the version's input format is only its **default** (PNG
when there is no input image), and a format the operator selects before downloading wins. The Story's "PNG (default)" is amended
accordingly. The selector value is per version and is not persisted (D-22). The conversion rules are FR-82. Recorded as OD-18 C-18.2 and OD-45 (D-22 confirmed).

**Failure path:** a failed conversion shows an error and downloads nothing and leaves the downloaded flag unset (FR-33).

#### FR-56: File name

The file name is `{product-name}_v{N}_{ratio}.{ext}`, for example `bambu-lab-h2d_v3_1x1.webp`; the product name is entered by the user
and is lower-cased with each run of invalid file-name characters replaced by one hyphen (SD-14), otherwise `image` is used; `{ratio}`
writes the aspect ratio with `x` for the colon; `{N}` is the version number within the current session (FR-23). The product-name field is the same field that fills `{product}` (FR-79, HUMAN-DECIDED). `{ext}` is the extension of the format of the delivered file (FR-82, SD-39): `png`, `jpg` or `webp`, so `bambu-lab-h2d_v3_1x1.webp` names a WEBP file.

**Failure path:** a product name that sanitizes to an empty string uses `image`.

#### FR-57: Copy to clipboard (PNG)

A "Copy to clipboard" action exists for PNG. The copy is always PNG whatever the target format of the version; when the API returned another format the client converts to PNG for the clipboard (CF-16). **HUMAN-DECIDED (OD-45 C-45.2):** the clipboard is always PNG, and the selector and the table of FR-82 do not govern it. A test copies versions whose source format is PNG, JPG and WEBP and asserts a PNG signature each time.

**Failure path:** if the browser does not permit the clipboard write, the user is shown an error, nothing is copied and the flag of
FR-33 stays unset.

#### FR-58: Download all versions as a ZIP

"Download all versions" returns a ZIP of the retained versions of the current session (OD-17 C-17.4, OD-23), built with the existing
`jszip` dependency (no new package), with file names per FR-56. Each entry is delivered in its version's current target format (FR-82, D-22 confirmed in OD-45; **HUMAN-DECIDED (OD-18 C-18.6)**): the API bytes unchanged when they already have that format, a client conversion otherwise, so one ZIP can hold entries of different formats, and each entry's extension follows its format. While the current session
retains no version (for example a new session before its first generation, or a seeded session before its first generation, since a
seed is not a version), the action is disabled (SD-28) and no ZIP is ever produced; a test asserts the disabled state for a session
with zero versions and the enabled state with one.

**Failure path:** a failure while building the ZIP shows an error and downloads nothing.

#### FR-59: The SynthID notice

The interface states that Gemini images carry an invisible SynthID watermark that cannot be removed. The notice is T-19 in the current `uiLanguage`.

**Failure path:** n/a.

### Errors

#### FR-60: Bounded retry on upstream 429 and 5xx

On an upstream HTTP 429 or any 5xx (including a bare 500) the BFF retries up to **3 times** with exponential backoff of exactly
1 s, 2 s and 4 s (no jitter; at most 4 upstream calls), then returns the exhausted answer of FR-61. The same loop applies to the
first upload, the re-upload and every `countTokens` call (OD-29 C-29.3, C-29.4). The repository's `withRetry` counts attempts
rather than retries, uses a 3000 ms base with jitter, a separate policy budget of 6 for 429 and 503, and does not retry a bare 500, so
its defaults do not meet this requirement; whether the loop parameterises it or is separate is a planning matter, provided that a
test with an injectable clock and a stubbed Gemini observes exactly four calls at offsets 0, 1 s, 3 s and 7 s. The model is never
silently substituted: a test asserts that every attempt names the requested model. The rate limiter lives outside every
retry-wrapped operation, because `withRetry` retries a message containing `429` or `rate_limit` (FR-66).

**Failure path:** after the fourth failure the exhausted answer is returned; a Retry button starts a new user action (a new counted
request, FR-66). A non-retryable upstream error is not retried (FR-61).

#### FR-61: The error taxonomy

Every failure is answered in the `{ error: string }` envelope (OD-29 C-29.1) with these outcomes, the client dispatching on status
**and** code (FR-52):

| Failure | Status | `error` | Retry button |
|---|---|---|---|
| Body over 30 MB | 413 | `REQUEST_BODY_TOO_LARGE` | no (T-8) |
| No `Content-Length` | 411 | `CONTENT_LENGTH_REQUIRED` | no |
| Protected remainder over the limits | 413 | `PROTECTED_HISTORY_EXCEEDS_LIMIT` | no (FR-47) |
| Expired file | 410 | `FILE_MISSING` | automatic repeat once (FR-17) |
| Rate limit | 429 | `RATE_LIMIT_EXCEEDED` | no (D-2) |
| Missing key | 501 | `GEMINI_KEY_MISSING` | no |
| Unsupported image bytes | 415 | `UNSUPPORTED_IMAGE_TYPE` | no |
| Invalid request | 400 | `INVALID_REQUEST` | no |
| Empty or truncated 200 (class 4 of FR-26) | 502 | `EMPTY_RESPONSE` | yes (T-5) |
| Paid generation with no resolvable price (FR-70) | 500 | `PRICE_NOT_CONFIGURED` | no (`Помилка API`) |
| Upstream 429 or 5xx after the 3 retries | the original upstream status | `UPSTREAM_RETRIES_EXHAUSTED` | yes (T-7) |
| Upstream 4xx other than 429 and other than the file-missing class | the upstream status | `Помилка API` | no |

An upstream-derived response never carries a reserved code, and a reserved status coming from upstream (410, 411, 413, 501) is not
interpreted as the BFF's own signal. A test feeds an upstream 410 that is not file-missing and asserts no re-upload (FR-17), and an
upstream 501 and asserts it is not read as `GEMINI_KEY_MISSING`. The failed turn keeps its content for the user (FR-36). The upstream
text is not sent to the browser; server-side logging of the upstream detail stays as `describeError` does today, without the API key
or the prompt payload (OD-29 C-29.6). An Express-default non-JSON error (for example a 413 from `express.json`) is shown as the
generic non-retryable error (FR-52).

**Failure path:** n/a, this requirement defines the failure paths cited by FR-16, FR-17, FR-35 and FR-40.

#### FR-62: A safety block explains itself and leaves the history intact

A safety block is exactly a response of **class 1** of FR-26 (SD-23): a candidate whose `finishReason` is SAFETY, BLOCKLIST,
PROHIBITED_CONTENT, SPII, IMAGE_SAFETY or IMAGE_PROHIBITED_CONTENT, or a response with no usable candidate whose
`promptFeedback.blockReason` is SAFETY, BLOCKLIST, PROHIBITED_CONTENT, IMAGE_SAFETY, MODEL_ARMOR or JAILBREAK. It is answered by the
BFF as HTTP 200 with `kind` = `safety` (OD-19(e)) and shows T-4, a plain explanation with a suggestion to rephrase; it is a non-history event (FR-36), so the
history is untouched. A safety-blocked request writes no usage row and has no cost, and it is a counted request (FR-66). The same-turn
Retry stays available; an edit is a new turn.

**Failure path:** n/a, this requirement is a failure path. A 200 `safety` envelope is never classed as an invalid response (FR-24).

#### FR-63: A text-only response shows the text, creates no version, offers Retry

If the model returns only text and no image with the normal finish STOP (class 3 of FR-26; HTTP 200 with `kind` = `text`; text only
with an abnormal finish is class 4, a failed turn, not this requirement), the text is shown, no version is created, no usage row
is written (cost 0), the turn is a non-history event (FR-36), and a Retry action is offered. It is a counted request (FR-66).

**Failure path:** n/a, this requirement is a failure path.

#### FR-64: A failed turn never enters the history

A failed turn never enters the history that is sent to the model. Failed means: any non-200 response, a Cancel, a timeout, a response
that fails FR-24 and an empty or truncated response (FR-26). A failed turn adds no user turn and no model turn, deletes no turn,
writes no usage row, and adds nothing to the session cost. Retry re-sends the same turn (FR-36). AC-21 "every request carries all
prior turns" is read as the retained accepted turns.

**Failure path:** n/a.

### Security, cost, accessibility

#### FR-65: The Gemini key is not in the client bundle, checked in the test suite

The Gemini API key exists only in the BFF environment and does not appear in the client bundle. The check is a logic-runner Vitest
spec under `test/` (`test/security.spec.ts`) run by `npm test` (there is no deploy-time hook and no CI): in `beforeAll` it builds the
client with `npm run build -- --output-path=.test-dist` (the literal `execSync('npm run build')` is insufficient because it writes
`dist/`), discarding the build output (`stdio: 'ignore'`, SD-5), scans the files under `.test-dist/browser/` recursively, and asserts
(1) the literal `GEMINI_API_KEY` is absent and (2) nothing matches `AIzaSy[0-9A-Za-z_-]{20,}` (SD-5). The key value is not available to a
committed test, so "does not appear" is verified as "no key name and no key-shaped string"; the Specification does not claim the
stronger statement and does not claim a deploy guard. The spec is non-vacuous: it fails if the build fails, fails if the scan finds
zero `.js` files, never skips when the output is missing, and exercises the scanner against a synthetic string that contains the name
and a key-shaped string. `beforeAll` has a 120 000 ms timeout. `.test-dist/` is added to `.gitignore` (a repository-config edit listed
for the human at approval) and removed in `afterAll`. No client string contains the literal `GEMINI_API_KEY` (FR-5). The check runs
in `npm test` and `npm run test:coverage`, so the gate builds the client about three times; this is a recorded tension with the
AGENTS.md section 5 "stay fast" rule, not a violation.

**Failure path:** a build failure fails the suite; the test never passes by skipping.

#### FR-66: Rate limit of 30 counted requests per hour per client IP

Image generation is limited to 30 requests per hour per client IP address (no user accounts exist). A request counts once it has
reached the Gemini generate call, whatever its outcome (OD-13 C-13.9, amending AC-42); the 31st such request within the window is
rejected under FR-68. The count is one **atomic check-and-increment step immediately before the Gemini generate call** (FR-27), so
concurrent requests cannot take a key past 30.

Counted: a 200 with an image; a 200 with text only; a safety block (a 200, candidate-level or prompt-level, SD-23); an empty or truncated response (class 4 of FR-26); an upstream 4xx or 5xx
after the BFF's retries (all BFF attempts of one request are **one** unit); a Cancel after the call started; a user Retry (a new
request); the automatic re-send after a `FILE_MISSING` 410 (one user action can consume two units); a manual re-send after a lost
response (the client's `retryTransport` never repeats a generate call, FR-85). Not counted: `countTokens`; `/api/image-studio/upload`; a request rejected by the
body-limit middleware (411, 413) or by the 501; the `PROTECTED_HISTORY_EXCEEDS_LIMIT` 413; a request rejected by body validation; the
limiter's own 429; a request aborted before the Gemini call started. Quota and `usage_log` diverge by design: a counted request that
failed, was blocked, returned text only or was cancelled consumes one unit, writes no row and costs 0 in the session total.

The client IP is `req.ip` with `app.set('trust proxy', 1)` (OD-2). **Assumption A-2:** Railway is the only proxy in front of the BFF;
if a CDN or host rewrite is added, `req.ip` becomes that proxy's address and the per-IP bucket becomes shared. A client-supplied
`X-Forwarded-For` entry does not reset the bucket.

**Failure path:** the rejection is FR-68. Tests (stubbed Gemini, injectable clock, no network): 30 counted then the 31st rejected;
each counted class consumes exactly one unit and each uncounted class consumes none; BFF retries consume one unit; two IPs are
isolated; the window resets after one hour; concurrent requests cannot exceed 30; the 429 triggers exactly one client request and zero
upstream calls.

#### FR-67: The limiter window, state and limitations

The window is a fixed one hour per client IP. **PROPOSED DEFAULT D-1:** a key's window starts at its first counted request and ends
exactly one hour later; the next counted request after expiry starts a new window (the alternative is clock-aligned hours). The state
is process memory, with no new dependency, no store and no migration; expired entries are purged (a sweep on access or a non-keeping
timer) so that, in a test with an injectable clock, the number of tracked keys never exceeds the number of IPs active in the last hour.
The limiter is code in `server/`, not an added package (adding one would be a new human decision, AGENTS.md section 1). **Accepted
limitations (not defects, OD-13 C-13.4):** a restart or Railway deploy resets every counter; the counter is per process, so with N
replicas the effective limit is up to 30 x N per hour; users behind one egress address share one pool of 30; a client that can rotate
addresses (for example across an IPv6 prefix) is not limited more strictly.

**Failure path:** n/a.

#### FR-68: The rejection of the 31st request

The 31st counted request in the window is answered with HTTP 429, `error` equal to `RATE_LIMIT_EXCEEDED` (SD-2), in the
`{ error: string }` envelope, from a limiter mounted after `cors()` so the browser can read it, with `Retry-After` carrying the whole
seconds left in the window (SD-16). The client shows the human's text "Перевищено ліміт генерацій (30 на годину). Спробуйте пізніше."
and maps the code to it without rendering the code. It is not retried by `retryTransport` or by the BFF. **PROPOSED DEFAULT D-2:** no
Retry button, and the user's text and attachments stay in the composer. The client dispatches on status **and** code: an exhausted
upstream 429 (`UPSTREAM_RETRIES_EXHAUSTED`) is a different outcome with a Retry button, and a test sends both and asserts the two
different outcomes. The rejection generates, bills and logs nothing.

**Failure path:** the rejection is itself the failure path; the text is T-13 in the current `uiLanguage` (OD-14).

#### FR-69: Successful generations log one usage row

Every successful generation (HTTP 200, `kind` = `images`) logs one `usage_log` row with input tokens, output tokens, the model and the
resolution (carried in `task_label`, SD-7), via the existing usage store with no schema change; AC-43 is read as "every HTTP 200
generation response that contains at least one image logs `usageMetadata`". A text-only response, a safety block, a failed turn and a
Cancel write nothing. The successful attempt writes exactly **one row per request** (not per image) even when preceded by BFF retries
(FR-60) or an FR-17 re-upload.

**Failure path:** a failure to write the row does not change the HTTP 200 response already produced (as for the existing
`/api/llm/generate`), and is logged as a server error.

#### FR-70: Cost is per generated image, from configuration

For each successful request the BFF computes `costUsd = unit price x number of images in the response` (thought images are excluded, FR-84); a response with zero images
costs 0. Fixed per-image prices live in `server/usage/pricing.js` keyed by the **exact catalogue model ID** of FR-2 (one spelling
everywhere), with a comment naming source and date as the existing entries do; the placeholders $0.03 (Flash) and $0.06 (Pro) stand
until check V-5 confirms them against the verified ID. The price is per image and independent of resolution (a per-resolution price
is a new human input). "Is this an image model" is read from the catalogue `modalities` field, with no second hard-coded list.
`computeCost` never applies the token rate path or `FALLBACK_PRICE` to an image model, and an image model with no price entry fails
loudly. Tests: every catalogue image model resolves to its per-image price, a response with two images costs twice the unit price, and
one without a price entry fails; a stubbed Gemini image response for a model with no price entry yields the 500 `PRICE_NOT_CONFIGURED`
answer and no row. `costUsd` is part of the FR-24 schema. Token counts are still stored (FR-69) but the cost of these
rows is not tokens x rate.

**Failure path:** a missing price is a loud error, not a silent fallback. For a generation that was already paid for (the Gemini call
returned an image) when no price resolves, the BFF answers HTTP 500 with `error` equal to `PRICE_NOT_CONFIGURED` (SD-26), which takes precedence over the class-2 outcome of FR-26 (N-11), and logs the
model ID server-side; the client shows `Помилка API` without a Retry button; no usage row is written, no `costUsd` is returned, no
image is shown or added to the history, no turn is deleted (the response carries no `trimmedTurnIds`), the session cost is
unchanged, and the request is a counted request (it reached Gemini, FR-66). The paid image is not recoverable; the catalogue/price
consistency test above is what prevents this state.

#### FR-71: The session shows a running estimated total

The session shows a running estimated cost in dollars as a cumulative total, the sum of the `costUsd` values of the successful

**Failure path:** a non-finite or negative `costUsd` makes the response invalid (FR-24).

#### FR-75: Alt text for each generated image

#### FR-82: The output format equals the input image's format; conversion rules

**HUMAN-DECIDED (approval-comment follow-up on OD-18, 2026-11-01); this replaces the earlier OD-18 text.** The format of a delivered file
(a single download, and each entry of the ZIP) equals the format of the input image, as follows. Recorded as OD-18 C-18.1 to C-18.9 and
OD-45 (the residues D-17 and D-19 to D-22 are confirmed).

**Input format of a version** (the turn that generated it; first match wins):

1. The message carried at least one user-uploaded image (rule (b)): the format of the **first** user-uploaded image of that message in
   attachment order, whatever the formats of the others. **Confirmed (D-21, OD-45):** this also wins when the message carries an attached
   version as well.
2. Otherwise the message carried an attached version (an "Edit this version", or a seed; rule (c)): the version inherits the input
   format of the version being edited, which itself inherited it from the original input.
3. Otherwise, if the session holds a version, the message edits the latest version (AC-20) and inherits its input format
   (**confirmed, D-20, OD-45**); if the session holds no version (text-to-image, no input image), the input format is PNG (rule (a)).

**Confirmed (D-19, OD-45):** the format of an uploaded image is identified by the magic bytes of the file as the user supplied it, before
any downscale or EXIF re-encode (the possible values are PNG, JPG and WEBP, AC-2). With OD-38 the EXIF-removing re-encode keeps this format (FR-13), so the sent bytes carry the same format; a canvas that returns another type is a re-encode failure. The input format is stored with the version (D-22).

**Target format.** The selector of FR-55 stays; the input format is only its **default** (rule (e)). The operator can change the selector
of a version before downloading, and that choice wins. **Confirmed (D-22, OD-45):** the selector value is per version; operator choices are
not persisted.

**Delivered bytes.** Let S be the format of the version's bytes as the API returned them and T the target format:

| S compared with T | Delivered file |
|---|---|
| S equals T | The API bytes **unchanged**, byte for byte; no decode, no re-encode. The extension is that of T (SD-39). |
| S differs from T | The client decodes the image and encodes it as T at the native pixel dimensions (never resized): JPG with quality 90 (rule (f), AC-32) and every transparent pixel filled with white `#FFFFFF` (rule (g)); PNG as a lossless encode of the decoded pixels; WEBP with quality 90 (**confirmed, D-17, OD-45**; this quality applies to a download conversion to WEBP only, not to the upload re-encode, SD-42). The extension is that of T. |

A conversion therefore happens in exactly two situations: the API returned a format other than the input's (rule (d), for example input
JPG and a PNG answer), and the operator changed the selector to a format other than S (rule (e)). In both the AC-31 clause "without
re-compression" does not hold (CF-16); the native pixel dimensions always hold. The clipboard copy of FR-57 is not governed by this
table: it is PNG (AC-34), converting when S is not PNG. Tests, with stubbed API bytes and an injectable encoder spy:
(i) PNG source, T = PNG; JPG source, T = JPG; WEBP source, T = WEBP: the delivered bytes equal the API bytes and no encoder is called;
(ii) a PNG with a fully transparent region, T = JPG: the file begins `FF D8 FF`, has the source width and height, and the formerly
transparent region decodes to white (255, 255, 255) within a test tolerance of 5 per channel for JPG rounding (a test tolerance, not a
product requirement); (iii) a JPG source, T = WEBP: the file begins `RIFF`, bytes 8 to 11 read `WEBP`, the dimensions equal the source
and the bytes differ from the API bytes; (iv) a version whose API answer is a JPG, T = PNG: the file begins with the PNG signature and has the answer's dimensions (a JPG answer carries no alpha, so no alpha is asserted); (v) the input is a JPG upload and the API returns PNG, no selector change: the file is a JPG
of quality 90 and is named `.jpg`; (vi) the same version with the selector changed by the operator from JPG to WEBP: the file is WEBP
(the operator's choice wins); (vii) a message with a PNG upload first and a JPG upload second: input format PNG; (viii) v1 generated
from a JPG upload, v2 generated by "Edit this version" on v1: v2's input format is JPG; (ix) a text-to-image message in a session
with no version: input format PNG; (x) a PNG source, T = WEBP: the file begins `RIFF`, bytes 8 to 11 read `WEBP`, the dimensions equal the source and the bytes differ from the API bytes; (xi) a WEBP source, T = PNG: the file begins with the PNG signature and has the source dimensions; (xii) a WEBP source with a fully transparent region, T = JPG: the file begins `FF D8 FF`, has the source width and height, and the formerly transparent region decodes to white (255, 255, 255) within the test tolerance of (ii). Together with (ii), (iii) and (iv) the tests cover all six cross conversions (PNG to JPG, PNG to WEBP, JPG to PNG, JPG to WEBP, WEBP to PNG, WEBP to JPG) and S equals T for the three formats (OD-18 C-18.8).

**Failure path:** a failed decode or encode shows an error and downloads nothing, and leaves the downloaded flag unset (FR-33, FR-55).

**Eviction (C-36.1).** Creating a session by any of the three paths, "New session" (FR-49), the model switch (FR-50) or the
blocked-state exit (FR-47), while 20 sessions are stored deletes the stored session with the oldest last-activity stamp (SD-32), the
whole record (FR-48), as part of the creation. There is no confirmation or notice about the eviction, no message, no `role="alert"` or
`role="status"` update and no `window.alert`. There is no refusal path and nothing blocks FR-47 or FR-50. With fewer than 20 stored
sessions nothing is deleted. The order is by last activity, not by creation: a session renewed by a committed write is not the one
deleted.

**Candidates (D-23, OD-50 P-1 / C-36.4, PROPOSED, awaiting confirmation).** Because viewing is not activity (SD-32), the session the
operator is standing in can hold the oldest stamp. The eviction candidate is chosen among the stored sessions other than (a) the
session the operator is leaving or using when the creation is triggered (for a model switch or a blocked-state exit this is also the
source of the seed), (b) a session with a generation in flight in this tab, and (c) the session being created. If no other session
exists the cap is not exceeded and nothing is deleted. The alternative named in the log and not applied: no exclusion (the literal
oldest stamp), which can delete the session in use, contradicts AC-26, FR-47 and the confirmed text T-23, and discards a paid response
(SD-22).

**Ties (SD-41, OD-50 P-2 / C-36.5, proposed value, awaiting confirmation).** Sessions with equal stamps are ordered by the smaller
session id in UTF-16 code-unit order, so that a test with a fixed clock is deterministic.

**Atomicity (D-24, OD-50 P-3 / C-36.6, PROPOSED).** The deletion and the creation are one IndexedDB transaction, and the seed
(FR-47, FR-50) is read from its source session before any deletion. A quota or other failure of the creation (FR-81) leaves no session
deleted. **Healing (D-25, OD-50 P-4 / C-36.7, PROPOSED).** The rule is "while the stored count would exceed 20, delete the next
candidate", so a count above 20 left by two tabs (OD-43) heals at the next creation. **Empty sessions (D-26, OD-50 P-5):** see FR-49.

**Tests (C-36.3; injectable clock, NFR-14).** With 20 stored sessions whose stamps differ and whose creation order differs from
their stamp order: a creation deletes the session with the oldest stamp (not the oldest created), 20 remain, the list shows 20 rows
without the deleted one, and no alert, confirm or `role` update about the eviction happens; the same through each of the three
creation paths; a session renewed by a committed write is not the one deleted; with fewer than 20 stored, nothing is deleted. Tests of
the proposals: the session being left is not deleted even when it holds the oldest stamp, and nor is a session with a generation in
flight (D-23); with all stamps equal the session with the smaller id is deleted (SD-41); a creation whose transaction fails deletes
nothing (D-24); a stored count of 21 is reduced to 20 by the next creation (D-25).

**Accepted consequences (C-36.9; listed under the accepted limitations).** The deletion is silent and irreversible: the turns,
versions (including never-downloaded ones), sent bytes, downloaded flags and the running cost total of the session are lost; the
Gemini Files API files are left as ever (FR-49) and the server-side usage rows remain. Twenty creations in a row (New session, model
switches, blocked-state exits) push out every older session. In a second tab the list is stale until its next load, and a response
for a session evicted by the other tab is discarded although the generation was paid (SD-22, OD-43). AC-25's 7 days becomes an upper
bound. The human's explicit choice of "silent" is the consent for this deletion (OD-36).

**Failure path:** a creation that fails (quota, FR-81) creates no session and deletes none (D-24); the eviction never blocks FR-47 or
FR-50 and has no failure message of its own.

## Automated-test waivers

### W-1: AC-20 is verified manually only (HUMAN-DECIDED, OD-20)

AC-20 reads: "Given a session that already holds v2, when the user sends a text-only correction, the model edits v2 and returns v3,
with the rest of the composition preserved." No deterministic test can assert that the composition of a generated image is preserved
(AGENTS.md section 5: no network, no model in the gate). **Explicit waiver, for the reconciliation stage:** the requirement that AC-20
be covered by an automated test is waived by the human; AC-20 is satisfied by the manual check below, and the AC-to-test matrix row for
AC-20 is to read "MANUAL (waived by the human, OD-20)". Missing manual evidence never blocks reconciliation (OD-6, NFR-11). The waiver's authority is OD-20 C-20.1 (and C-20.2 for the matrix row).

What stays automated (a different, deterministic property, not the waived one; CF-8): FR-34's assertions that, given a session holding
v2, a text-only correction sends a request containing v2 as the model turn's image plus the new text, that the returned image is stored
as v3, and that version numbers follow FR-23. The waiver covers only "the rest of the composition preserved". AC-47 is **not**
waived: it has the deterministic rule of FR-75.

**Manual check procedure** (post-deployment QA; no artifact is required, OD-6; the Story's key scenario is the script):

1. Open the Image Studio on the deployed application with the real Gemini key (any `uiLanguage`).
2. Upload one product photo and send "white background, soft shadow below, 1:1": version v1 appears.
3. Send the text-only correction "make the shadow softer": version v2 appears.
4. Send the text-only correction "add a subtle gradient": version v3 appears, labelled v3, in the chat and the strip.
5. Open v2 and v3 in the full view and compare them side by side.

**Pass criterion (SD-38):** v3 exists and is labelled v3, and the comparison shows the subject, its position and size, the framing and
the background unchanged except for the change the correction asked for. **Fail:** the subject, its position or its framing changed,
or an object was added or removed that the correction did not ask for. The operator who runs the check judges the comparison.

### W-2: AC-5 is verified in two parts, plumbing in the gate and the real canvas in the browser (PROPOSED, awaiting confirmation; OD-50 W-2, OD-39 C-39.4)

**This is a proposed waiver, not a decision.** AC-5, as narrowed by OD-28 and OD-40, reads: EXIF metadata, including GPS, is stripped
from every image added through the Image Studio UI before it is sent to the model. Neither test runner has a working canvas (`happy-dom`

test. The AC-5 row of the AC-to-test matrix is then to read "client-side; gate = plumbing; real property = V-8". **Alternatives, not
applied:** (B) a test-only dependency that provides a real canvas (a new dependency, AGENTS.md section 1, a human decision; it would
still not prove what a real browser does); (C) another verification. Until the human confirms W-2, the Specification claims for the
gate only the plumbing and never the stronger statement (AGENTS.md section 6, item 7), and a missing V-8 record is handled as for
every V-check (NFR-12).
